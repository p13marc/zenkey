# `modem-contract` as a zk2 contract crate (#623)

r3.2 claims that codegen can emit a publishable **contract crate**: types, bundle and traits,
with the zenoh glue behind a feature (`docs/zk2/architecture.md:121`, §3.14). It also claims
that zenoh-modem's out-of-tree backends depend on it as they do today (§4.10). This file states
what `modem-contract` exports under zk2, and how each kind of dependent uses it.

## 1. Today (`modem-contract` 0.3.0 on crates.io)

| Today | What it is |
|---|---|
| `registry/modem.toml`, `types.toml` + `build.rs` (zenkey-build) | the v1 contract, linted at build time, with typed key builders generated into `registry::modem::{Subject, key}` |
| `documents.rs` | every payload type, with serde and `schemars::JsonSchema` derives: what is described is what is serialized (#37) |
| `schema.rs` | the `SchemaSet` that `describe` serves, and `verify_total`, which refuses to start a producer that describes less than it declares |
| `config.rs` | the conversions from `modem_device::config` to `zenkey::config` |
| `PROFILE`, `PRODUCER` | the `AppProfile` with the origin salt `zenoh-modem-host-id-v1`, and the producer name `modem` |
| dependencies | `zenkey = { version = "0.11", default-features = false, features = ["schemars"] }`, `modem-device`, serde, schemars. **No zenoh**, and `scripts/guards.sh` holds the line at the `zenoh` crate. |

Three crates depend on it, each in its own way:
- `modem-device`, the seam a backend implements, links neither zenkey nor zenoh;
- `modem-mgmt`, the plane, links zenoh;
- conformance is split between `modem_device::conformance` (the traits, no zenoh) and
  `modem_mgmt::conformance::Wire` (a running plane: declared − gated = served, `error/gated` on
  every procedure a device lacks a plane for, and the write path).

## 2. Under zk2: the layout

```text
modem-contract/
  contract/
    modem.v3.toml              this directory's modem.v3.toml
    schemas/modem.json         GENERATED by schemars from src/documents.rs, committed (r3 §3.9, Rust-first)
  contracts/.history/modem.v3/ published bundles, append-only (r3.1 §3.11)
  build.rs                     zenkey-build (zk2): validate, canonicalize, fingerprint, bundle, generate
  src/
    lib.rs                     re-exports, `v3` module
    documents.rs               the payload types: names and fields unchanged
    config.rs                  modem_device::config ⇄ config.v1's types (was zenkey::config)
```

The schema direction stays Rust-first, as today.
1. `documents.rs` is the source.
2. schemars emits `schemas/modem.json`, and the generated file is committed.
3. `build.rs` refuses to build if the committed file differs from what the types derive. This is
   today's guarantee that the description cannot drift from the thing described, moved from
   `describe` to the build.
4. The bundle is built from the committed file. The contract's CI builds it once and appends it
   to `.history/`, and every implementation embeds it and only verifies it (r3 §3.11).

Two zk2 requirements follow, and README gap 19 records both:
- **Binding type references to Rust types.** `json:LinkState` must be bound to
  `crate::documents::LinkState`. v1 spelled that `types.toml`'s `rust =` field. In zk2 it belongs
  in zenkey-build's configuration, not the fingerprinted contract.
- **The schema subset.** The zk2 JSON Schema subset (S7) must admit what schemars 1.x emits:
  `anyOf` with `null` for `Option`, `enum` for a unit enum, untagged unions (`ParamValue`), and
  flattened internally-tagged enums (`zenkey::config::ParamSpec`).

## 3. What it exports

With **default features**, nothing depends on zenoh:

| Export | What | Replaces |
|---|---|---|
| `v3::types::*` | `LinkState`, `Capabilities`, `Lane`, `LaneTable`, `EndpointState`, `SecurityState`, `Oper`, `Identity`, `RadioState`, `DestinationState`, `OperChange`, `IdentityChange`, `DeviceFault`, `ActionRequest`, `ActionOutcome`, `ActionEvent`, `ModemError`, and their `of(…)` constructors from `modem_device` facts | `documents.rs`, unchanged |
| `v3::BUNDLE: &[u8]`, `v3::FINGERPRINT: [u8; 32]`, `v3::contract()` | the bundle `{contract, schemas}`, its sha256, and the parsed contract (`zenkey-model`, static half) | `introspect` (the registry text) and `describe` (the `SchemaSet`), both served over `@rpc`; `schema::verify_total` |
| `v3::Stream`, `v3::State`, `v3::Op` enums, and `v3::keys` | typed key builders and parsers over an `Addr` (`h-3fa9c2d41b7e/rf0`). For example `keys::stream(&addr, Stream::SduDroppedTotal)` gives `zk2/h-3fa9c2d41b7e/rf0/modem.v3/stream/sdu/dropped_total`. Pure strings, slugged injectively. | `registry::modem::{Subject, key}` |
| `v3::Reading` | one variant per stream with its typed value, such as `Reading::SduDroppedTotal(u64)` or `Reading::RadioRssi(f64)` | telemetry.rs's `READINGS` table. A name can no longer be zipped to the wrong value (#100) by construction. |
| `v3::Capability` (30 variants) and `CapabilitySet` | the gate names `modem.v3` declares | the strings in `Sensor.capabilities` |
| `v3::availability(&CapabilitySet) -> Availability` | **declared − gated**, as a pure function: the exposed resources, and each unavailable optional resource with its gate and cause | `Wire::gate_open`, and the `sensor` document. Its output feeds the descriptor (r3.2 §3.10). |
| `v3::Ops` (async trait) | the server side of the two operations: `lanes() -> Result<LaneTable, Error>` and `action(name, ActionRequest, CallMeta) -> Result<ActionOutcome, Error<ModemError>>`. `CallMeta` is the O7 `{actor, request_id}`, claimed. | modem-mgmt's `rpc.rs` handlers |
| `v3::Client` (async trait) | the same two calls from the caller's side; mockable in-process (r3 §3.14) | hand-written zenctl calls |
| `v3::Error<E>` | the zk2 core error envelope, with `unavailable{cause}`, and `E` as the `app` detail | `error/gated`, `error/busy`, `error/modem/action-refused`, … |

Behind **features**:

| Feature | Adds | Dependencies |
|---|---|---|
| `zenoh` | the generated glue. `v3::Server::declare(&svc, impl Ops) -> Handles` gives one typed writer per stream and state, with the contract's QoS applied: v1's `sampled`/`refreshed`/`transition`, now fingerprinted. `Handles::publish(Reading)`, the `Client` over a session, and `Consumer::bind(&svc, role)` for a far-side reader. | `zenkey` (the zk2 runtime) and `zenoh` |
| `conformance` | the static kit: an implementation's `Availability` against the contract; every unavailable resource names a declared gate; no exposed resource has its gate unheld | none beyond the default |
| `conformance-wire` (implies `zenoh`) | today's `modem_mgmt::conformance::Wire`, moved here so an out-of-tree daemon can run it. Over a window, the served streams equal the descriptor's exposed set. Every unavailable operation answers `unavailable{cause: capability}`. `config.v1`'s write-path scenarios (wildcard refused, stale revision refused, `dry_run` inert, a sensitive value in no reply, view or event) come from **config.v1's own kit**, which this one calls. | `zenoh` |

The guard stays. `cargo tree -e normal --no-default-features -p modem-contract` must not contain
`zenoh`, and `scripts/guards.sh` keeps checking that.

**What it no longer exports.**
- `PROFILE`: the host id is `hostid.v1`'s. Its salt question is README gap 22.
- `PRODUCER`: there is no producer chunk. The device is the service.
- `schema::SchemaSet`: the bundle carries the schemas.

**What it depends on.** `config.v1`'s types (`ParamValue`, `ConfigView`, …) come from the
`config.v1` contract crate, which the profile publishes. `modem-contract` depends on it for
`ActionRequest.arguments` and for `config.rs`. That is the crate-level face of README gap 18.

## 4. How each kind of dependent uses it

**A device backend** (the owner's IP driver, a new radio):
- It implements `modem_device::{Device, Medium | Netdev, Configure, Actions}`.
- It depends on `modem-device` alone, **unchanged**. It never sees zk2, zenkey or zenoh.
- The `modem_device::conformance` trait kit still checks it from its own test suite.

**A daemon that serves it:**
- It links `modem-mgmt`, which enables `modem-contract/zenoh`.
- The call site is today's: `Host::new().with(Node::device(my_backend))`.
- Each node becomes a zk2 service `zk2/<host-id>/<node.name()>`.
  - It implements `modem.v3`; `config.v1` when the device has a configuration plane; `health.v1`.
  - modem-mgmt derives the `CapabilitySet` from the device as today's `sensor` does: from the
    readings that have values, plus `sdu` for a lane driver and `config` for a configuration
    plane.
  - `availability()` gives the descriptor's exposed and unavailable lists.
- `conformance-wire` runs against it, as `Wire::all()` does today.

**A consumer that already owns a session** (a ground-station tool, or the far side of an RF link
reading the four link streams):
- It depends on `modem-contract` with **default features off**: key strings, serde types, the
  bundle and `availability`, with no zenoh brought in by the contract crate.
- It binds statically to `h-<12hex>/rf0` and decodes `sdu/dropped_total` and the rest from the
  compiled types. It needs no descriptor and no bundle fetch ([`link.md`](link.md) §5).

```toml
# an out-of-tree daemon (the backend crate itself needs only modem-device)
[dependencies]
my-radio       = { path = "../my-radio" }                        # implements modem_device::Medium + Configure
modem-device   = "0.4"                                          # the seam: no zenkey, no zenoh
modem-mgmt     = "0.4"                                          # the plane; enables modem-contract/zenoh
modem-contract = { version = "0.4", features = ["conformance-wire"] }
```

```toml
# a far-side reader with its own zenoh session
[dependencies]
modem-contract = { version = "0.4", default-features = false }  # types, keys, bundle: no zenoh
```

These are the next breaking release of the three seam crates, published together in dependency
order as today (modem-device, modem-contract, modem-mgmt). zk2's zenkey is `0.20` on the strangler
layout.

## 5. Versions: crate semver against the contract major

- **One module per major.** `modem.v3` is the `v3` module. A later `modem.v4` lives beside it in
  the same crate (`modem_contract::{v3, v4}`) while a fleet migrates. A service may implement both
  majors at once, because their keys are mutually invisible.
- **A minor revision is a crate minor.** It is additive, and FULL_TRANSITIVE guarantees it. That
  matches zenoh-modem's terminals and gateways being upgraded months apart. Removing a major's
  module is a crate major.
- **Fingerprints, not crate versions, decide compatibility on the wire.** Two builds whose bundle
  is byte-identical are the same contract: the retention rule (r3 §3.11) keeps the old bundle when
  the classifier judges a rebuild identical.

## 6. What the crate cannot carry, and the runtime must

- **A new continuity epoch on a running service.** A netdev's counters reset when its ifindex
  changes. modem-mgmt cycles the device token today (`modem-mgmt/src/lib.rs:644-680`). Under zk2
  it must mint a new instance id **without restarting the process**: r3.2 §3.5 says MUST. zk2's
  start-up order (§3.10) and Rust shape (§3.14) describe only a start, so `zenkey` needs a
  `Service::new_epoch()` with a stated order (README gap 16). The contract crate only documents
  that every `telemetry.kind = "counter"` resource is reset across an epoch.
- **The host id.** `hostid.v1` mints it. Today the derivation is salted per application
  (`zenoh-modem-host-id-v1`), so README gap 22 decides what `modem-contract` stops exporting.
