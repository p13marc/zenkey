# `freshness.v2`: confirmed by a heartbeat

| | |
|---|---|
| **Text version** | 0.7 ([`CHANGELOG.md`](CHANGELOG.md)) |
| **Status** | draft |
| **Written against** | core 0.99 ([`../../core.md`](../../core.md)) |
| **Uses** | no other profile. It restates [`freshness.v1`](v1.md)'s rules by reference, text 0.5, and replaces its §2.4. |
| **Evidence** | [`conformance/apply.json`](conformance/apply.json), the core's [`heartbeat/times.json`](../../conformance/heartbeat/times.json), [`scenarios-v2.md`](scenarios-v2.md) |

`freshness.v2` gives a resource the staleness horizon `freshness.v1`
gives it, judged the same way. What changes is how an owner confirms a
state member. Under `freshness.v1` it puts the member again, whole and
freshly stamped, at most every ttl/2. Under `freshness.v2` it sends one
**heartbeat** per interface instead, core §7.5's form 6, which vouches
for each member by a bit and puts no value again.

```toml
[interface]
name = "modem"
major = 3
uses = ["freshness.v2"]

[resources."sdu/endpoint/{endpoint}"]
kind        = "state"
type        = "json:Endpoint"
params      = { endpoint = "string" }
cardinality = 64
annotations = { "freshness.ttl_s" = 60 }   # vouched for by a heartbeat every 28.5 s
```

A reader judges every member as `freshness.v1` judges it. Only what counts
as a confirmation grows: a heartbeat that confirms the member, by the
rule of §2.5, is one.

---

## 0. Conventions

The keywords, the roles and the evidence tags are core §0's. Here,
`[F: <file>]` names a fixture in [`conformance/`](conformance/), `[Sc: §n]`
a section of [`scenarios-v2.md`](scenarios-v2.md), and `core` marks the
core's own evidence. `v1 §n` names a section of
[`freshness.v1`](v1.md).

Terms are `freshness.v1`'s (v1 §0), and these:
- **Heartbeat:** a put on the heartbeat key (§3) whose payload is core
  §7.5's form 6. It covers one interface, its **covered interface**.
- **Collection:** a `state` or `@state` resource of the covered revision
  whose `freshness.ttl_s` is above 0 (core §7.5). A heartbeat's body has a
  section for each collection its map marks.
- **Vouch:** an owner vouches for a member when it holds the member's value
  as current. Its heartbeat then sets the member's bit (core §7.5).
- **Confirmation:** a put of a member by its owner, a sample of a stream,
  or a heartbeat that confirms the member under §2.5's rule. A delete is
  not one.
- **Last confirmation:** the later of a member's last mutation and the
  last heartbeat that vouched for it.
- **The view:** the members of one owner's collections for one interface,
  as a reader heard them, each with its in-band stamp (core §4.3).

| 3. A registered verbatim kind | None. |
| 4. The descriptor's `profiles` | As core §3.3 lists every profile a contract uses. An owner also implements the standard contract (§3), so its descriptor lists the interface `freshness.v2`. |

**One text per contract.** A contract lists `freshness.v1` or
`freshness.v2` in `uses`. A contract that lists both is read under this
text: its owner sends heartbeats, and re-puts nothing.

## 2. Rules

### 2.1 to 2.3: the value, the kinds, no horizon

They are v1 §2.1, §2.2 and §2.3, word for word. Where they cite v1 §2.4,
read this text's §2.4.

### 2.4 The owner's obligation

**State.** An owner of an interface whose contract uses `freshness.v2`
confirms its collections' members by a heartbeat, never by putting them
again.
- **The heartbeat.** An owner MUST publish a heartbeat for each interface
  it serves whose contract uses `freshness.v2` and has a collection. Its
  heartbeats MUST be at most half the shortest horizon among that
  interface's collections apart. `[Sc: §1]`
  - It is a put on the heartbeat key covering the interface (§3), with
    the contract's QoS: reliable, `drop`, priority `data`, not express.
  - Its payload is core §7.5's form 6. CH carries the covered revision's
    tag, and the run and seq are the heartbeat key's own (core §4.3,
    "Streams").
  - **The time** is the owner's clock when it writes the heartbeat. It is
    the instant of the Zenoh timestamp the owner mints then, to the
    millisecond (core §4.3, "Minting"). All ones say it is unknown, as
    while the clock guard holds (§2.10).
    - **Its epoch.** The time counts from the deployment epoch (core
      §7.6). For an owner given a catalog, that is the catalog's epoch,
      the one its frames and packed records count from (core §8.6).
      For an owner given none, it is 0. Its 32 bits of seconds are then
      Unix seconds, to 2106. `[F: core heartbeat/times.json]`
    - **No code.** An instant before the epoch, or 2^32 s or more after
      it, has no code (core §7.6). An owner MUST write all ones as its
      heartbeat's time while its clock reads such an instant.
      `[F: core heartbeat/times.json]` A device with no real-time clock
      reads 1970 at boot. Under a catalog whose epoch is later, it writes
      all ones until its clock is set.
  - **When.** The owner sends heartbeats while it serves the interface:
    from its interface tokens on (core §8.2, step 4), never from a standby
    ([`redundancy.v1`](../redundancy/v1.md) §2.4). It sends them with no
    member live too, so that liveness has its evidence (§2.9).
  - **They stop** when the owner stops serving the interface: when its
    process ends, when its service closes, or when it steps down.
- **The map.** The owner sets a collection's map bit when it exposes the
  collection (core §3.3). A collection gated on a capability it does not
  hold, or listed `unavailable`, has its bit clear.
- **The sections.** Each section's digest is the collection's over the
  members the owner holds live, as core §7.5 computes it.
- **The bits.** An owner MUST set a member's bit only while it vouches for
  the member's value. A member that is not live has no bit. `[Sc: §1, §2]`
  - **Only a value it holds current.** An owner that can no longer vouch
    for a value, because the source it reports went away, clears its bit
    and lets the member go stale, or deletes it. A bit left set would turn
    a stale value fresh.
  - **A change is a confirmation.** A put starts the member's interval
    again, as under `freshness.v1`. A member put more often than its
    heartbeats needs nothing from them.
- **No re-put.** An owner SHOULD NOT put a member again to confirm it: its
  heartbeat does. `[Sc: §1]`
- **Its stamps.** Core §4.3's table lists no state of a contract that uses
  `freshness.v2`. So its puts carry no Zenoh timestamp on a session
  without timestamping (core §8.2). A GET answers its members by snapshot
  (core S2), each live entry with its **confirmation** (core §7.5). A GET
  reader ages a member from it (§2.6). `[Sc: §3]`
  - **Vouched for now:** confirmation 1, at the snapshot's time, while
    the owner vouches for the member, as a heartbeat sent then would.
  - **Otherwise** confirmation 2, with the member's last confirmation.
    For a member no heartbeat vouched for since its put, it is the put's.
  - **The times** are minted at each mutation of the member, at each
    heartbeat that vouches for it and as the owner builds the snapshot
    (core §4.3, "Minting"). Only a snapshot carries them, to the
    millisecond.
- **Why half.** One lost heartbeat still leaves a confirmation within ttl,
  as one lost re-put did (v1 §2.4).
- **The cost** is one put per covered interface every period, whatever
  its members: the digest, 32 bits per collection, and a bit or a rank
  per member. A collection of 64 members at ttl 60 costs a few bytes every
  28.5 s, where `freshness.v1` put 64 values every 30 s.

**Stream.** v1 §2.4's stream half, word for word: an owner publishes a
sample on each member at least every ttl/2, and no runtime repeats one.
A heartbeat confirms no stream (core §7.5's collections hold none).

### 2.5 A subscriber's age

A subscriber ages a member as v1 §2.5 says, on its own monotonic clock,
from its last confirmation. A heartbeat that confirms the member is one,
at the heartbeat's arrival.

**Following a collection.** A subscriber follows a collection it hears
whole: its subscription names no parameter of the collection's template.
It holds its view from the puts and deletes it heard, each with its
in-band stamp, and from a read's answer (below). It subscribes to each
provider's heartbeat key covering the interface (§3).

**The rule.** A subscriber MUST confirm a member by a heartbeat only as
this rule says. `[F: apply.json]` `[Sc: §4]` It reads each heartbeat in
these steps, and stops at the first that answers:
1. **Another revision.** CH's tag is not the revision the reader holds:
   nothing is confirmed (`revision`).
2. **Refused.** The body is refused (core §7.5): nothing is confirmed.
3. **Older.** Within one run, its seq is not after the last read
   heartbeat's (step 4), by core §4.3's serial order: nothing is
   confirmed (`older`).
4. **Read.** Otherwise each collection's section is read, in map order:
   - a collection it does not follow: nothing (`not_followed`);
   - a map bit of 0: nothing confirmed there (`absent`);
   - a digest or a live count that is not the view's: nothing confirmed
     there (`diverged`);
   - otherwise, each member whose bit is set is confirmed at the
     heartbeat's arrival (`confirmed`).

The view's digest is core §7.5's, over the live members it holds. A live
member it holds with no in-band stamp has no digest, so its collection
diverges.

**What counts.** A **read heartbeat** is one read at step 4. A heartbeat
stopped at step 1, 2 or 3 is not counted. It moves neither the sequence
(below) nor a count of divergences in a row. `[F: apply.json]`

**A lost heartbeat.** A read heartbeat whose seq is not the last read
one's plus 1, within one run, follows a lost one. A subscriber MUST then
read every member of the interface's collections as v1 §2.5 rule 3 reads
a lost delivery, until a heartbeat arrives in sequence. `[F: apply.json]`
`[Sc: §4]` A heartbeat of another run starts the sequence again.

**A cleared bit** is no confirmation. The member ages from its last
confirmation, as a `freshness.v1` member ages once its re-puts stop. It
is not stale at once. `[F: apply.json]` `[Sc: §2]`

**The re-read.** A divergence says the view missed a put or a delete, or
holds another run's value.
- After two read heartbeats in a row diverge on a collection, a subscriber
  SHOULD read the collection again from its owner, by core S4's GET. The
  answer MUST then replace its view of the collection.
  `[F: apply.json]` `[Sc: §4, §5, §6]`
  - The GET is a collection read: the collection's snapshot key followed
    by `/**` (core §4.2). The owner answers with the collection's
    snapshot.
  - The answer is merged with what the subscriber heard of the
    collection after it asked, as core §4.2 merges a late joiner's seed.
    Within one run the higher seq is kept. Across two runs the answer's
    value stands, as core §4.3's consumer rule accepts another run.
  - A member a complete snapshot left out leaves the view, by core §4.2's
    omission rule. An incomplete one removes nothing: the subscriber
    reads again.
- **Why two.** zenoh carries each priority in a queue of its own, so a
  heartbeat and a put on another priority can cross in flight. The
  second heartbeat absorbs that race (core Appendix B).
- **A read that fails**, silent or ended at its timeout, replaces
  nothing. So does a GET the reader is not granted. The collection stays
  unconfirmed and goes stale, the safe side.
- **How often.** A re-read costs the collection's snapshot, a reply per
  page. It follows two divergences, so a collection is read at most once
  every two heartbeats.

**A late joiner** follows a collection from its seed (core §4.2): its own
S4 GET's answer is a read, which replaces its view as above. Without one,
its first heartbeats diverge, and the re-read seeds it. `[Sc: §5]`

**The first heartbeat** after a subscription can come a period late. zenoh
drops a put at its owner until the owner's router has declared the new
subscriber. v1 §2.5 rule 6 already reads that wait as unobservable.

### 2.6 A GET reader's age

v1 §2.6, word for word, read over a snapshot's entries (core §4.2). A GET
reader MUST age an entry from its confirmation as v1 §2.6 ages a reply
from its stamp, by its trust rules, its band and its order of checks.
`[F: judgements.json]` `[Sc: §3]`
- **The confirmation's time** is the snapshot's time for confirmation 1,
  and the entry's conf for 2. An unknown time is no stamp: unobservable.
- **The clock** is the owner's, which built the snapshot. v1 §2.6's
  grounds trust it as they trust the clock a stamp's id names.
- **Confirmation 0** on a member with a horizon breaks core S2. It is no
  stamp: unobservable.
- **A tombstone** is a `reply_del`: deleted, not this profile's.
- **A member a complete snapshot omits** has no value, by core §4.2's
  omission rule: deleted, as a tombstone. One an incomplete snapshot
  omits is a member the read did not reach: unobservable.
- **The order** is v1 §2.6's, an entry for a reply: no entry, then a
  tombstone, then no confirmation's time, then a clock not trusted, then
  the band. At ttl 0, any live entry is fresh (v1 §2.3).
- **Why a time per entry.** A collection has no one confirmation once a
  member's bit is clear. So the snapshot's time is when it was built, and
  each entry says whether the owner vouches for it then.

### 2.7 and 2.8: several observations, archives

They are v1 §2.7 and §2.8, word for word. An archive sees no heartbeat,
so its last-known stamp is the member's last change: display only.

### 2.9 Constrained faces

v1 §2.9, with its last item replaced:
- **The heartbeat crosses** where `link.v1` lets a collection it covers
  cross ([`link.v1`](../link/v1.md) §2.9). Never downsampled, it costs the
  face one put per covered interface every period (link.v1 §2.8).
- **It is liveness evidence.** Its own horizon is the shortest horizon of
  the collections it covers. A provider is live across the face while its
  heartbeat is fresh by a subscriber's receive clock, as a member is
  (link.v1 §2.12). `[Sc: §7]` `[Sc: core constrained.md §3]`
- **A GET across the face** needs its round trip within the reader's
  timeout. A deployment whose face is slow sets the re-read's timeout
  above it.

### 2.10 Clock ahead

An owner whose clock guard finds it ahead of its router beyond the delta
stops the state writes that carry a Zenoh timestamp (core §4.3). On a
session without timestamping, the puts and deletes of a member of this
profile carry none, so the guard holds none of them.
- **The heartbeats go on,** as at any other time: each sets a member's
  bit while the owner vouches for it (§2.4). A subscriber ages a member
  on its own clock (§2.5), which the owner's does not move.
- **A held write.** Where the guard holds a member's write (a candidate's
  session stamps every write), the owner clears its bit until a write of
  it goes on. `[Sc: §2]` A `redundancy.v1` candidate's session is the one
  that stamps (core §8.2). The value it still holds is one it was asked
  to replace or delete, which it can no longer vouch for (§2.4).
- **Their time is unknown** while the guard holds. An owner MUST write
  all ones as its heartbeat's time while its guard holds. `[Sc: §2]` The
  time is the owner's word of its clock, and that clock is ahead.
- **Its snapshots** carry times minted from the clock ahead: the
  snapshot's time, and each entry's conf (§2.4, core §4.3). No router
  reads them (core §4.1).
  - An entry confirmed within the offset reads as ahead of a right
    clock. A GET reader then judges it unobservable, by v1 §2.6's band.
    `[Sc: §2]`
  - An older one reads younger by the offset. Under the deployment's
    word, which a clock ahead breaks, that error is the deployment's
    (v1 §2.6, ground 1).
- **When the guard releases,** the next heartbeat's time is known again.

### 2.11 Stale is a finding, never "down"

v1 §2.11, word for word. A heartbeat gone silent says its covered
members are no longer confirmed, as this reader observed: never that the
provider is down (core R7).

## 3. Contract

[`freshness.v2.toml`](freshness.v2.toml) is the standard contract, the
interface `freshness.v2`, published in `../.history/freshness.v2/`.

| Resource | Kind | Key | What it carries |
|---|---|---|---|
| `heartbeat/{iface}` | stream | `zk2/<system>/<service>/freshness.v2/stream/heartbeat/<iface>` | the heartbeat covering `<iface>`, an interface id (§2.4) |

- **Who implements it.** An owner of an interface whose contract uses
  `freshness.v2` and has a collection implements it beside that
  interface, once for all of them. Its descriptor lists it (core §3.3).
- **The key's parameter** is the covered interface's id, a plain chunk
  (core §1.2), so it needs no slug.
- **Its interface token** is held as any interface's (core §8.1). The
  interface is one every such service implements, so a deployment near
  the presence budget names it in its tokenless set.
- **QoS.** Reliable, `drop`: two lost heartbeats in a row read as stale,
  safe but wrong, where `block` would let a heartbeat stall a link.

## 4. Vocabulary

| Key | Type | On | Meaning |
|---|---|---|---|
| `freshness.ttl_s` | v1 §4's | v1 §4's | v1 §4's, but above 0 the owner confirms each member of a state by its heartbeat at least every ttl/2 (§2.4). |

## 5. What a tool may conclude

v1 §5, word for word, and these:
- **A heartbeat's confirmation** is shown as the heartbeat's arrival, or,
  for a GET's snapshot entry, as its confirmation's time. It is never
  shown as a change.
- **A divergence** is the reader's word: its view missed something, which
  a re-read mends. It is no finding about the owner.
- **Is this provider live across the face?** Yes also when its heartbeat
  is fresh by a subscriber (§2.9).

## Appendix A. Against v1

| `freshness.v1` | `freshness.v2` | Why |
|---|---|---|
| An owner re-puts each member with a horizon, whole, at most every ttl/2 (v1 §2.4) | One heartbeat per covered interface vouches for every member by a bit (§2.4) | On W2, re-puts of unchanged values cost about 6.2 MB a day, config.v1's view and status most of it |
| A re-put carries a fresh Zenoh timestamp, which a GET reader ages (core §4.3's table, row 1) | Puts carry none; a GET answers by snapshot, each entry with its confirmation: vouched for at the snapshot's time, or its last confirmation (§2.4, §2.6) | The confirmation is the heartbeat's, not a mutation's, and a snapshot carries it in band |
| A lost re-put is a lost delivery | A lost heartbeat is one, by a gap in its key's seqs (§2.5) | The heartbeat key's own stream seq counts heartbeats |
| A reader that missed a change learns of it at the next re-put | A digest that is not the view's says so, and two in a row are re-read (§2.5) | A high-water seq would read a lost change of one member followed by another's as in sync |
| `set_refresh(false)` stops the re-puts (the reference) | A cleared bit stops the confirmations (§2.4) | The same intent, at one bit's cost |
| A clock ahead stops the re-puts, and the members go stale (v1 §2.10) | The heartbeats go on vouching, their time unknown, except for a member whose write the guard held (§2.10) | A put on a session without timestamping carries no Zenoh timestamp, so the guard holds none (core §4.3) |

**What deliberately did not change.** The horizon, its value and its
kinds (v1 §2.1–§2.3), the subscriber's and the GET reader's judgements
(v1 §2.5, §2.6), the combination (v1 §2.7), archives (v1 §2.8) and "stale
is never down" (v1 §2.11). `freshness.v1` stays defined for the contracts
that use it.
