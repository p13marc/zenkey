# `config.v2`: a configuration declared in its contract, read back in one record

| | |
|---|---|
| **Text version** | 0.1 ([`CHANGELOG.md`](CHANGELOG.md)) |
| **Status** | experimental |
| **Written against** | core 0.94 ([`../../core.md`](../../core.md)) |
| **Uses** | [`freshness.v2`](../freshness/v2.md), text 0.5. It restates [`config.v1`](v1.md)'s rules by reference, text 0.9, and replaces its wire. |
| **Evidence** | [`conformance/v2/`](conformance/v2/), [`scenarios-v2.md`](scenarios-v2.md), and `config.v1`'s for the rules it keeps |

`config.v1` lets a caller change a running service's configuration
without locking itself out of it. Its wire is JSON: a 1.3 KB view that
serves the schema with the values, a compact status beside it, and a
read-back in every control reply. On a radio link the view is eight
frames, and a confirm's reply crosses only when all eight do.

`config.v2` keeps every rule of `config.v1` and changes its wire:
- **The schema moves into the contract.** Each configured kind of device
  has a config contract of its own, which declares its groups, classes,
  kinds and bounds. Nothing of the schema travels.
- **One packed record** replaces the view and the status. It holds the
  running values, the pending and the last change, the floor and the
  desired report, in about 30 bytes.
- **Every operation answers the record**, in core §7.5's value form, or
  refuses in its error form.
- **Tokens, times and keys are numbers:** a token is 48 bits, a time 32
  bits, an idempotency key 32 bits.

A config contract for zenoh-modem's SX1262 radio, trimmed:

```toml
[interface]
name  = "sx1262_config"
major = 1
uses  = ["config.v2", "freshness.v2"]

[schemas]
packed     = ["schemas/sx1262_config.json"]   # Duty, Radio, Modulation, and the derived types
jsonschema = ["config.v2.json"]               # this profile's standard schema, copied

[resources.config]                            # the record
kind = "state"
type = "packed:Record"

[resources.config.annotations]
"freshness.ttl_s" = 300
"config.groups"   = [
  { name = "duty",       class = "hot",      type = "packed:Duty",  units = { fraction_ppm = "ppm" } },
  { name = "radio",      class = "reach",    type = "packed:Radio", units = { frequency_hz = "Hz" } },
  { name = "modulation", class = "contract", type = "packed:Modulation" },
]

[resources."set/radio"]                       # one per hot or reach group; none for modulation
kind     = "operation"
request  = "packed:SetRadio"
response = "packed:Record"
error    = "packed:Error"

# set/duty alike; confirm, cancel and extend take packed:Control; persist too,
# with optional = true; change is the event (§3).
```

Its keys:

```text
zk2/<system>/<service>/sx1262_config.v1/state/config            the record; a GET is the read
zk2/<system>/<service>/sx1262_config.v1/@op/set/<group>          change some parameters of one hot or reach group
zk2/<system>/<service>/sx1262_config.v1/@op/confirm              keep the pending change
zk2/<system>/<service>/sx1262_config.v1/@op/cancel               undo it now
zk2/<system>/<service>/sx1262_config.v1/@op/extend               move its deadline
zk2/<system>/<service>/sx1262_config.v1/@op/persist              make the last change survive a restart (optional)
zk2/<system>/<service>/sx1262_config.v1/events/change/<ulid>     one change as it ended
```

## 0. Conventions

The keywords, the roles and the evidence tags are core §0's. Here,
`[F: <file>]` names a fixture in [`conformance/`](conformance/), and
`[Sc: §n]` a section of [`scenarios-v2.md`](scenarios-v2.md). `v1 §n`
names a section of [`config.v1`](v1.md), and a fixture of v1's says so,
as in `[F: v1 lifecycle.json]`.

**By reference.** Every rule of `config.v1` holds for a config contract's
owner, caller and tool, as written, except where §2 replaces it. Where a
rule of v1 names the view or the status, it reads the record. Where it
names a reply's document, it reads the record the reply carries.

Terms are v1 §0's, and these:
- **Config contract:** a contract that lists `config.v2` in `uses`. Its
  interface is a **config interface**.
- **Declaration:** its `config.groups` (§2.2). **Group type:** the packed
  type (core §7.6) a group names, whose fields are its parameters.
- **Settable group:** a `hot` or `reach` group. A `contract` group is not
  settable.
- **Derived types:** `Record`, one `Set<T>` per settable group, `Control`
  and `Error`, each derived from the declaration (§3).
- **Record:** a value of `Record`, the state `config` (§2.3).
- **Instance number:** the record's `instance`, the run an instance first
  wrote under (core §4.3). The envelope's run can change within an
  instance. The instance number never does.
- **Token:** a change's name, 48 bits (§2.6). **Time:** an instant in a
  `time` field without milliseconds, seconds since the deployment epoch
  (core §7.6, §8.6).
- **As-of mark:** core §5.1's, a reply's run and seq.

## 1. Extension points

| Point (core §10) | `config.v2` |
|---|---|
| 1. A standard contract or a standard schema | A standard schema, [`config.v2.json`](config.v2.json): the change event (§3). No standard contract: each configured kind of device has its own. |
| 2. An annotation vocabulary | `config.groups` (§4). Core Appendix D lists no `config` vocabulary, so W105 reads none, and no `config.<key>` draws W105 (core §10). §2.2's lint reads §4. |
| 3. A registered verbatim kind | None. |
| 4. The descriptor's `profiles` | Through `uses` alone. An instance implementing a config contract lists `config.v2` and `freshness.v2` (core §3.3), and the config interface in `interfaces`. |

**Beside `config.v1`.** An instance implements `config.v1`'s standard
contract or a config contract, never both: it has one configuration
(§2.1). A service moves from one to the other with a new instance, and a
tool reads both.

**Why a new id.** `config.v1`'s wire is its standard contract's JSON
documents. A reader of `config.v1` alone finds no `config.v1` interface
on a `config.v2` owner, so it never misreads a record as a view.

## 2. Rules

### 2.1 Who implements it

v1 §2.1, with these changes:
- **The profile is the gate.** A service is configurable when its
  descriptor's `profiles` lists `config.v2`. Its config interface is the
  one whose contract uses `config.v2`. A tool reads descriptors to find
  both. Across a face, the deployment's word stands for the descriptor
  (core R7).
- **No token selector.** Each config interface is its adopter's, so no
  one selector lists configurable services, as `config.v1`'s alive
  token did. v1's advice on the tokenless set goes.
- **One configuration per service.** An instance implements at most one
  config contract.
- **Exposure.** Every resource of §3 is required, except `persist`.

### 2.2 The schema, in the contract

The schema is declared, not served. A tool renders a form and checks a
change from the contract, which it holds by fingerprint (core §8.4), never
from the wire.

**The declaration.** The state `config` declares the groups in one
annotation, `config.groups`. Its value is an array: one entry per group,
in the owner's order, and markers.
- **An entry** is a table of `name`, `class` and `type`, and optionally
  `units` and `sensitive`:
  - `name`: `[a-z][a-z0-9]*(_[a-z0-9]+)*`, unique among the groups. It is
    the `<group>` of `@op/set/<group>`;
  - `class`: `hot`, `reach` or `contract` (v1 §2.4), the owner's;
  - `type`: a packed type, `packed:<Name>` or `packed:<stem>#<Name>`,
    named by no other entry;
  - `units`: a table from a parameter's name to its unit, a non-empty
    string, for an `int` parameter;
  - `sensitive`: an array of parameter names, each once (§2.15).
- **A marker** is the string `"..."`. A later revision appends groups
  behind one (§3).
- **At most 16 groups,** and at least one.

**The group type** is a packed type whose fields are the group's
parameters, in the owner's order.
- **A parameter** is a field of type `int`, config.v1's `integer` with
  its bounds, or `bool`. Its `description` is the parameter's doc
  string. It is not the wire, so core §9.8 reads a change to it as
  compatible. The packed file's id hashes it, though, so a new
  description is a new revision (core §9.4).
- **No more:** no optional field, no reserved code, no marker, and at most
  16 fields. A field's name has a group name's form. It is none of
  `confirm_s`, `token`, `expected_revision`, `idempotency_key`, `dry_run`,
  `writable`, `pending` and `last`, which the derived types use.
- **No text yet.** Text, an enum and a fixed-point parameter wait for an
  owner that needs them and a packed format that carries them.

**A bound is the wire.** Moving one is a breaking revision (core §9.8).
A contract SHOULD declare its device's widest bounds, and a device that
refuses a value within them answers `device_refused` (§2.9).
`[F: v2/lifecycle.json]`

**Reading it.** A reader and a linter MUST read `config.groups` exactly
as the fixtures do: the same groups, or the same reasons in the same
order. `[F: v2/derive.json]`
- **The annotation whole** is checked first: `groups_value` when it is
  not an array, holds no group or more than 16, or puts a marker first,
  last or after a marker. Nothing else is then checked.
- **Each item,** by its index, its checks in this order. Each check is
  made alone, and a check that needs a wrong value is skipped:
  1. `group_value`: an item that is neither a table nor a marker skips
     the rest; a table with a member outside the five is reported, and
     checked on;
  2. `group_name`, `group_class`, `group_type`: that member is not as
     above;
  3. `group_units`, `group_sensitive`: that member is not as above. Each
     needs a valid type to name its parameters.

**The contract's lint.** Beside the declaration, a linter checks that the
contract holds §3's resources, and that each derived type equals its
derivation. It MUST report the fixtures' findings, in their order.
`[F: v2/derive.json]`
- `groups_missing` and `groups_invalid` stop the lint.
- Then, for `config`, each `set/<group>` in the groups' order, `confirm`,
  `cancel`, `extend`, `persist` and `change`: `resource_missing`, else
  `resource_shape`, else `config_derivation`. For `config` alone,
  `freshness` follows.
- Then `set_not_settable`, for a `set` resource of no settable group.
  Then `groups_place`, for `config.groups` anywhere but `config`.

**An error, never a warning.** An implementation that lints a contract
MUST report an invalid declaration or a finding as an error.
`[F: v2/derive.json]` A reader MUST NOT read a record by a contract that
has one: its records are unobservable. `[F: v2/derive.json]`

### 2.3 The record

`state/config` carries the record, which replaces v1 §2.3's view and v1
§2.19's status. It is a value of `Record` (§3):
- the **instance number**, the **revision** and the **floor**,
  `floor_s`;
- **`would_be`**, set only in a dry run's reply (§2.9);
- the **pending change**: its token, its deadline, and `apply_at` while a
  reach group waits (§2.9);
- the **last change**: its token;
- the **desired report** (§2.18);
- for each settable group, three bits: **`writable`** (§2.16), and
  whether it is in the pending change and in the last change;
- for each parameter, its **`source`**, whether its startup value
  **`differs`**, and its **value**.

**A GET is the read,** as v1 §2.3 says.

**Per parameter,** in v1 §2.3's terms:
- `source` is the running value's, and is absent when the value is
  unknown;
- `differs` is set when the startup value is not the running value. It
  is clear when the value is unknown;
- the value is the running value, absent when unknown;
- a sensitive parameter has `source` alone (§2.15).

**The revision** counts acts, as v1 §2.3 says, from 0 in each instance.
At 32 bits it holds 4,294,967,295 acts.

**The instance number** is the run an instance first wrote under,
zero-extended to 32 bits. A run that changes within the instance, its
seq or its token counter spent, leaves it. A 16-bit run and a 32-bit run
can share a number, which a reader accepts as a 1 in 2^32 risk.

**Writing and reading it.** An owner MUST write its record, and a reader
MUST read one, exactly as the fixtures do. `[F: v2/records.json]` A reader
refuses a record for the first of these:
- core §7.6's refusals;
- `group`: a group behind a marker written in part;
- `pending`: the pending fields not all present or all absent, or a
  pending change in no group;
- `last`: a last token and no group's last bit, or the reverse;
- `desired`: the desired fields that do not hold together (§3);
- `parameter`: a value and its source not both present or both absent, or
  `differs` set with no value.

**When it is put.**
- An owner MUST put its record before core §8.2's step 4, and so before
  its instance token. `[Sc: §1]`
- It MUST put it on every change of any field, and at nothing else.
  `[F: v2/lifecycle.json]` `[Sc: §1, §2]`
- It confirms it by its heartbeat (`freshness.v2` §2.4), and never puts
  it again unchanged. The contract declares the record's
  `freshness.ttl_s` (§2.2).
- It MUST NOT delete it while it runs. `[Sc: §1]`

**One key.** v1's two documents, and its rule for reading them together,
go. The record and every reply are one value at one seq.

### 2.4 The classes

v1 §2.4, with these changes:
- **`hot`:** a `set` answers the record after the apply.
- **`reach`:** a `set` answers the record before the apply, the change
  pending with its `apply_at` (§2.9).
- **`contract`:** no `set`. The contract states the class, and a tool
  reads it there. A call to a key no settable group has reaches no
  queryable, which is silence (core O5). `restart-required` goes.

### 2.5 Validating a set

**The request** is `Set<T>`, the group's derived type (§3): each of the
group's parameters, optional, then `confirm_s`, `token`,
`expected_revision`, `idempotency_key`, each optional, and `dry_run`.

**Before the device sees anything.** The core's refusals come first
(core §5.1): `fanout_forbidden`, then `unavailable`. Then a request that
does not parse is `invalid_request`: core §7.5's refusals for a query,
then core §7.6's for `Set<T>`. A value outside its parameter's bounds has
no code, so a writer cannot send it, and a reader reads an unused code.

**Then the rows.** The owner MUST refuse the request for the first of
these that applies, in this order, and otherwise accept it.
`[F: v2/validation.json, v2/lifecycle.json]` They are v1 §2.5's, with
their numbers kept:

| # | Check | Refusal |
|---|---|---|
| 1 | An act is in flight. | `busy` |
| 2 | The request carries an `idempotency_key` whose first answer the owner holds (§2.14). | the first answer, for the same group and request; `invalid_request` otherwise |
| 4 | The group is outside the startup allowlist. | `unavailable`, cause `config` |
| 5 | A change is pending, and the request does not carry its token; or it does, and the deadline has come. | `busy` |
| 6 | The request carries a `token`, and no change is pending. | `not_found` |
| 7 | The request carries an `expected_revision` other than the revision. | `invalid_request` |
| 9 | The request carries both `token` and `confirm_s`. | `invalid_request` |
| 10 | The group is `reach`, and the request carries neither `confirm_s` nor `token`, and is not a dry run. | `invalid_request` |
| 12 | Not a dry run, and the `set` would start a change while the event's rate is spent. | `busy` |
| 13 | Not a dry run, the group is `reach`, the request joins, and the group could not apply before the deadline. | `busy` |
| 14 | Not a dry run, and the device refuses the group. | `app`, `Error{code: device_refused}` |

Three rows go:
- **Row 3,** no such group: each `set/<group>` is a concrete key with its
  own queryable, so a call to another key reaches none.
- **Row 8,** a contract group: it has no `set`.
- **Row 11,** the values: the request's type holds each parameter's kind
  and bounds, so its parse refuses them.

**The error form.** An owner MUST answer a refusal in core §7.5's error
form, under the Encoding `zenoh/bytes`, with `Error`'s tag and its as-of
mark (§2.9). `[F: v2/validation.json, v2/lifecycle.json]`
- **The detail** is an `Error` record, `{code}`, on `app` alone (core
  §5.2). Its one code at this version is `device_refused`. Its enum is
  open: a reader shows a code it does not name as the escape, and acts on
  none.
- **The message** is for a person, never parsed (core §5.2). With
  `device_refused`, it carries the device's words, unless the change
  carries a sensitive value (§2.15). An owner MAY send one with any
  refusal, and the fixtures' bytes send one with `device_refused` alone.
- **`busy`** names no token. The record carries the pending change's.

**An empty change** is v1 §2.5's: an act that sets no value.
`[F: v2/lifecycle.json]`

**A caller that checks first** MAY run the rows from 4 on against a
record and the contract.

### 2.6 Changes and their tokens

v1 §2.6, with tokens of 48 bits.
- **The layout.** A token is `run × 65536 + counter`: the run current
  when it was minted, zero-extended to 32 bits, then a 16-bit count
  within that run.
- **The counter.** An owner starts it once per run, and adds one at each
  token. It MUST NOT let it pass 65,535. Before it would, the owner takes
  a new run (core §4.3), whose counter starts afresh.
  `[F: v2/lifecycle.json]` `[Sc: §7]`
- **Never reused.** No run is written under twice (core S7), so no token
  is minted twice, and v1 §2.6's rule holds. `[F: v2/lifecycle.json]`
  `[Sc: §7]`
- **A random start.** An owner SHOULD start each run's counter at a value
  it draws at random. `[Sc: §7]` A restored run record repeats a run, and
  a random start makes a token repeated with it unlikely.
- **The last change** is v1 §2.6's.

### 2.7 One pending change

v1 §2.7, with one change. The record shows the change's groups as bits
in the contract's order, never in the order they joined. The event's
edits follow the contract's order too (§2.17). `[F: v2/lifecycle.json]`

### 2.8 The window, the floor, and time

v1 §2.8, with these changes:
- **Bounds.** `confirm_s` and the floor are from 1 to 65,535 seconds,
  their fields' bounds. v1 set no upper bound.
- **Time on the wire.** `apply_at` and the deadline are times: whole
  seconds since the deployment epoch, on the owner's clock (core §7.6,
  §8.6).
- **Rounded up.** An owner MUST round a deadline and an `apply_at` up to
  the next whole second, and MUST act at the instant it states: the undo
  at the deadline, the apply at `apply_at`.
  `[F: v2/window.json, v2/lifecycle.json]` `[Sc: §3]` So a window is
  never shorter than asked.
- **The epoch.** A reader that dates a time without the owner's epoch
  misdates it, and refuses as core §8.6 says. Across a face, the catalog
  is provisioned at both ends.

### 2.9 Applying, and every reply

**Every operation answers the record.** An owner MUST answer every call it
accepts with its record, in core §7.5's value form, under the Encoding
`zenoh/bytes`, with `Record`'s tag. `[F: v2/lifecycle.json]` `[Sc: §1, §2]`
That replaces v1's `SetReply`, `PendingReply` and `ControlReply`.
- **Put first.** When the call changes the record, the owner MUST put
  it, then reply with it, minting no seq between.
  `[F: v2/lifecycle.json]` `[Sc: §1]` So the reply's seq is the put's.
- **The as-of mark.** An owner MUST write a reply's run and seq as core
  §5.1 defines them: the run it writes under, and the last seq it minted
  for state and events under that run, or 0. `[F: v2/lifecycle.json]` A
  replayed first answer keeps the mark it was first sent with (§2.14).
- **A caller across a face** holds the current record from a reply
  alone. It orders a reply against a record it holds by seq, within one
  run (core §5.1).

**Hot, without a window.** The owner applies the group, puts the record
and replies with it: the values at `runtime`, the revision moved by one,
the change the last change. Its event follows (§2.17).

**Any class, with a window.** v1 §2.9's, the reply being the record:
- **hot:** after the apply, the change pending;
- **reach:** the owner MUST put and reply before it applies anything:
  the change pending, the group's bit set, its `apply_at` stated.
  `[F: v2/lifecycle.json]` `[Sc: §2]` It applies the group at `apply_at`,
  and puts the record again.

**`apply_at` in the record** is the one of the last reach group to join
that has not applied. It is absent when none waits, and the change is
then applied: v1's `pending.applied`. A `confirm` before then is `busy`.

**The device refuses.** v1 §2.9's, in the error form (§2.5).

**A dry run** answers the record as it would read, with `would_be` set,
and puts nothing (v1 §2.9). A caller MUST NOT hold a record with
`would_be` set as the owner's state. `[F: v2/lifecycle.json]` `[Sc: §1]`

### 2.10 Confirm, cancel and extend

v1 §2.10, with these changes:
- **The request** is `Control`: the token, and `confirm_s`, for `extend`
  alone.
- **The reply** is the record after the act (§2.9). v1's `answer` goes:
  the record is smaller than v1's status.
- **A request that does not parse** is `invalid_request`, first, as §2.5
  says of a `set`. `[F: v2/validation.json]`

### 2.11 The deadline and the undo

v1 §2.11, at the deadline the record states (§2.8).
`[F: v2/lifecycle.json]` `[Sc: §3, §4]`

### 2.12 A restart is a rollback

v1 §2.12, with one change. A new instance writes under a run no instance
wrote under before (core S7), so its record's instance number differs.
Across a face, a caller tells a restart from it. `[Sc: §7, §13]`

### 2.13 Persist

v1 §2.13. Its reply is the record (§2.9). `[F: v2/lifecycle.json]`

### 2.14 Idempotency keys

v1 §2.14, with these changes:
- **The key** is a caller's 32-bit nonce, from 0 to 4,294,967,295.
- **Equal requests.** An owner MUST compare two requests by their bytes.
  `[F: v2/lifecycle.json]` A packed record has one encoding per value, so
  v1's "equal as decoded" is equal bytes.
- **The first answer, byte for byte.** An owner MUST answer a retry
  within 300 s with the first answer's bytes, its as-of mark included.
  `[F: v2/lifecycle.json]` `[Sc: §10]` The record is as of that mark: a
  later mark would let a caller order it over a newer put.

### 2.15 Sensitive values

v1 §2.15, with these changes:
- **No value bits.** The record has no field for a sensitive parameter's
  value, and none for whether its startup value differs. An owner MUST
  NOT carry the value, or its startup value, in the record, a reply, an
  event, the error form, a log line or the persisted layer.
  `[F: v2/redaction.json]` `[Sc: §11]`
- **Write-only.** `Set<T>` carries it, as v1's request does.
- **The device's words.** An owner MUST NOT send the device's words
  refusing a change that carries a sensitive value: its `device_refused`
  carries no message. `[F: v2/redaction.json]`
- **A log line** writes its value `"<redacted>"`, as v1 says.

### 2.16 The startup allowlist

v1 §2.16, its `writable` a bit for each settable group. An owner MUST
state it in each. `[F: v2/records.json]` `[Sc: §9]`

### 2.17 The change event

v1 §2.17, with these changes:
- **Its type** is `ConfigChangeEvent` from [`config.v2.json`](config.v2.json)
  (§3): `instance` is the instance number, `token` the token as an
  integer, and each edit's `old` and `new` a boolean or an integer.
- **Its edits** follow the contract's order of groups, then of
  parameters. v1 took the change's join order, then the byte order of
  the names.
- **After the reply.** An owner MUST publish a change's event after its
  reply, or after its put when no call is answered.
  `[F: v2/lifecycle.json]` `[Sc: §1, §2]`
- **It stays on the host.** The event is JSON, so a face where packed
  records alone cross does not carry it (`link.v2`).

### 2.18 Desired state

v1 §2.18, with these changes:
- **The report** is the record's desired fields (§3): the outcome, the
  observed revision, and a refusal's code, group index and parameter
  index.
- **Indices.** A refusal names a declared group or parameter by its index
  in the declaration. One the contract does not declare has no index:
  its `not_found` names nothing.
- **The revision** is reported in 32 bits. An owner MUST refuse whole a
  document whose `revision` is above 4,294,967,295, `invalid_request`,
  naming no group. `[F: v2/validation.json]`
- **Its values** are read by the group types: a text value is of no kind
  at this version.
- **Through `desired.v1`.** `desired.v1` §2.16 names `config.v1`. A
  `config.v2` owner fed through it acts as that section says, with this
  section's report.

### 2.19 Constrained faces

v1 §2.19's status goes, with its projection rule.
- **The record crosses.** For zenoh-modem's SX1262 it is 36 to 50 bytes
  with its envelope, one radio frame. A face can carry its push where the
  contract exposes it, and its GET.
- **No GET after a reply.** A caller holds the current record from each
  reply, and from each push it receives. `[Sc: §13]`
- **Its confirmation** is the owner's heartbeat covering the config
  interface (`freshness.v2`).

## 3. The contract

`config.v2` defines no standard contract. A config contract holds these
resources, which §2.2's lint checks:

| Resource | Kind | Request → response, or type | Notes |
|---|---|---|---|
| `config` | `state` | `packed:Record` | `config.groups`; `freshness.ttl_s` above 0, under `freshness.v2` |
| `set/<group>`, one per settable group | `operation` | `packed:Set<T>` → `packed:Record`, error `packed:Error` | none for a contract group |
| `confirm`, `cancel`, `extend` | `operation` | `packed:Control` → `packed:Record`, error `packed:Error` | |
| `persist` | `operation`, `optional` | `packed:Control` → `packed:Record`, error `packed:Error` | |
| `change` | `event`, `burst(600/h)`, `7d` | `json:ConfigChangeEvent` | from the standard schema |

Every operation is `idempotent = false`, `fanout = "forbidden"`,
`serving = "exclusive"` and `replies = "one"`. None has a parameter.

**The standard schema** is [`config.v2.json`](config.v2.json). Its first
revision is
`sha256:0dadb0afae6b405abf958f23a2ff8d61063580028afb6980fdfc208d53a730f1`.
A contract lists it, or a copy whose JCS bytes are equal (core §10), and
its `change` takes `ConfigChangeEvent` from it.

**The derived types** live in the contract's packed files.
`zk2 config derive` writes them from the declaration as below. The lint
compares each with its derivation, field by field, names and descriptions
of the types aside.

**`Record`'s header,** in order:

| Field | Type | Meaning |
|---|---|---|
| `instance` | `int` 0 to 2^32 − 1 | the instance number |
| `revision` | `int` 0 to 2^32 − 1 | the revision |
| `floor_s` | `int` 1 to 65,535 | the floor |
| `would_be` | `bool` | a dry run's reply |
| `pending_token` | `int` 0 to 2^48 − 1, optional | the pending change's token |
| `pending_apply_at` | `time`, optional | while a reach group waits |
| `pending_deadline` | `time`, optional | the pending change's deadline |
| `last_token` | `int` 0 to 2^48 − 1, optional | the last change's token |
| `desired` | `enum` `converged`, `refused`, `failed`, with an escape, optional | the desired outcome |
| `desired_revision` | `int` 0 to 2^32 − 1, optional | its observed revision |
| `desired_code` | `enum` of the desired refusal codes (§4), with an escape, optional | for `refused` and `failed` |
| `desired_group` | `int` 0 to 15, optional | the refusal's group, by index |
| `desired_parameter` | `int` 0 to 15, optional | the refusal's parameter, by index in its group |

**Then each group,** in the declaration's order, `<g>` its name and `<p>`
each parameter's:

| Field | Type | For |
|---|---|---|
| `<g>__writable`, `<g>__pending`, `<g>__last` | `bool` | a settable group |
| `<g>__<p>__source` | `enum` `default`, `file`, `overlay`, `runtime`, optional | every parameter |
| `<g>__<p>__differs` | `bool` | a parameter that is not sensitive |
| `<g>__<p>` | the parameter's field, optional | a parameter that is not sensitive |

**Then markers.** A marker of the declaration is a marker of `Record`,
and every field of a group behind one is optional. `Record` ends with a
marker.

**Growth.** A revision that appends groups behind a marker keeps every
earlier record readable. Core §9.8 reads the record's growth as
compatible, and the annotation's change as a review. A reader of the
earlier revision ignores the appended groups. A reader of the later one
reads an earlier writer's groups as absent.

**The desired fields hold together** when `desired_revision` is present
with `desired`, and absent without it; `desired_code` is present for
`refused` and `failed` alone; `desired_group` comes only with a code, and
`desired_parameter` only with a group; and each index names a declared
group, or a parameter of it.

**`Set<T>`,** for a settable group of type `T`:

| Field | Type |
|---|---|
| each parameter | its field, optional |
| `confirm_s` | `int` 1 to 65,535, optional |
| `token` | `int` 0 to 2^48 − 1, optional |
| `expected_revision` | `int` 0 to 2^32 − 1, optional |
| `idempotency_key` | `int` 0 to 2^32 − 1, optional |
| `dry_run` | `bool` |

**`Control`:** `token`, `int` 0 to 2^48 − 1, then `confirm_s`, `int` 1 to
65,535, optional.

**`Error`:** `code`, an `enum` of `device_refused`, with an escape, 4
bits wide.

**Sizes.** For the SX1262's three groups, a record is 30 bytes idle with a
last change, and 44 with a reach change pending. Its put or reply adds a
6-byte envelope. A `set/radio` with a window, an expected revision and an
idempotency key is 16 bytes, and a `confirm` 8. A refusal is 7 bytes, or
8 with an `Error` detail.

## 5. What a tool may conclude

v1 §5 holds, read from the record and the contract. A fresh record is a
fresh view and status. The premise is a descriptor listing `config.v2`
(§2.1), or the deployment's word across a face.

| Question | Yes | No | Unestablished | Finding on |
|---|---|---|---|---|
| Is a change pending? | A fresh record with `pending_token`: its groups, its deadline, applied when no `pending_apply_at`. | A fresh record without it. | **Unobservable:** no fresh record. | Neither: informative. |
| Did my change land? | Its token is the `last_token` of a fresh record of the instance number that answered the `set`; or an event `applied` or `confirmed`. | An event `rolled-back` or `partial`; or the record's instance number is another, so a restart rolled it back. | **Not yet:** its token is pending. **Unobservable:** v1 §5's cases. | No. |
| Was its undo clean? | An event `rolled-back`. | An event `partial`. | **Unobservable:** no event read. | No: `partial`. |
| Is this group writable? | The contract declares it `hot` or `reach`, and a fresh record's `writable` bit is set. | The bit is clear, or the class is `contract`. | **Unobservable:** no fresh record. **Not asked:** the contract declares no such group. | Neither: informative. |
| Will this value survive a restart? | A fresh record has its value, and `differs` clear. | It has `differs` set. | **Unobservable:** the value is unknown, or sensitive, or no fresh record. | No. |
| Has it converged to its desired document? | `desired` `converged`, at a `desired_revision` at least the document's. | `refused` or `failed` at that revision. | **Not yet**, **not asked**, **unobservable:** as v1 §5 says. | No. |

`[Sc: §14]`

**A reply is evidence,** and so is its record: a caller that holds a
reply holds a fresh record as of its mark. Silence is not, as v1 §5 says.

## Appendix A. Against `config.v1`

| `config.v1` | `config.v2` |
|---|---|
| The schema served in the view (§2.2) | The contract: `config.groups` and the group types |
| The view and the status (§2.3, §2.19) | One record (§2.3) |
| The instance id, a string | The instance number, the first run, 32 bits |
| `set/{group}`, up to 16 members | One concrete `set/<group>` per settable group |
| `SetReply`, `PendingReply`, `ControlReply`, `answer` | The record, in the value form |
| `restart-required` | No `set` for a contract group |
| The JSON error envelope (core §5.2) | Core §7.5's error form |
| RFC 3339 times, to the millisecond | Times in whole seconds, rounded up |
| Tokens `<instance>-<n>`, 1 to 64 characters | 48 bits: the run, then a count |
| `idempotency_key`, 1 to 128 characters | A 32-bit nonce |
| The kinds `bool`, `integer`, `text` | `bool` and `int` |
| Join order in `pending.groups` and the edits | The contract's order |
| `startup`, the startup value | `differs`: a tool reads the startup value on the host |
| `confirm_s` with no upper bound | At most 65,535 s |
| Rows 3, 8 and 11 of §2.5 | Gone: no queryable, no `set`, and the request's type |
| A desired refusal naming any group | An index, none for an undeclared one |

**What did not change:** the three classes, the window raised to the
floor, the undo once, `partial`, one pending change, joining, the last
change, `persist` as its own grant, the allowlist, sensitive values
write-only, one event per change, and desired documents refused whole.

**What waits:** text, enums and fixed-point parameters, the four
zenoh-modem backends that need text, and a packed change event, which
would lose its claimed attribution.
