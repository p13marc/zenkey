# `config.v1`: changing a running service's configuration

| | |
|---|---|
| **Text version** | 0.5 ([`CHANGELOG.md`](CHANGELOG.md)) |
| **Status** | draft |
| **Written against** | core 0.28 ([`../../core.md`](../../core.md)) |
| **Uses** | [`freshness.v1`](../freshness/v1.md), text 0.3 |
| **Evidence** | [`conformance/`](conformance/), [`scenarios.md`](scenarios.md) |

`config.v1` lets a caller change the configuration of a running service
without being able to lock itself out of it. The thing being configured is
often the thing the call travels through: a radio's frequency, a modem's
access point. So a change that can cut the link is applied only under a
window, and is undone at the window's end unless the caller confirms it
over the new link. Its standard contract, [`config.v1.toml`](config.v1.toml),
gives a service these resources:

```text
zk2/<system>/<service>/config.v1/state/view             the read-back: the served schema and the running values; a GET is the read
zk2/<system>/<service>/config.v1/state/status           the compact status a constrained face can afford
zk2/<system>/<service>/config.v1/@op/set/{group}        change some parameters of one group, up to 16 groups
zk2/<system>/<service>/config.v1/@op/confirm            keep the pending change
zk2/<system>/<service>/config.v1/@op/cancel             undo it now
zk2/<system>/<service>/config.v1/@op/extend             move its deadline
zk2/<system>/<service>/config.v1/@op/persist            make the last change survive a restart (optional)
zk2/<system>/<service>/config.v1/events/change/<ulid>   one change as it ended
```

Each act is its own key, so a deployment grants each one separately, per
service. The view and the status declare `freshness.ttl_s = 60`, so the
contract uses [`freshness.v1`](../freshness/v1.md), and so does every
instance that implements it (core §3.3). The protocol is zenkey v1's
RFC 05 §5.1, taken whole as zenoh-modem implements it, with what zk2's keys
and the radio links of its reference adopter add (Appendix A).

---

## 0. Conventions

The keywords, the roles and the evidence tags are core §0's. Here,
`[F: <file>]` names a fixture in [`conformance/`](conformance/),
`[Sc: §n]` a section of [`scenarios.md`](scenarios.md), and `core` marks
the core's own evidence. References to `docs/zk2/architecture.md` (r4: its
§0.2, D11, D12, §4.8 and §4.10) and to
`examples/zk2/zenoh-modem/config.v1-binding.md` (the binding, #623) are
informative: every rule is stated here.

Terms:
- **Owner** is core §0's: the service that implements `config.v1` and
  serves its keys (core §6). The **device** is what its configuration
  configures: a radio, an interface, the service's own process.
- **Caller** is core §0's. A **tool** is core §0's.
- **Group:** the parameters that change together, the unit one `set`
  addresses (§2.2). **Parameter:** one named value of a group. **Class:**
  a group's `hot`, `reach` or `contract` (§2.4). **Kind:** a parameter's
  `bool`, `integer` or `text` (§2.2).
- **Schema:** the owner's groups and parameters, as the view serves them
  (§2.2).
- **Running value:** what the device runs with, as the owner holds it.
  **Startup value:** what the owner would run with after a restart: the
  persisted layer's, else the startup file's, else the owner's default
  (§2.3). **Persisted layer:** the owner's own store of persisted changes
  (§2.13).
- **Act:** an apply of a group's values to the device, or an undo. An act
  is **in flight** from when the owner starts it until it knows the
  device's result.
- **Change:** what a `set` that applies or arms starts, with every `set`
  that joins it, named by its **token** (§2.6). **Pending change:** a
  change under a window, not yet ended (§2.7). **Last change:** the most
  recent change made permanent in this instance (§2.6).
- **Window:** how long a change may stay pending, in seconds; **floor:**
  the owner's smallest window, `confirm_floor_s`; **deadline:** the
  instant the window ends (§2.8).
- **Revision:** the owner's count of acts that moved its running values,
  in this instance (§2.3).
- **First answer:** the reply, or the error envelope, an owner sent to the
  first `set` carrying an idempotency key (§2.14).

## 2. Rules

### 2.1 Who implements it

- **A service with something to configure at runtime.** A service that
  lets a caller change its configuration while it runs implements
  `config.v1`. One that has nothing to configure implements none and owes
  nothing here.
- **The interface is the gate** (architecture D12). No capability says
  "configurable": a service is configurable when its descriptor lists
  `config.v1` in `interfaces`. A tool lists the configurable services by
  instance tokens and descriptors (core §8.1). Where `config.v1` is not in
  the owner's tokenless set, the selector
  `zk2/*/*/@zk/alive/config.v1/**` lists them too. `config.v1` is not an
  interface every service implements, so its token says something the
  instance token does not, and a deployment SHOULD NOT put it in the
  tokenless set.
- **One configuration per service.** The configuration a `config.v1`
  serves is its own service's. A device served as a service has its own
  (§2.20).
- **Exposure.** Every resource of the contract is required except
  `persist`, which an owner without a persisted layer lists unavailable
  (§2.13). `set/{group}` is exposed by a queryable over the template, or
  one per group (core §8.2).

### 2.2 The served schema

The schema is served, not documented: the view carries, beside every
value, the declaration it satisfies, so a tool renders a form, and checks
a change before it sends it, without being compiled against the owner.
`[F: validation.json]`

- **A group** has:
  - a `name`: a non-empty string, unique among the groups. It is the
    `{group}` of `@op/set/{group}`, slugged into the key as any value is
    (core §1.4). A name that is a plain chunk (core §1.2) reads in the key
    as written, and an owner SHOULD choose one;
  - a `class` (§2.4), declared by the owner per group, and never inferred
    from a name;
  - a `description`, one line for a person reading the schema cold;
  - `writable`, whether the startup allowlist lets a `set` reach it
    (§2.16);
  - its `parameters`, in the owner's order.
- **At most 16 groups,** the contract's cardinality of `set/{group}`. An
  instance's descriptor MAY lower it (core §3.3).
- **A parameter** has a `name`, a non-empty string unique within its
  group, a `kind`, a `description`, and `sensitive` when it is write-only
  (§2.15). The kinds:
  - `bool`: `true` or `false`;
  - `integer`: a signed 64-bit integer, with an optional `min` and `max`,
    both inclusive, and an optional `unit`, a word for a person (`s`,
    `ms`, `By`, `Hz`, `ppm`, `packets`). An owner that gives both bounds
    gives `min` ≤ `max`;
  - `text`: any string.

  There is no float. A value that needs one is an integer in a finer unit
  (`milli-dBm`), which also keeps equality exact. A fourth kind arrives
  with the first owner that needs it (Appendix B).
- **Why groups.** Coupled parameters share a group (a frequency with its
  bandwidth) because a state where one has changed and the other not can
  be unsafe, and because a group is the unit that has a class and that an
  access-control rule sees in the key.
- **One schema per instance.** An owner SHOULD keep its schema, its
  groups, their classes and their parameters, for the life of an
  instance, and start a new instance (core §1.5) when it changes: a caller
  checks a change against the view it read (§2.5), and the revision counts
  values, not declarations (§2.3).

### 2.3 The read-back

- **`state/view`** carries a `ConfigView`: the owner's `service` address
  (`<system>/<service>`), its `instance` id, the `revision`, the floor
  (`confirm_floor_s`, §2.8), the `pending` change and the `last_change`
  when there are, the `desired` report when the owner converges desired
  state (§2.18), and the `groups` with their parameters.
- **A GET is the read.** A caller reads the configuration by an S4 GET of
  the view (core §4.2). There is no read operation.
- **Per parameter,** beside its declaration:
  - `value`: the running value. It is absent for a sensitive parameter
    (§2.15), and for one whose value the owner cannot read back: absence
    is unknown, never a guessed value;
  - `source`: where the running value came from: `default`, the owner's
    own; `file`, its startup file; `overlay`, its persisted layer
    (§2.13); `runtime`, a change in this instance. It is absent with the
    value when the owner cannot read the value back (§2.11);
  - `startup`: the startup value, present only when it differs from the
    running value, and never for a sensitive parameter. A parameter with
    `startup` runs a value a restart would not keep (§2.12, §5).

  `[F: lifecycle.json, redaction.json]`
- **The revision** counts the owner's acts on its running values in this
  instance: an owner MUST add one at each apply, an empty one included
  (§2.5), and each undo (§2.9, §2.11), and at nothing else. A confirm, an
  extend, a persist, a join that has not yet applied, a dry run and a
  refusal leave it. It starts at 0 in each instance. `[F: lifecycle.json]`
  A hot apply its device refused, left part applied and not restored,
  moved the running values: one act (§2.9, text 0.3).
- **The instance** is the owner's instance id (core §1.5). The revision is
  a counter that crosses constrained faces, where presence does not, so it
  carries its epoch, as core §1.5 says a counter does (§2.12, §2.19).
- **When it is put.**
  - An owner MUST put its view and its status (§2.19) before core §8.2's
    step 4, and so before its instance token: a GET made when the token
    appears finds them, and with them whether a change is pending. Core
    §8.2 says SHOULD of every state value an owner holds at start; this
    profile makes it a MUST for these two, as core §8.2 lets a profile do.
    `[Sc: §1]`
  - It MUST put both on every change of either: a value, a source, the
    floor, the pending change (armed, applied, joined, extended, ended),
    the last change, the desired report. `[Sc: §1, §2]`
  - Both declare `freshness.ttl_s = 60`, so the owner confirms each at
    least every 30 s, by a change or a re-put of the value unchanged
    (`freshness.v1` §2.4). `[Sc: §1]`
  - It MUST NOT delete either while it runs. `[Sc: §1]`
- **Two keys, one revision.** The view and the status are two keys, and
  no two keys change at once (core §2.1). An owner SHOULD put the view
  first, then the status. The revision counts acts, not versions of the
  documents: an arm, a join, an extend, a confirm, a cancel with nothing
  applied, a persist and a desired report each re-put both at the same
  revision. So `instance` and `revision` name the running values, never
  a pair: a reader that reads both pairs them only when the status is the
  view's projection (§2.19), and otherwise takes each by itself, judged by
  its own freshness.

### 2.4 The classes

- **`hot`:** takes effect at once, and nothing above the owner needs to
  know: a transmit power, a poll interval, a queue length. A `set`
  answers with the read-back after the apply, never an echo of the
  request (§2.9).
- **`reach`:** decides whether the owner can reach the bus at all: a
  frequency, a network id, an access point name.
  - A `set` on a reach group MUST carry a window (`confirm_s`) or the
    pending change's token (joining a change that has one, §2.7), unless
    it is a dry run. `[F: validation.json]`
  - It is answered `{token, apply_at, deadline}` **before** it is applied,
    because the read-back would cross the link being changed. The caller
    observes the view over the new link, then confirms (§2.9).
  - A reach group is never carried by desired state (§2.18): one bad
    desired document would lock the service out of its own supervision.
  - A tool that cannot read a group's class, with no view to read it from,
    SHOULD treat a change carrying `confirm_s` as reach when it asks its
    operator's consent: asking once too often costs a keystroke, and not
    asking can cost the link.
- **`contract`:** part of what the owner's transport was started against:
  an SDU size, a reliability claim. A `set` on a contract group is refused
  with `app` and `ConfigError{code: "restart-required"}` (§2.5); it is
  changed in the owner's startup configuration. `[F: validation.json]`
- **The class is the owner's, per group.** The same parameter can be hot
  on one owner and contract on another: an MTU is hot where the transport
  sizes itself from the link, and contract where the transport was started
  against it.

### 2.5 Validating a set, and the order of refusals

**Before the device sees anything.** An owner checks a `set` before it
applies anything. The core's own refusals come first (core §5.1, "The
order of refusals"): a key expression that is not concrete is
`fanout_forbidden` (every operation of the contract forbids fan-out), an
operation not exposed is `unavailable`, a key that names no member is
`invalid_request`, and a request that does not decode as `SetRequest` is
`invalid_request`. Then the owner MUST refuse the request for the first
of these that applies, in this order, and otherwise accept it.
`[F: validation.json, lifecycle.json]`

| # | Check | Refusal |
|---|---|---|
| 1 | An act is in flight (§2.7). | `busy` |
| 2 | The request carries an `idempotency_key` whose first answer the owner holds (§2.14). | the first answer, for the same group and request; `invalid_request` otherwise |
| 3 | The schema declares no group by the key's `{group}`. | `not_found` |
| 4 | The group is outside the startup allowlist (§2.16). | `unavailable`, cause `config` |
| 5 | A change is pending, and the request does not carry its token; or it does, and the change's deadline has passed (§2.7, §2.11). | `busy` |
| 6 | The request carries a `token`, and no change is pending. | `not_found` |
| 7 | The request carries an `expected_revision` other than the revision. | `invalid_request` |
| 8 | The group is `contract` (§2.4). | `app`, `ConfigError{code: "restart-required"}` |
| 9 | The request carries both `token` and `confirm_s` (§2.7). | `invalid_request` |
| 10 | The group is `reach`, and the request carries neither `confirm_s` nor `token`, and is not a dry run (§2.4). | `invalid_request` |
| 11 | A value, taken in the bytewise order of the parameter names: the group declares no parameter by its name; or it is not of the parameter's kind, or outside its bounds. | `not_found`; `invalid_request` |
| 12 | Not a dry run, and the `set` would start a change while the event's rate is spent (§2.17). | `busy` |
| 13 | Not a dry run, the group is `reach`, the request joins, and the group could not apply before the change's deadline (§2.9). | `busy` |
| 14 | Not a dry run, and the device refuses the group (§2.9). | `app`, `ConfigError{code: "device-refused"}` |

- **Why this order.** What the request cannot change comes before what
  it can: the owner's state (an act in flight, a key it holds) before the
  schema, the schema before the allowlist, the pending change before the
  request's own guards, the request's guards before its values, and the
  device last, since only a request that passed everything else reaches
  it. A retry (row 2) comes before any check that the first attempt's own
  effects would fail, such as row 5's `busy` against the change that
  attempt armed.
- **A request outside its type** is refused `invalid_request` before
  row 1: by the core's decode, or by the owner's own check of the schema's
  bounds where its decode does not hold them (core §5.1, "The request").
  `[F: validation.json]` Outside its type are:
  - a `confirm_s` of 0, a `token` or an `idempotency_key` empty or longer
    than its bound (§2.6, §2.14), a `values` that is not an object;
  - a value in `values` that is not a `ParamValue` (§3): `null`, a number
    with a fractional part, an array, an object. A decode that holds the
    schema refuses these, so every owner refuses them here, before any
    row, whatever its decode;
  - a member of the request other than `values` that JSON Schema reads as
    an integer and core §3.3 does not: `confirm_s` or `expected_revision`
    written with a fraction or an exponent (`30.0`, `3e1`), or beyond the
    unsigned 64-bit range. Unlike a value in `values`, whose kind only row
    11 knows, each of these members has one type, the request's, so it is
    read as core §3.3 reads an integer, and the decode refuses it (text
    0.3, F-115);
  - a member of the wrong JSON type: a `dry_run` that is not a boolean, a
    `token` or an `idempotency_key` that is not a string, an `answer` (§2.10)
    other than `view` or `status`;
  - several at once: the first in the bytewise order of the member names,
    `values` last, and in `values` the first in the bytewise order of the
    parameter names. A control operation's request is taken the same way
    (§2.10): `answer`, then `confirm_s`, then `token`.
- **A value of the wrong kind** is a `ParamValue` outside the parameter's
  kind, refused at row 11: `1` for a `bool`, `"1"` for an `integer`,
  `true` for a `text`. An integer is written without a fraction or an
  exponent, as core §3.3 reads one, so `2.0` and `2e0` are not integers of
  the kind, though JSON Schema 2020-12 reads them as integers, and so of
  the request's type. That is the owner's further check, which core §5.1
  ("The request") allows, and a writer sends integers as integers (core
  §9.8). An integer is accepted when it is within the bounds the parameter
  declares, both inclusive; a parameter without bounds accepts any signed
  64-bit integer, and a value beyond 64 bits, an integer of the request's
  type, is out of every parameter's bounds.
- **Values in bytewise order.** `values` is a JSON object, whose members
  have no order, so row 11 takes them in the bytewise order of their names
  (UTF-8), and the first problem is the same everywhere.
- **The envelope** is core §5.2's. Only `app` carries a detail, a
  `ConfigError`: `code` and, optionally, a `detail` for a person, which
  for `device-refused` is the device's own words (§2.15 says when they are
  left out). The `message` is for a person, never parsed, and names what
  the refusal is about: the group, the parameter, the field of the
  request. A `busy` message names the pending change's token for a person;
  a program reads it from the view or the status (§2.7).
- **An empty `values`** is a change of nothing. It is accepted, and its
  apply is an act that sets no value: the owner makes it, and the device
  has nothing to change. Its change, its event, with no edits, and its
  revision are as any other's (§2.3). Its undo, under a window, has
  nothing to restore, and is no act (§2.11). `[F: lifecycle.json]`
- **A caller that checks first.** A tool MAY run the same checks against
  a view it read before it sends, from row 3 on, so that the refusal it
  prints is the one the owner would send. The owner's word is still the
  reply (core §5.1, "The request").

### 2.6 Changes and their tokens

- **Every applied change has a token.** A `set` that passes §2.5 and is
  not a dry run either starts a change or joins the pending one (§2.7). A
  `set` that starts one mints its token:
  - with a window, the change is pending until it is confirmed, cancelled
    or undone at its deadline;
  - without a window, on a hot group, it is applied and made permanent at
    once: its event is `applied` (§2.17).

  A dry run and a refused `set` start nothing and mint nothing.
  `[F: lifecycle.json]`
- **A token is never reused.** It is an opaque string of 1 to 64
  characters. An owner MUST NOT mint a token that any instance of its
  service minted before, so that a token from before a restart names
  nothing after it (§2.12). `[F: lifecycle.json]` `[Sc: §7]` The
  reference mints `<instance>-<n>`, the instance id and a count of the
  instance's changes from 1.
- **The last change** is `{token, groups}`: the most recent change made
  permanent in this instance, confirmed or applied without a window. A
  pending change is never the last change, and a cancel or an undo leaves
  the last change as it was. It is what `persist` takes (§2.13), and how a
  change made without a window survives a restart. `[F: lifecycle.json]`

### 2.7 One pending change

- **One at a time.** An owner holds at most one pending change. A `set`
  that does not carry the pending change's token is answered `busy`
  (§2.5, row 5), whatever its group and class. A hot `set` without a
  window is refused too: it would be a change of its own.
  `[F: validation.json, lifecycle.json]` `[Sc: §5]`
- **Joining.** A `set` that carries the pending change's token joins it.
  `[F: lifecycle.json]` `[Sc: §5]`
  - Its group joins the change's `groups`, once, in the order groups first
    joined, and its values apply under the change: they are confirmed,
    cancelled, persisted or undone with it, as one.
  - A joining `set` carries no `confirm_s` (§2.5, row 9): one change, one
    window. **Joining does not move the deadline**; `extend` does (§2.10).
  - A hot group joins by its apply, at once. A reach group joins by its
    pending reply, and applies at its own `apply_at`, before the change's
    deadline (§2.9).
  - A group may join twice. The undo restores each parameter to its value
    before the change, not to a value a join set within it (§2.11).
  - Joining is how a coupled change spanning two groups, a frequency in
    one and a network id in another, is applied and confirmed as one act.
- **A token that names nothing.** A `set` carrying a token when no change
  is pending is answered `not_found` (§2.5, row 6). One carrying another
  token while a change is pending is `busy` (row 5): the caller reads the
  pending token from the view or the status, and decides again.
- **One act at a time.** An owner MUST NOT start an act while another is
  in flight, and answers `busy` to every call that arrives meanwhile:
  a `set` (§2.5, row 1), and `confirm`, `cancel`, `extend` and `persist`
  (§2.10, §2.13). A call is answered once the act's result is known, so a
  caller never sees a change half made. `[F: lifecycle.json]`
- **Calling again after `busy`** is a new call, which the caller decides,
  never a retry (core §5.1).

### 2.8 The window, the floor, and time

- **The window** is `max(confirm_s, confirm_floor_s)` seconds. A shorter
  `confirm_s` is raised to the floor, and the reply's `deadline` says so.
  `[F: window.json]`
- **The deadline** is the instant the owner received the `set` (or the
  `extend`, §2.10) plus the window. `[F: window.json, lifecycle.json]`
- **The floor** is the smallest window that makes sense on the device's
  link: on a satellite terminal, two sessions; on a LoRa radio, twenty full
  frames of airtime (Appendix B). It is an instance fact, at least 1 s,
  and the owner states it as `confirm_floor_s` in the view and the status,
  so a caller learns it before the call. `[Sc: §1, §13]`
  - **Above the apply's delay.** An owner MUST keep its floor above the
    longest delay its device states for a reach `apply_at`, from the
    `set`'s receipt (§2.9), so every change it starts can apply before its
    deadline. An owner whose device cannot keep that runs with a larger
    floor. Row 13 of §2.5 is then a join's alone: a join keeps the change's
    deadline, which may have come closer than the floor.
- **`confirm_s`** is an integer number of seconds, at least 1. There is no
  upper bound in this text; an owner's device may make a long window
  pointless, and the owner says so in its own documentation.
- **Time on the wire.** `apply_at` and `deadline` are instants on the
  owner's clock, written as RFC 3339 date-times in UTC with `Z`. An owner
  writes them to the millisecond, `YYYY-MM-DDTHH:MM:SS.sssZ`; a reader
  accepts any RFC 3339 date-time. `[F: window.json]`
- **A caller on another clock.** Across a link, the caller's clock and the
  owner's can differ. A caller reads the deadline as the owner's instant,
  and counts its own margin from the reply's arrival: the window it asked
  for, raised to the floor, less the reply's transit.

### 2.9 Applying: hot and reach

- **Hot, without a window.** The owner applies the group, and answers
  `{applied: <view>}` with the read-back after the apply: the values at
  `source: runtime`, the revision moved by one. The change is the last
  change, and its event is `applied`. `[F: lifecycle.json]` `[Sc: §1]`
- **Any class, with a window.** The deadline is armed when the `set` is
  received (§2.8).
  - **Hot:** the owner applies at once, and answers `{applied: <view>}`,
    the view showing the change `pending`.
  - **Reach:** the owner MUST answer `{pending: {token, apply_at,
    deadline}}` before it applies anything, and apply the group at
    `apply_at`. `[Sc: §2]`
    - `apply_at` is the device's to state. The owner MUST state it, and
      MUST state one before the deadline `[F: lifecycle.json]`, which its
      floor allows for a change it starts (§2.8); how it is derived is the
      owner's. It SHOULD leave the reply time to cross the link before the
      apply cuts it: at least the reply's transit, with a margin. On a
      2,400 bit/s link a 114 B reply takes 0.73 s; at 300 bit/s it takes
      3 s, longer than v1's fixed 1 s (Appendix A).
    - A reach group joining a pending change (§2.7) applies at its own
      `apply_at`, before the change's deadline. When its device cannot
      apply it before the deadline, the `set` is refused `busy` (§2.5,
      row 13), and the caller extends the change first. `[F: lifecycle.json]`
- **Applied.** The view's `pending.applied` is `true` when every group of
  the change is applied, and `false` while a reach group waits for its
  `apply_at`. A `confirm` before then is answered `busy`: confirm it once
  the view shows it applied (§2.10). `[F: lifecycle.json]` `[Sc: §2]`
- **The device refuses.**
  - A hot group refused by its device is answered `app` with
    `ConfigError{code: "device-refused"}` (§2.5, row 14). Nothing is
    applied, so the request starts no change, mints no token and joins
    nothing. `[F: lifecycle.json]`
  - A reach group whose apply fails at `apply_at`, after its reply has
    gone, ends the change: the owner runs the undo at once, as at the
    deadline (§2.11), and the change ends `rolled-back`, or `partial` if
    the undo fails. `[F: lifecycle.json]` `[Sc: §3]`
  - An owner whose device applies a group whole or not at all needs no
    more. One whose device can be left with part of a group applied reads
    the device back, and the read-back is the truth (§2.11).
  - **A hot group left part applied** (text 0.3). The refusal is still
    `device-refused`, and it still starts no change, mints no token and
    publishes no event: the profile's changes are the ones a `set` started.
    So an owner whose device can be left part applied restores what was
    applied before it answers, once, as an undo restores (§2.11); a restore
    that succeeds leaves the running values as they were, and is no act.
    One that fails leaves the read-back the truth: the view shows each
    parameter as the device holds it, at `source: runtime` where it moved
    and with neither value nor source where it cannot be read, and the
    revision moves by one, since the running values moved (§2.3). The
    owner SHOULD report that fault in its own interfaces (`health.v1`
    §2.3). How it restores is its own: deliberately left to the owner, as
    an undo's means are.
- **A dry run** runs every check of §2.5 but the device's (rows 1 to 11),
  and answers `{applied: <view>}` with the view as it would read with the
  request's values applied: those parameters at `source: runtime`, and
  the revision, the pending change and the last change as they are. It
  touches nothing, mints nothing, and publishes no event. Its reply is a
  first answer like any other (§2.14). `[F: lifecycle.json]`

### 2.10 Confirm, cancel and extend

Each carries a `ControlRequest` with the pending change's token. A
request outside its type (a `confirm_s` of 0, an empty `token`, an
`answer` other than `view` or `status`) is refused `invalid_request`
first, as §2.5 says of a `set`. Then the owner MUST refuse, for the first
that applies, in this order: `[F: validation.json, lifecycle.json]`
1. an act in flight (§2.7): `busy`;
2. for `extend`, no `confirm_s`; for `confirm` and `cancel`, a
   `confirm_s`: `invalid_request`;
3. no change pending, or one with another token: `not_found`;
4. the change's deadline passed, its undo not yet run (§2.11): `busy`;
5. for `confirm`, a group of the change not yet applied (§2.9): `busy`.

Then:
- **`confirm`** keeps the change: it becomes the last change, nothing is
  pending, and its event is `confirmed`. `[F: lifecycle.json]` `[Sc: §2]`
- **`cancel`** undoes the change now, as §2.11 says, whether or not every
  group of it is applied. Its event is `rolled-back`, or `partial`.
  `[F: lifecycle.json]`
- **`extend`** moves the deadline to the instant the owner received it
  plus the window of its `confirm_s` (§2.8): earlier or later than
  before. It publishes no event. `[F: lifecycle.json]` `[Sc: §6]`
- **The reply** is the read-back as it stands after the act,
  `{view: <view>}`, so the caller sees the outcome without a second call.
  A request with `answer = "status"` is answered `{status: <status>}`
  instead, the compact status (§2.19): on a radio link the view is six
  frames, the status two. `[F: lifecycle.json]` `[Sc: §13]`
- **A confirm retried after a lost reply** finds nothing pending, and is
  answered `not_found`. No control operation is idempotent (core O4). The
  caller reads the last change to learn whether its change was kept (§5).

### 2.11 The deadline and the undo

- **At the deadline** a change still pending is undone: the owner
  restores every parameter the change set to its value before the change,
  and stops waiting for any group not yet applied. It MUST apply the undo
  **once**: never retried, never escalated. `[F: lifecycle.json]`
  `[Sc: §3, §4]`
  - Its value before the change is the running value the owner held when
    the change first set the parameter, its startup value where it held
    none.
  - The undo is one act over the change's applied groups. A change none
    of whose groups is applied yet (a reach change cancelled before its
    `apply_at`, or whose apply failed) has nothing to restore: no act is
    made, the revision does not move, and the change ends `rolled-back`.
- **The outcome.**
  - An undo that succeeds ends the change `rolled-back`. The restored
    parameters read their values and sources from before the change.
  - An undo that fails ends it `partial`. The read-back is the truth: the
    owner shows each parameter the change set as it reads it back from
    the device, and with no value, unknown, where it cannot: such a
    parameter has no `source` either (§2.3). It retries nothing. It MAY
    report the failure in its own interfaces, as zenoh-modem's
    `device_fault` event does, or as a `health.v1` fault (`health.v1`
    §2.3). `[F: lifecycle.json]` `[Sc: §4]`
  - A parameter read back after a failed undo shows the value read: with
    the source it had before the change when that is the value it had
    before, and `runtime` otherwise.
  - Either way, an undo act moves the revision by one (§2.3), the last
    change stays as it was, nothing is pending, and the change's event is
    published (§2.17).
- **`cancel`** runs the same undo, at once (§2.10).
- **Between the deadline and the undo,** the change is no longer
  confirmable: a `confirm`, `cancel` or `extend` that arrives then is
  answered `busy` (§2.10), and once the undo has run, `not_found`. A `set`
  is `busy` throughout (§2.5, row 5). The deadline instant belongs to the
  undo: a `confirm` received at the deadline is too late.
  `[F: lifecycle.json]`
- **Why once.** The undo exists for when the caller cannot reach the
  owner. A retried undo against a device that refused the first would
  hide the fault behind a loop; a `partial` change, read back, shows it.
  This is RFC 6241 §8.4's confirmed commit, MikroTik's Safe Mode and
  airOS's test mode, and it is what makes a reach change survivable.

### 2.12 A restart is a rollback

- **Runtime changes are not persisted** (§2.13), so a restart during a
  pending change rolls it back by construction. An owner MUST start from
  its startup values (its persisted layer, its startup file, its
  defaults), and never from a runtime change of an earlier instance.
  `[F: lifecycle.json]` `[Sc: §7]`
- **A restart is a new instance** (core §1.5): a new instance id, the
  revision from 0, nothing pending, no last change, and no idempotency key
  held (§2.14). The change events of the last hour still count against
  the rate (§2.17). `[F: lifecycle.json]`
- **A late confirm** with a token from before the restart is answered
  `not_found`: no instance mints a token twice (§2.6). `[F: lifecycle.json]`
  `[Sc: §7]` The caller tells why from presence, where it crosses: the
  instance token it knew is gone, and another is there (core §8.1). Across
  a constrained face, it tells from the status's `instance` (§2.19).
- **A re-mint is a restart** (text 0.3). Core §1.5 lets a running process
  mint a new instance, and a new instance starts from its startup values,
  the revision from 0, nothing pending (above). So an owner re-mints while
  `config.v1` runs only with its device running its startup values:
  nothing pending, and every runtime change of the instance undone or
  persisted, a persisted value being a startup value (§2.13). It returns
  the device to them first, as a restart does, where it must. The
  reference refuses the re-mint (`zenkey::config_v1`), the simplest owner
  that keeps the rule.
- **The new instance says nothing of the old one's pending change,** which
  it never knew: no event is published for it. An owner that keeps a
  record of its own across a restart (zenoh-modem reports an overlay it
  set aside at boot as a change by the actor `boot`) MAY publish what it
  knows, as a change of the new instance.

### 2.13 Persist

- **What it does.** `persist` writes the last change into the owner's
  persisted layer, so that it survives a restart. Where and how is the
  owner's; that it is explicit, and separately granted, is this profile's.
- **Which change.** Its token MUST be the last change's (§2.6). The owner
  refuses, for the first that applies, in this order:
  `[F: validation.json, lifecycle.json]` `[Sc: §8]`
  1. no persisted layer: `unavailable`, cause `config`. An owner with none
     does not expose `persist`, and the core refuses the call so before
     any handler runs, its request's type included (below). A layer it
     cannot write to now is refused the same way, first of the handler's
     refusals: before the request's type too, so that the refusal does
     not depend on whether the layer was ever there;
  2. an act in flight (§2.7): `busy`;
  3. a `confirm_s`: `invalid_request`;
  4. the pending change's token: `busy`. Confirm it first: a persisted
     change that was never confirmed would come back after a restart, and
     a restart would no longer roll it back (§2.12);
  5. any token but the last change's: `not_found`. Nothing older than the
     last change can be persisted;
  6. a last change that set a sensitive parameter: `forbidden`, core
     §5.2's refusal by a rule of the owner's own (0.28). A sensitive value
     is never written to the persisted layer (§2.15).
- **What it writes.** The values the last change set, as it set them:
  never a value a pending change runs since, which a restart must roll
  back (§2.12). `[F: lifecycle.json]`
- **After it.** Each parameter the change set that runs the value written
  reads `source: overlay`, and `startup` leaves it (its startup value is
  now its running value). A pending change may hold one:
  - a parameter an applied group of the pending change set keeps its
    running value and its source, and shows the value written as its
    `startup`. If that change is undone, the parameter returns to its
    value before the change, at `source: overlay` when that is the value
    written (§2.11);
  - a parameter only a reach group not yet applied set still runs the
    value written, and reads `source: overlay` at once.

  The revision does not move, and no event is published: the running
  values did not change. A second `persist` of the same change persists
  nothing new, and is answered as the first. `[F: lifecycle.json]`
- **The reply** is §2.10's: the view after the act, or the status when
  asked.
- **No persisted layer.** An owner that has none lists `persist`
  unavailable in its descriptor, with cause `config` (core §3.3), and is
  answered `unavailable` with that cause (core O3). `[Sc: §8]` A write
  that fails for another reason, a full disk say, is `internal`.
- **Its own key.** A deployment can grant a caller a change and withhold
  making it survive a restart (§2.21). `[Sc: §8]`

### 2.14 Idempotency keys

- **Retry safety for `set`.** On a link where a lost reply is the common
  case, a caller that resends a `set` must not apply it twice. A `set` MAY
  carry an `idempotency_key`, 1 to 128 characters.
- **The rule.** An owner MUST keep the first answer to a `set` carrying a
  key, value or refusal, for 300 s from that answer. A `set` carrying that
  key within the 300 s, for the same group with an equal request (every
  member of `SetRequest` equal), is answered the first answer, and nothing
  is applied, minted or published. One carrying it for another group or
  request is answered `invalid_request`. `[F: lifecycle.json]` `[Sc: §10]`
  - **Equal as decoded** (text 0.3). A member at its default is the member
    absent, so `"dry_run": false` and no `dry_run` are one request; every
    other member, and each value of `values`, compares as the JSON value it
    is. `[F: lifecycle.json]`
  - **The first answer** is the one to the first `set` with the key that
    reached §2.5's row 3. A refusal before it (the request's type, an act
    in flight) is sent before the owner reads the key, and is not kept, so
    a retry that meets the first attempt's own act in flight is `busy`, and
    the attempt's answer is kept when its act ends. Row 2's own
    `invalid_request` is not kept either.
- **At 300 s and after,** the key is forgotten, and a `set` carrying it is
  a new request, checked from §2.5's row 3. `[F: lifecycle.json]`
- **A restart forgets every key** (§2.12). The first attempt's change was
  a runtime change, rolled back by the restart, so applying it again is no
  double write. `[F: lifecycle.json]`
- **Why 300 s:** zenoh-modem's, which covers retries over its slowest
  links. **Why the first answer, refusals included:** a retry learns what
  happened to its first attempt, which is all it asked; a caller that
  wants a fresh decision sends a new key.
- **Control operations carry no key.** A `confirm` retried after a lost
  reply is answered `not_found` (§2.10).

### 2.15 Sensitive values

A parameter declared `sensitive` is **write-only**: a PIN, a key. A
caller sets it, and nothing reads it back. This is RFC 8341's
`default-deny-all`, as data.
- **Never carried.** An owner MUST NOT carry a sensitive value, or its
  startup value, in: `[F: redaction.json]` `[Sc: §11]`
  - the view or the status. The view shows the parameter's declaration and
    its `source`, without `value` or `startup`; the status leaves the
    parameter out;
  - a reply, including a dry run's would-be view;
  - an event: the parameter's edit is `{group, parameter, redacted:
    true}`, with neither `old` nor `new`;
  - an error envelope's `message` or `detail`. A refusal of a sensitive
    parameter's value names the parameter, never the value;
  - the device's words: a `device-refused` detail for a change carrying a
    sensitive value leaves the device's words out, since they may repeat
    it;
  - a log line: a request logged by the owner writes the value
    `"<redacted>"`;
  - the persisted layer (§2.13).
- **The owner still holds it.** It applies the value, and holds the value
  it replaced, so that the undo can restore it (§2.11).
- **Desired state never carries one** (§2.18).

### 2.16 The startup allowlist

- **Remote writes, per group.** An owner MAY keep a startup allowlist of
  the groups a `set` may reach. A `set` on a group outside it is answered
  `unavailable`, cause `config` (§2.5, row 4), by the handler, for one
  member of an operation the owner exposes (core §5.1, 0.28). An owner
  that keeps none lets every group. `[F: validation.json]` `[Sc: §9]`
- **Shown in the view.** An owner MUST state in each group's `writable`
  whether the allowlist lets a `set` reach it. `[F: lifecycle.json]`
  `[Sc: §9]` A tool reads "can I set this group?" from `writable` and the
  class (§5).
- **What it is for.** An operator switches remote writes off, group by
  group, in the owner's startup configuration, without touching a router.
  The allowlist binds desired state too (§2.18). It changes only with the
  owner's startup configuration, so not while an instance runs.

### 2.17 The change event

- **One event per change, when it ends.** An owner MUST publish exactly
  one event for each change, on `events/change/<ulid>` (core §2.6), when
  the change ends: `[F: lifecycle.json]` `[Sc: §1, §2, §3, §4]`
  - `applied`: applied without a window, and permanent at once;
  - `confirmed`: a pending change kept by `confirm`;
  - `rolled-back`: undone, by `cancel`, at its deadline, or after its
    apply failed;
  - `partial`: its undo failed (§2.11).

  A dry run, a refusal, a join, an extend and a persist publish none: a
  join ends with its change.
- **What it carries** (`ConfigChangeEvent`, after RFC 6470's
  `netconf-config-change`):
  - `service`, `instance`, and the `revision` after the act that ended the
    change: for `confirmed`, the revision as it stands;
  - the change's `token` and `outcome`;
  - its `edits`: one per parameter the change set, in the order of the
    change's groups, then the bytewise order of the parameter names. Each
    is `{group, parameter, old, new}`: `old` its value before the change,
    absent when unknown, and `new` the value the change set. The edits are
    the change's, whatever its outcome: an `old` that a `rolled-back`
    change restored is the parameter's value again. A sensitive parameter's
    edit is redacted (§2.15);
  - the attribution (below).
- **Attribution is claimed.** `actor` and `request_id` are those of the
  call metadata of the `set` that started the change (core O7), and are
  absent when it carried none. They are what the caller claimed, never
  authentication: the access control is the authority. `claimed_source`
  MAY carry where the call came from, as far as the owner can tell: zenoh's
  source information is unstable API in zenoh 1.10.1 (core §0), so it is
  best effort, unauthenticated, and often absent.
- **The rate,** `burst(600/h)`, is the owner's to keep (core §2.7). It
  keeps it by refusing `busy` a `set` that would start a change while 600
  change events were published within the last hour (§2.5, row 12),
  joins and dry runs aside. The hour is core §2.7's span: an event
  published exactly an hour before no longer counts. A change's event is
  never dropped: at most one change is pending (§2.7), so none can end
  while another starts, and no end event can break the rate.
  `[F: lifecycle.json]`
  - **Across a restart.** The rate bounds the service's one member,
    `events/change`, and a restart does not reset it (core §2.7, 0.28), so
    the events an owner counts are its earlier instances' too: it counts
    them from a record of their instants that it keeps across the
    restart, as it keeps its persisted layer.
- **The retention,** `7d`, is how far back a reader replays (core §2.6).
  At the rate, a service holds at most 100,800 events.

### 2.18 Desired state

`config.v1` does not define desired state;
[`desired.v1`](../desired/v1.md) does, and its §2.16 states this
profile's rules as those of one document type (config.v1 text 0.4: an
owner fed through `desired.v1` acts as its §2.7 says, below; text 0.5,
F-182: this marker is this text's version, never `desired.v1`'s). A `config.v1` owner MAY
converge a desired document that a deployment binds to it, a
`DesiredConfig` (§3): the author's `revision`, and `values` by group and
parameter.
- **Refused whole.** Before it applies anything, the owner MUST refuse a
  desired document that names any of these, and apply nothing of it:
  `[F: desired.json]` `[Sc: §12]`
  - a `reach` group (code `reach`), a `contract` group (`contract`), or a
    sensitive parameter (`sensitive`): the class is runtime data in the
    view, not a contract fact, so neither codegen nor an access-control
    generator can refuse them, and the server does;
  - what a `set` would refuse of it with no state: a group or a parameter
    the schema does not declare (`not_found`), a group outside the
    allowlist (`unavailable`), a value of the wrong kind or out of bounds
    (`invalid_request`).
- **The order.** The owner reports the first problem it finds: groups in
  the bytewise order of their names, and in each group, the group's
  checks (`not_found`, `contract`, `reach`, `unavailable`), then each
  parameter in the bytewise order of its name (`not_found`, `sensitive`,
  `invalid_request`). `[F: desired.json]`
- **Reported in the owner's own state.** The view and the status carry
  `desired`: the `observed_revision` of the last document the owner acted
  on, and its `outcome`:
  - `converged`: every value the document names was the running value
    when the owner acted on it (below);
  - `refused`, with the `refusal`'s code, group and parameter;
  - `failed`, when a `set` made to converge it was refused, with that
    refusal's code (`busy` for the rate, `device-refused`) and group.

  `[Sc: §12]` It maps onto `desired.v1`'s Report as its §2.16 says
  (config.v1 text 0.4, F-172): the refusal's pointer is `/values/<group>`, then
  `/<parameter>` when the refusal names one, each name escaped as RFC
  6901 says.
- **Converging.** The owner converges through `set`: one `set` without a
  window per group whose values differ from the document, in the bytewise
  order of the group names, each its own change, `applied`. While a change
  is pending, or an act is in flight (§2.7), it waits until it ends. It
  tries a failed document again when its revision changes.
  - A converging `set` is the owner's, not a call: it carries no call
    metadata, so its change's event has no `actor` and no `request_id`
    (§2.17).
- **Each revision once, in an instance** (text 0.3). An owner acts on each
  revision of the document bound to it once in an instance, whatever the
  outcome: a later `set` that changes a value the document names does not
  make it converge again, and its report keeps the outcome it had. A
  desired document is not a lock on the configuration; the document's next
  revision is acted on, and so is the same revision by a new instance
  (below). A tool that wants to know whether a converged document still
  holds compares it with the view.
- **Fed through `desired.v1`** (text 0.4, F-171). An owner whose document
  reaches it through `desired.v1`'s reading, a role bound to its author's
  slice (desired.v1 §2.3), acts as desired.v1 §2.7 says: on each version
  of the document, its author's stamp, once in an instance, whatever the
  outcome, and adopting without an act a version whose document equals
  that of the last version it acted on or adopted. So that this rule and
  the one above never diverge, a `DesiredConfig`'s author MUST move
  `revision` whenever `values` change. `[Sc: §12]` Then a revision put
  again unchanged, by a freshness re-put or its author's restart, is the
  same document, adopted, and "once per revision" reads as desired.v1's
  once per version. A document whose `values` changed under one revision
  breaks the author's rule, and desired.v1 §2.7 acts on it.
- **A delete** (text 0.5). An owner fed through `desired.v1` reverts, on
  a delete it acts on, as `desired.v1` §2.16 (its text 0.3) says: each
  parameter a document it acted on in this instance named, a refused
  document's aside, back at its startup value (§2.12), through one `set`
  without a window per group whose running values differ, as converging
  does. Its view and its status carry no `desired` from then on: no
  document is bound, so a tool's §5 question is not asked, as for an
  owner that converges none.
- **After a restart** (text 0.3, F-114). The binding is the deployment's, and
  survives a restart; the values a document converged were runtime changes,
  which the restart rolled back (§2.12). So the new instance acts on the
  document bound to it as the first instance did, converging it again,
  and its view and its status carry no `desired` until it has acted: a new
  instance knows nothing of the old one's report.
- **Why the server.** v1 kept reach out of desired state by rule (RFC 05
  §5.1). Here the rule is whole, and it lives where the class is known.

### 2.19 Constrained faces and the compact status

- **The status** carries a `ConfigStatus`: the view's `instance`,
  `revision`, `confirm_floor_s`, `pending`, `last_change` and `desired`,
  and the `values` by group and parameter name. A sensitive value, and a
  value the owner cannot read back, is left out, and so is a group left
  with no value. An owner MUST keep the status equal to this projection of
  its view. `[F: lifecycle.json, redaction.json]` `[Sc: §13]`
- **Its size.** For zenoh-modem's SX1262 radio, three groups, the view is
  about 1,286 B of JSON, six 220 B frames, 4.4 s of air at 2,400 bit/s. The
  status is about 330 B, two frames.
- **Across a face** (core §8.5), presence and descriptors do not cross. A
  caller on the far side binds statically (core R7), reads the status by
  GET, asks `answer = "status"` of the control operations (§2.10), and
  gets a reach `set`'s 114 B pending reply. The status's `instance` shows
  it a restart (§2.12), which presence would show on the near side.
  `[Sc: §13]`
- **The status's refresh** is one put every 30 s (§2.3). A face that cannot
  afford it denies the subscription and lets the GET cross, as the
  binding's grants do (`config.v1-binding.md` §12).
- **Silence across a face** is not a verdict (core O5, R7): a GET that
  draws nothing says nothing about the change, the owner, or the link.

### 2.20 Device-as-service

- **A device served as a service implements its own.** A device a parent
  serves as a service (core §1.5), such as each of zenoh-modem's radios,
  implements `config.v1` for itself, under its own address, with its own
  schema, floor and `apply_at`.
- **A parent's configuration is its own.** A parent service does not
  configure its device services through its own `config.v1`, and does not
  repeat their views.
- **A device modelled as a member** (core §8.1) is not a service, and has
  no `config.v1` of its own: the contract's resources are one service's. A
  service that configures members carries that in its own interface.

### 2.21 Access control

- **Each act its own grant.** `@op/set/<group>`, `@op/confirm`,
  `@op/cancel`, `@op/extend` and `@op/persist` are distinct keys, per
  service, so a deployment grants each separately (core §11.1's Call),
  group by group, service by service: rf0 and not sat0, `set` and not
  `persist`.
- **No fan-out.** Every operation of the contract is
  `fanout = "forbidden"`, so a wildcard call reaches no handler: the owner
  refuses it `fanout_forbidden`, whatever the access control allows (core
  O2, §11.3). `[Sc: core operations.md §2]`
- **A grant to arm without a grant to confirm** makes every reach change a
  guaranteed rollback: safe, which is the point of the class, but not
  configuration. The binding's §11 shows how v1's grants did that to
  zenoh-modem's far side, and its §12 the zk2 grants that do not.
- **`persist` withheld** lets a caller change a value and not make it
  survive a restart.

## 3. Contract

The standard contract is [`config.v1.toml`](config.v1.toml), with its
types in [`schemas/config.json`](schemas/config.json) (JSON Schema, core
§7.3's subset). Revision 1.0 is
`sha256:727ff0090b99ad8fc09b5398804d1a14288bebf661f374ec6904351344a1a7b1`,
published in [`../.history/config.v1/`](../.history/config.v1/) (core
§9.7).

| Resource | Kind | Request → response, or type | Notes |
|---|---|---|---|
| `view` | `state` | `json:ConfigView` | `freshness.ttl_s = 60`; QoS state's default, `reliable`, `block` |
| `status` | `state` | `json:ConfigStatus` | `freshness.ttl_s = 60` |
| `set/{group}` | `operation`, `group` a string, cardinality 16 | `json:SetRequest` → `json:SetReply`, error `json:ConfigError` | |
| `confirm`, `cancel`, `extend` | `operation` | `json:ControlRequest` → `json:ControlReply`, error `json:ConfigError` | |
| `persist` | `operation`, `optional` | `json:ControlRequest` → `json:ControlReply`, error `json:ConfigError` | unavailable, cause `config`, without a persisted layer |
| `change` | `event`, `burst(600/h)`, `7d` | `json:ConfigChangeEvent` | `reliable`, `block` (events' default) |

Every operation is `idempotent = false` and `fanout = "forbidden"`, and
none declares `timeout_ms`: a call across a radio takes what the link
takes, and the caller sets its own timeout (core §5.1).

**The types,** each an open object (a member a reader does not know is
ignored, and a later minor may add one):
- **`ConfigView`:** `service`, `instance`, `revision`, `confirm_floor_s`,
  `pending?`, `last_change?`, `desired?`, `groups[]` (§2.3).
  - **`Group`:** `name`, `class`, `description`, `writable`,
    `parameters[]` (§2.2, §2.16).
  - **`Parameter`:** tagged by `kind`: `bool`, `integer` (with `min?`,
    `max?`, `unit?`) or `text`; with `name`, `description`, `sensitive?`,
    `value?`, `source?`, `startup?`, the values of the kind's type (§2.2,
    §2.3).
  - **`Pending`:** `token`, `groups[]`, `deadline`, `applied` (§2.7,
    §2.9). **`LastChange`:** `token`, `groups[]` (§2.6).
  - **`DesiredReport`:** `observed_revision`, `outcome`, `refusal?`
    `{code, group, parameter?}` (§2.18).
- **`ConfigStatus`:** `instance`, `revision`, `confirm_floor_s`,
  `pending?`, `last_change?`, `desired?`, `values{group → {name →
  value}}` (§2.19).
- **`SetRequest`:** `values{name → value}`, `confirm_s?`, `token?`,
  `expected_revision?`, `idempotency_key?`, `dry_run?` (§2.5). Its
  members name no template parameter (core W102).
- **`SetReply`:** `{applied: ConfigView}` or `{pending: PendingReply}`.
  **`PendingReply`:** `token`, `apply_at`, `deadline` (§2.9).
- **`ControlRequest`:** `token`, `confirm_s?` (`extend` alone), `answer?`
  (`view`, the default, or `status`) (§2.10).
  **`ControlReply`:** `{view: ConfigView}` or `{status: ConfigStatus}`.
- **`ConfigChangeEvent`:** `service`, `instance`, `revision`, `token`,
  `outcome`, `edits[]{group, parameter, old?, new?, redacted?}`, `actor?`,
  `request_id?`, `claimed_source?` (§2.17).
- **`ConfigError`:** `code` (`restart-required` or `device-refused`),
  `detail?` (§2.5).
- **`DesiredConfig`:** `revision`, `values{group → {name → value}}`, for
  an authoring service's contract to carry (§2.18). No resource of
  `config.v1` carries it; until a contract can reference another's types
  (zenoh-modem's README, gap 18), an author copies it.
- **`ParamValue`:** a boolean, an integer or a string, untagged; the
  parameter's kind says which.

**The unions.** `SetReply` and `ControlReply` are `oneOf`s whose branches
each require one member that no other branch has (`applied` or `pending`;
`view` or `status`). A value with both, or with neither, matches no
branch exactly once, so it is not the type. This is the discriminated
union of architecture D11, and core §7.3's `oneOf` is all it needs.
`Parameter` is a `oneOf` tagged by a `const` `kind`.

## 4. Vocabulary

`config.v1` defines no annotation key (§1). Its vocabularies are payload
values, each closed in this major: a later text of it MAY add a value, and
a reader shows one it does not know as written, and acts on none.

| Vocabulary | Values | Where |
|---|---|---|
| Class | `hot`, `reach`, `contract` | `Group.class` (§2.4) |
| Kind | `bool`, `integer`, `text` | `Parameter.kind` (§2.2) |
| Source | `default`, `file`, `overlay`, `runtime` | `Parameter.source` (§2.3) |
| Outcome | `applied`, `confirmed`, `rolled-back`, `partial` | `ConfigChangeEvent.outcome` (§2.17) |
| `ConfigError` code | `restart-required` (a contract group, §2.4), `device-refused` (the device refused, §2.9) | the `app` detail (§2.5) |

## 5. What a tool may conclude

"Not asked" (nobody put the question, or its premise does not hold) and
"unobservable" (it was put, and the reading could not answer it) are
different facts, and neither is a "no" (core O5). A tool reads the view or
the status by GET (core S4), or by subscription, and judges their
freshness by `freshness.v1`, at 60 s. A view or a status that is stale, or
that a GET did not draw, is unobservable, never the owner's word.

The premises, for every row: the service implements `config.v1`, as its
descriptor says (§2.1); otherwise, or when presence shows it absent, the
question is **not asked**. Its descriptor unread, or the presence read
possibly incomplete (core §8.1), is **unobservable**. Across a constrained
face, the deployment's word stands for the descriptor (§2.19).

| Question | Yes | No | Unestablished | Finding on |
|---|---|---|---|---|
| Is a change pending? | A fresh view or status with `pending`: its token, groups, deadline, and whether it is applied yet (§2.7, §2.9). | A fresh view or status without `pending`. | **Unobservable:** neither is fresh, or neither was drawn. | Neither: informative. A tool shows a pending change's deadline as the owner's instant (§2.8). |
| Did my change land? (a change named by its token, as the `set` that started it was answered) | Its token is the `last_change` of a fresh view or status of the instance that answered the `set`; or an event `applied` or `confirmed` with its token. | An event `rolled-back` or `partial` with its token; or the instance that held it pending is gone, and the view's `instance` is another, so the restart rolled it back (§2.12). | **Not yet:** its token is still `pending`. **Unobservable:** no fresh view or status; the last change is another token and no event of this one was read, which a later change explains as well as an undo; the `set` drew no reply, so no token is known (core O5). | No. |
| Was its undo clean? (a change that did not land) | An event `rolled-back` with its token. | An event `partial` with its token: the read-back is the truth, and the tool shows it (§2.11). | **Unobservable:** no event of it read. A change rolled back by a restart is clean by construction (§2.12). | No: `partial` is a finding about the device. |
| Is this group writable? | The view's group is `writable`, and its class `hot` or `reach`. | Not `writable` (§2.16), or its class `contract` (§2.4). | **Unobservable:** no fresh view: the status carries no class and no `writable`. **Not asked:** the schema declares no such group. | Neither: informative. |
| Will this value survive a restart? | A fresh view shows the parameter with a value and no `startup`: it runs its startup value (§2.3). | A fresh view shows it with `startup`: it runs a runtime change that a restart would not keep. | **Unobservable:** the value is unknown; the parameter is sensitive, whose startup value is never shown (§2.15); no fresh view. | No: a divergence an operator may want persisted (§2.13) or undone. |
| Has it converged to its desired document? (a document at a revision the tool knows) | `desired` in a fresh view or status, `converged`, at an `observed_revision` at least the document's: what the owner did when it acted, which a later `set` may have changed since (§2.18). | `refused` or `failed` at that revision, with the refusal (§2.18). | **Not yet:** an `observed_revision` below the document's. **Not asked:** no `desired` member: the owner converges no desired state, or, a new instance, has acted on none yet, or it reverted on a delete (§2.18, text 0.5). **Unobservable:** no fresh view or status. | No. |

**A reply is evidence, silence is not.** A `set` answered with a token
starts the second row's question; a `set` that drew nothing started
nothing a tool can name, and a tool that resends it without an
idempotency key may make a second change (§2.14).

## Appendix A. Against v1

v1's configuration was RFC 05 §5.1 (normative from v1.42; amended v1.47,
v1.48 and v1.50), with its reference types and validator in `zenkey::config`
(the `v1` branch). zenoh-modem implements it whole, in
`modem-mgmt/src/config.rs`.

**What changed.**

| v1 | `config.v1` | Why |
|---|---|---|
| `@rpc/<producer>/config/<r>` read, and `state/<producer>/config/<r>` echo | One `state/view`; a GET on it is the read (§2.3) | A state GET is the read (core S2), so the read procedure is gone. |
| `config/<r>/…`: the configured resource a chunk of the key, and the grant carving only `config/*/*/set` | The configured resource is the service (§2.20), and each act a key of its own under it (§2.21) | zk2's generator reads the deployment's services, so it grants rf0 and withholds sat0, which v1's could not (`grant_cannot_carve`). |
| `set` declared to reply `ConfigView`, while a reach `set` replied `{token, apply_at, deadline}` | `SetReply`, a discriminated union (§2.9, §3) | The registry did not tell the truth for the one case the reach class exists for (the binding's §10, finding 1; architecture D11). |
| `PendingReply{token, apply_at?}`, and zenoh-modem's undeclared `deadline` | `{token, apply_at, deadline}`, all required (§2.9) | The deadline shows the floor's raise; zenoh-modem already sent it (finding 2). |
| The floor learned only from a reply's `deadline` | `confirm_floor_s` in the view and the status (§2.8) | A caller sizes its window before the call (zenoh-modem's README, gap 9). |
| No way to see whether a group is writable before a refusal | Each group's `writable` (§2.16) | Gap 9. |
| `confirm`, `cancel`, `extend` and `persist` answer the read-back, 1,286 B on a radio | The read-back, or with `answer = "status"` the compact status (§2.10, §2.19) | Gap 9: the confirm's reply was the largest single cost of a far-side reach change. |
| — | `state/status`, the compact status (§2.19) | Gap 9: the echo did not fit a constrained face. |
| `persist` replied `Ack` in zenoh-modem | The read-back, as RFC 05 v1.47 said (§2.13) | Finding 3. |
| Joining and `last_change` specified (v1.50), not implemented in zenoh-modem | Both, with fixtures (§2.6, §2.7) | Finding 4: a change applied without a window could not be persisted. |
| `APPLY_AFTER`, a fixed 1 s in zenoh-modem | `apply_at`, the device's to state, before the deadline, and leaving the reply time to cross (§2.9) | Finding 5: at 300 bit/s the reply takes 3 s, so the apply would cut the link before its own reply had left. |
| `persist` takes the pending change's token or `last_change.token` | The last change's alone; the pending change's is `busy` (§2.13) | A persisted, unconfirmed change would survive a restart, which v1's own rule makes a rollback. |
| Errors `error/not-found`, `invalid-args`, `busy`, `gated`, `unsupported`, `fanout-forbidden`, and the producer's `restart-required`, `device-refused` | Core §5.2's envelope: `not_found`, `invalid_request`, `busy`, `unavailable` with cause `config`, `fanout_forbidden`, and `app` with `ConfigError` (§2.5) | Core O3: `unavailable`'s cause keeps v1's split between reconfigure and rebuild. Every adopter needs both `app` codes, so the profile standardizes them. |
| `busy` named the pending token in its body | The message names it for a person, and the view and the status for a program (§2.5, §2.7) | Core §5.2 carries a detail on `app` alone. |
| No order among the refusals but the validator's | One order, from the core's refusals to the device (§2.5) | Every owner refuses the same input the same way, so a fixture can pin it. |
| `?actor=` and `?request_id=` selector parameters | Core O7's call metadata (§2.17) | The attachment works on every operation, and is claimed, never authentication, as before. |
| `events/<producer>/config_change/<ulid>`, `low` in the RFC, `burst(600/h)` in zenoh-modem | `events/change/<ulid>`, `burst(600/h)`, `7d` (§2.17) | Core §2.6's events, with zenoh-modem's rate. |
| An edit `{parameter, old, new}` | `{group, parameter, old, new}` (§2.17) | A joined change spans groups, whose parameter names may repeat. |
| The resource's name in the document | The `service` address, and the `instance` (§2.3) | The revision crosses faces where presence does not, so it carries its epoch (core §1.5). |
| A restart: a rollback | A rollback, and a new instance: a late confirm is `not_found`, and the caller tells why (§2.12) | Core §1.5. |
| Desired state never carries reach, by rule | The server refuses reach, contract and sensitive values, and reports it in its own state (§2.18) | The class is runtime data, so only the server can check it (the binding's §9). |

**What deliberately did not change.**
- **The three classes,** the window raised to the floor, the undo once,
  `partial`, and the read-back as the truth.
- **One pending change per configured resource,** joined by its token, a
  joining `set` without a window of its own, and joining never moving the
  deadline.
- **Every applied change has a token,** and the last change is what
  `persist` takes.
- **The schema served with the values,** the three kinds and no float,
  sensitive values write-only, and each value's source and startup value.
- **The startup allowlist,** a reconfiguration, not a router change.
- **No operation is idempotent**; retry safety is `idempotency_key`'s, for
  300 s.

**What is not ported.**
- **zenoh-modem's three persisted layers and its boot** (startup file,
  overlay, provisional boot): the owner's business. The profile names the
  act, `persist`, and each value's `source`.
- **`config_hash`** in zenoh-modem's v1 `sensor` document: the view's
  `instance` and `revision` say what it said.
- **A datastore model beyond running and persisted, and a coordinated
  change across services at an agreed time,** which v1 deliberately left
  out too.

|---|---|---|

- No shipped configuration makes a reach group writable, so every reach
  change is refused `unavailable` until an operator names the group in the
  allowlist (§2.16).
- The binding's §11 and §12 give the far side's grants: v1's armed a reach
  change and could neither confirm it nor see the echo; zk2's grant `set`,
  `confirm`, `cancel` and `extend` on rf0, a GET of its view and status,
  and withhold `persist` and everything of sat0 (§2.21).
- Its v1 drifts are fixed by this text (Appendix A, findings 1 to 5).
  Finding 6, the SBD floor protecting a path its faces close, and finding
  7, the `ops` principal reaching every v1 read, are the deployment's.

**ROS 2 parameters** (architecture §4.8). A ROS 2 bridge maps a node's
parameters onto the node's service's `config.v1`.

| ROS 2 | `config.v1` |
|---|---|
| a node's parameters | its service's schema; one group per parameter, as `set_parameters` changes each alone, or a group per set the node changes with `set_parameters_atomically` |
| `bool`, `integer`, `string` | `bool`, `integer`, `text` |
| `double`, byte and array types | no kind yet (§2.2): a bridge carries a double as an integer in a finer unit where it can, and otherwise does not expose the parameter |
| `ParameterDescriptor.read_only` | a `contract` group, or a group outside the allowlist |
| `integer_range` (`from_value`, `to_value`; a `step` has no home) | `min`, `max` |
| `description` | `description` |
| `set_parameters` | `set` without a window, `hot`; ROS 2 has no confirmed commit, so a bridge offers none it cannot honour |
| `/parameter_events` (new, changed, deleted) | the change event's edits; ROS 2 adds and deletes parameters at runtime, which a schema fixed for an instance does not, so a bridge re-mints its instance when the set of parameters changes (core §1.5) |

The double is the first case for a fourth kind (§2.2). Adding one is a
`oneOf` branch in `Parameter`, which core §9.8 classifies as breaking (a new
writer sends the new variant, and an old reader refuses it, spike S7), so a
fourth kind is a new major of the contract, left to the first bridge that
needs it (text 0.3; 0.2 said review).
