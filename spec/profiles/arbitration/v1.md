# `arbitration.v1`: one commander at a time, in the binding's order

| | |
|---|---|
| **Text version** | 0.1 ([`CHANGELOG.md`](CHANGELOG.md)) |
| **Status** | draft |
| **Written against** | core 0.54 ([`../../core.md`](../../core.md)) |
| **Uses** | [`timing.v1`](../timing/v1.md), text 0.1, for the deadline; [`redundancy.v1`](../redundancy/v1.md), text 0.5, where it governs a provider's interface (§2.5) |
| **Evidence** | [`conformance/`](conformance/), [`scenarios.md`](scenarios.md) |

`arbitration.v1` lets a consumer bound to several providers of one stream
follow one of them at a time: the first, in the binding's order, whose
stream still arrives within its deadline and whose interface token it has
not heard withdrawn; and none, the **dead-man**, when no provider is left.
It is the `twist_mux` pattern, which zk2 puts in the consumer: "when
several providers are bound, choosing between them is the consumer's"
(core §3.2). An actuator's contract declares the role arbitrated:

```toml
# thruster.v1: what an actuator provides, and what it requires
[interface]
name = "thruster"
major = 1
uses = ["arbitration.v1"]

[requires.cmd]
interface   = "twist_cmd.v1"
resources   = ["cmd"]
cardinality = "many"
annotations = { "arbitration.policy" = "priority" }
```

The deadline is the commanders' stream's, as [`timing.v1`](../timing/v1.md)
declares it:

```toml
# twist_cmd.v1: what a commander provides
[resources.cmd]
kind        = "stream"
type        = "twist_cmd.v1.Twist"
annotations = { "timing.period_ms" = 20, "timing.deadline_ms" = 100, "timing.lifespan_ms" = 100 }
```

The deployment's binding is the priority, its first entry the highest
(core R1, R3, 0.54):

```toml
[service.bindings.cmd]
providers = ["vehicle-01/safety", "vehicle-01/teleop", "vehicle-01/autopilot"]
```

So `thruster-l` follows `safety` while safety's commands arrive within
100 ms of each other, else `teleop`, else `autopilot`, and else none: it
then holds the dead-man, and applies the safe value its application
chose. A commander whose interface token is withdrawn stops being
followed at once, which is never a conclusion that it left, and only its
token re-admits it, never its next sample. The profile adds no key, and
puts nothing of its own on the bus: a consumer tells its application of
each switch, and a tool asks the same rules of what it hears itself.

---

## 0. Conventions

The keywords, the roles and the evidence tags are core §0's. Here,
`[F: <file>]` names a fixture in [`conformance/`](conformance/),
`[Sc: §n]` a section of [`scenarios.md`](scenarios.md), and `core` marks
the core's own evidence. References to `docs/zk2/architecture.md` (r4: E14,
§3.4, the §3.12 row, §3.14, §4.2), to the spike report (S11) and to ROS's
`twist_mux` are informative: every rule is stated here (Appendix B).

Terms:
- **Role, requirement, binding, parameter binding:** core §3.1–§3.2's. A
  role is **arbitrated** when its declaration is valid (§2.2); one that
  carries no policy is **not arbitrated**, and not this profile's.
- **Consumer:** core §0's, an instance (an owner or a pure consumer, core
  §8.1) holding an arbitrated role. Its **runtime** applies this profile
  for it; its **application** is the code the runtime delivers to.
- **The required interface** and **the role's stream:** the interface the
  role names, and the one stream resource of it the role consumes (§2.2),
  as the revision the consumer holds declares it (§2.3).
- **Entry:** one element of the role's binding, a service address
  `<system>/<service>`, each chunk a plain chunk or `*` (core §1.2, D009),
  a `self.system` already resolved (core §3.2). An entry is **exact** when
  neither chunk is `*`, else a **wildcard**.
- **Provider:** an address `<system>/<service>` (core §1.1) that an entry
  **matches**: an exact entry its own address, a wildcard entry every
  address whose chunks equal its chunks where they are not `*`. The
  profile works per provider, that is per address, never per instance
  (§2.6).
- **Rank:** a provider's place in the binding's order (§2.4). **Higher**
  is earlier.
- **Sample:** a delivery the role's subscription receives. An **arrival**
  is a sample the consumer counts for a provider (§2.5).
- **Deadline:** the role's stream's deadline, as `timing.v1` §2.2 and
  §2.5 read it (§2.3). **Detection bound:** `timing.v1` §2.5's, deadline +
  max(deadline/50, 1 ms). Both run on the consumer's own monotonic clock
  (`timing.v1` §0).
- **Watch session, round trip, a transport's move, a complete read:** core
  §8.1's (0.37, 0.41, 0.42). The consumer's **watch** is the liveliness
  subscriber it holds on its watch session (§2.7).
- **Known held:** an interface token of the required interface at a
  provider's address that the consumer heard declared, or that a read
  showed held, and that it has not heard withdrawn since (§2.7).
- **Withdrawn:** a provider whose last interface token known held the
  consumer heard withdrawn, until its **re-admission** (§2.7).
- **Eligible:** a provider not withdrawn, with an arrival within the
  deadline since its last re-admission (§2.6).
- **Active:** the eligible provider of highest rank, the one whose samples
  are delivered (§2.9). **Dead-man:** no provider eligible, the state at
  start too (§2.11).
- **Switch:** a change of the active provider, a change to or from the
  dead-man included, with its **cause** (§2.10).
- **Instant:** a reading of the consumer's monotonic clock. "At" an
  instant `t` means by the clock reading `t`.

## 1. Extension points

| Point (core §10) | `arbitration.v1` |
|---|---|
| 1. A standard contract or a standard schema | None (§3). |
| 2. An annotation vocabulary | Yes: `policy` (§4), on a requirement. This table replaces the interim row of core Appendix D (core 0.54), with the same key. It is the first vocabulary read on a requirement rather than on a resource. |
| 3. A registered verbatim kind | None. |
| 4. The descriptor's `profiles` | Only through `uses`: a contract declaring an arbitrated role lists `arbitration.v1`, so an instance implementing it lists the profile in its descriptor's `profiles` (core §3.3). It is not derivation-only. |

What the profile reads of the core besides: a binding's order (core R1,
R3, which 0.54 makes ordered), presence (core §8.1), and the stream's
samples and keys (core §1.1, R6). What it reads of `timing.v1`: the
deadline, the detection bound, and which samples are expired.

## 2. Rules

### 2.1 Who implements it

- **A consumer's runtime,** for each arbitrated role: it refuses an
  invalid declaration at start (§2.2), ranks the providers (§2.4), counts
  each sample (§2.5), judges eligibility (§2.6 to §2.8), selects and
  delivers (§2.9), and tells its application of each switch (§2.10) and
  of the dead-man (§2.11).
- **The consumer's application:** it chooses and applies the safe value
  while the role holds the dead-man (§2.11), and does what it chooses on a
  switch.
- **A provider:** nothing new. It publishes its stream as its contract
  declares, at its period (`timing.v1` §2.4), holds its interface token as core
  §8.1 says, and stops as core §8.2 says: its tokens first, then its
  resources, the order §2.7's re-admission stands on.
- **A deployment:** it writes each arbitrated binding in priority order
  (§2.4), and binds providers whose streams can arrive within the deadline
  (§2.12).
- **A tool:** it answers §5's questions (§2.14).

### 2.2 The declaration

A reader MUST read a role's declaration exactly as the fixture does.
`[F: declarations.json]`
- **Arbitrated** is a role whose requirement (`[requires.<role>]`, core
  §3.1) carries the annotation `arbitration.policy`, declared in a
  contract whose `uses` lists `arbitration.v1`.
  - **A role carrying no policy is not arbitrated**, and not this
    profile's, whatever its cardinality and whatever its contract's
    `uses`: a `many` role without one receives from every bound provider,
    merged, as core §3.2 says.
  - **Another major.** A role whose contract's `uses` lists another major
    of `arbitration`, and not `v1`, is that major's.
  - **Where the key means something:** on a requirement only. On a
    resource it means nothing, and the reader ignores it; `[defaults]`
    reaches resources and no requirement (core §9.3). Another
    `arbitration.<key>` is W105's (§4), and makes nothing invalid.
- **The inputs:** the role as its contract declares it (that contract's
  `uses`, the role's `resources`, its cardinality and its annotations), or
  the fact that a component's manifest declares it; the revision of the
  required interface the consumer holds (§2.3); and the role's parameter
  bindings as configured (core R2).
- **What a role consumes** is every resource of the revision held whose
  template is one the requirement's `resources` names, or every resource
  of it when the requirement names none (core §3.1).
- **A declaration is invalid** for each of these, checked in this order,
  each alone: `[F: declarations.json]`
  1. `not_used`: the policy is carried, and the declaring contract's
     `uses` names no major of `arbitration`. A contract that loads cannot
     hold it (core E020); a reader of a requirement's annotations that
     come from elsewhere can.
  2. `manifest_role`: a component's manifest declares the role. Its
     descriptor entry names `"declared_by": null`, and no descriptor
     carries an annotation (core §3.3), so no tool could see its policy:
     1.0 arbitrates contracts' roles only.
  3. `policy_unsupported`: the policy is the string `freshest` or
     `lease`, which §4 reserves.
  4. `value`: the policy is not one of the strings `priority`, `freshest`
     and `lease`.
  5. `cardinality`: the role's cardinality is not `many`. A role with one
     provider has nothing to choose between, and `timing.v1` §2.5's missed is
     its signal (§2.11).
  6. `resource`: the role does not consume exactly one resource, or the
     one it consumes is not a stream (core §2.1: kind `stream`, with or
     without `explicit`). A state's latest value, an event's occurrences
     and an operation's calls carry no deadline to judge by (`timing.v1`
     §2.3).
  7. `no_deadline`: that stream has no deadline as `timing.v1` reads the
     revision held: its declaration invalid, any of its values not a
     whole number of milliseconds from 1 to 2^53−1 (`timing.v1` §2.2: one
     wrong value, a lifespan's included, and none is judged); no
     `timing.deadline_ms` written; or a deadline below the stream's period,
     which is no deadline (`timing.v1` §2.5). Read only when check 6
     passes.
  8. `params_unbound`: a parameter of that stream's template is bound by
     none of the role's parameter bindings (core R2). A binding to
     `self.system` or `self.service` binds it. So each provider has
     exactly one key in the role, and the deadline is per address
     (§2.3). Read only when check 6 passes.
- **No revision held.** A reader that holds no revision of the required
  interface reads checks 1 to 5 only, and when none fails the declaration
  is **unread**: neither valid nor invalid. A consumer always holds one,
  since it is built against one (core R4); a tool may not (§2.14).
- **What a reader does with an invalid declaration.**
  - A consumer's runtime MUST refuse to start an instance holding a role
    whose declaration is invalid, as core §8.2 step 2 refuses: no instance
    token appears, and nothing of the instance is declared or put
    (`redundancy.v1` §2.2's precedent). `[Sc: §8]`
  - A contract linter SHOULD warn of checks 1 to 7 (6 and 7 when it holds
    the required interface's contract, as a set check does, core E035).
    `params_unbound` needs the deployment's parameter bindings, which a
    linter does not have. No core lint reads an annotation's value.
  - A tool reports it as the contract's finding (§2.14).
- **An unbound optional role** (`"bindings": []`, core §3.2) is valid. Its
  consumer holds the dead-man for good (§2.11). A required role bound to
  nothing already refuses the start (core §3.2).
- **Across revisions.** A minor that adds or drops `arbitration.v1` in
  `uses` is a review (core §9.8, `uses_changed`), and so is one that
  changes a role's policy (`role_resources_changed`: the annotations a
  role consumes) or the required stream's deadline
  (`annotations_changed`).

### 2.3 The deadline

- **From the revision the consumer holds.** The role's deadline is its
  stream's deadline in the revision of the required interface that the
  consumer holds: the one it was built against, or the one its runtime
  loaded at its start. It is read once, at start, and does not change
  while the consumer runs. A provider may run another revision of the
  interface (core R4), with another deadline: the consumer judges every
  provider by its own. `[F: declarations.json]`
- **What it means is `timing.v1`'s,** cited here and not restated: per
  (provider address, key), on the consumer's monotonic clock, from
  arrival to arrival; a member is missed once more than the deadline has
  passed since its last arrival, and a miss is seen within the detection
  bound, deadline + max(deadline/50, 1 ms) (`timing.v1` §2.5). An
  arbitrated role's stream has one key per provider (§2.2, check 8), so
  the deadline is per provider here, and a consumer MAY judge it with
  `timing.v1`'s own tracker of that key, as the reference does.
- **The period** (`timing.period_ms`) plays no part beyond §2.2's check 7.
- **Not tightened at 1.0.** Neither the binding nor the requirement lowers
  it (§2.15), and a `timing.<key>` on a requirement means nothing
  (`timing.v1` §2.3).

### 2.4 The ranking

A consumer MUST rank providers exactly as the fixture does.
`[F: rankings.json]` `[Sc: §9]`
- **The binding's order is the priority.** A binding is an ordered list,
  and a descriptor lists it in its configured order (core R1, R3, 0.54).
  Its first entry ranks highest.
- **An exact entry** ranks its own address at its position.
- **A wildcard entry** ranks every address it matches at its position, and
  those addresses among themselves by system, then by service, each
  compared byte by byte (a plain chunk is ASCII, core §1.2). So
  `vehicle-01/*` ranks `vehicle-01/autopilot` above `vehicle-01/teleop`.
  The address's text compared whole is not this order: `a-b/x` sorts
  before `a/x` as text, and after it here, since system `a` comes before
  `a-b`.
- **An address matched twice** ranks at its first entry, and is one
  provider: its arrivals count there only. An entry that can rank no
  address of its own is **shadowed**: an exact entry listed again, or
  listed after an entry that matches its address, and a wildcard entry
  after an earlier entry that matches every address it does (each chunk
  of the earlier `*` or the same as the later's). A shadowed entry is no
  error; a tool warns of it (§2.14).
- **Which addresses rank.** An exact entry's address ranks whether or not
  the consumer has heard from it, and is eligible only once it has
  arrivals (§2.6). A wildcard entry's providers are the addresses it
  matches that the consumer has heard from: a sample counted for one
  (§2.5's outcomes 4 to 7), a token or a read (§2.7). An address no entry
  matches is no provider (§2.5).
- **A priority nobody chose.** The byte order among one wildcard's
  addresses is deterministic, and nobody wrote it. A deployment SHOULD
  write an arbitrated binding with exact entries only, and a tool warns of
  a wildcard there (§2.14).
- **Fixed at start.** The binding is resolved when the consumer starts (a
  `self.system` provider, core §3.2) and does not change while it runs.

### 2.5 Samples, and who sent them

A consumer MUST attribute each sample to its provider by its key, and
count it, exactly as the fixture does. `[F: arbitrations.json]`
- **From the key, never the payload.** A sample's provider is the address
  its key names, positions 2 and 3 (core §1.1), the key read
  base-relative (core §1.6: the session strips the namespace). Nothing a
  payload says of its sender is read: ownership makes the key the one
  thing only that provider may write (core §6, §11.1).
- **Each sample has one outcome,** the first of these that holds:
  1. `wild`: its key is not concrete, and core R6 discards it.
  2. `unresolved`: its key is not the role's stream's key at any address:
     not a zk2 data key (core §1.1), another interface, another kind token,
     or resource chunks the stream's template does not match with the
     role's parameter values (core R2).
  3. `unbound`: no entry of the binding matches its address.
  4. `deleted`: a delete sample, which is no arrival: a stream's samples
     are values (`timing.v1` §2.5, core §2.1).
  5. `expired`: `timing.v1` §2.6 reads it expired, on the deployment's
     stated ε, and an expired sample is not an arrival (`timing.v1` §2.6).
     With no ε stated, nothing is expired.
  6. `not_incumbent`: the required interface is governed
     (`redundancy.v1` §2.2), and `redundancy.v1` §2.10 does not accept it:
     its stamp is not the incumbent's. A consumer MUST count as arrivals
     only the samples §2.10 accepts, so that the second incumbent of a
     split, or the late writes of one stepping down (`redundancy.v1`
     §2.9), cannot keep the address eligible. `[F: arbitrations.json]`
  7. otherwise it is an **arrival** of its provider, `timing.v1` §2.5's,
     and is `delivered` or `not_active` (§2.9).
- **Counted.** A consumer keeps the count of each outcome, per provider
  where the sample has one (4 to 7), so that what it did not deliver is
  never silent (core O5).
- **History.** A sample replayed from an advanced publisher's history at
  the subscription's start is an arrival like any other (`timing.v1`
  §2.5), so a commander that stopped within the history's reach would be
  eligible for a deadline after the consumer's start. A contract SHOULD
  NOT declare `history` on a stream an arbitrated role consumes.

### 2.6 Eligibility

A consumer MUST judge each provider's eligibility exactly as the fixture
does. `[F: arbitrations.json]`
- **Eligible** at an instant `t`: the provider is not withdrawn (§2.7), and
  its last arrival since its last re-admission, or since the consumer's
  start when it was never withdrawn, is within the deadline at `t`: the
  arrival at `a` with `t` ≤ `a` + deadline. A member is missed once more
  than the deadline has passed since its last arrival, so an arrival
  exactly the deadline after the one before is in time (`timing.v1`
  §2.5).
- **Never heard is not eligible.** A provider with no such arrival is
  ineligible, whatever its tokens: a token says a provider is alive, never
  that its commands arrive. `timing.v1`'s rule for a known member never
  heard (`timing.v1` §2.5) makes none eligible: nothing it reports missed
  was eligible to lose.
- **A token is never needed.** A provider whose token the consumer never
  heard, or which holds none (§2.12), is eligible on its arrivals alone:
  a binding never requires presence (core R7).
- **Per address.** Eligibility is the provider's, the address's: two
  instances of one address are one provider, whose samples on its one key
  arrive from whichever of them publishes, and a re-mint changes nothing
  (§2.7).

### 2.7 Withdrawals and re-admission

- **A withdrawal makes a provider ineligible.** A consumer MUST make a
  provider withdrawn, and so ineligible, when its watch hears withdrawn an
  interface token of the required interface at the provider's address, at
  any revision (any `fp16`, core §8.1), and none other is known held there
  after it; and MUST NOT otherwise. A withdrawal heard during a move of
  the watch session is kept, and applied when the move's round trip
  stands (§2.8). `[F: arbitrations.json]` `[Sc: §3, §4]`
  - **What is known held** comes from declarations the watch heard, and
    from reads (below). A withdrawal of a token never known held leaves
    the address with none known held: the consumer fails toward a lower
    priority, and reads again.
  - **It forgets the provider's arrivals:** only an arrival after its
    re-admission makes it eligible again.
  - **Seen at once.** If the provider was active, the consumer switches at
    the withdrawal, cause `withdrawn` (§2.10). S11 measured a commander's
    crash seen in 4–5 ms by liveliness, where its deadline took 100.
- **A re-mint is no withdrawal.** While another instance of the address is
  known to hold the interface's token, the withdrawal of one changes
  nothing: a make-before-break re-mint declares its new tokens before its
  old ones go (core §8.1). `[F: arbitrations.json]` `[Sc: §5]` A consumer
  whose watch did not hear the new token declared (its subscriber has no
  history, core §8.1, 0.41, and the token came before it) knows none held
  at the old one's withdrawal, and its read again re-admits the address:
  a re-mint it could not see costs that provider a read and its next
  arrival.
- **Re-admission,** and nothing else, ends a withdrawal: the watch
  hearing an interface token of the required interface declared at the
  address, or a read showing one held there. A consumer MUST NOT re-admit
  a provider on a sample. `[F: arbitrations.json]` `[Sc: §4]`
  - **Why never a sample.** A provider that stops cleanly withdraws its
    interface token before it undeclares its resources (core §8.2,
    "stopping"), so its last samples can arrive after its withdrawal, and
    a write already in flight later still. Re-admitting on them would
    hand the role back to a provider that has left, until its deadline.
  - **Eligible again at its next arrival.** Re-admission alone makes no
    provider eligible, since it forgot its arrivals: the switch back comes
    at the arrival after it, cause `sample` (§2.10).
- **Read again.** After a withdrawal that leaves an address with no token
  known held, the consumer SHOULD read the address's presence again, as
  core §8.1 asks of a reader following presence live (the reference: one
  read 0.1 s after the first withdrawal of a burst), on a session that has
  never held a liveliness subscriber (core §8.1, 0.37). A read showing an
  interface token of the required interface held at the address re-admits
  the provider, complete or not, since a read cannot invent a token (core
  §8.1, 0.38). What a read shows held is known held from then on: a
  complete read replaces what was known held at the address, and a read
  that is not complete adds to it. `[F: arbitrations.json]`
- **A read never makes a provider ineligible,** whatever it shows: only a
  withdrawal heard does. A complete read that shows no token establishes
  the token's absence (core §8.1), and the provider is judged by its
  deadline all the same, as a tokenless one is (§2.12). `[F:
  arbitrations.json]`
- **Ineligible is never absent.** A withdrawal heard live is a reason to
  read again, never absence by itself (core §8.1, 0.37), and this profile
  concludes no absence from it: the consumer stops following the
  provider, a local decision that fails toward a lower priority or the
  dead-man, and is cheap when wrong, costing that provider's authority
  until its re-admission and next arrival. Nothing here reports a provider
  down, gone or absent: a switch caused `withdrawn` says what the
  consumer heard, and a tool reads it so. Where the provider holds on
  while the watch heard it withdrawn (the watch's own link dropping, its
  router restarting, core §8.1), the read again re-admits it, and §2.8
  keeps a move of the watch's own transport from withdrawing anything.
  Core §8.1 says since 0.54 that a reader may act on a withdrawal heard
  live so ("Acting on a withdrawal").
- **Heard on a watch session, never polled.** The consumer's watch is a
  liveliness subscriber on a watch session of its own (core §8.1, 0.37),
  without history, its round trip made after declaring it (0.41), and in
  no namespace on the wire keys when the consumer's sessions are
  namespaced (0.42). It covers `zk2/<entry>/@zk/alive/<iface>/**` for each
  entry, `<iface>` the required interface's id, a wildcard entry's `*`
  kept. A consumer that holds no watch session judges every provider by
  its deadline alone, as across a face (§2.12). Since a read makes no
  provider ineligible, a poll of presence would cost a read per period and
  change no selection: it is never a stand-in for the watch.

### 2.8 A move of the watch session

- **What a move does.** When the watch session's transport closes or
  opens, a **move** (core §8.1, 0.41), zenoh 1.10.1 can tell its
  subscriber withdrawn, at the close, every token it was told of, and
  declared, at the reopen, every token it matches (core §8.1, 0.42, 0.44;
  Appendix B), unordered with the consumer's other sessions, whose
  samples go on arriving. Applied as heard, the close's withdrawals would
  make `safety` withdrawn, and hand its authority to `teleop` until the
  reopen's telling and safety's next arrival, while safety's commands
  never stopped.
- **The rule.** From a move until the round trip asked after the last
  move stands (core §8.1, 0.41 to 0.45), a consumer MUST keep every
  withdrawal and declaration its watch hears, and every read's result,
  and apply none of them; when that round trip stands, it MUST apply them
  in the order heard, as one change, and select once. `[F:
  arbitrations.json]` `[Sc: §7]`
  - **As one change:** an address ends withdrawn when what was kept
    leaves it with no token known held and holds a withdrawal of it, and
    forgets its arrivals then; an address withdrawn before the move ends
    re-admitted when what was kept leaves a token known held there; any
    other address is as it was. So a close's withdrawal followed by the
    reopen's telling of the same token changes nothing, and no provider
    loses its arrivals to a move.
  - **Meanwhile** arrivals and the deadline go on as before (§2.6). A
    provider that stops while the watch's transport is down is never heard
    withdrawn (core §8.1, 0.42: a token withdrawn then is never told), and
    its deadline makes it ineligible. A move so hands no authority to a
    lower priority, and none to a provider that has left beyond its
    deadline.
  - **A round trip that does not stand** (asked through a session cut off,
    or its time reaching the session's interests timeout, core §8.1, 0.41,
    0.42) applies nothing: the consumer keeps on keeping, and asks the
    round trip again once its transport opens (core §8.1, 0.44, 0.45).
- **At start** there is no move: what the watch hears from its
  declaration on is applied as heard. The consumer needs no presence read
  at start: a provider is eligible on its arrivals (§2.6).

### 2.9 Selection and delivery

A consumer MUST select and deliver exactly as the fixture does.
`[F: arbitrations.json]`
- **The active provider** is the eligible provider of highest rank (§2.4),
  and none, the dead-man (§2.11), when no provider is eligible.
- **Decided at every event**, at the event's instant, for every event the
  runtime hands the consumer: each sample (§2.5), each withdrawal,
  declaration and read (§2.7), a move and the round trip after it (§2.8),
  and its timer. The runtime arms its timer to fire after the active
  provider's **due instant**, its last arrival plus the deadline, and
  within the detection bound of it, and so decides the active provider's
  miss as `timing.v1` §2.5 asks (§2.3); with
  no provider active, it needs no timer, since only an arrival makes one
  eligible. `[Sc: §2, §6]`
- **An event decides the time first.** At an event at `t`, a consumer
  first decides the active provider's miss before `t`, as its timer would
  have, cause `deadline`, and then the event itself. One event can
  so make two switches, the miss's, then the event's (§2.10).
- **No hysteresis.** A provider of higher rank than the active one becomes
  active at its first arrival that makes it eligible: no hold time, no
  count of samples, no margin. S11 measured a takeover in one sample's
  latency, 0.26 ms. The cost, stated: at start, and after a re-admission,
  a lower provider may drive until a higher one's first arrival, one
  period at most for a provider publishing at its period (`timing.v1` §2.4).
  `[Sc: §1]`
- **Only the active provider's samples are delivered.** A consumer MUST
  deliver to its application every arrival of the active provider and
  nothing else: an arrival is decided before it is delivered, so the
  arrival that makes its provider active is delivered, and an arrival of
  any other provider, eligible or not, is `not_active`, counted and never
  delivered. In the dead-man nothing is delivered. `[F: arbitrations.json]`
  `[Sc: §1]`
- **Each consumer decides alone,** from its own arrivals and clock. Two
  actuators bound to the same commanders can switch at different
  instants: S11's two switched within 0.02 ms of each other, which the
  profile does not promise.

### 2.10 Switches

- **Every switch is told.** A consumer MUST tell its application of every
  switch, with the provider it left, the provider now active (or none, the
  dead-man) and the cause, exactly as the fixture decides them:
  `[F: arbitrations.json]` `[Sc: §1–§9]`
  - `start`: the consumer's first state, at its start, which is always the
    dead-man, left from none;
  - `sample`: an arrival made its provider active: a higher provider's
    first arrival since it was last ineligible, or any provider's in the
    dead-man;
  - `deadline`: the active provider missed its deadline (§2.6), and the
    next eligible provider, or the dead-man, is active;
  - `withdrawn`: the active provider was withdrawn (§2.7), a move's change
    included (§2.8).
- **The order within one event:** the miss first (`deadline`), then the
  event's own (`sample` for an arrival, `withdrawn` for a withdrawal or a
  round trip standing). A declaration, a read, a move and a timer make no
  switch of their own: a re-admission makes no provider eligible (§2.7).
- **Nothing else is a switch.** The active provider's own arrivals, a lower
  provider's coming and going, and a higher one's re-admission before its
  next arrival change nothing.
- **What the profile does not carry.** A switch is the consumer's to tell:
  its application, its log, and any interface of its own. The profile puts
  nothing on the bus (§3), and a consumer that exposes its switches on a
  resource of its own contract does so as that contract says. For the
  scenarios, a consumer prints each switch as a JSON line (`scenarios.md`,
  its conventions): two implementations are compared on what that output
  shows, as a black box is in core `presence.md` §10 (0.46).

### 2.11 The dead-man

- **What it is:** the state with no eligible provider. A consumer MUST
  hold it at its start, cause `start`, and whenever no provider is
  eligible, and MUST tell its application on entering it, as a switch to
  none (§2.10). `[F: arbitrations.json]` `[Sc: §1, §6]` It leaves it at the
  first arrival of any provider (cause `sample`).
- **The safe value is the application's,** on purpose. The runtime tells
  the application that the role holds the dead-man, and delivers nothing;
  the application applies its safe value, S11's "defined safe value",
  `twist_mux`'s zero command:
  - **only the application knows one.** A zero velocity is safe for a
    thruster; a heater's safe setpoint is off, and a valve's is open or
    closed as its process needs;
  - **a value the runtime made up would be a command nobody sent,**
    delivered as if a commander had sent it, into the loop the
    application runs. A switch to none says what happened instead;
  - **when and how to apply it,** at once or ramped down, is the
    actuator's control law, not a bus rule.
- **Why it is here, and not in `timing.v1`.** Architecture §3.12's row put
  "dead-man stops" under `timing.v1` and "no fresh provider means the
  dead-man value" under this profile. A dead-man is a state of a role, not
  of a stream: one commander missing its deadline is a dead-man only when
  no other provider is eligible, and only arbitration knows the other
  providers and their withdrawals. `timing.v1` judges one (address, key),
  met or missed (`timing.v1` §2.5), and a consumer with one
  provider acts on its miss itself.
- **Unbound.** An optional role bound to nothing holds the dead-man for
  good (§2.2).

### 2.12 Tokenless interfaces and constrained faces

- **The deadline alone.** A provider whose required interface is in its
  tokenless set holds no interface token of it (core §8.1, U22), and
  presence does not cross a constrained face (`link.v1` §2.6, core §8.5).
  A consumer then hears no withdrawal of the provider, and judges it by
  its deadline alone (§2.6): it loses only the early sight of a crash
  (§2.7). `[F: arbitrations.json]`
- **What crosses a face** is all a far provider has: it is eligible only
  while what crosses arrives within the deadline. A face that downsamples
  the stream (`link.v1` §2.8) to an interval at or above the deadline
  leaves the provider ineligible between crossings. A deployment SHOULD
  bind an arbitrated role across a face only to a provider whose stream
  crosses more often than the deadline, and SHOULD rank it below a
  provider on the consumer's side, whose arrivals do not ride the face.

### 2.13 Cost

- **What a role costs a consumer:** one subscription per entry, as any
  role (core §3.2); one liveliness subscriber per entry on its watch
  session (§2.7); a timer armed at the active provider's due instant; and
  one read after each withdrawal that leaves an address with no token
  known held. It puts nothing on the bus.
- **What it holds per provider:** its last arrival, whether it is
  withdrawn, and the instances known holding its token. A wildcard
  entry's providers are the addresses heard from (§2.4), as many as the
  deployment runs.
- **Measured:** S11's two actuators in one process, each evaluating on a
  2 ms tick, took 7.0 % of one core. A timer armed at the due instant
  meets the detection bound with no tick between events.

### 2.14 What a tool concludes

A tool answers §5's questions of one consumer's role, from the consumer's
descriptor (its `requires` entry, core §3.3: the role, `declared_by`, the
bindings in their order and the parameter bindings), the contracts it
holds, and what it hears itself, and MUST conclude exactly as the fixture
does. "Not asked", "unobservable" and "not this profile's" are never
folded into "no" (core O5). `[F: conclusions.json]` `[Sc: §10]`
- **The declaration.** The tool reads the role's requirement from the
  contract the entry's `declared_by` names, at the revision the
  consumer's descriptor lists for that interface (core §3.3), held offline
  or retrieved (core §8.4); not held, the declaration is unobservable,
  `no_contract`. An entry naming `"declared_by": null` is a manifest's
  role, whose policy no tool sees: not this profile's, `not_arbitrated`.
- **Which revision of the required interface.** A descriptor names a
  role's interface, never the revision its consumer holds (core §3.3), so
  the tool reads §2.2 against every revision of the required interface it
  holds, offline or retrieved from the bound providers' descriptors (core
  §8.4). The declaration is the one they all give; two that differ are
  **unobservable**, `revisions_disagree`; none held leaves it unread
  (§2.2), **unobservable**, `no_provider_contract`.
- **The tool's view.** The tool runs §2.4 to §2.11 over its own arrivals,
  its own watch and its own clock, with the role's binding, its parameter
  bindings (a `self.system` or `self.service` there resolved to the
  consumer's own address, which its descriptor names), and the deadline,
  and reports which provider that view selects, **labelled as its own**.
  It is never the consumer's: the tool's samples ride another path, with
  another latency and another loss, and a commander the consumer hears
  may be one the tool does not. A consumer's switches are the consumer's
  to tell (§2.10).
  - **Listening.** Before the tool has listened for one deadline, a view
    in the dead-man answers nothing: **unobservable**, `listening`.
  - **Lost.** A tool that knows it lost samples within the last deadline
    (its own queue refused one, or it saw its own receive path stall, as
    core §2.7's reader does) answers **unobservable**, `lost`, whatever
    its view selects: a lost sample may have been a higher provider's.
- **A wildcard in an arbitrated binding** is a warning: the byte order
  among its addresses is a priority nobody chose (§2.4). A shadowed entry
  is one too.

### 2.15 Not at 1.0

- **The `freshest` and `lease` policies,** reserved (§4), and
  **`acquire`/`release` operations** for explicit control authority:
  exclusivity between commanders is `redundancy.v1`'s `external`, or a
  lock outside the bus (its §2.11).
- **Hysteresis,** a hold time, or a minimum dwell (§2.9).
- **`clock.v1`'s simulated time:** the deadline runs on the consumer's
  monotonic clock (`timing.v1` §2.5, §2.9).
- **A deadline tightened** by the binding or the requirement (architecture
  §3.12's "a binding may tighten it"): a binding has no field to carry it
  to a tool, and a requirement's annotations reach no descriptor (§2.3).
- **A selection contract:** the consumer's switches as a standard resource
  on the bus (§2.10, §3).
- **Manifest-declared arbitrated roles** (§2.2).

## 3. Contract

None. The profile defines no standard contract and no standard schema:
its inputs are a contract's requirement, the binding, presence and the
stream's samples, and a consumer puts nothing of its own on the bus for
it (`redundancy.v1` §3's precedent). A selection contract would type the
consumer's switches, which at 1.0 are the consumer's to tell (§2.10).

## 5. What a tool may conclude

"Not asked" (nobody put the question), "unobservable" (it was put, and
the reading could not answer it) and "not this profile's" (the role
carries no policy) are different facts, and none is a "no" (core O5). The
fixture [`conclusions.json`](conformance/conclusions.json) states the
tokens: `yes`, `no`, `unobservable`, `not_asked`, `not_this_profiles`,
each with a reason (§2.14).

The premises, for every row: the role's contract held
(**unobservable**, `no_contract`); the role carrying a policy (**not this
profile's**, `not_arbitrated`).

| Question | Yes | No | Unestablished | Finding on |
|---|---|---|---|---|
| Is the role's declaration valid? | Arbitrated, with its policy and deadline (`valid`, §2.2). | Invalid, with its reasons in their order (`invalid`): the consumer refuses to start. | **Unobservable:** the revisions of the required interface held give two declarations (`revisions_disagree`); none held, and checks 1 to 5 pass (`no_provider_contract`). | No. |
| Which provider does the tool's view select? | One, named, labelled the tool's view (`selected`). | None: the tool's view holds the dead-man after listening one deadline (`dead_man`), or the role is bound to nothing (`unbound`). | **Unobservable:** the declaration not valid (`invalid`) or not read (`revisions_disagree`, `no_provider_contract`); listened less than one deadline, nothing eligible (`listening`); samples lost within the last deadline (`lost`). **Not asked:** the tool did not listen (`not_listened`). | No, `dead_man`, where the deployment expects a commander, as the tool's view; `unbound` is informative. |
| Does the binding leave a priority to an order nobody chose? | A wildcard entry (`wildcard`), naming the wildcard entries and the shadowed ones; else a shadowed entry (`shadowed`), naming them. | Exact entries, none shadowed (`exact`). | None beyond the premises: the binding is the descriptor's. | Yes: a warning. |

**Which cause** a switch had beyond its token (a commander's crash, its
link, or the consumer's own watch) is unobservable from the switch alone:
`withdrawn` says what the consumer heard, and the read after it says what
presence holds.

## Appendix A. Against v1

v1 had no arbitration between commanders. Its commands were operations,
with desired state as the one escape hatch (RFC 05, RFC 12 §3), and every
consumer of a stream received every producer's samples. The arbitration
rules v1 did state are the other way round:
- **RFC 07 §1.2:** a producer acting on several consumers' feedback MUST
  state its arbitration rule, and that rule MUST NOT be "the most recent
  report": it chooses among its consumers, not among its commanders.
- **RFC 06 §5.3:** the ownership protocol chose which instance serves a
  service origin, which is `redundancy.v1`'s election now.

**What is new:** everything in §2. A binding's order is a priority (core
0.54); an actuator chooses among its commanders by deadline and presence,
from keys only those commanders may write (core §6, R6), with no payload
field naming a sender, which spike S11's P2 variant needed and P3 does
not.

**What deliberately is not:** a commander's claim on an actuator, a lock
topic, a lease, or a policy other than priority (§2.15).

**What is not ported:** nothing. There was no rule to port.

**Spike S11** (#594): two actuators in one process bound `twist_cmd.v1`
as `cmd` to `[safety, teleop, autopilot]`, commanders at 50 Hz in
processes of their own, deadline 100 ms, a 2 ms evaluation tick.
- **Measured:** a takeover in one sample (0.26 ms from teleop's first send
  to the switch); a silent commander caught at 100–102 ms by the deadline;
  a crash at 4.9–5.0 ms by liveliness; the dead-man at the deadline; 7.0 %
  of one core. §2.7, §2.9 and §2.13 cite them.
- **Its arbiter** took the first fresh source in a fixed order, with no
  hysteresis, as §2.9 does. It dropped a source on any token delete and
  re-admitted it at its next sample, which §2.7 refuses; and its dead-man
  emitted nothing, as §2.11's does.
- **Its "0 false stops"** holds by its construction: it counted a false
  stop when it chose none while a source was fresh, which its own rule
  never does. It is no evidence that a consumer's stop comes late enough;
  the scenarios check that instead (`scenarios.md` §2, §6: never before
  the deadline).
- **Only `priority` was exercised.** `freshest`, `lease` and
  `acquire`/`release` have no measurement and no text beyond the row.

**The walkthrough** (architecture §4.2): `thruster.v1`'s `[requires.cmd]`

vehicle-01/autopilot]`. The declaration is valid as written, and its
contracts need no new revision.

is not a settled API: the deadline is the contract's (§2.3), never the
call's, and the runtime's interface is the reference's.

**`twist_mux`** (ROS) gives each input topic a priority and a timeout, and
follows the highest-priority topic still within its timeout; its lock
topics, which block lower priorities, are close to the `lease` this text
