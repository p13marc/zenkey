# `telemetry.v2`: a frame's fields as metric series

| | |
|---|---|
| **Text version** | 0.1 ([`CHANGELOG.md`](CHANGELOG.md)) |
| **Status** | experimental |
| **Written against** | core 0.87 ([`../../core.md`](../../core.md)) |
| **Uses** | no other profile. It restates [`telemetry.v1`](v1.md)'s rules by reference, text 0.7, and adds §2.16 to §2.21. |
| **Evidence** | [`conformance/v2/`](conformance/v2/), [`scenarios-v2.md`](scenarios-v2.md), and `telemetry.v1`'s for §2.1 to §2.15 |

`telemetry.v1` reads a metric from one sample per put: a Point, or a
bare JSON value. A constrained owner sends its readings as a **frame**
instead (core §7.7): several packed records under one envelope, each
holding every field or only those that changed. `telemetry.v2` binds a
frame's fields to metric series. Each field gets a kind and a unit from
the contract, never from the wire. Its epoch is the envelope's run, and
its time is its record's.

```toml
[interface]
name  = "modem"
major = 3
uses  = ["telemetry.v2", "link.v1"]

[resources."sdu/dropped_total"]                # a bare JSON counter, as under telemetry.v1
kind        = "stream"
type        = "json:Counter"
annotations = { "telemetry.kind" = "counter" }

[resources."frames/link"]                      # the same reading, and three more, in one frame
kind        = "stream"
type        = "packed:modem-frames#Link"
frame       = { records = 1 }

[resources."frames/link".annotations]
"link.exposure" = "link"

[resources."frames/link".annotations."telemetry.series"]
dropped        = "sdu/dropped_total"                     # a mirror: its kind and unit from there
queue_depth    = { kind = "gauge", unit = "1" }          # an inline series
duty_available = { kind = "gauge", unit = "1" }
duty_wait_ms   = { kind = "gauge", unit = "ms" }
```

A contract that moves its `uses` from `telemetry.v1` to `telemetry.v2`
reads every resource that is no frame resource as before. Only its frame
resources gain series.

---

## 0. Conventions

The keywords, the roles and the evidence tags are core §0's. Here,
`[F: <file>]` names a fixture in [`conformance/v2/`](conformance/v2/),
and `[Sc: §n]` a section of [`scenarios-v2.md`](scenarios-v2.md). `v1 §n`
names a section of [`telemetry.v1`](v1.md), and a fixture of v1's says
so, as in `[F: v1 continuity.json]`.

**By reference.** Every rule of `telemetry.v1` holds for a contract that
uses `telemetry.v2`, as written, on every resource that is no frame
resource. On a frame resource, §2.16 to §2.21 replace them, as the table
under §2.1 to §2.15 says. Where a rule of v1 cites a section, it cites
v1's.

Terms are v1 §0's, and these:
- **Frame resource, frame key, field, record:** core §7.7's. A frame
  resource has no parameter, so it has one key.
- **Series field:** a field that the resource's `telemetry.series` binds
  to a series (§2.16).
- **Series:** one frame key and one of its series fields (§2.17).
- **Mirror:** a resource that a series field borrows its kind, unit and
  semantic from (§2.16).
- **Sample** of a series: a record that includes its field with a value
  (§2.18).
- **Run:** core §4.3's. A frame's run is its envelope's.
- **Width:** a `counter` field's width w, from 1 to 64 bits (core §7.6).

## 1. Extension points

| Point (core §10) | `telemetry.v2` |
|---|---|
| 1. A standard contract or a standard schema | v1's standard schema, [`telemetry.v1.json`](telemetry.v1.json), by the ids v1 §3 publishes. No contract. |
| 2. An annotation vocabulary | v1's four keys and `series` (§4). W105 reads this table for a contract that uses `telemetry.v2`. |
| 3. A registered verbatim kind | None. |
| 4. The descriptor's `profiles` | As v1's: through `uses` alone. |

**One major per contract.** A contract lists `telemetry.v1` or
`telemetry.v2` in `uses`, never both: core §10 makes two majors of one
profile E002.
- A contract moves by its `uses`, which core §9.8 classifies as a review.
- Two contracts of one instance may use the two majors, so a deployment
  may run both (core §10).
- `telemetry.v1` stays defined for the contracts that use it.

**Why a new id.** A reader of `telemetry.v1` alone never reads a frame's
fields as series: `telemetry.series` is not one of its keys, and v1 §2.4
makes no packed type a carrier. So it never reads a frame under v1's
epoch rules, which would read every decrease across a face as a reset
(v1 §2.14).

### 2.16 The declaration: `telemetry.series`

A frame resource declares its series in one annotation,
`telemetry.series`. It is a table, and each entry binds one field of the
record type to a series. The entry's key is the field's name, and its
value is one of two:
- **a mirror:** a string, the template of a resource of the same
  interface;
- **an inline series:** a table of `kind`, `unit` and `semantic`, each
  valued as v1 §2.2 says. `kind` is required.

A field the table does not name is no series field. A reader reads no
metric from it.

**The mirror lends.** A mirror names one resource of the interface, under
any kind token. That resource is no frame resource, and its template has
no parameter. Its resolved declaration (v1 §2.2, §2.4) gives the series
its kind, its unit and its semantic. A mirror is a label, never the
series' identity (§2.17).

**Only the table.** On a frame resource, v1's four keys mean nothing,
wherever they resolve from, `[defaults]` included. A reader MUST NOT read
a kind, a unit or a conformance from them there.
`[F: v2/declarations.json]`
- A frame resource with no `telemetry.series` is not this profile's. It
  is `ignored` when it resolves one of v1's four keys, and
  `not_this_profiles` otherwise.
- `telemetry.series` on a resource that is no frame resource means
  nothing. That resource reads as v1 §2.2 says, from its other keys.

**The carriers.** A field's packed type (core §7.6) carries one kind:

| Kind | The field's type |
|---|---|
| `counter` | `counter` |
| `gauge` | `int` or `fixed` |
| `boolean` | `bool` |
| `text` | `enum`: the value's name |
| `histogram`, `binary` | none at this version |

A `time` field carries no kind.

**Reading it.** A reader and a linter MUST read `telemetry.series`
exactly as the fixtures do: the same series, or the same reasons in the
same order. `[F: v2/declarations.json]`

**An invalid declaration.** A reader MUST NOT read a field of a frame
resource whose `telemetry.series` is invalid. Every series' samples and
continuity are then unobservable, naming the reasons, as v1 §2.2 says
of a member. `[F: v2/declarations.json]` A contract linter SHOULD warn
of one. `[F: v2/declarations.json]`
- **The annotation whole** is checked first: `series_value` when it is
  not a table, or is an empty one. Nothing else is then checked.
- **Each entry** is checked next, in byte order of its key. Each check is
  made alone, and a check that needs a wrong value is skipped:
  1. `series_field`: the key names no field of the record type;
  2. `series_value`: the value is neither a string nor a table, or it is
     a table holding a member other than `kind`, `unit` and `semantic`.
     A value that is neither skips checks 3 to 7;
  3. `kind_value`, `unit_value`, `semantic_value`: an inline series'
     member is present and its value is not one, as v1 §2.2 says;
  4. `mirror_missing`: the mirror names no resource of the interface, or
     two of them (under two kind tokens). Or it names a frame resource, a
     template with a parameter, or a resource that is not a metric
     resource (v1's `not_this_profiles` or `ignored`);
  5. `mirror_invalid`: the mirror's own declaration is invalid;
  6. `kind_missing`: an inline series with no `kind`, or a mirror that
     declares no kind, a Point with no `telemetry.kind`;
  7. `not_a_carrier`: the field's type cannot carry the series' kind.

### 2.17 The series

**The series is the frame key and the field.** One frame key and one of
its series fields are one series, as v1 §2.12 makes one key one series.
It is never the mirrored key's.
- **Two series of one quantity.** A reader that hears a mirrored stream
  and its frame holds two series. A reader MUST NOT pair a sample of one
  with a sample of the other: their epochs and their clocks are not one.
  `[Sc: §7]`
- **The mirror is a label.** A tool shows it beside the series, as
  "`sdu/dropped_total` (`frames/link`)". A sum over series would count
  the quantity twice, and the label is how a person tells.
- **Its kind, unit and semantic** are its entry's (§2.16). They play v1
  §2.5's declared kind and unit. A unit that no entry gives is unknown,
  never dimensionless.

### 2.18 Samples, and no value

**A sample** of a series is a record that includes its field with a code
that is a value. Its value is the code's (core §7.6), as the series' kind
reads it:
- a `counter`: the count, modulo 2^w (§2.20);
- a `gauge`: the `int`'s integer, or the `fixed` value, exact as its
  decimal string;
- a `boolean`: the `bool`;
- a `text`: the enum value's name.

**What is no sample.** A reader MUST NOT form a pair, a rate or a value
from a record that did not include the field. `[F: v2/readings.json]`
- **An omitted field** holds a value, `known` since it was included or
  `within` its deadband (core §7.7). The owner did not write it, so it is
  no sample. A tool still shows it in its state, as core §7.7 says.
- **Two samples are exact**, whatever was omitted, unknown or lost
  between them. So a pair of them is exact too.

**No value, never zero.** These are no value, whether the record included
the field or not. A reader MUST NOT show or use one as a value, as 0 or
as the series' last value. `[F: v2/readings.json]` `[Sc: §4]`

| What the field holds | A reader shows | Token |
|---|---|---|
| `not_available`, or the field absent | absent | `absent` |
| `error` | the owner's error: that record says nothing of the series | `owner_error` |
| `out_of_range` | beyond the declared range | `beyond_range` |
| an enum's escape | a value this revision does not name | `unnamed` |
| `unknown` (core §7.7) | unknown, with why | `unknown` |

None of them is a finding: the owner said what it knew.

**Conformance.** Core §7.7's reader refuses a frame that holds an unused
code, so a sample's code is one its field reads. v1 §2.6's checks have
nothing more to find: every sample of a valid declaration conforms. A
frame its layout refuses is undecodable (core §7.7), and v1 §5 says what
that leaves unanswered.

### 2.19 The epoch is the run

**In band, always.** Two samples of a series are of one epoch when its
reader read both under one run, with no frame between them read as a
rewind or as another run's (core §7.7, "The frames it expects"). Two
samples are of two epochs otherwise. Either way, the epoch is established
in band. Presence plays no part, and v1 §2.9's step 2 is never reached.
`[F: v2/continuity.json]`
- **A gap** keeps the epoch: records lost are records of the run.
- **A rewind is a reset.** A pair across a rewind is a reset, established
  in band. It is never a decrease, and never a finding.
  `[F: v2/continuity.json]` `[Sc: §6]`

**The owner's obligations.**
- An owner MUST write a counter field's samples under a new run from the
  moment the counter restarts. `[Sc: §2]` A new instance takes a new run
  (core §4.3), and a device's restart is a new instance (v1 §2.15).
- Within one run, an owner MUST NOT write a counter field's count below
  one it wrote before on that key. `[Sc: §5]` The count is the one before
  §2.20's reduction. So a decrease of a 64-bit counter within one run is
  the finding (v1 §2.7).

**A new run within an instance** reads as a reset. Core §4.3 takes one
when the seqs run out, and an owner may take one at any other time. The
counter did not restart, but the pair across loses its rate.

**Across a constrained face** no presence is needed: every pair of a
frame's series is established in band. So a decrease of a 64-bit counter
within one run is a finding across a face, where v1 §2.14 reads any
decrease there as a reset. `[Sc: §5]` `link.v1` §2.13's in-band epoch is
the run, and costs no byte.

### 2.20 A counter's width

**A declared loss.** A `counter` field of width w below 64 carries its
count modulo 2^w (core §7.6). A reader cannot recover the total.

**The serial window.** Take a pair of samples a and b of one counter
series under one epoch, and d = (b − a) mod 2^w. A reader MUST read it
so: `[F: v2/continuity.json]` `[Sc: §3]`
- **d < 2^(w−1):** an increase of d, `same_epoch`. A wrap between the two
  samples is included in d.
- **d ≥ 2^(w−1):** `unobservable` (`wrap_or_decrease`), with no rate
  (`wrap_or_decrease`). It is never a decrease, a finding, an increase or
  a rate.
- **At w = 64,** v1 §2.10 holds as written: b below a is `decreased`, the
  finding.

A pair under two epochs is a reset, whatever its values (§2.19). Two
counter samples of two widths are incomparable, v1 §2.10's `unobservable`,
with no rate (`kind`).

**The owner's width.** An owner SHOULD declare each counter field wide
enough that its increase between two samples of its series stays below
2^(w−1). `[Sc: §3]` Past it, a reader reads a smaller increase than
happened, or no rate.
- A 24-bit byte counter at 10 Mbit/s wraps in 13 s, so one frame a
  minute cannot carry it.
- At 300 B/s, the same counter wraps in 15.5 hours.

**Why a window.** Without one, a 32-bit counter that went back by 5 reads
as an increase of 2^32 − 5, a rate of billions.

**In place of widening.** v1 §2.7 asks a producer to widen a narrow
counter. A frame declares its counter's width instead, so a reader knows
the window.

### 2.21 Time, and the rate

**A sample's time** is its record's (core §7.7): measured, scheduled
within `jitter_ms`, or unknown. Only record 0 of a frame whose time is
unknown has an unknown time: a later record keeps its offset.

**The time base.** A reader MUST time a pair of samples of one series by
the first of these that applies, in place of v1 §2.11's list:
`[F: v2/continuity.json]`
1. **In one frame:** the later record's offset after record 0, less the
   earlier's. It is known even when the frame's time is not. A scheduled
   record's offset is `step_ms` times its index.
2. **In two frames, both instants known:** the later record's instant,
   less the earlier's.
3. **Otherwise:** the reader's arrivals of the two frames, v1's third
   base.

**The basis** is named:
- **`measured`:** base 1 or 2, neither record scheduled;
- **`scheduled`:** base 1 or 2, at least one time scheduled. The elapsed
  time is exact to within the sum of the scheduled records' `jitter_ms`,
  either way: 2 × `jitter_ms` when both are;
- **`arrival`:** base 3.

**The value** is v1 §2.11's formula, `double(d) / (double(e) / 1e9)`. Here
d is §2.20's increase, and e the elapsed time in nanoseconds,
milliseconds times 10^6. There is no rate when e is 0 or less
(`elapsed`). Two readers that follow it agree bit for bit.
`[F: v2/continuity.json]`

**A scheduled rate.** A reader MUST report a rate whose basis is
`scheduled` with its bound, and MUST NOT show it as a measured rate.
`[F: v2/continuity.json]` `[Sc: §1]`

**Measurement time is not publication time,** as v1 §2.12 says of the
Point's `timestamp`. A record's time times a rate. It ages nothing.

## 3. The standard schema

v1 §3's, unchanged. This text adds no type, and a frame carries none of

## 4. Vocabulary

v1 §4's four keys, and this one:

| Key | Type | On | Meaning |
|---|---|---|---|
| `telemetry.series` | a non-empty table: a field's name → a mirror, a template, or an inline series, `{kind, unit, semantic}` | a frame resource; meaning nothing on any other (§2.16) | Which fields are series, and each one's kind, unit and semantic (§2.16). |

On a frame resource, v1's four keys mean nothing (§2.16). Any other key
`telemetry.<key>` is outside the table: W105.

## 5. What a tool may conclude

v1 §5's questions hold on every resource that is no frame resource, and
these on a frame resource. The fixtures state the tokens:
[`declarations.json`](conformance/v2/declarations.json),
[`readings.json`](conformance/v2/readings.json) and
[`continuity.json`](conformance/v2/continuity.json).

| Question | Yes | No | Unestablished | Finding on |
|---|---|---|---|---|
| Is this frame resource's `telemetry.series` valid? (§2.16) | `declared`, with each series' field, kind, unit, semantic, mirror and width. | `invalid`, with its reasons, each with its entry. | **Not this profile's:** `ignored`, `not_this_profiles`. | No, for a contract linter: a warning, no core code. |
| What does this record say of this series? (§2.18) | `sample`, its value. | `held`: no sample, its value shown in its state. | **No value:** `absent`, `owner_error`, `beyond_range`, `unnamed`, `unknown`. | Neither: none is a finding. |
| Did this counter go backwards within one epoch? (§2.19, §2.20) | `decreased`: a 64-bit counter within one run. | `same_epoch`, or `reset`: another run, or a rewind. | **Unobservable:** `wrap_or_decrease`, `incomparable`. **Not asked:** not a counter (`kind`). | Yes: `decreased`. |
| What is this counter's rate over the pair? (§2.21) | A rate, its unit, its elapsed time and its basis; a `scheduled` one with its bound. | None, with why: `reset`, `decreased`, `elapsed`, `wrap_or_decrease`. | **Not asked:** not of two counters of one width (`kind`). | Neither: informative. |

**Over many pairs,** v1 §5 holds, read for a series. A counter series
could not tell when it formed no pair in the window, or when one of its
pairs is `wrap_or_decrease` and none is `decreased`. A series with fewer
than two samples formed no pair, and so did one that was unknown
throughout. A tool says so for each, and a finding still stands.
- Every pair of a frame's series is established, so its epoch is never
  assumed.
- A window shorter than `keyframe_every` puts can leave a field that only
  a keyframe includes unknown throughout.

## Appendix A. What moves from `telemetry.v1`

| `telemetry.v1` | `telemetry.v2`, on a frame resource |
|---|---|
| The Point (§2.3) and its conformance (§2.6) | Kept for JSON carriers. A frame is packed, and core §7.7's reader checks its codes |
| The Epoch attachment (§2.4, §2.9 step 1) | Kept for a bare value. A frame's epoch is its run |
| Widening a narrow counter (§2.7) | Kept for JSON. A frame declares its counter's width, read in a serial window (§2.20) |
| Histograms (§2.8) | Kept for JSON. No frame field carries one yet |
| Presence as epoch evidence (§2.9) | Kept for JSON. Never used for a frame |
| The pair (§2.10) | Kept. The epoch is always in band, and a narrow counter reads in its window |
| The rate (§2.11) | The formula kept. The time base is the record's, its basis named (§2.21) |
| Absent is not zero (§2.12) | Kept, and widened to `unknown`, the reserved codes and the escape (§2.18) |
| Constrained faces (§2.14) | No presence is needed for a frame (§2.19) |
| Device-as-service (§2.15) | Kept: a new instance, so a new run |
| §5's questions and the tool's exit | Kept. "Could not tell" also covers a series with fewer than two samples, or one unknown throughout |

**What did not move.** Histograms and templated series wait: a histogram
needs its buckets as a group of counter fields, and a frame resource has
no parameter (core §7.7), so no series has a member epoch.

## Appendix B. The adopters' mappings

No adopter's contract uses this text yet. It was written for
zenoh-modem's `modem.v3`, whose link readings core §7.7's fixtures carry
as the record type `Link`. Its frame `frames/link` mirrors four `link`
streams: `sdu/dropped_total` as a 32-bit counter, `sched/queue_depth`,
`air/duty_cycle_available` and `air/duty_cycle_wait_ms`. Across the
radio, `telemetry.v1` reads any decrease of `sdu/dropped_total` as a
reset (v1 Appendix B). Read through the frame, a decrease within one run
is never a reset. At 32 bits it is `wrap_or_decrease` (§2.20), and at 64
bits the finding (§2.19). The ranges and widths are modem.v3's own to
fix.
