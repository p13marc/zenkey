# `telemetry.v1`: what a metric is, and how a reader reads one

| | |
|---|---|
| **Text version** | 0.5 ([`CHANGELOG.md`](CHANGELOG.md)) |
| **Status** | draft |
| **Written against** | core 0.35 ([`../../core.md`](../../core.md)) |
| **Uses** | no other profile |
| **Evidence** | [`conformance/`](conformance/), [`scenarios.md`](scenarios.md) |

`telemetry.v1` says what a metric resource carries, and what a reader may
conclude from it: a member's kind and unit, whether a sample conforms,
whether a counter went backwards, and the counter's rate. It gives a
contract two things:
- **a vocabulary,** four annotations: `telemetry.kind`, `telemetry.unit`,
  `telemetry.buckets` and `telemetry.semantic` (§4);
- **a standard schema,** [`telemetry.v1.json`](telemetry.v1.json), whose
  Point carries one self-describing measurement (§2.3, §3).

```toml
# zenoh-modem's shape: a bare number, declared by its annotations
[resources."sdu/tx_bytes_total"]
kind        = "stream"
type        = "json:Counter"                 # {"type": "integer", "minimum": 0}
annotations = { "telemetry.kind" = "counter", "telemetry.unit" = "By" }

# ZenSight's shape: the profile's Point, which describes itself
[resources."flow/reassembly_gap_bytes_total"]
kind        = "stream"
type        = "json:telemetry.v1.Point"      # schemas: "…/spec/profiles/telemetry/telemetry.v1.json"
annotations = { "telemetry.unit" = "By" }
```

It defines no contract, no interface and no kind, and puts nothing of its
own on the bus. An instance whose contract uses it lists it in its
descriptor's `profiles`, as core §3.3 lists every profile a contract uses.

---

## 0. Conventions

The keywords, the roles and the evidence tags are core §0's. Here,
`[F: <file>]` names a fixture in [`conformance/`](conformance/),
`[Sc: §n]` a section of [`scenarios.md`](scenarios.md), and `core` marks
the core's own evidence. References to `docs/zk2/architecture.md` (D9,
D19, §3.12, §4.9), to v1's RFC 08 §2, RFC 11 §4 and RFC 13 §3, and to the
adopters' files under `examples/zk2/` are informative: every rule is
stated here.

Terms:
- **Metric resource:** a `stream` or `state` resource, `@stream` and
  `@state` included, whose resolved annotations (core §9.3) hold a key of
  this profile's vocabulary, or whose type is the profile's Point (§2.3).
  Its members are **metric members**.
- **Member:** one concrete key of a resource (core §2.2). The member is
  the series: one key, one series (§2.12).
- **Sample:** one value of a member: a stream sample, or a state put or
  GET reply carrying a value.
- **Carrier:** what a sample's payload is. The **Point** carries a
  measurement of any kind and says which (§2.4). A **bare value** carries
  one kind, the declared one: a JSON number, boolean or string, the
  profile's Histogram, or raw bytes.
- **Declared kind:** the resolved resource's `telemetry.kind`.
  **Self-described kind:** a Point's tag, its `value.type`.
- **Epoch:** a counter's or a histogram's continuity epoch. Within one
  epoch, its values never decrease (§2.7, §2.8); across two, they may
  restart (§2.9).
- **Reader:** a consumer or a tool that reads a metric member. A tool is
  core §0's.
- **The declaration:** what a reader reads of a resource before any sample
  (§2.2, §2.4): valid, with its kind, unit, buckets and semantic; invalid,
  with its reasons; ignored; or not this profile's.

## 1. Extension points

| Point (core §10) | `telemetry.v1` |
|---|---|
| 1. A standard contract or a standard schema | A standard schema: [`telemetry.v1.json`](telemetry.v1.json) (§3, core 0.35), whose types are the profile's by the artifact's id. No contract. |
| 2. An annotation vocabulary | Yes: `kind`, `unit`, `buckets`, `semantic` (§4). This table replaces the interim row of core Appendix D (core 0.35): W105 reads it. |
| 3. A registered verbatim kind | None. |
| 4. The descriptor's `profiles` | Only as core §3.3 lists every profile a contract uses: an instance implementing a contract that lists `telemetry.v1` in `uses` lists it. The profile adds no listing of its own. |

## 2. Rules

### 2.1 Metric resources, and who lists the profile

- **Annotations need `uses`.** A contract that writes a `telemetry.*`
  annotation lists `telemetry.v1` in `uses`, as core §10 requires of every
  vocabulary: E020 otherwise. `[F: core contracts/e020-annotation]`
- **The Point alone.** A contract that carries the Point and writes no
  annotation SHOULD list `telemetry.v1` too: `uses` is fingerprinted
  (core §9.5), and says what the contract means its payloads to be read
  by. ZenSight's four do (Appendix B).
- **The Point is known by its id.** A reader MUST recognize the Point, and
  the profile's other types, by their artifact's id (§2.3), whatever the
  contract's `uses` says: a stream or state resource typed by the Point is
  a metric resource (§0) in a contract that does not list the profile too.
  An event or an operation typed by it is not one (below, and §2.2; 0.2).
  `[F: declarations.json]`
- **Which kinds.** Streams and state carry metrics. On an event, an
  operation or a requirement, the vocabulary means nothing at this
  version, and a reader ignores it (§2.2).
  - **Events.** An occurrence stands alone (core §2.6): it has no series
    to be a counter of. A count of occurrences is a counter of its own.
  - **Operations** hold no value a reader samples.
  - **Requirements.** A consumer's own reading of a role, a unit it
    converts to for instance, is the consumer's.

### 2.2 The vocabulary's values

Each key is read by its reader, as this section says. The core has no
code for an annotation's value: W105 is about keys, and no core lint reads
values (core 0.35).

- **`telemetry.kind`** is a string, exactly one of `counter`, `gauge`,
  `histogram`, `text`, `boolean` and `binary`, compared byte for byte.
  `[F: declarations.json]`
  - **counter:** a count from 0 to 2^64−1 that never decreases within one
    epoch (§2.7).
  - **gauge:** a number, which may go up or down.
  - **histogram:** a distribution over fixed buckets, cumulative within
    one epoch (§2.8).
  - **text**, **boolean**, **binary:** a string, a boolean, bytes.

  The annotation and the Point spell a kind the same way, so `boolean`,
  never v1's `bool` (Appendix A).
- **`telemetry.unit`** is a string of 1 to 64 characters, each a printable
  ASCII character from 0x21 to 0x7E, so no space and no control.
  `[F: declarations.json]`
  - It SHOULD be a UCUM case-sensitive code (`By`, `By/s`, `s`, `ms`, `%`,
    `Cel`, `1`).
  - It is compared byte for byte, and never parsed, converted or
    normalized: `ms` and `s` are two units, and so are `By` and `byte`.
  - Any such string is valid: zenoh-modem's `dBm` is not UCUM's spelling,
    and `us` is UCUM's microsecond (Appendix B). A unit is a label for a
    reader to show and compare, not a quantity to compute with.
- **`telemetry.buckets`** is a non-empty array of numbers, strictly
  ascending, each finite. `[F: declarations.json]`
  - **Compared by value.** A bound is read as the IEEE 754 double nearest
    its value, and two bounds are compared as doubles: `-0.0` equals `0`,
    and `1` equals `1.0`. The canonical form writes an integral float as
    the integer (core §9.5), so a reader of a bundle could not tell them
    apart, and neither may a reader of the source.
  - **`+Inf` is implicit,** and MUST NOT be written. It cannot be: JSON
    has no infinity, and TOML's `inf` is E028 (core §9.5).
    `[F: core contracts/e028-non-finite]`
  - **Present iff the kind is `histogram`.** `telemetry.buckets` on a
    resource whose declared kind is anything else, or that declares no
    kind, and a declared `histogram` without `telemetry.buckets`, are
    invalid declarations. `[F: declarations.json]` Two producers of one
    histogram are comparable only if their bounds are.
- **`telemetry.semantic`** is a string, exactly one of `temperature`,
  `power`, `bytes`, `duration`, `ratio`, `count`, `identity` and `state`.
  `[F: declarations.json]`
  - It is a presentation hint, for what `kind` and `unit` leave ambiguous:
    a `1`-unit gauge that is a `ratio` (0 to 1) rather than a `count`; a
    `text` member that is an `identity` (a hostname, never truncated)
    rather than a `state` (an enumeration, shown as a chip).
  - It is never a finding about a sample: no rule reads it but a
    presenter.
- **Where they are written.** On a resource, or in `[defaults]` or
  `[defaults.<kind>]` (core §9.3). The resolved resource is what a reader
  reads. `[defaults.stream] "telemetry.kind" = "gauge"` gives every stream
  of a contract one kind, a resource's own value overriding it.
  `[F: declarations.json]`
- **On an event or an operation, ignored.** `[defaults]` spreads
  annotations to every kind, so a contract may resolve one there without
  meaning it. A reader MUST NOT read a kind, a unit or a conformance from
  an event's or an operation's `telemetry.*` annotations, whatever their
  values. `[F: declarations.json]`
- **An invalid declaration.** A reader MUST NOT read a member of a
  resource whose declaration is invalid by it: the member's kind, its
  samples' conformance and its continuity are unobservable, naming the
  reasons (§5). `[F: declarations.json, samples.json]` A contract linter
  SHOULD warn of one. The reasons, in the order a reader checks them, each
  key checked alone and a check that needs a wrong value skipped:
  1. `kind_value`, `unit_value`, `buckets_value`, `semantic_value`: the
     key is present and its value is not one, as above;
  2. `kind_missing`: no `telemetry.kind`, and the type is not the Point,
     so nothing says what the annotations describe;
  3. `buckets_without_histogram`: valid `telemetry.buckets`, and a valid
     declared kind other than `histogram`, or none;
  4. `histogram_without_buckets`: the declared kind `histogram`, and no
     `telemetry.buckets`;
  5. `not_a_carrier`: a valid declared kind its type cannot carry (§2.4).

### 2.3 The standard schema

- **The file.** [`telemetry.v1.json`](telemetry.v1.json) is a JSON Schema
  artifact (core §9.4), in the subset of core §7.3. A contract lists it
  in `[schemas] jsonschema`, as any listed file, by its path or a copy's.
  It defines four types:
  - **`telemetry.v1.Point`:** one measurement, an object with:
    - `timestamp`, required: the measurement time, an integer of Unix
      epoch milliseconds, which a reader reads from −2^63 to 2^63−1, as
      ZenSight's `i64` (§2.6, §2.12);
    - `value`, required: a `telemetry.v1.Value`;
    - `labels`: an object of strings, context (§2.12);
    - `unit`: a string, the member's unit where the resource declares
      none (§2.5);
    - `epoch`: a `telemetry.v1.Epoch`, its in-band epoch (§2.9, 0.1).
  - **`telemetry.v1.Value`:** internally tagged,
    `{"type": <kind>, "value": …}`, one branch per kind of §2.2: an
    integer from 0 for `counter`, a number for `gauge`, a string, a
    boolean, an array of byte values from 0 to 255 for `binary`, and a
    `telemetry.v1.Histogram`.
  - **`telemetry.v1.Histogram`:** `buckets`, `counts`, `count` and `sum`
    (§2.8).
  - **`telemetry.v1.Epoch`:** a string of 1 to 64 characters (0.1).
- **A type is the profile's by its artifact's id.** A type is one of the
  profile's when its kind is `jsonschema`, its name is one of the four,
  and its artifact's id, the hash of the document's JCS bytes (core §7.1,
  §9.4), is one this profile publishes (§3). `[F: schema.json, declarations.json]`
  - A contract that lists a copy of the file, byte for byte or only
    JCS-equal, carries the profile's types: the id is the same.
  - A `telemetry.v1.Point` defined in any other document is not the
    Point, whatever its shape: a type's identity is its kind, its name and
    its artifact (core §7.1). `[F: declarations.json]`
- **Its revisions.** A later text that changes the file publishes the new
  id beside the old ones, and every published id stays the profile's: a
  reader of an old bundle meets an old id (§3). A change inside the file is
  classified as any contract's types are (core §9.8): a contract that
  moves to a new revision republishes, compatible or not as the change
  is. 0.1's revision adds an optional member and a definition, which is
  compatible.

### 2.4 Carriers

A resource's type is what its samples can carry. `[F: declarations.json]`
- **The Point** carries every kind. A Point-typed resource needs no
  `telemetry.kind`: each sample says its own (§2.5).
- **A bare JSON Schema type** carries a kind by its root schema: the
  named definition, its `$ref`s followed as core §9.8 follows them (a
  keyword beside a `$ref` added to its target, an outer one taking the
  place of the target's own). Its `type`, read as a set of names (core
  §7.3), decides:

  | Declared kind | The root's `type` |
  |---|---|
  | `counter` | exactly `integer` |
  | `gauge` | `integer`, `number`, or both |
  | `boolean` | exactly `boolean` |
  | `text` | exactly `string` |
  | `histogram` | none: the type is the profile's `telemetry.v1.Histogram`, by its artifact's id (§2.3) |
  | `binary` | none: no JSON Schema type carries it |

  The root's other keywords (bounds, `enum`) narrow what an owner writes,
  and are the core's to check (core §7.3), never this profile's: a counter
  typed `{"type": "integer", "minimum": 0}`, as zenoh-modem's `Counter`
  is, carries `counter`.
- **A bare `raw` type**, of any media type, carries `binary`, and nothing
  else.
- **Nothing else is a carrier at 1.x:**
  - a JSON object or array other than the profile's Histogram, such as
    tcgui's composite states;
  - a root with no `type`, such as a `oneOf`;
  - a **nullable**, in either spelling of core §7.3: `null` in the `type`
    set, or the nullable form, whose reading adds `null` to it. `null` is
    no value of any kind, and absent is not zero (§2.12), so a type that
    admits it carries none;
  - a protobuf message, wrappers included.

  A declared kind on a type that cannot carry it is an invalid declaration
  (`not_a_carrier`, §2.2). A field-level kind map, a kind per member of a
  composite, is not adopted at this version.
- **The epoch's carrier** (§2.9). A Point carries an in-band epoch in its
  `epoch` member: the Point of every published revision (§3), the
  pre-profile one included, whose file defines no `epoch` but whose Point
  is the Point all the same, a member the schema does not name being one
  every reader tolerates (core §9.8; 0.2). A bare `counter` or `histogram` carries one in its
  attachment, when the resource's attachment type is the profile's
  `telemetry.v1.Epoch`, by its artifact's id. Any other attachment carries
  none, and so does an Epoch attachment on a Point or on another kind.
  `[F: declarations.json]`

### 2.5 A member's kind and unit

- **The kind** is, for each sample, the first of: `[F: samples.json]`
  1. the declared kind;
  2. for a Point, the sample's tag, `value.type`;
  3. otherwise none: the member is not this profile's.

  A declared kind is authoritative: a Point whose tag differs keeps the
  member's kind the declared one, and does not conform (§2.6).
- **The unit** is, for each sample, the first of: `[F: samples.json]`
  1. the declared unit;
  2. for a Point, the sample's `unit`, when it is a unit (§2.2);
  3. otherwise **unknown**. A reader MUST NOT read an unknown unit as
     dimensionless, nor show it as `1`.
- **A label named `unit`** is context, like every label (§2.12). A reader
  MUST NOT read it as the member's unit. `[F: samples.json]`
- **An invalid declaration** leaves both unobservable (§2.2).

### 2.6 A sample's conformance

A reader asks whether one sample of a metric member conforms. It checks
the carrier and what the member's kind requires. Whether a value satisfies
its resource's own schema is the core's question (core §7.3), asked
apart. `[F: samples.json]`

**How a value is read.**
- **The data item.** A sample is read as its decoded data item: strict
  JSON's data model for a JSON resource, CBOR's for a CBOR resource
  (RFC 8949, core §7.2), bytes for a raw one. One value has one reason in
  either encoding.
- **Strict JSON** (0.2). A JSON sample is read as `alarms.v1` §2.4 reads a
  payload, as core §3.3's D000 reads a descriptor: UTF-8, RFC 8259's
  grammar with nothing after the value but whitespace, no duplicate member
  at any depth, every string with a UTF-8 form (so no lone surrogate
  escape), and every number finite. A JSON sample that is not strict JSON
  is `undecodable`. RFC 8259 leaves each of these to the parser, and two
  readers would read two data items. `[F: samples.json]`
  - **Finite** (0.3) is by rounding: a number's text, an integer's
    included, is finite when its exact value, rounded to the nearest double
    (IEEE 754 binary64, round to nearest, ties to even), is not an
    infinity. The edge is a magnitude of 2^1024 − 2^970, the largest double
    (2^1024 − 2^971) and half its last unit: a value there is a tie, which
    rounds to even, 2^1024, an infinity, so its text is undecodable, as is
    any text past it — `1.7976931348623159e308`, `1e400`, 10^400 written
    out. Text below it decodes: `1.7976931348623158e308` rounds to the
    largest double. `[F: samples.json]`
  - **Exact.** An integer's text that decodes is read exactly, however
    long its text (0.2).
- **CBOR** (0.2). An integer is CBOR's major type 0 or 1, or a bignum,
  tag 2 or 3 around a byte string of any length, definite or not, read as
  the integer it denotes (RFC 8949 §3.4.3): a bignum of 2^64 in a counter
  is `out_of_range`, as the JSON text 2^64 is. Every other tag, and a tag
  2 or 3 around anything but a byte string, is read as its content, and a
  map as the envelope's are read (core §5.2): its keys text, none twice,
  and `undefined` is `null`. Anything else does not decode. CBOR also
  carries byte strings and floats that are not finite. A reader of a CBOR
  sample MUST keep a non-finite float as one, never read it as `null` and
  never refuse the sample for it: such a value is `not_finite` here.
  `[F: samples.json]`
- **Depth** (0.3). A data item nests at most 256 arrays and maps deep,
  JSON's objects and CBOR's maps alike: an array or a map at the top is at
  depth 1, and an array or a map inside another is one deeper. A scalar
  adds no depth, and nor does a CBOR tag, which is read as its content. A
  sample with an array or a map at depth 257 is `undecodable`, in JSON as
  in CBOR, so that two readers stop at one place: 256 nested arrays decode,
  257 do not. The bound is this profile's reading of a sample, and no
  other's: core D000, which reads a descriptor, is not changed by it.
  `[F: samples.json]`
- **A member written `null` is present** (0.2). `null` is no string and no
  object, so a Point's `"epoch": null` is `epoch_invalid`, and a `null`
  `unit` or `labels` makes it no Point (check 1). The standard schema says
  the same: its `epoch`, `unit` and `labels` are typed, and `null` fails
  each. Core §5.2's "a `cause` or `detail` that is `null` is absent" is
  the envelope's own rule, not a reading of every payload.
  `[F: samples.json]`
- **An integer is read exactly:** JSON text with no fraction and no
  exponent, CBOR's major types 0 and 1, and CBOR's bignums (tags 2 and 3,
  the CBOR reading above; 0.5). A reader MUST NOT read a counter
  through a double: 2^64−1, `18446744073709551615`, is a counter, and
  2^64 is not. `[F: samples.json]`
- **A float** (JSON text with a fraction or an exponent, a CBOR float) is
  the IEEE 754 double it denotes, the nearest one for JSON text. An
  integral double is the integer it equals, as JSON Schema's `integer`
  and `freshness.v1` §2.1 read it: `5.0` is the counter 5, and
  `18446744073709551615.0` is the double 2^64, out of range.
  `[F: samples.json]`
- **A sample the core could not decode** (bytes that are not its JSON or
  its CBOR, as this section reads them) is unobservable here
  (`undecodable`): the core's verdict stands, and this profile reads
  nothing of it. `undecodable` names the payload alone: an attachment
  that does not decode is read by check 2 (0.2). `[F: samples.json]`

**The checks.** The reasons are a closed list. A reader reports every one
that applies, in this order, each check made alone, and a check that
needs a value an earlier check found wrong skipped: `[F: samples.json]`
1. **`not_a_point`:** a Point carrier whose value is not one: not an
   object; `timestamp` missing, or not an integer from −2^63 to 2^63−1;
   `value` missing, not an object, or without `value`, or its `type` not
   one of the six kinds; `labels` present and not an object of strings;
   `unit` present and not a string, a member written `null` being present
   (0.2). A Point that is not one is checked no further. Members the schema does not name are tolerated, as every
   reader tolerates unknown properties (core §9.8).
2. **`epoch_invalid`:** an in-band epoch present (the Point's `epoch`, or
   the Epoch attachment, §2.4) that is not a string of 1 to 64 characters,
   counted as Unicode code points, as JSON Schema counts them. An Epoch
   attachment is read as this section reads a sample of its encoding:
   strict JSON, or CBOR, depth included (0.3). One whose bytes do not
   decode so is an epoch present and not a string, zero bytes included, and
   so is the JSON text `"\ud800"`, a lone surrogate escape, which is not
   strict JSON (0.3); the sample is still read (0.2).
3. **`unit_invalid`:** a Point's `unit` that is not a unit (§2.2).
4. **`tag_disagrees`:** a Point whose tag differs from the declared kind.
5. **`unit_disagrees`:** a Point whose valid `unit` differs, byte for
   byte, from the declared unit.
6. **`wrong_type`:** the value is not of the type its kind needs. The kind
   is the Point's tag for a Point, the declared kind for a bare value:
   - `counter`: an integer, or an integral float;
   - `gauge`: a number;
   - `boolean`: a boolean; `text`: a string;
   - `binary`: for a Point, an array of integers from 0 to 255; a bare
     raw value is bytes, always;
   - `histogram`: an object whose `buckets` is an array of numbers,
     `counts` an array of integers, `count` an integer and `sum` a
     number.

   A value of the wrong type is checked no further.
7. **`out_of_range`:** a counter, a histogram's `count`, or one of its
   `counts`, outside 0 to 2^64−1.
8. **`not_finite`:** a gauge, a histogram's `sum`, or one of its bounds,
   that is NaN or infinite.
9. **`bounds_invalid`:** a histogram's bounds, all finite, that are empty
   or not strictly ascending, compared as §2.2 compares bounds.
10. **`bounds_differ`:** a histogram's bounds, valid, that differ from the
    declared `telemetry.buckets` by value: another length, or one bound
    another double.
11. **`counts_length`:** `counts` not one longer than `buckets`, checked
    whenever the value is a Histogram (check 6): it needs the two lengths
    alone, whatever checks 8 and 9 found of the bounds (0.2).
12. **`count_sum`:** `count`, and every one of `counts`, in range, and
    `count` not their sum, computed exactly.

**The answer.** `[F: samples.json]`
- **`conforms`:** no reason applies.
- **`does_not`,** with the reasons: the finding.
- **`unobservable`:** the declaration is invalid (`declaration_invalid`),
  or the sample is undecodable (`undecodable`).
- **`not_asked`:** the resource is not a metric resource
  (`not_this_profiles`), or an event or an operation (`ignored`).

A sample that does not conform is not read: it gives no value to a pair
(§2.10) and no unit or kind beyond the declared ones.

### 2.7 Counters

- **The value** is an integer from 0 to 2^64−1, read exactly (§2.6).
- **Within one epoch,** an owner MUST NOT publish a counter value below
  one it published before for that member. `[Sc: §3]` A reader that finds
  one within an established epoch reports the pair `decreased`, the
  finding (§2.10).
- **A fixed-width counter is widened by its producer.** An owner that
  reads a counter narrower than 64 bits (SNMP's Counter32, a driver's
  32-bit statistic) SHOULD publish it widened to 64 bits, adding 2^w at
  each wrap it sees between two of its reads. It is the only party that
  sees every read; a reader sees what crosses, which may be downsampled
  (`link.v1` §2.8).
- **A wrap reads as a reset.** A wrap published unwidened is a decrease:
  a reset where the epoch is unobservable, and the finding within an
  established one (§2.10).
- **A count only.** A counter carries no rate. A reader derives one from a
  pair (§2.11), and a producer that publishes one publishes a gauge
  (§2.13).

### 2.8 Histograms

- **The shape** is fixed buckets, as RFC 11 §4 had it (informative):
  - **`buckets`:** the bounds, as the declared `telemetry.buckets` gives
    them, equal by value (§2.2), `+Inf` implicit;
  - **`counts`:** a count per bucket, **not cumulative**, one more than
    the bounds, the overflow last. Bucket `i` holds the observations in
    `(buckets[i-1], buckets[i]]`, upper-inclusive: the first
    `(-Inf, buckets[0]]`, the last `(buckets[n-1], +Inf)`;
  - **`count`:** the sum of `counts`;
  - **`sum`:** the sum of every value observed, which may be negative.
- **Cumulative within one epoch.** An owner MUST NOT publish a `count`,
  or a bucket's count, below one it published before for that member in
  the same epoch. `sum` may decrease, since an observation may be
  negative. `[Sc: §5]` `[F: continuity.json]`
- **A pair** of a histogram is judged as a counter's (§2.10), on `count`
  and on each bucket's count.
- **The reader's, not the owner's:** quantiles, a window's delta, a rate
  per bucket. This text gives no rule for them.
- **A Point without a declared kind** may carry a histogram: its bounds
  are then checked for validity (§2.6), and compared with no declaration.

### 2.9 The epoch

The epoch says whether two samples of a member can be compared: within
one, a counter or a histogram never decreases; across two, it may start
again. A reader takes it from the first of these that answers, for each
pair (§2.10). `[F: continuity.json]`

1. **In-band.** Both samples carry an in-band epoch: the Point's `epoch`,
   or the Epoch attachment of a bare counter or histogram (§2.4). Each is
   an opaque string, compared for equality.
   - Equal: the same epoch, established. Different: a different epoch,
     established.
   - **The owner's obligation.** An owner that writes an in-band epoch on
     a member MUST change it whenever a counter or histogram it carries
     on that member restarts. `[Sc: §1, §2, §7]`
   - It SHOULD use its instance id (core §1.5), or, on a template that
     declares `epoch` (core §2.2), that member's epoch, the one its member
     token carries (core §8.1). Core §1.5 already makes an owner mint a
     new instance id whenever its counters reset, so the instance id
     changes when the counter restarts, and presence agrees with it.
   - It SHOULD write it on every sample of the member: a pair with one
     sample lacking it has no in-band evidence.
2. **Presence.** Otherwise, what the reader observed of the owning
   service's instance tokens (core §8.1), or, for a member of a template
   that declares `epoch`, of that member's tokens, whose epoch is the one
   that counts. A reader's view of them stands on a complete read of the
   tokens (core §8.1, which a subscription's history alone is not), and on
   nothing lost since it; and it folds the tokens' moves and the samples in
   the one order it received them, so that what it saw between two
   arrivals is what it saw (0.3):
   - **The same epoch, established:** it observed one instance, or one
     member epoch, alone and without a loss on its presence view, from
     before the earlier sample's arrival to after the later one's.
   - **A different epoch, established:** the only instance present at the
     earlier sample's arrival differs from the only one present at the
     later's, with no loss on the presence view between them (0.3).
3. **Otherwise, unobservable.** Two instances present at once (a
   make-before-break overlap, core §8.1), a loss on the presence view
   between the two arrivals, a view that stands on no complete read, or no
   presence at all (across a face, §2.14) establish nothing: a loss
   between them establishes neither the same epoch nor a different one,
   whatever the view showed at each arrival (0.3).
   `continuity.json`'s `presence` is what a reader saw, and a reader that
   lost something between the two arrivals gives none.

**The residual risk.** A sample in transit across a re-mint can arrive
after the old instance's tokens are gone, and read as the new instance's
(core §4.3 accepts the same risk for state). A reader that judged by
presence then compares an old epoch's value with a new one's. An owner
that writes an in-band epoch closes the risk. A tool reporting a decrease
it judged by presence says so (§5).

### 2.10 The continuity of a pair

A **pair** is two conforming samples (§2.6) of one member, in the order
the reader received them for a stream. For state, it is in the order a
late joiner's merge keeps them (core §4.2): a reader that seeds by a GET
and a subscription receives a member's samples by two paths, so receipt is
not the owner's order, and a sample the merge does not keep (a GET's reply
older than a live put already held) is no sample of any pair (0.2).
`[Sc: §9]` A **decrease** is a later counter below the
earlier one, or a later histogram with its `count`, or any bucket's
count, below the earlier one's.

The answer is the first of these that holds: `[F: continuity.json]`
1. **`not_asked`:** neither sample is a counter or a histogram (`kind`).
2. **`unobservable`:** the two samples' kinds differ (an undeclared
   Point's tags), or two histograms' bounds differ by value, or their
   `counts` differ in length (`incomparable`).
3. **The epoch is established (§2.9):**
   - the same epoch, and a decrease: **`decreased`**, the finding;
   - the same epoch, and none: **`same_epoch`**;
   - a different epoch: **`reset`**, whatever the values.
4. **The epoch is unobservable,** so it is assumed:
   - a decrease: **`reset`**. A reader MUST read a decrease it cannot
     place in one epoch as a reset: never a negative count, a negative
     rate or a finding. `[F: continuity.json]` `[Sc: §8]`
   - none: **`same_epoch`**.

The answer says whether the epoch was **established** or **assumed**. A
tool MUST NOT report a decrease as a finding unless the same epoch was
established. `[F: continuity.json]`

### 2.11 The rate of a pair

- **Only over one epoch.** A reader derives a rate from a pair of counter
  samples whose continuity is `same_epoch`, established or assumed.
  `[F: continuity.json]` There is no rate across a reset or a decrease,
  none of a histogram at this version, and none of an incomparable pair,
  which is never of two counters (`kind`, §5; 0.2): a reader MUST NOT
  derive one there, never restarting from zero. `[F: continuity.json]`
  `[Sc: §1, §2]`
- **The time base** is the first that both samples have:
  1. the Point's `timestamp`, the measurement time;
  2. for state, the owner's stamp (core §4.1, S2);
  3. the receipt time, on the reader's monotonic clock.
- **The elapsed time** `e` is the later time minus the earlier, an integer
  of nanoseconds: a Point's milliseconds times 10^6, a receipt in the
  reader's nanoseconds, and a stamp's time in nanoseconds as zenoh reads
  it (0.2): its NTP64 seconds, the high 32 bits, times 10^9, plus its
  32-bit fraction times 10^9 divided by 2^32 and rounded up (uhlc's
  `NTP64::as_nanos`, which zenoh-python wraps). Each stamp is converted
  alone: `e` is the later stamp's nanoseconds less the earlier's, never the
  converted difference of the two raw values, which differs from it by a
  nanosecond about half the time. There is no rate when `e` is 0 or less
  (`elapsed`). `[F: continuity.json]`
- **The value.** With `d` the later counter minus the earlier, an exact
  integer from 0 to 2^64−1, the rate is, in IEEE 754 binary64 arithmetic
  rounding to nearest, ties to even:

  ```text
  rate = double(d) / (double(e) / 1e9)
  ```

  where `double(n)` is the double nearest the integer `n`. Two readers
  that follow it agree bit for bit. `[F: continuity.json]`
- **The rate's unit** is the counter's unit (§2.5) followed by `/s`, or
  none when the counter's unit is unknown: `By` reads `By/s`.
  `[F: continuity.json]`

### 2.12 Time, labels and absence

- **The Point's `timestamp` is the measurement time,** when the owner took
  the value, never when it published it. It times a rate (§2.11). It does
  not age a sample: a subscriber ages a sample by its receipt
  (`freshness.v1` §2.5), and the timestamp is the owner's clock, on no
  stated agreement with the reader's.
- **Labels are context, never identity.** The series is the key: two
  samples of one member with other labels are one series, and a label
  never names another. An OID, an interface's description, an unslugged
  path are labels; a unit is not one (§2.5).
- **Absent is not zero.** A reader MUST NOT read a sample that did not
  arrive, or a member with no sample, as 0: not in a display, a sum, a
  rate or a comparison. It is unknown. `[Sc: §6]`

### 2.13 Rates a producer publishes

- **A gauge with a rate unit.** A producer that publishes a rate it
  derived publishes a `gauge`, with a unit such as `By/s` or `1/s`, never
  a `counter`.
- **No suffix means anything.** A template ending `.rate`,
  `_per_second` or `_total` says nothing to a reader: the kind and the
  unit do. The profile names no suffix, and infers no unit from one.

### 2.14 Constrained faces

- **Presence does not cross** a constrained face: `@zk` is denied there
  (core §8.5, `link.v1` §2.6), so a reader across one has no presence
  evidence of an epoch (§2.9).
- **A counter or a histogram that crosses SHOULD carry its epoch
  in-band** (§2.9), as core §1.5 asks of every counter that crosses.
  `link.v1` §2.13 states the face's side of this rule, and cites this
  section for the counter and its epoch.
- **Without one, a decrease reads as a reset** (§2.10): never a finding,
  never a negative rate. A reader across the face cannot tell a reset
  from an owner's fault. `[Sc: §8]`
- **What it costs.** An instance id, 16 hex digits, adds 27 bytes to a
  JSON Point (`,"epoch":"…"`), and an 18-byte JSON attachment to a bare
  value. A deployment counts it on its face's budget.

### 2.15 Device-as-service and proxied devices

- **The device's restart is a new instance** (core §1.5). A service that
  stands for a device mints a new instance id when the device's counters
  reset: a polled device's uptime rewinding (SNMP's `sysUpTime`), a
  netdev re-enumerated, a container restarted. An in-band epoch changes
  with it (§2.9).
- **A member of a template that declares `epoch`** cycles its member
  token when its own counters reset (core §8.1), and that member's epoch
  is the one presence reads (§2.9).
- **The proxy decides.** The process that polls a device is the only one
  that can see its restart. A poller that cannot tell whether one
  happened between two reads (a missed poll across a reboot) SHOULD start
  a new epoch: a reset a reader reads is safe, and a decrease within one
  epoch is a finding.

## 5. What a tool may conclude

"Not asked" (nobody put the question, or its premise does not hold) and
"unobservable" (it was put, and the observation could not answer it) are
different facts, and neither is a "no" (core O5). The fixtures state the
tokens: [`declarations.json`](conformance/declarations.json),
[`samples.json`](conformance/samples.json) and
[`continuity.json`](conformance/continuity.json).

| Question | Yes | No | Unestablished | Finding on |
|---|---|---|---|---|
| Is this resource's declaration valid? (§2.2, §2.4) | `declared`: every value valid, the kind carried by the type; with the kind (or none, for a Point), the unit, the buckets, the semantic, the carrier and where an in-band epoch rides. | `invalid`, with its reasons: `kind_value`, `unit_value`, `buckets_value`, `semantic_value`, `kind_missing`, `buckets_without_histogram`, `histogram_without_buckets`, `not_a_carrier`. | **Not this profile's:** a stream or state with no key of the vocabulary and not the Point (`not_this_profiles`); an event or an operation (`ignored` when it writes a key, else `not_this_profiles`). | No, for a contract linter: a warning, no core code. |
| What is this member's kind, and its unit? (§2.5) | The declared kind, else the conforming Point's tag; the declared unit, else the Point's, else **unknown**, never dimensionless. | Never. | **Unobservable:** the declaration invalid; no declared kind, and the sample undecodable or not a Point. **Not this profile's:** as above. | Neither: informative. |
| Does this sample conform? (§2.6) | `conforms`. | `does_not`, with its reasons: `not_a_point`, `epoch_invalid`, `unit_invalid`, `tag_disagrees`, `unit_disagrees`, `wrong_type`, `out_of_range`, `not_finite`, `bounds_invalid`, `bounds_differ`, `counts_length`, `count_sum`. | **Unobservable:** `declaration_invalid`, `undecodable`. **Not asked:** `not_this_profiles`, `ignored`. | No. |
| Did this counter or histogram go backwards within one epoch? (§2.10) | `decreased`: a decrease within an established epoch. A tool says how the epoch was established, in-band or by presence (§2.9's residual risk). | `same_epoch` (no decrease, the epoch established or assumed), or `reset` (another epoch established, or a decrease read as a reset where the epoch is unobservable). | **Unobservable:** `incomparable`. **Not asked:** not a counter or a histogram (`kind`). | Yes: `decreased`. A `reset` is informative. |
| What is this counter's rate over the pair? (§2.11) | A rate, and its unit, or none when the counter's unit is unknown. | None, with why: `reset`, `decreased`, `elapsed`. | **Not asked:** not of two counters (`kind`), an incomparable pair included (0.2). | Neither: informative. |

**Which cause** a decrease has (a restart the owner did not mark, a wrap
it did not widen, a sample in transit across a re-mint) is unobservable
from the values alone. The epoch's evidence says how much a tool may
claim.

**Over many pairs** (0.3, 0.4). A pair whose epoch was assumed answers
`same_epoch` or `reset`, and never `decreased`: a no that has no evidence
behind it. A tool asked "did anything go backwards?" over pairs of
counters or histograms whose every epoch was assumed, or that formed no
pair of a counter or histogram it read, SHOULD say it could not tell,
never that nothing went backwards: no decrease could have been found.
- **Each counter or histogram read is asked** (0.4). One that formed no
  pair (one sample of it in the window, or none that conforms), or only
  pairs whose epoch was assumed, could not tell, whatever another formed:
  a pair established in-band of one says nothing of another. A tool says
  so for each.
- **A finding still stands.** A decrease within an established epoch, or a
  sample that does not conform, is the yes whatever could not be told.

**Over many samples** (0.5). A sample that does not decode as §2.6 reads
bytes is `undecodable`, and one of a member whose declaration is invalid
is `declaration_invalid` (§2.2): each is a question put that the
observation could not answer, never a sample that conforms. A tool asked
"did every sample conform?" over a window SHOULD say it could not tell
when any sample in it was undecodable, or any member it read had an
invalid declaration, never that every sample conformed.
- **Every question of such a member** is unanswered: an invalid
  declaration leaves its kind, its samples' conformance and its continuity
  unobservable (§2.2). The declaration's own answer, `invalid`, is a
  linter's warning, never a finding.
- **A finding still stands** beside it, as over many pairs.
- **Only what was read counts.** A resource none of whose members was
  heard in the window leaves no question of a sample unanswered, whatever
  its declaration says.

**The reference tool,** `zenctl telemetry`, exits 1 on a finding; 2, the
no verdict, when any counter or histogram it read could not tell (0.4) or
any sample's conformance was unobservable (0.5); and 0 only when every
question it asked was answered. Its reason names the first member that
could not tell: a narrower selector asks the rest.

## Appendix A. Against v1

v1 stated metrics in RFC 08 §2 (the registry's `kind`, `unit`, `buckets`
and `semantic` columns), RFC 11 §4 (ZenSight's `TelemetryValue` and its
histogram shape) and RFC 13 §3 (the observer's kind judge), on the `v1`
branch.

**What changed.**

| v1 | `telemetry.v1` | Why |
|---|---|---|
| `kind` = `counter`, `gauge`, `text`, `bool`, `histogram` (RFC 08 §2) | Six kinds, `binary` added, `bool` spelled `boolean` on the annotation as on the wire (§2.2) | One spelling: RFC 11 §4 already mapped `bool` to the tag `boolean`. ZenSight's `TelemetryValue` carries bytes. |
| The reset: the origin's `alive` token, or a device's, cycling (RFC 08 §2, v1.39) | The epoch: in-band first, then the instance's or member's presence, else assumed (§2.9) | Presence does not cross a constrained face (§2.14), and an in-band epoch closes the residual risk of a re-mint. |
| A decrease with no `alive` cycle is *established(no)* (RFC 13 §3) | `decreased` only within an established epoch; without evidence, a decrease is a reset (§2.10) | Silence is never a verdict (RFC 13 §2): an epoch nobody observed is not the same epoch. |
| The payload shape is the application profile's (RFC 08 §2) | The Point is the profile's standard schema, known by its artifact's id (§2.3) | A tool reads any application's Point without its source (core §7.1). |
| `unit`: the leaf's unit; numeric leaves carry it as a suffix too (RFC 08 §4) | The annotation, else the Point's; byte for byte; no suffix read (§2.5, §2.13) | A suffix is a convention no reader can check. |
| Histogram bounds compared bit for bit (RFC 11 §4) | Compared by value, as doubles (§2.2) | The canonical form writes `1.0` as `1` (core §9.5), so bits are not what a bundle keeps. |
| The kind judge per origin, over a window (RFC 13 §3) | Per member, per pair, with the epoch's evidence named (§2.10, §5) | The key is the series (§2.12). |

**What deliberately did not change.**
- **The histogram's shape:** per-bucket counts, one more than the bounds,
  the overflow last, `count` their sum, cumulative within an epoch
  (RFC 11 §4).
- **`buckets` iff `histogram`,** strictly ascending, finite, `+Inf`
  implicit (RFC 08 §2).
- **The tag agrees with the declared kind** (RFC 08 §2): a disagreeing
  Point does not conform.
- **`semantic`'s closed eight,** a presentation hint no judge reads.
- **Absent unit means unknown,** never dimensionless.

**What is not ported.**
- **Export naming:** Prometheus's `_total` and unit suffixes, OTLP
  instrument names. An exporter's, and dark in the tools.
- **Units inferred from suffixes** (`usage_percent`, `_bytes`, RFC 08 §4).
- **The historian's aggregation:** rollups, downsampling, retention.
- **The window of a published quantile gauge** (parallax's p95): what
  window a producer's quantile covers is its own documentation.

**The record.** Architecture D9(c) and `link.v1` §2.13 waited for
"telemetry.v1's counter type has `epoch`": it is the Point's `epoch` and
the Epoch attachment (§2.9). Architecture §4.9 imagined the Point as "a
protobuf oneof"; ZenSight's wire is the JSON Schema Point (G13), which
this profile adopts.
