# `alarms.v1`: the active alarms of one service

| | |
|---|---|
| **Text version** | 0.5 ([`CHANGELOG.md`](CHANGELOG.md)) |
| **Status** | draft |
| **Written against** | core 0.34 ([`../../core.md`](../../core.md)) |
| **Uses** | [`freshness.v1`](../freshness/v1.md), text 0.3 |
| **Evidence** | [`conformance/`](conformance/), [`scenarios.md`](scenarios.md) |

`alarms.v1` lets a service say which of its alarms fire, one key per
alarm, and lets a reader tell a firing alarm apart from a resolved one,
from one its owner no longer confirms, and from one whose owner is gone.
Its standard contract, [`alarms.v1.toml`](alarms.v1.toml), gives a service
one resource:

```text
zk2/<system>/<service>/alarms.v1/state/alarms/{alert_key}   up to 256 Alarms, keyed from their own documents, confirmed at least every 450 s while firing
```

An alarm is state (core §2.1): its key is its identity from its raise to
its resolve, and what fires now is one selector,
`zk2/*/*/alarms.v1/state/alarms/*`. The resource declares
`freshness.ttl_s = 900`, so the contract uses
[`freshness.v1`](../freshness/v1.md), and so does every instance that
implements it (core §3.3). This text says how the key is derived, what
the document says, how an alarm lives and ends, and what a reader may
conclude.

---

## 0. Conventions

The keywords, the roles and the evidence tags are core §0's. Here,
`[F: <file>]` names a fixture in [`conformance/`](conformance/),
`[Sc: §n]` a section of [`scenarios.md`](scenarios.md), and `core` marks
the core's own evidence. References to `docs/zk2/architecture.md` (D23,
§3.12, §4.7, §4.9) and to v1's RFC 04 §1.2 and RFC 11 §3 are informative:
every rule is stated here.

Terms:
- **Owner** is core §0's. The owner of a service's `alarms.v1` keys is
  that service (core §6).
- **Alarm:** a member of `state/alarms/{alert_key}`. Its **document** is
  an `alarms.v1.Alarm` (§2.4), and its **alert key** the value of
  `{alert_key}` (§2.2).
- **Rule** and **labels:** the document's `rule` and `labels`. A
  **host-scoped** label is named `host`, or has a name starting with
  `host.` (§2.2). Every other label is **discriminating**.
- **Firing** and **resolved:** the document's `state`.
- **Transition:** a raise, an escalation or a resolve (§2.5). A refresh
  and a confirmation are not transitions.
- **Reader, subscriber, GET reader** are `freshness.v1`'s (its §0). A
  **tool** is core §0's.
- **Reading:** what one reader observed of one alarm key at one instant:
  its owner's presence and descriptor, the key's observations, and the
  latest sample by the owner's stamp, a subscription and a GET merged as
  core §4.2 says.

## 2. Rules

### 2.1 Who implements it

- **A service that raises alarms** implements `alarms.v1`, and puts its
  own alarms, no other service's (core §6). An alarm about a device that a
  parent serves as a service is that service's (§2.10).
- **With nothing firing,** it still implements it: its template is exposed
  with no member (core §8.2), and its descriptor lists it.
- **A framework set** puts it on every service, beside `health.v1`, as
  ZenSight's does (Appendix B).

### 2.2 The key

- **The recipe.** An owner MUST key each alarm by the alert key derived
  from its document as follows, and a reader that derives one MUST derive
  it the same way. `[F: keys.json]`
  1. **Host-scoped labels are removed,** before anything else: the label
     named `host`, and every label whose name starts with `host.`. The
     comparison is exact, without trimming or case folding: `hostname`,
     `Host` and `hosts.x` are discriminating.
  2. **The input** is the rule, followed, for each discriminating label,
     by a newline (0x0a), its name, `=` (0x3d) and its value. The labels
     are sorted ascending by name, then by value, each compared as UTF-8
     bytes (memcmp).
  3. **The hash** is FNV-1a over the input's UTF-8 bytes, 64 bits: offset
     basis `0xcbf29ce484222325`, prime `0x100000001b3`; for each byte, the
     hash is XORed with it, then multiplied by the prime modulo 2^64.
  4. **The alert key** is the hash written as 16 lowercase hexadecimal
     digits, zero-padded.
- **The test vector.** Rule `link_down`, labels `{peer: r2, port: eth0,
  host: h-3fa9c2d41b7e}`: `host` drops out, `peer` sorts before `port`,
  and the input is `link_down\npeer=r2\nport=eth0`, 27 bytes
  (`6c696e6b5f646f776e 0a 706565723d7232 0a 706f72743d65746830`). Its alert
  key is `a659f813308ad1da`. Put by `netlink` on `h-3fa9c2d41b7e`, its key
  is `zk2/h-3fa9c2d41b7e/netlink/alarms.v1/state/alarms/a659f813308ad1da`.
  `[F: keys.json]`
- **What is never hashed.** The system and the service are in the key
  (core §1.1), so the same alarm on two hosts has one alert key under two
  systems. Host-scoped labels are removed for the same reason (D23): they
  name the host, or its boot, which the system already scopes, and a
  change of one is a refresh, never another alarm (§2.5).
- **Why the value orders too.** The labels are a JSON object, whose names
  are distinct, since a payload is strict JSON (§2.4), but two names can
  sanitize to one (§2.3), and their values then order them.
- **The chunk.** An alert key is a plain chunk, so it is its own slug
  (core §1.4).

### 2.3 The framing, and the sanitizing step

- **Framed input.** The input is injective when the rule is not empty and
  holds no newline, no discriminating label's name is empty or holds a
  newline or `=`, and no discriminating label's value holds a newline. An
  owner SHOULD put only documents whose input is framed.
  `[F: keys.json, documents.json]`
- **Unframed input is sanitized, never refused.** A reader derives every
  key through this step, and so does an owner that puts an unframed
  document: `[F: keys.json]`
  1. host-scoped labels are removed, as §2.2's step 1;
  2. in the rule and in each value, each newline becomes `_`;
  3. in each name, each newline and each `=` becomes `_`;
  4. an empty rule becomes `unnamed`, and an empty name `_`;
  5. then §2.2's steps 2 to 4.
- **The step changes nothing in framed input,** so a reader applies it to
  every document and reaches the owner's key either way. A host-scoped
  label is removed before it, so nothing in one breaks the framing.
- **It is not injective.** `link\ndown` and `link_down` share an alert
  key, and so do the empty rule and `unnamed`: the reason for the SHOULD.
  A firing alarm and its resolve still share one, which is what a key must
  keep. ZenSight's derivation is this step (Appendix B).
- A tool MAY report a document that needs it (§5, the third question).

### 2.4 The document

The document is the 1.0 schema's `alarms.v1.Alarm` (§3), a JSON object.
`[F: documents.json]`
- **`timestamp`**, required: when the alarm's latest transition happened
  (§2.5), in milliseconds since the Unix epoch, on the owner's clock.
- **`observed_at_ms`**, on a refresh only (§2.5): when the owner last
  re-observed the firing alarm whose content it refreshed, on the same
  clock, and never earlier than `timestamp`. Absent reads "not
  refreshed", never "not observed".
- **`rule`**, required: the stable name of what raised the alarm, and the
  recipe's first input. A rule renamed re-keys every alarm it raises
  (§2.9).
- **`severity`**, required: `info`, `warning` or `critical`, in that
  order. A severity is **at or above** another when it is the same, or
  comes later.
- **`state`**, required: `firing` or `resolved` (§2.6).
- **`summary`**, required: one line for a person. A reading that changes
  while the condition holds belongs here, never in a label.
- **`category`**, optional: free text naming what produced the alarm
  (ZenSight's `anomaly`, `expectation`, `sensor_health`). It is not hashed,
  and no rule here interprets it: a tool shows it, and MAY filter by it.
- **`labels`**, optional: an object of strings. Every discriminating label
  is identity, in the key (§2.2), so a value that changes while the
  condition holds makes another alarm at each change.
  - A name SHOULD be one or more segments `[a-z][a-z0-9_]*` joined by `.`:
    `peer`, `if_index`, `host.boot_id`.
  - A value SHOULD be written in one canonical form, as core §1.4 asks of
    a value it slugs (an IPv6 address in RFC 5952 form), so that one
    condition has one key.
- **The owner's document.** An owner MUST put documents that satisfy the
  schema, as strict JSON (below), with both times from 0 to 2^53−1,
  `observed_at_ms` not earlier than `timestamp`, and no `observed_at_ms`
  on a resolved document. `[F: documents.json]`
- **Strict JSON first** (0.2). A reader reads a payload's bytes as core
  §3.3's D000 reads a descriptor: UTF-8, JSON (RFC 8259) with nothing
  after its value but whitespace, no duplicate member at any depth, every
  number finite, and every string with a UTF-8 form, so no lone surrogate
  escape. A payload that is not strict JSON is undecodable. Otherwise one
  put could read at two severities, or derive two keys, as two parsers
  keep the first or the last of a duplicate member, and a string with no
  UTF-8 form has no input bytes for the recipe (§2.2).
  `[F: documents.json]`
  - **Whitespace** (0.3) is RFC 8259's `ws`, before the value and after
    it: space, horizontal tab, line feed and carriage return, so a
    trailing newline reads. Any other character after the value, a form
    feed or a no-break space included, is text after it.
    `[F: documents.json]`
- **The reader's.** A reader MUST read a payload outside the schema, or
  with a time out of that range, as undecodable: never at a severity or in
  a state it guesses (§2.14). It reads an integral number as an integer
  (`1000.0` is `1000`), as JSON Schema 2020-12 does, and ignores members
  the schema does not name, which a later minor may add. A document that
  breaks the rules of `observed_at_ms` is read as written, and a tool MAY
  report it as malformed. `[F: documents.json]`

### 2.5 The lifecycle

An owner raises, escalates, refreshes, confirms and resolves each alarm
by putting its whole document on its one key.

| Act | When | `state` | `timestamp` | `observed_at_ms` |
|---|---|---|---|---|
| raise | the condition is found | `firing` | new | absent |
| escalate | the severity changes, either way | `firing` | new | absent |
| refresh | the content of a firing alarm changes at one severity: its summary, its category, a host-scoped label | `firing` | kept | the instant of the re-observation |
| confirm | neither, within 450 s (§2.7) | as held | kept | as held |
| resolve | the condition no longer holds | `resolved` | new | absent |

- **Its MUSTs.** An owner MUST put each act as the table says: a new
  `timestamp` at each transition, the one it holds on a refresh and a
  confirmation. `[Sc: §1–§4]`
  - **New** is later than the `timestamp` of the transition before it on
    that key, as far as the owner knows of one: its clock's instant, or
    the previous one plus 1 where its clock has not passed it.
  - **Why it moves only at a transition.** A transition is what a reader
    acts on, and an acknowledgement is keyed by it: ZenSight's applies
    while the alarm's `timestamp` is at most the acknowledged one
    (Appendix B). A refresh that moved it would undo the acknowledgement,
    and an escalation should.
  - A discriminating label cannot change: a document with another one is
    another alarm (§2.2).
- **A resolve is a put, then a delete.** After its resolved put, the owner
  MUST delete the key (core S3) within its tombstone window, and SHOULD at
  once. It MUST NOT delete a firing alarm without first putting it
  resolved, except a key it retires at a restart (§2.9). `[Sc: §3]`
- **A re-raise** is a raise of an alarm resolved before: a put, firing,
  with a new `timestamp` (above). `[Sc: §4]`
- **A duplicate observation** (0.2): the condition found again, at the
  severity and with the content held, is no act. The owner puts nothing,
  or the same document, which confirms it (§2.7). `[Sc: §1]`
- **What a resolve says.** An owner resolves an alarm when the condition
  it raised it for no longer holds, or when it will evaluate it no more
  while it runs: its rule removed from its configuration, or its target.
  Nothing else is a resolve: a restart and a close are §2.9's.

### 2.6 Reading transitions

- **The state is the document's.** A reader MUST read an alarm's state
  from its document's `state`, never from the sample's kind: a put of a
  resolved document is a resolve. A delete, or a `reply_del`, of an alarm
  it held firing reads as resolved too. `[F: transitions.json]`
- **In the owner's order.** A reader reads a key's samples in the order of
  the owner's stamps, a subscription and a GET merged as core §4.2 says,
  each against the document it held before it: `[F: transitions.json]`

  | Held \ sample | put, firing | put, resolved | delete |
  |---|---|---|---|
  | nothing | raised | resolved | retired |
  | firing | **escalated** if the severity differs; else **raised** if the `timestamp` does; else **confirmed** if the document is equal; else **refreshed** | resolved | resolved |
  | resolved | raised | **resolved** if the `timestamp` differs; else **confirmed** if the document is equal; else **refreshed** | retired |

  - **Equal** is equal in every member this text names (§2.4). `labels`
    absent is equal to `labels: {}`: neither has a label, and both derive
    one key. Any other member absent is equal only to itself absent, so
    `category: ""` is not an absent `category` (0.2).
  - **A put that does not read** (§2.4) is **unreadable**, and the reader
    holds nothing after it.
- **A late reader** reads its first put of a key as raised or resolved.
  The document's `timestamp` says when that transition happened.

### 2.7 Freshness

- **By `freshness.v1`, at 900 s.** An alarm's freshness is
  `freshness.v1`'s: how a subscriber and a GET reader age it (its §2.5 to
  §2.7), archives (§2.8), constrained faces (§2.9), a clock ahead
  (§2.10). A reader MUST judge it as `freshness.v1` does, at the
  contract's horizon. `[F: conclusions.json]`
- **Confirmed every 450 s.** An owner MUST put each firing alarm whose
  condition it evaluates at least every 450 s: a transition or a refresh
  does, and when neither happened the owner re-puts the document unchanged
  (`freshness.v1` §2.4). `[Sc: §2]`
- **Only while it still evaluates it.** A confirmation says the owner
  still sees the condition (`freshness.v1` §2.4, "only a value it holds
  current"). An owner MUST NOT confirm an alarm whose condition it has
  stopped evaluating, its evaluator stuck or its source gone: it lets the
  alarm go stale, or resolves it (§2.5). An evaluation that finds the
  condition again confirms it again (0.2). `[Sc: §6]`
- **A resolved alarm** is never confirmed: it is deleted within the
  tombstone window, 60 s by default (§2.5, core S3).
- **Stale is not resolved, and not firing now.** A firing alarm its
  present owner has not confirmed within 900 s is stale: the owner hung,
  its writer closed, or its clock ahead (`freshness.v1` §2.10). A reader
  MUST NOT report it as firing now, nor as resolved, and a tool reports it
  as a finding about the owner (§5). `[F: conclusions.json]` `[Sc: §6]`
- **An absent owner's alarms are last-known.** With its tokens gone, its
  alarms are presence's word and an archive's last-known (core S6), never
  firing now (§2.14). `[F: conclusions.json]` `[Sc: §8]`
- **The cost** is at most one put per firing alarm every 450 s: 256 alarms
  firing put one every 1.8 s.

### 2.8 The bound

- **256, or the descriptor's.** An owner holds at most 256 alarms, the
  contract's cardinality, which its descriptor MAY lower (core §3.3,
  §2.7). A resolved alarm counts until its delete.
- **At the bound,** the owner refuses the raise that would add an alarm,
  as core §2.7 says, and its writer is told. It MUST NOT resolve or delete
  a firing alarm to make room: a resolve says the condition cleared
  (§2.5). `[Sc: §7]`
- It SHOULD report the refusal where a reader looks: a `health.v1` check
  at `DEGRADED`, or a fault (`health.v1` §2.3).

### 2.9 A restart, and a clean close

- **A new instance puts again what it keeps.** An owner whose instance
  changes, by a restart or a re-mint (core §1.5, §8.1), MUST put each
  alarm it keeps again from its new instance, unchanged, before it answers
  a GET with it, and SHOULD before its new instance token (core §8.2).
  Its GET answers then carry its own stamps (core S2), and a reader does
  not read the alarm as an earlier instance's (§2.14). `[Sc: §5]`
  - **How "before its token" is observed** (0.5). As core §8.2 observes
    it: a GET made when the new instance token appears finds each alarm
    under the new instance's stamp, and a `reply_del` for each key the
    restart deleted. A subscriber that hears the put and the token hears
    two messages on two subscriptions, with no order kept between them,
    so the order it receives them in is not the owner's.
- **A restart adopts.** Before its first put, an owner takes the alarms
  its previous instance held from its own persistent record, else from an
  explicit read of an archive on its own side, last-known: the sources
  core §4.3's catch-up names. A GET to its own keys reaches nothing: its
  previous process answered them, and no storage may (core S4). For each
  document it finds, in this order: `[Sc: §5]`
  1. **resolved:** its delete was lost. The owner deletes the key;
  2. **undecodable, or its key does not re-derive from it** (§2.2, §2.3):
     a phantom of another derivation, or of a renamed rule. The owner
     deletes the key, which reads as resolved to whoever held it firing
     (§2.6);
  3. **firing, under a rule it no longer evaluates:** the owner resolves
     it (§2.5);
  4. **firing otherwise:** the owner adopts it, its `timestamp` kept, puts
     it again (above), and resolves it at its first evaluation that finds
     the condition clear.
- **The work's order** (0.2). The steps decide what each document gets;
  the owner deletes and resolves before it adopts, so that a key it
  retires takes none of the bound's room (§2.8). If it finds more firing
  alarms to adopt than its bound, it adopts up to the bound, and neither
  resolves nor deletes the rest: a resolve would say their condition
  cleared, and §2.5 forbids the delete. A reader that held one reads it as
  the previous instance's last word (§2.14), stale within 900 s.
- **What the record holds** (0.2). An owner's record SHOULD hold each
  alarm's latest document as put, by the key it was put on, a resolved
  one included until its delete. A process that ends between a resolve's
  put and its delete then finds the alarm resolved at its restart, and
  deletes it (step 1). A record that still held it firing would have the
  restart put it firing after its resolve, which a reader reads as a raise
  under an old `timestamp` (§2.6).
- **A re-mint that keeps its session** keeps its zid (core §1.5 asks a new
  session, a SHOULD). The owner still puts each alarm again, as above, but
  a reader cannot tell its instances apart by the stamp (§2.14, step 5).
- **With no source,** the owner starts a new epoch (core §4.3) and adopts
  nothing. A reader that held one of its previous instance's alarms reads
  it as that instance's last word (§2.14), and the alarm goes stale within
  900 s.
- **A clean close leaves them.** An owner SHOULD NOT resolve or delete an
  alarm because it closes. Its tokens going are presence's word (core
  §8.1), its alarms then read last-known (§2.7), and its next instance
  adopts them with their timestamps. A service removed for good, which
  will evaluate none of its rules again, MAY resolve its alarms before it
  closes (§2.5). `[Sc: §8]`
  - **Why not resolve them.** A close is not the condition clearing, and
    a resolve and a raise across every restart would notify twice and
    undo every acknowledgement (§2.5). v1 resolved them because a storage
    served an abandoned firing document as current for ever. zk2 refuses
    such a storage (core S4), and an archive's answer is never current
    (core S6).

### 2.10 Device-as-service

- **Each device service puts its own.** A device that a parent serves as a
  service (core §1.5), such as ZenSight's `snmp.router01`, implements
  `alarms.v1` for itself: an alarm about the device, its being unreachable
  included, is that service's, under its own address.
- **A parent's alarms are its own:** about its own function, such as its
  target set or its budget, never about one of its device services.
- **A device modelled as a member** (core §8.1) is not a service, and has
  no alarms of its own. Its service raises them with a label naming the
  member, which keys them apart (§2.2).
- **No service name is split here.** A reference carries the service whole
  (§2.12). How a device service is named, `<parent>.<slug(device)>` by
  D23, is a deployment's convention
  ([`examples/zk2/shapes.md`](../../../examples/zk2/shapes.md)), not this
  profile's.

### 2.11 Constrained faces

- **Alarms stay home, at 1.0.** The contract declares no `link.exposure`,
  so its resource is `host` (`link.v1` §2.2): no push of an alarm crosses
  a constrained face (`link.v1` §2.7).
- **A far reader GETs them by grant** (`link.v1` §2.9), and ages the
  replies by the deployment's word for its clock (`freshness.v1` §2.6,
  §2.9). Presence does not cross, so an owner gone is not told from one
  the GET did not reach, and an empty GET establishes nothing (§2.15).
  `[F: conclusions.json]`
- **A face closed to them,** where the far principal is granted no GET of
  them: a tool across it MUST answer whether an alarm fires, and whether
  anything does, unobservable, and MUST NOT report that nothing fires.
  `[F: conclusions.json]`
- A later minor MAY expose the resource: an annotation changed is a
  review (core §9.8). Each firing alarm's confirmation would then cross
  the face, one put every 450 s.

### 2.12 References from other interfaces

- **Three members, never one string.** An interface that names an alarm,
  an acknowledgement or an incident for instance, SHOULD name it by its
  owner's system, its owner's service and its alert key, as three strings
  or as three template parameters (`acks/{system}/{service}/{alert_key}`).
  It MUST NOT pack them into one string: a dotted service, such as
  `snmp.router01`, would not split back (D23, Appendix A).
  `[F: keys.json]`
- **The key it names** is
  `zk2/<system>/<service>/alarms.v1/state/alarms/<alert_key>`, the alert
  key slugged as any parameter value is (core §1.4), at this profile's
  major. `[F: keys.json]`
- **Named here, not in the schema.** The 1.0 schema defines no reference
  type, and adding one would be a revision that no alarm's wire needs. A
  referring interface declares its own, as `zs.catalog.v1`'s `AlertRef`
  does.

### 2.13 The tokenless set

- **Recommended near the budget.** A deployment near the presence budget
  (core §8.3) whose services all implement `alarms.v1` SHOULD put it in
  their tokenless set (core §8.1, U22).
- **Found by descriptor, never by token.** A reader MUST find
  `alarms.v1`'s owners through instance tokens and descriptors, and MUST
  NOT conclude that a service does not implement it from a missing
  `alive/alarms.v1/…` token. `[F: conclusions.json]`
- **The split-brain check** (core §6) does not cover a tokenless
  interface.

### 2.14 What a reader concludes of one alarm

A reader answers "is this alarm firing?" from one reading by the first of
these steps that answers. `[F: conclusions.json]`
1. **Presence** (core §8.1):
   - absent, a complete read without its instance token: **not asked**,
     `absent`. An archive's document, if one was read, is shown as
     last-known (core S6), and plays no part;
   - its token not seen, in a read possibly incomplete or refused:
     **unobservable**, `presence_incomplete`;
   - across a constrained face, where the deployment's word stands for the
     descriptor: when the face closes the alarms to this reader (§2.11),
     **unobservable**, `face_closed`; otherwise step 3;
   - present: step 2.
2. **The descriptor** (§2.13): not listing `alarms.v1`, **not asked**,
   `not_listed`; not read, **unobservable**, `no_descriptor`.
3. **An archive alone** (`freshness.v1` §2.8): **not asked**,
   `last_known`.
4. **A loss.** A subscription lost deliveries, and since then no GET has
   answered this key, with a value or a `reply_del`, nor has the GET that
   established its owner's alarms (§2.15) left it out (step 5):
   **unobservable**, `incomplete`. A lost delivery may have been this
   key's latest, so a reader that lost one re-seeds by S4's GET (core
   §4.2). A GET that drew nothing for the key, complete or not, does not
   heal the loss for it (0.2): an empty reply set is no verdict (core O5).
   - **The establishing GET heals the keys it leaves out** (0.5). It was
     asked after the loss: a window that lost a delivery establishes
     nothing, and after a loss a window runs from the first complete GET
     that followed it (§2.15). The owner answered it with every live key
     (core S2), and the window has heard everything since. So a key it left
     out, with nothing of the key arriving after it was asked, was neither
     live when the owner answered nor put since: step 5 reads it `not_held`.
     Before 0.5, a key whose resolve and delete a loss took read
     `incomplete` for as long as the reader held it, since past the
     tombstone window no GET answers it again, and "is anything firing?"
     over its owner could never read no. A key something of which arrived
     after that GET was asked is not left out: a GET that answers it heals
     it, as before.
5. **The latest sample:**
   - a delete or a `reply_del`: **no**, `deleted`;
   - a resolved document: **no**, `resolved`, whatever its age;
   - none, and the owner's alarms established (§2.15): **no**,
     `not_held`. A sample the reader holds, a delete included, is none
     (0.3, 0.5) when the GET that established its owner's alarms, either
     way (`answered` or `window`), **left the key out**: it answered the key
     with neither a value nor a `reply_del`, and nothing of the key arrived
     after that GET was asked. The owner answers every live key (core S2),
     so the key's delete went past the tombstone window unheard. A held
     delete so reads `not_held`, which is no as `deleted` is;
   - none otherwise: **unobservable**, `not_read`, or `nothing_crossed`
     across a face;
   - a put whose stamp's id is not the present descriptor's `meta.zid`,
     compared by value (core §4.3, §3.3): **not asked**,
     `previous_instance`. An earlier instance stamped it, and it is that
     instance's last word, which a tool shows as last-known; or another
     session did, which is also core §4.2's foreign stamp, a finding a
     tool reports apart (0.2). With no `meta.zid`, a stamp is
     unattributable, never foreign (core §3.3), and the reader goes on to
     step 6. A re-mint that keeps its session keeps its zid, so its earlier
     instance's put is not told apart (§2.9);
   - otherwise: step 6.
6. **Its freshness,** at 900 s (§2.7):
   - fresh, and a firing document: **yes**, `firing`;
   - fresh, and a put that does not read: **unobservable**,
     `undecodable`;
   - stale because nothing was delivered, across a face:
     **unobservable**, `nothing_crossed`;
   - stale otherwise: **unobservable**, `stale`;
   - unobservable, or not asked by `freshness.v1` (observations that
     contradict the latest sample): **unobservable**, with
     `freshness.v1`'s reason.

"Is this firing alarm past its horizon, its owner present?" (§5) reads the
same steps, with other answers in three places. `[F: conclusions.json]`
- At step 1, across a face that does not close the alarms: **unobservable**,
  `across_face`, since presence does not cross.
- At step 5, a delete, a resolved document, or none with the owner's
  alarms established: **not asked**, `not_firing`.
- At step 6, a put that does not read: **unobservable**, `undecodable`,
  whatever its freshness; stale: **yes**, `stale`; fresh: **no**,
  `fresh`.

### 2.15 What a reader concludes of an owner's alarms

- **Established.** An owner's alarms are known whole, **established**,
  in one of two ways, each reached by the order below: a reader's S4 GET
  of its `alarms.v1/state/alarms/*` ran to its final reply with no error
  reply (core §2.7, a complete reading), its subscription, if it has one,
  lost no delivery over its window and, but across a face, its owner was
  present throughout, and either: `[F: conclusions.json]`
  - **`answered`:** the GET answered at least one key with a value. The
    owner answers every live key (core S2), so its answer is its alarms;
  - **`window`:** the GET answered none, and the subscription, declared
    before it (core §4.2), has listened for longer than 900 s. The owner
    puts every firing alarm at least every 450 s (§2.7), so a lossless
    window longer than the horizon has heard each one.
- **The window** (0.2). A subscription's window runs from its
  declaration, or, after a loss, from the first complete GET that
  followed it: a reader that lost a delivery re-seeds by S4's GET (core
  §4.2), which heals a loss before it and not one after it. A GET is
  dated by the instant it was asked, its replies included (0.5): one
  asked before a loss heals nothing of it, wherever its replies arrive.
  The window is lossless when it lost no delivery, and its owner was
  present throughout when it held its instance token from the window's
  start until one lease after its end (core §2.7, 0.25). `window`'s
  900 s are counted over it.
  - **Its span counts as core §2.7 counts a window's** (0.3): from the
    declaration plus the reply timeout, or from that GET, to its end; the
    owner is watched one lease and the reply timeout past the end. So a
    reader judging at an instant ends its window that long before it.
  - **A gap in the owner's presence** (0.3) breaks the window as a loss
    does: its instance token withdrawn, or a new instance's appearing
    (core §2.7, a new instance or a gap). The window runs again from the
    first complete GET that followed the gap, which the new instance
    answers with its own puts (§2.9); until one, the owner was not present
    throughout.
  - **Lost no delivery** is core §2.7's: the reader's own queue lost
    nothing, and its receive path never stalled past the bound (0.27). A
    stall is a loss at the instant the reader sees it.
- **The order** (0.2). A reader judges an owner's alarms by the first of
  these that answers: `[F: conclusions.json]`
  1. **§2.14's steps 1 and 2,** with their answers and reasons: absent,
     **not asked**, `absent`; presence possibly incomplete or refused,
     **unobservable**, `presence_incomplete`; a face closed to the alarms,
     **unobservable**, `face_closed`; not listed, **not asked**,
     `not_listed`; the descriptor not read, **unobservable**,
     `no_descriptor`. An owner across a face that does not close them goes
     on, the deployment's word standing for its descriptor (§2.11);
  2. **the seed:** no GET, `no_seed`; one that ended at its timeout or with
     an error reply, `seed_incomplete`: **unobservable**;
  3. **the window,** when the reader subscribes: one that lost a delivery,
     `window_lost`; one over which the owner was not present throughout,
     `owner_gap`: **unobservable**. Across a face, presence does not
     cross, so whether the owner was present is not asked there;
  4. `answered`: **established**;
  5. across a face, an empty GET: **unobservable**, `across_face`, since
     presence does not cross, so no window is of an owner known present;
  6. an empty GET and no window, `no_member` (an empty reply set is no
     verdict, core O5), or a window no longer than 900 s, `window_short`:
     **unobservable**;
  7. otherwise, `window`: **established**.
- **Why the window needs the GET.** A present owner that has stopped
  writing is as silent as one with nothing firing. Its GET then ends at
  its timeout (`seed_incomplete`), or answers its alarms, which read stale
  (§2.14).
- **The owners in scope** of a selector (0.2) are the services it selects
  that the reader knows of: those its presence read finds, through
  instance tokens and descriptors (§2.13), and those it knew of before,
  by an earlier reading of its own or by an archive's keys (core S6). An
  owner known only the second way, which a complete presence read does not
  find, is absent: **not asked**. A tool says which owners it asked, and
  how it knew of each. `[Sc: §8]`
  - **Whole** (0.5). The reads that found the owners in scope are whole
    when the reader's latest presence read of them ran to its final reply
    (core §8.1) and, for a reader that follows instance tokens since, it
    lost none of their moves. A read possibly incomplete or refused, no
    read made, or a loss since, may have missed a present owner, which no
    verdict below counts, and which may fire. Across a constrained face the
    deployment's word names the owner (§2.11), and is whole.
    `[F: conclusions.json]`
  - **An archive's read plays no part in it** (0.5). An owner that only an
    archive's keys name, and that a complete presence read does not find,
    is absent, not asked, and stops no answer. An archive's read short of
    its final reply, or a key of it that does not read back into an
    alarm's key, can leave out only such an owner: the owners a tool
    counts not asked may then be short, and it says so.
- **Anything firing at or above a severity *S*,** over the owners in a
  scope: `[F: conclusions.json]`
  1. an alarm read of any of them reads **yes** at *S* or above:
     **yes**, `any_firing`, with the count;
  2. an owner in scope is unobservable: **unobservable**,
     `owner_unobservable`;
  3. the reads that found the scope were not whole (above, 0.5):
     **unobservable**, `scope_incomplete`: an owner they missed is in no
     other step, and may fire;
  4. an alarm of an established owner, at *S* or above or at no severity
     known, reads unobservable, or yes without a severity:
     **unobservable**, `alarm_unobservable`;
  5. no owner is established: **not asked**, `no_owner`;
  6. otherwise **no**, `none_firing`.

  Each owner is counted by its verdict: established, unobservable, not
  asked. An owner the reads may have missed is counted nowhere: a count
  is of owners asked (0.5).

### 2.16 Reporting changes

A tool that reports each alarm's changes as they happen, a notifier,
reports what §2.14 answers, never only what a sample did (0.4).
- **The answer after the change.** It reports §2.14's answer after each
  change of a key, §2.6's transition or the reader's own (a loss, its
  verdict moving with no sample), never the change's name alone. A raise
  read from an earlier instance's put, or read while the reader cannot yet
  judge the key, is no firing to report; a resolve heard after a loss is
  no resolve to report until a GET answers the key, or the GET that
  establishes its owner's alarms leaves it out (§2.14 steps 4 and 5).
  `[F: transitions.json, conclusions.json]`
- **What is a change to report:** the answer moving between yes, no and
  neither; and, while yes, the document's severity moving, an escalation
  either way (§2.5). A refresh and a confirmation are not transitions
  (§0), and move neither; nor does a raise of an alarm already reported
  firing at its severity, whose `timestamp` moved with no resolve heard.
  `[F: transitions.json]`
- **A loss is the reader's.** A loss makes every key unobservable at once
  (§2.14 step 4). A tool MAY report it once for its scope rather than once
  per key, if it then reports no key's answer the loss made unobservable,
  and reports each key again as the GET that heals the loss answers it,
  or, establishing its owner's alarms, leaves it out (§2.14, §2.15).
- **An alarm firing at the first reading** is a late reader's raise
  (§2.6), its document's `timestamp` saying since when. A tool that reports
  changes SHOULD report it, rather than assume it as a fact that predates
  its reading: an alarm is its owner's own word that something is wrong.

## 3. Contract

The standard contract is [`alarms.v1.toml`](alarms.v1.toml), with its
type in [`schemas/alarms.v1.json`](schemas/alarms.v1.json). Revision 1.0
is
`sha256:95579151aa231d2ba1224eae828083bdfc7f4f9403a80c831c1915decca9e8b6`,
published in [`../.history/alarms.v1/`](../.history/alarms.v1/) (core
§9.7). It was written with ZenSight's mapping (#622), and the same bundle
is in `examples/zk2/.history/alarms.v1/`, which is append-only. A new
revision is published in `spec/profiles/.history/`.

| Resource | Kind | Type | QoS | Annotations |
|---|---|---|---|---|
| `alarms/{alert_key}` | `state`, `alert_key` a string, cardinality 256 | `alarms.v1.Alarm` `{timestamp, observed_at_ms, rule, severity, state, summary, category, labels}` | `reliable`, `block`, `interactive_high`, `express`: v1's `alert` profile | `freshness.ttl_s = 900` |

- **Required:** `timestamp`, `rule`, `severity`, `state` and `summary`.
  `Severity` is `info`, `warning`, `critical`, and `State` is `firing`,
  `resolved`. The object admits members it does not name, so a later minor
  may add some (core §9.8).
- **`reliable` and `block`:** no queue on the path drops a raise or a
  resolve (core §2.7, "the path could not drop one silently").
- **No application field.** The document names no producer, host or
  source: the key names its publisher (core §1.1, Appendix A).
- The interface `uses = ["freshness.v1"]`, for the horizon.

## 4. Vocabulary

None, published (core 0.34). `alarms.v1` defines no annotation key. The
interim `alarms.severity_default` of core Appendix D is dropped: every
document carries its severity (§2.4), so a default has nothing to fill. A
contract that writes `alarms.<key>` draws W105.

## 5. What a tool may conclude

"Not asked" (nobody put the question, or its premise does not hold) and
"unobservable" (it was put, and the reading could not answer it) are
different facts, and neither is a "no" (core O5). The fixture
[`conclusions.json`](conformance/conclusions.json) states the tokens:
`yes`, `no`, `unobservable`, `not_asked`, each with a reason (§2.14,
§2.15).

| Question | Yes | No | Unestablished | Finding on |
|---|---|---|---|---|
| Is this alarm firing? (§2.14) | Its owner present and listed, or reachable across a face; the latest a firing document of the present instance, fresh within 900 s. | The latest a resolved document, a delete or a `reply_del`; or the key not held by the owner's alarms, established (§2.15). | **Not asked:** absent, last-known (core S6); not listed; an archive alone; an earlier instance's put. **Unobservable:** the presence read possibly incomplete or refused; the descriptor not read; a face closed to it, or nothing crossed; a delivery lost and no GET since that answered it or, establishing its owner's alarms, left it out; nothing read; the alarm stale (the last row's finding); its freshness unobservable (`freshness.v1`); its latest put undecodable. | Yes. |
| Is anything firing at or above *S* under this selector? (§2.15) | An alarm in scope reads yes at *S* or above, whatever else is known. | The reads that found the scope whole, every owner asked in it established, and none of its alarms reads yes, or unobservable, at *S* or above. | **Unobservable:** an owner in scope unobservable, with §2.15's reason; the reads that found the scope not whole (`scope_incomplete`); an established owner's alarm unobservable at *S* or above, or at no severity known. **Not asked:** no owner established, the scope's reads whole. Each owner counted by its verdict. | Yes. |
| Does this key re-derive from its document? (§2.2, §2.3) | **`strict`:** the recipe gives the key. **`sanitized`:** only through the sanitizing step, a break of §2.3's SHOULD, which a tool MAY report. | **`mismatch`:** the key is not its document's: a phantom (§2.9), an owner that hashed a host-scoped label, or another recipe. | **Not asked:** a delete, which carries no document (`no_document`). **Unobservable:** the payload undecodable (`undecodable`). | No. |
| Is this firing alarm past its horizon, its owner present? (§2.7, §2.14) | Present and listed; the latest a firing document of the present instance, stale at 900 s. | The same, fresh. | **Not asked:** absent, since an absent owner's alarms age by design; not listed; an archive alone; the latest not firing; an earlier instance's put. **Unobservable:** across a face, where presence does not cross; the presence read possibly incomplete or refused; the descriptor not read; a delivery lost and no GET since that answered it or, establishing its owner's alarms, left it out; nothing read; undecodable; its freshness unobservable. | Yes: about the owner, which broke §2.7's confirmation, or whose clock is ahead. |

**Which cause** a stale alarm has (the owner hung, its writer closed, its
clock ahead) is unobservable from the alarm alone. `health.v1` tells some
apart: a `clock_ahead` fault names one, and its status goes stale with the
alarm when the owner stops writing (`health.v1` §2.5).

## Appendix A. Against v1

v1's alerts were state, `state/<producer>/alert/<alert_key>` (RFC 04
§1.2, "Alerts are state"), keyed by ZenSight's recipe (RFC 11 §3.1) and
named across producers by the alert ref (RFC 11 §3.2), with `zenkey::alert`
and `zenkey-fleet`'s alert projection (`model/alert.rs`) on the `v1`
branch.

**What changed.**

| v1 | `alarms.v1` | Why |
|---|---|---|
| A family in every application's registry | A standard contract, one resource (§3) | A tool reads any service's alarms without the application's registry. |
| The recipe a constant of each application's profile chapter (RFC 04 §1.2) | One recipe, fixed here (§2.2) | D23, G3. Its one implementer is ZenSight, and a parameter would need a slot that no extension point gives (core 0.34). |
| Host-scoped: `host`, "and any label the producer documents as host-scoped" | `host` and `host.*`, normative (§2.2) | G3: a standard contract cannot carry each implementer's list. |
| Unframed input refused (v1's `alert_key` returns an error) | Sanitized by a stated step, the owner's and the reader's (§2.3) | ZenSight's fallback is what runs, and a reader must re-derive the key it keys on. |
| A put read as firing, a delete as resolved (v1's `alert_transition`, so zenwatch's `alerts`) | The state read from the document (§2.6) | A put of a resolved document read as firing re-fired every resolve. |
| `alert_ref = origin.producer.alert_key`, split on the first two dots (RFC 11 §3.2) | Three members, never packed (§2.12) | G4: a dotted service splits wrong. |
| `source`, `protocol` and `kind` in ZenSight's document | None of them; `kind` rides `category`, which is not hashed (§2.4, §3) | The key names the publisher (core §1.1). |
| The firing set durable in a `latest` storage; resolved at a clean stop; adopted by a GET of the owner's own selector (ZenSight #882) | No storage on an owner's keys (core S4); a close leaves its alarms; adoption from the owner's record or an archive on its side (§2.9) | An absent owner's alarms are last-known (core S6), never current; resolving at a close would undo acknowledgements at every restart. |
| A 900 s bound in the registry, and ZenSight's alerts put only on a change or a rate-limited refresh, a late joiner seeding from the producer's queryable (#1081) | 900 s by `freshness.v1`, every firing alarm confirmed every 450 s, and only while evaluated (§2.7) | A hung owner's alarms read stale, never firing now, and a window can establish that nothing fires (§2.15). |

**What deliberately did not change.**
- **The recipe's bytes.** The test vector holds, and every key ZenSight
  mints is the profile's.
- **One key per alarm,** firing, then resolved, then deleted.
- **`timestamp` and `observed_at_ms`:** the transition's instant, moved by
  an escalation and never by a refresh, and the refresh's instant
  (ZenSight #1081).
- **The QoS,** v1's `alert` profile, and **the 900 s** horizon.

**What is not ported.**
- **The dotted alert ref** (§2.12).
- **Acknowledgements, silences, incidents and impact.** They stay
  ZenSight's, in `zs.catalog.v1`, keyed by the structured reference.

**The record.** D23 holds as written, with its derivation of a dotted
service left a convention (§2.10). Architecture §3.12 lists `alarms.v1`
as "active alarms as state plus transitions": the transitions are the
stamped changes of each alarm's state (§2.6), with no stream of their own
at 1.0. §4.9's fleet-wide selector, `zk2/*/*/alarms.v1/state/**`, selects
the one resource.
