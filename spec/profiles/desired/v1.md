# `desired.v1`: desired documents, from their author to their target

| | |
|---|---|
| **Text version** | 0.1 ([`CHANGELOG.md`](CHANGELOG.md)) |
| **Status** | draft |
| **Written against** | core 0.37 ([`../../core.md`](../../core.md)) |
| **Uses** | [`freshness.v1`](../freshness/v1.md), text 0.3: a document is never stale, so its author never re-puts it (§2.2, §2.11) |
| **Evidence** | [`conformance/`](conformance/), [`scenarios.md`](scenarios.md) |

`desired.v1` lets a service say what another service should be doing, and
lets that service converge on it when it can: across an outage, a restart
of either side, or a link that is up an hour a day. The document is state
of its **author**, keyed by its **target** (core §2.1, P3): the author
writes it under its own address, and the target binds its own slice of the
author's template (core R2), converges, and says what it did in a report
of its own.

```text
zk2/<author system>/<author>/<iface>/state/<template, its target parameters filled>   the document: state of its author, one per target and document type
zk2/<target system>/<target>/<iface'>/state/<a resource of the target's>              the target's report: a desired.v1.Report, its own state
```

```toml
# The walkthrough's shape: one target parameter, bound to the target's system
[resources."plans/{vehicle}"]
kind        = "state"
type        = "mission_plan.v1.Plan"
params      = { vehicle = "string" }
cardinality = 1000
annotations = { "desired.target_param" = "vehicle" }

# ZenSight's shape: a system and a service, one template per document type
[resources."desired/{host}/{service}/thresholds"]
kind        = "state"
type        = "json:ThresholdsConfig"
params      = { host = "string", service = "string" }
cardinality = 150000
annotations = { "desired.target_param" = ["host", "service"], "freshness.ttl_s" = 0 }
```

A document's version is its author's stamp (core S1, S7), which every
state put already carries. A target acts on each version once, never on
an older one, reverts to its own baseline when the document is deleted,
and refuses whole a document it cannot take, keeping what was in force.
The profile defines no contract and no kind, and puts nothing of its own
on the bus: the documents are the author's, and the reports the target's.

---

## 0. Conventions

The keywords, the roles and the evidence tags are core §0's. Here,
`[F: <file>]` names a fixture in [`conformance/`](conformance/),
`[Sc: §n]` a section of [`scenarios.md`](scenarios.md), and `core` marks
the core's own evidence. References to `docs/zk2/architecture.md` (D16,
D22, E20, §3.12, §4.3), to the spike report (S5, S12), to v1's RFC 05
§3, RFC 07 §3 and RFC 12 §3, and to the adopters' files under
`examples/zk2/` are informative: every rule is stated here.

Terms:
- **Author:** the service that owns a desired resource (core §6), and the
  only writer of its keys.
- **Desired resource:** a state resource whose resolved annotations hold
  `desired.target_param` (§2.2). Its type is the **document type**, and
  each member a **document**.
- **Target parameters:** the template parameters `desired.target_param`
  names. A **target** is a service whose own system and service fill them,
  through its binding (§2.3). Its **slice** is the one key they give: its
  document's key.
- **Version:** one mutation of a document's key, a put or a delete, named
  by the stamp the author set on it (§2.4).
- **Act:** what a target does with a version: apply a put, or revert on a
  delete (§2.7, §2.8). Each act ends in an **outcome** (§2.10).
- **Baseline:** what a target runs with no document: its own
  configuration, its startup file or its defaults. **In force:** what the
  target runs now, the baseline, a document, or a change its own
  operation made (a **call**).
- **Report:** a `desired.v1.Report` (§3), which the target puts as its
  own state (§2.10).
- **Reader, tool:** core §0's tool, or any participant that reads a
  target's report against its author's document (§2.17, §5).

## 2. Rules

### 2.1 Who implements it

- **An author** implements it for each desired resource of its own
  contract: one template per document type (D22), keyed by target (§2.2),
  each document its own state (core S1–S3), and it follows §2.11.
- **A target** implements it for each requirement it holds on a desired
  resource: one role per document type, bound to one author (§2.3). It
  reads its slice (§2.5), orders the versions (§2.6), acts (§2.7, §2.8),
  and reports (§2.10). A service may be the target of several document
  types, from several authors, each through its own role.
- **Both at once.** A service can author documents for others and be the
  target of documents of its own, through different interfaces.
- **`config.v1`'s owner** is a target whose document type is
  `DesiredConfig` (§2.16).

### 2.2 The declaration

`desired.target_param` names a desired resource's target parameters. A
reader MUST read a resource's declaration exactly as the fixture does.
`[F: declarations.json]`
- **Its value** is a string, or an array of one or two strings, each the
  name of a parameter of the resource's template. A string is the same as
  a one-element array.
- **Which binds to which.** The binding gives each target parameter the
  target's own identity (core R2), in R2's order:
  - **one parameter** binds to `self.system` or to `self.service`, as the
    deployment chooses: the walkthrough's `{vehicle}` names a system;
  - **two parameters:** the first binds to `self.system`, the second to
    `self.service`. ZenSight's `["host", "service"]` is that order (D22,
    ZenSight's G5).
- **Every parameter is a target parameter.** A target's slice is one key,
  one document per target and document type: a template parameter the
  value does not name would make it a collection.
- **A declaration is invalid** for each of these, checked in this order,
  each alone, a check that needs a value an earlier one found wrong
  skipped: `[F: declarations.json]`
  - `not_state`: the resource is not `state` or `@state` (a document is its
    author's state, core S1–S7);
  - `value`: not a string, nor an array of one or two strings;
  - `repeated`: a name twice;
  - `not_a_param`: a name that is no parameter of the template;
  - `rest_param`: a name of a rest parameter (`{x...}`), which no single
    identity fills;
  - `param_not_target`: a template parameter the value does not name;
  - `horizon`: a resolved `freshness.ttl_s` that `freshness.v1` reads as a
    horizon above 0 (its §2.1). Its owner would re-put every document
    within half of it (`freshness.v1` §2.4), and every re-put is a version
    each target acts on again (§2.6). A desired resource SHOULD declare
    `freshness.ttl_s = 0` instead, never stale (D16, `freshness.v1` §2.3).
- **A resource without the key** is not this profile's, whatever else it
  declares; another `desired.<key>` is W105's (§4). On a requirement
  (`[requires.<role>]`) the key means nothing at this version, and a
  reader ignores it.
- **What a reader does with an invalid declaration.** A tool reports it
  as a contract's finding, and a target SHOULD refuse to bind a role to
  such a resource. The core has no code for it: no core lint reads an
  annotation's value. A contract linter SHOULD warn of one.

### 2.3 The binding

A target binds its role to its own slice (core R2). A tool MUST read a
requirement's binding as the fixture does, from the descriptor's
`requires` entry as core §3.3 lists it. `[F: bindings.json]`
- **One author.** The role MUST be bound to one exact address, the
  author's (core R1): a document's versions are one author's stamps, and
  two authors' documents for one target would contend. A standby that
  holds only its instance token (`redundancy.v1`) is the same address.
  `[F: bindings.json]`
- **Its own slice.** Each target parameter MUST be bound to `self.system`
  or `self.service`, as §2.2's order says, never to a literal: a target
  converges on its own document, never another's. `[F: bindings.json]`
- **The slice's key** is the author's address, the interface, the
  resource's kind token and its template, each target parameter filled
  with the target's own system or service as its binding says, slugged as
  any parameter value is (core §1.4):
  `zk2/fleet/desired/zs.desired.v1/state/desired/h-3fa9c2d41b7e/sysinfo/thresholds`
  for `h-3fa9c2d41b7e/sysinfo`. `[F: bindings.json]`
- **A binding is invalid** for each of these, in this order:
  `[F: bindings.json]`
  - `required_unbound`: no binding, and the role is required (core §3.2
    refuses such an owner's start, so a descriptor that lists one is
    wrong);
  - `not_one_author`: more than one binding, or one with `*` at either
    position;
  - `target_unbound`: a target parameter the requirement's `params` does
    not bind;
  - `not_self`: a target parameter bound to anything but `self.system` or
    `self.service`;
  - `wrong_self`: of two target parameters, the first not bound to
    `self.system`, or the second not to `self.service`.
- **Unbound** (`"bindings": []`) and optional is the kill switch (§2.12),
  not a finding.

### 2.4 The document and its version

- **A document is its author's state** (core S1–S3), put whole on its
  key, decoded by its type (core §7). A target reads only its slice.
- **Its version is its author's stamp.** Every put and delete of a state
  key carries a timestamp the owner set (core S1), and a GET reply carries
  the stamp of the mutation it represents (core S2): that stamp is the
  version, and nothing else orders documents (§2.6). It needs no member of
  the document, so any type can be a document type.
- **A stamp is written** as zenoh writes a timestamp: its NTP64 time in
  decimal, without leading zeros, then `/`, then its id in lowercase
  hexadecimal without leading zeros (core §4.1, Appendix B):
  `7386690599959157260/33`. Its time is a 64-bit unsigned value, too large
  for a JSON number to carry exactly, so a report writes the stamp as a
  string (§2.10). `[F: reports.json]`
- **A type MAY carry its own revision:** a top-level member named
  `revision` of a JSON Schema type, or a field named `revision` of a
  protobuf message, an integer from 0 to 2^64−1. config.v1's
  `DesiredConfig` and the walkthrough's `Plan` carry one. A target reports
  it beside the stamp (§2.10). It orders nothing: two versions are ordered
  by their stamps alone, whatever their revisions say.
- **A delete has no document,** so its version has a stamp and no
  revision.

### 2.5 Reading

A target reads its slice as core §4.2's late joiner does. `[Sc: §1, §5]`
- **Subscribe, then seed.** A target MUST declare its subscription to its
  slice's key first, then make S4's GET of it (core S4, §4.2), and judge
  every sample and every reply it receives, from either path, as §2.6
  says, in the order it receives them. `[Sc: §1]`
- **When it seeds.** A target MUST seed at its start, and again each time
  its author's instance token appears: a new instance, or one coming back
  after an absence (core §8.1). `[Sc: §1, §5]` It SHOULD seed again after
  its subscription loses a delivery, which may have been a version.
  - The author's **instance token**, never an interface token: the
    author's interface may be in its tokenless set (§2.15, core §8.1).
  - **A periodic re-read** is a deployment's setting, not a rule here. A
    deployment MAY give a target one, and SHOULD across a constrained face
    (§2.14). ZenSight's v1 re-read every 300 s (Appendix B).
- **A GET that draws nothing for the key**, complete or not, is no verdict
  (core O5): the target keeps what it holds, and acts on nothing (§2.8).
- **The author absent.** With its author's instance token gone, or its
  GET silent within the timeout, the target MAY read an archive's
  last-known instead (§2.9, core S6).
- **R6.** A sample or a reply whose key is not concrete is discarded (core
  R6), whichever path brought it.

### 2.6 The order of versions

A target holds the version it last acted on (§2.7). It judges each
version it receives against that one, or against the one it holds waiting
while an act runs (§2.7), and MUST judge it exactly as the fixture does:
`[F: order.json]` `[Sc: §2]`
1. **Unstamped:** a sample with no timestamp. A target MUST NOT act on
   one, and ignores it (`unstamped`): it cannot be ordered, and its author
   broke core S1. Nothing it holds changes. `[F: order.json]`
2. **Nothing held:** the first version a target receives in an instance
   is acted on, whatever its stamp.
3. **The same id:** a stamp whose id is the held version's is ordered by
   time (core §4.3):
   - later: acted on;
   - equal: **the same version** (`same_version`), received again by
     another path or another seed, never acted on again; its author's own
     sample of a version the target holds from an archive **confirms** it
     (`confirmed`, §2.9);
   - earlier: **older** (`older`), and a target MUST NOT act on it.
     `[F: order.json]` `[Sc: §2]`
4. **Another id:** a stamp whose id differs from the held version's is
   another session of the author: a new epoch (core §4.3, a new instance
   with no record of its last stamp), or a restart that took a new zid. A
   target accepts the first value under a new id, acts on it, and orders
   by time within the new id from then on, whatever the two times say:
   core `scenarios/state.md` §7's new epoch, its clock 5 s behind, is
   accepted so.

- **Never an older version.** Within one id, a target never acts on a
  version older than one it acted on, in one instance, by any path: the
  owner's reply, its subscription, an archive's last-known (S12: zero
  stale plans applied).
- **Within one id this is core §4.2's merge,** which keeps the later
  stamp and the equal one once. Two ids for one key are the case the merge
  leaves to core §4.3: a value of the author's old epoch still in transit
  when its new epoch's first value has been acted on is acted on as
  another id, and the new epoch's next value after it. That is core §4.3's
  residual risk, accepted at this version. An author's failover is a new
  epoch like any other; fencing a stale author, so that two never write
  at once, is `redundancy.v1`'s.
- **Stamps compare by value:** the time as an unsigned 64-bit integer, the
  id as a 128-bit value (core §4.2).

### 2.7 Acting

- **Once per version, in an instance.** A target MUST act on each version
  it admits (§2.6) once, whatever the outcome, and records it as acted on
  when the act starts: a later delivery of that version is the same
  version. `[F: order.json]` `[Sc: §2, §4]`
- **One act at a time.** While an act runs, a target holds the latest
  version it admits, judged against the running act's and then against
  the held one, the later replacing the earlier, and acts on it when the
  running act ends. A version a later one replaced while it waited is
  never acted on: it is passed over, not older. `[F: order.json]`
- **Two phases.** An act is the target's: it decodes the document, checks
  it, and applies it (a put), or applies its baseline (a delete), then
  ends with an outcome (§2.10). The reference's model is a pure state
  machine that says what to act on, and is told how the act ended
  (`zenkey_model::desired`).
- **Refused whole.** A target MUST refuse a document whole, applying none
  of it, and keep in force what was, when `[F: order.json]` `[Sc: §4]`:
  - it does not decode as the document type (`undecodable`), core §7.2's
    decoding, a JSON Schema type read as strict JSON;
  - it names what the target needs to reach the bus (`reach`): its
    endpoints, its namespace, its credentials and TLS material, its
    access-control identity, and anything whose wrong value would cut the
    target off the bus that carries the next document. One bad document
    would otherwise lock the target out of its own supervision, and the
    correction could not reach it (v1's RFC 05 §5.1, config.v1 §2.18's
    `reach` group);
  - it carries a secret (`secret`): a document is published, read by every
    principal granted it, and kept by archives (core §4.4). An author
    SHOULD NOT put one;
  - its type refuses it (`invalid`): a value out of the range the target
    accepts, an expired plan, anything the target's own validation of the
    type refuses.

  Which members are reach or secret is the document type's, and the
  target decides: the server refuses, as config.v1's does, since only it
  knows what it needs to reach the bus. A type SHOULD give such values no
  member at all, so that a document cannot carry one.
- **Failed.** An act that applied part of a document and could not finish
  is `failed`: what it applied stays applied, and no one version is wholly
  in force. A target that undoes what it applied, keeping what was in
  force, reports `refused` instead.
- **Not a lock.** A document a target converged stays converged in its
  report: a later change through the target's own operation makes the
  report's `source` `call` (§2.10), and does not make the target act on
  the version again. The next version is acted on, a call or not. There is
  no drift detection at 1.0: a tool that wants to know whether a converged
  document still holds compares it with what the target says is running.
- **A restart acts again.** A new instance of the target holds nothing of
  its previous instance's acts, and MUST act on the first version it
  reads, the one its previous instance acted on included: what that one
  applied may be gone with its process, and its report is gone with it.
  `[Sc: §5]` config.v1 §2.18 says the same of its owner.

### 2.8 Absence, deletes and cancellation

- **A delete reverts.** A delete, or a `reply_del` (core S3), that §2.6
  admits means there is no document for the target: it MUST revert to its
  baseline, and reports `reverted`. `[F: order.json]` `[Sc: §3]` A revert
  is never refused; one that could not finish is `failed`.
- **Only on positive evidence.** A target MUST NOT revert, nor act at all,
  on silence: a complete GET that draws nothing for its key, its author
  absent, a refused read, a subscription that hears nothing. Each is no
  verdict (core O5), and the target keeps what it holds. `[Sc: §3]`
- **The tombstone window covers the outage.** A delete reaches a target
  that was cut off when it was made only as a `reply_del` to the seed
  after the heal, and only within the author's tombstone window (core
  S3). A deployment MUST configure each author with a window at least the
  longest outage it expects between the author and any of its targets,
  and between it and every archive recording its documents (core S3).
  Across a constrained face, that is the face's maximum outage, which
  `link.v1` §2.11 floors. `[Sc: §3]` A delete made during a longer
  outage is never answered, and the target keeps the deleted document in
  force: the window is what prevents it.
- **Ending an act is a document.** An author that ends what a document
  asks for, a plan cancelled for instance, SHOULD put a terminal document
  of the type (the plan's `cancelled` form), never a delete (E20). An
  archive that missed a put aligns it from the author when the link heals
  (core §4.4), but one that missed a delete past the window keeps the
  document unconfirmed, and a target that later reads it as last-known
  (§2.9) would act on the plan again (spike S5's resurrection). A delete
  says that there is no desired state for the target any more: its
  removal from the policy, or the target's own removal (§2.11).

### 2.9 Last-known

- **From an archive, explicitly.** With its author absent or silent (core
  S6), a target MAY read its slice's last-known from an archive, through
  the key's archive form (core §4.4, S5). It judges the archive's version,
  a put or a `reply_del`, by §2.6 like any other: an archive older than
  what it acted on changes nothing. `[F: order.json]` `[Sc: §7]`
- **Reported as last-known.** A target that acts on an archive's version
  MUST say so in its report, `last_known: true` (§2.10): its author did
  not answer for it (core S6). `[F: order.json]` `[Sc: §7]`
- **Confirmed by the author.** When its author's answer, or a live sample,
  later carries the same version, the target holds it as its author's: it
  does not act again, and its report's `last_known` goes. `[F: order.json]`
- **Placement.** An archive on the target's side covers losing the link,
  and one on the author's side covers losing the author (core §4.4): the
  walkthrough's vehicle archive aligns from the ground's while the fleet
  manager is down, so a plan written while the vehicle was offline still
  reaches it. Store-and-forward uses both.
- **An archive's alignment status** (core §4.4: `confirmed`, and what it
  cannot say) plays no part at 1.0.

### 2.10 The report

- **The standard Report.** A target MUST report each role it holds on a
  desired resource in a `desired.v1.Report` (§3): the member of a state
  resource of its own contract, typed by the standard schema, which it
  puts as its own state (core S1–S3). The report of a role is the one
  whose `key` is that role's slice (§2.3), so one resource may carry the
  reports of several roles (ZenSight's `applied/{topic}`). `[F: reports.json]`
- **Put before the tokens, and after each change.** A target MUST put its
  first report of each role before its tokens (core §8.2, which lets a
  profile make it a MUST), `source` `baseline`, so that a GET made when
  its instance token appears finds it; and MUST put it again whenever an
  act ends, the author confirms a last-known version (§2.9), or a call
  changes what is in force. `[Sc: §1, §5]`
- **Its members** (§3): `[F: reports.json, order.json]`
  - `key`: the slice's key (§2.3). Absent only for a role left unbound
    (§2.12), whose report is then `{"source": "baseline"}`.
  - `source`: what is in force: `baseline`, `desired` (a document the
    target acted on, converged or applied in part), or `call` (a change
    its own operation made since, §2.7).
  - `in_force`: with `source` `desired`, the version wholly in force: the
    last version that converged. Absent after `failed`.
  - `observed`: the last version the target acted on in this instance,
    its stamp and, when its type carries one, its revision (§2.4). Absent
    before the first act.
  - `outcome`, with `observed`: `converged` (applied whole; `source`
    `desired`, `in_force` the version), `refused` (nothing applied;
    `source` and `in_force` as they were), `failed` (applied in part;
    `source` `desired` for a put, `baseline` for a delete, `in_force`
    absent), `reverted` (a delete acted on; `source` `baseline`).
  - `refusal`, with `refused` or `failed`: `code`, `pointer` (where in the
    document, a JSON Pointer, RFC 6901) and `detail` (a line for a
    person). The profile's codes are `undecodable`, `reach`, `secret` and
    `invalid` for a refusal (§2.7), and `apply` for a failure. A type MAY
    use codes of its own, as config.v1's are (§2.16); a reader shows a code
    it does not know as written.
  - `last_known`: `true` when `observed` was read from an archive (§2.9).
    Absent is `false`.
- **A target's report MUST be consistent.** Beyond the schema, a reader
  checks these, and a report that breaks one is malformed: `[F: reports.json]`
  - `keyless`: no `key`, with a `source` other than `baseline`, or with
    `observed`;
  - `key_form`: a `key` that is not a concrete zk2 data key of a `state`
    or `@state` resource (core §1.1);
  - `observed_outcome`: `observed` without `outcome`, or `outcome`
    without `observed`;
  - `refusal`: a `refusal` with an outcome other than `refused` or
    `failed`, or one of those without it;
  - `source`: `desired` with no `observed`; `converged` with `baseline`;
    `reverted` with `desired`;
  - `in_force`: an `in_force` with a `source` other than `desired`, or
    with `failed`; or, with `converged` and `desired`, an `in_force` that
    is not `observed`;
  - `revision_on_revert`: `reverted` with a revision in `observed`;
  - `last_known`: `last_known` with no `observed`.
- **How a reader reads one.** As `alarms.v1` §2.4 reads a document:
  strict JSON first (UTF-8, RFC 8259, nothing after the value but
  whitespace, no duplicate member at any depth, every number finite, every
  string with a UTF-8 form); then the schema, an integral number read as
  an integer (`3.0` is `3`), a member the schema does not name ignored; a
  stamp in the form of §2.4, its time at most 2^64−1 and its id at most
  128 bits; a revision at most 2^64−1. A report that fails one of these is
  unreadable, and one that reads with a finding above is malformed: a
  tool answers nothing from either (§2.17). `[F: reports.json]`
- **A tool finds a target's reports** by type identity, never by name:
  the state resources of its contracts typed `desired.v1.Report` from an
  artifact whose id §3 publishes (core §7.1, §10), read by S4's GET. The
  report of one document is the one whose `key` is its key.
- **Its horizon** is the target's to declare. A report resource MAY
  declare `freshness.ttl_s`; its owner then re-puts it unchanged as
  `freshness.v1` §2.4 says, which is no version of any document, and a
  tool judges its age by `freshness.v1` (§2.17). ZenSight's declares 900.

### 2.11 The author

- **One writer.** The author is the only writer of its documents (P3,
  core §6), and puts each target's document on that target's slice
  (§2.3). It writes no other service's keys, and the target writes none of
  the author's.
- **Only on a change.** An author MUST put a document only when its
  content differs from the one it last put on that key, and MUST NOT
  re-put one unchanged: every put is a version, which every target acts on
  again (§2.6, §2.7). So its desired resources declare no horizon above 0
  (§2.2), and its runtime's refresher, if it has one, is off for them.
  `[Sc: §6]` It SHOULD encode each document deterministically (JSON's
  members in one order, protobuf's fields in field order), so that equal
  content is equal bytes.
- **Its stamps.** An author MUST NOT stamp at or below the last timestamp
  it issued for its keys (core §4.3's catch-up): spike S12's author,
  restarted 5 s behind without it, had its next plan rejected as stale,
  and never converged. `[Sc: core state.md §7]`
- **A restart from its record.** Before its first write, an author takes
  its documents from its own persistent record, else from an explicit
  read of an archive on its own side: the sources core §4.3's catch-up
  names. It MUST NOT seed from a GET of its own keys: no storage may answer
  one (core S4), and its previous process, which did, is gone. `[Sc: §6]`
  - It answers each document it took under the stamp the record holds for
    it (core S2: a reply carries the stamp of the mutation it represents),
    and puts nothing that did not change: a target that acted on that
    version holds it as the same version (§2.6). `[Sc: §6]`
  - **What the record holds.** An author's record SHOULD hold each
    document as it was put, with its stamp, by its key, and each delete it
    made within its tombstone window, with its stamp, so that it still
    answers `reply_del` for it after the restart (core S3).
  - It SHOULD keep its session's zid across such a restart, so that the
    stamps it answers with are its own: a tool reads a reply's stamp as the
    owner's when its id is the descriptor's `meta.zid` (core §4.2's S1
    check), and core §1.5's new session is for an owner whose state's
    ordering restarts, which a catch-up from the record does not (core
    0.37). An author that takes a new zid answers with its previous
    session's stamps, which a tool's S1 check reads as foreign.
  - **With no record,** it starts a new epoch (core §4.3) and puts every
    document again, under its new id: each target acts on each again
    (§2.6). That is the cost of keeping no record.
- **Deletes on positive evidence.** An author SHOULD delete a target's
  document only on positive evidence that the target is to have none: its
  own source no longer yields a document for a target it still knows, or
  the deployment's inventory removes the target. It SHOULD NOT delete one
  because the target is absent from presence, or because a read of its
  inventory failed or came back short: silence is not a verdict (core O5),
  and an absent target converges when it returns. ZenSight's author holds
  such documents, and deletes one only after several passes that did not
  yield it (Appendix B).
- **Ending an act** is a terminal document of the type (§2.8).
- **Its window** is the deployment's (§2.8).

### 2.12 The kill switch

- **An optional role.** A target's role on a desired resource SHOULD be
  optional (core §3.1), so that a deployment can disarm desired state from
  outside the mechanism that could misbehave, by leaving it unbound:
  ZenSight's `desired.enabled = false`.
- **Unbound.** A role listed with `"bindings": []` (core §3.2) is the kill
  switch: the target MUST NOT read or act on any document for it, and it
  runs its baseline. Its report is `{"source": "baseline"}`, with no key,
  put before its tokens like any other (§2.10). `[F: bindings.json]`
  `[Sc: §8]`
- **A required role** left unbound refuses the target's start (core §3.2).

### 2.13 Population

- **The cardinality bounds the targets.** A desired template holds one
  member per target (§2.2), so its cardinality (core §2.2) is the number
  of targets one author serves with that document type, and the author
  keeps the population budget (core §2.7): at the bound, a new target's
  first document is refused, and the author's writer is told.
- **Explicit state for large populations.** An author whose desired
  resource serves more targets than a fleet-wide state subscriber should
  receive SHOULD declare it explicit (`@state`, core §1.3): `**` never
  crosses a verbatim chunk, so `zk2/*/*/*/state/**` never carries its
  documents, which ZenSight's G7 counted at about 210,000. A target reads
  its one key exactly, and S4's GET reaches it under `@state` (core S2).

### 2.14 Constrained faces

- **What crosses.** A document crosses a constrained face as a push only
  when its resource is exposed (`link.exposure = "link"`) and the face
  exposes (`link.v1` §2.7); otherwise a target across it reads its slice
  by a GET it is granted (`link.v1` §2.9). A report crosses back the same
  way.
- **Presence does not cross** (`link.v1` §2.6), so a target across a face
  never sees its author's instance token appear (§2.5). It seeds at its
  start and after a loss, and re-reads on its deployment's period, which
  is the only way it learns a version an outage cost it. A deployment
  SHOULD give such a target a period, and counts its cost: on
  zenoh-modem's SBD bearer, a GET and its reply are two billed messages
  (Appendix B).
- **The window's floor** is the face's maximum outage (§2.8, `link.v1`
  §2.11).
- **Liveness.** A document never goes stale (§2.2), so it shows nothing of
  its author's liveness across the face (`link.v1` §2.12).
- **A tool across the face** takes the deployment's word for what presence
  and the descriptor would say (§2.17).

### 2.15 The tokenless set, and access control

- **Found by the instance token.** A target watches its author's instance
  token (§2.5), which every instance holds (core §8.1), and MUST NOT
  conclude from a missing interface token that its author is absent: the
  author's interface may be in its tokenless set (core §8.1, U22).
  `[Sc: §1]`
- **Grants** (core §11.1). The author holds the put and delete grants on
  its own keys, and its targets the Consume grant on its interface, which
  covers their subscription, their GET and the author's presence. A
  target's report is its own state, which its readers consume. Nothing
  crosses principals: a target never writes its author's keys, and no
  storage on the author's keys stands in for it (core S4).

### 2.16 `config.v1` as a target

- **One document type.** `config.v1` §2.18 states this profile's rules for
  one type, `DesiredConfig` (its §3): its refusals are §2.7's refusals
  whole, with codes of its own (`reach`, `contract`, `sensitive`,
  `not_found`, `invalid_request`, `unavailable`), its `failed` is §2.7's,
  and its acting once per revision in an instance, a restart acting again,
  is §2.7's once per version.
- **Its report is its own.** A `config.v1` owner reports in its view and
  its status (`DesiredReport`, its §2.18), which maps onto the Report
  member for member: `observed_revision` is `observed.revision`,
  `outcome` is `outcome`, and `refusal` `{code, group, parameter}` is
  `refusal` with that code and the pointer `/values/<group>/<parameter>`.
  It carries no stamp, so a tool asks `config.v1` §5's question of it,
  and this profile's §5 does not read it.
- **What a delete reverts it to** is `config.v1`'s to say, and its text
  0.3 does not say it. The values a document converged are runtime
  changes (its §2.12), so its baseline is its startup and persisted
  values; how it undoes them is a question for #840's DB, which feeds a
  `config.v1` owner through this profile.

### 2.17 What a tool concludes of one target

A tool judges one target's role against its author's document by the
first of these that answers, and MUST conclude exactly as the fixture
does. "Not asked" and "unobservable" are never folded into "no" (core
O5). `[F: conclusions.json]` `[Sc: §9]`
1. **The target's presence** (core §8.1): absent, **not asked**,
   `target_absent`; its token not seen in a read possibly incomplete or
   refused, **unobservable**, `presence_incomplete`; across a constrained
   face, the deployment's word stands for the descriptor, and step 3;
   present, step 2.
2. **Its descriptor:** not read, **unobservable**, `no_descriptor`; not
   listing the role, **not asked**, `not_a_target`; listing it unbound,
   the kill switch: **not asked**, `unbound`, but for "is a document in
   force?", which answers **no**, `unbound`.
3. **Its report** of the role's slice (§2.10): none read, **unobservable**,
   `no_report` (`nothing_crossed` across a face); unreadable or malformed,
   **unobservable**, `report_invalid`.
4. **Its report's age**, by `freshness.v1` where its resource declares a
   horizon: stale, **unobservable**, `report_stale`; its freshness
   unobservable, **unobservable**, `report_unobservable`. Fresh, or no
   horizon declared: go on.
5. **The question:**
   - **Is the last act refused or failed?** No `observed`: **not asked**,
     `not_acted`. Otherwise by `outcome`: **yes**, `refused` or `failed`;
     **no**, `converged` or `reverted`.
   - **Is what the target acted on last-known?** No `observed`: **not
     asked**, `not_acted`. `last_known`: **yes**, `last_known`; else
     **no**, `current`.
   - **Is a document in force?** `source` `desired`: **yes**, `desired`
     with `in_force`, or `partial` without it. `baseline`: **no**,
     `baseline`. `call`: **no**, `call`.
   - **Has the target converged on its author's current document?** Steps
     6 and 7.
6. **The author:**
   - its presence: absent, **not asked**, `author_absent` (a tool MAY
     show the report against an archive's last-known, never as current);
     possibly incomplete or refused, **unobservable**,
     `author_presence_incomplete`; present, or across a face, go on;
   - its current version of the slice, by S4's GET (core §4.2): no GET
     made, **unobservable**, `author_not_read`; one that ended at its
     timeout or with an error reply, **unobservable**,
     `author_read_incomplete`; one that drew nothing for the key,
     **unobservable**, `author_silent` (core O5);
   - otherwise its latest put or delete, by its stamp: step 7.
7. **The comparison,** of the report's `observed` with the author's
   version:
   - no `observed`: **not yet**, `not_acted`;
   - the same stamp: by `outcome`, **yes**, `converged` or `reverted`;
     **no**, `refused` or `failed`;
   - the same id, an earlier time: **not yet**, `behind`;
   - the same id, a later time: **unobservable**, `ahead`: the two reads
     raced, or the author's answer is older than a version the target
     acted on;
   - another id: **not yet**, `other_epoch`: the author started a new
     epoch the target has not acted on (§2.6).

**Not yet** is unestablished, as `config.v1` §5's is: the target has not
acted on the author's current version, which time or its next seed may
change. A tool MAY report a target behind for longer than it expects.

## 3. The standard schema

No contract. The profile's standard schema is
[`desired.v1.json`](desired.v1.json) (core §10 point 1). Its types are the
profile's in any artifact whose id is one of these, and in no other,
whatever its types are named (core §7.1):

| Artifact id | Revision | What it holds |
|---|---|---|
| `sha256:0b249e71ab1b20cad122aecda2ef02c62e97a6e7db13a47e33ef0cf4f89856cd` | text 0.1 | `desired.v1.Report`, `desired.v1.Version` and `desired.v1.Refusal` |

`[F: schema.json]` A target's contract lists the file, by its path or a
copy's, byte for byte or JCS-equal, in `[schemas] jsonschema`, and types
its report resource `json:desired.v1.Report`. The file in this directory
is always the latest revision; a later text that changes it publishes the
new id beside this one, and every published id stays the profile's.

| Type | Members | Notes |
|---|---|---|
| `desired.v1.Report` | `key?`, `source`, `in_force?`, `observed?`, `outcome?`, `refusal?`, `last_known?` | §2.10. `source`: `baseline`, `desired`, `call`. `outcome`: `converged`, `refused`, `failed`, `reverted`. |
| `desired.v1.Version` | `stamp`, `revision?` | §2.4. The stamp a string, as zenoh writes one; the revision an integer from 0. |
| `desired.v1.Refusal` | `code`, `pointer?`, `detail?` | §2.10. The code 1 to 64 characters. |

Every object is open: a member a reader does not know is ignored, and a

## 5. What a tool may conclude

"Not asked" (nobody put the question, or its premise does not hold),
"unobservable" (it was put, and the reading could not answer it) and "not
yet" (the target has not acted on the version yet) are different facts,
and none is a "no" (core O5). The fixture
[`conclusions.json`](conformance/conclusions.json) states the tokens:
`yes`, `no`, `not_yet`, `unobservable`, `not_asked`, each with a reason
(§2.17).

The premises, for every row (§2.17 steps 1 to 4): the target present and
its descriptor listing the role bound, or across a face; its report of the
slice read, readable and consistent; fresh, where it declares a horizon.
Otherwise, as §2.17 says: **not asked** for a target absent, not a target
of the role, or unbound (the kill switch, which the third row answers
**no**); **unobservable** for presence possibly incomplete, a descriptor
not read, no report, a report unreadable or malformed, stale, or of an
unobservable age.

| Question | Yes | No | Unestablished | Finding on |
|---|---|---|---|---|
| Has the target converged on its author's current document? (§2.17) | The report's `observed` is the author's current version, its stamp equal, `converged` (a put) or `reverted` (a delete): what the target did when it acted, which a later call may have changed since (`source` `call`). | The same version, `refused` or `failed`, with the refusal. | **Not yet:** no act yet (`not_acted`); an earlier time of the same id (`behind`); another id (`other_epoch`). **Not asked:** the author absent. **Unobservable:** the author's presence possibly incomplete; its GET not made, incomplete, or drawing nothing for the key (core O5); the report's version later than the author's answer (`ahead`). | No: about the target, or the document. |
| Is the target's last act refused or failed? (§2.17) | `refused` or `failed`, with the refusal's code. | `converged` or `reverted`. | **Not asked:** no act yet in this instance. | Yes. |
| Is what the target acted on last-known? (§2.9) | `last_known`: an archive's version, its author absent or silent. | Its author's own. | **Not asked:** no act yet. | Neither: informative. |
| Is a desired document in force? (§2.10, §2.12) | `source` `desired`: wholly (`desired`, with `in_force`), or in part after a failed act (`partial`). | `baseline` (no document, or a delete reverted), `call` (a later change of the target's own), or the role unbound (`unbound`, the kill switch). | As the premises. | Neither: informative. |

**Why a target behind** cannot be told from the reports alone: its link,
its author's window, a loss its seed has not healed, or an act it holds
while another runs. The target's presence, its subscription's losses and
its deployment's period say more; the reports say what it did.

## Appendix A. Against v1

v1's desired state was the `@desired` plane: a controller published
`v1/@desired/state/<host>/<producer>/<topic>` under a registered service
origin, with the target host as the first subject chunk (RFC 07 §3, the
service-origin carve-out; RFC 12 §3, RFC 05 §3, the escape hatch that RPC
was not to be made durable), granted as one put and delete on the
origin's subtree (RFC 09 §3). A `latest` storage kept it, and the target
reconciled on (re)connect. Reach groups were never carried (RFC 05 §5.1).
ZenSight implemented both halves on the `v1` branch's grammar
(`zensight-sensor-core/src/desired.rs`, `zensight-desired`).

**What changed.**

| v1 | `desired.v1` | Why |
|---|---|---|
| A registered verbatim origin, `@desired`, writing for a target host | The author's own address and contract, the target in the template's parameters (§2.2) | P3: a key is written only by its owner; zk2 has no service origins. |
| `{host}/<producer>/<topic>`: one family of seven types | One template per document type, every parameter a target parameter (§2.2) | D22, ZenSight's G5: a template has one type. |
| The target host only | A system, or a system and a service, bound by R2's `self.system` and `self.service` (§2.3) | Device-as-service and per-service documents; G5: `self` alone could not say which. |
| A `latest` storage answered the seed and the periodic re-GET; the controller's restart re-read its own storage | The author answers (core S4); last-known from an archive, never current (§2.9); the author restarts from its record or an archive on its side (§2.11) | A storage answering on an owner's keys is refused (core S4), and spike S5 measured it resurrect deleted keys. |
| Last writer wins by the sample's HLC timestamp, ordered across ids | Ordered by time within one id, a new id accepted (§2.6, core §4.3) | An author's new epoch, its clock behind the old one's last stamp, is the author's word: core §4.3 accepts it, where zenoh's order would ignore it until its clock passed. Spike S12's author restarted behind without a catch-up never converged (§2.11). |
| A rejected document re-considered at every re-GET | Once per version in an instance, whatever the outcome (§2.7) | A refusal is the target's answer to that version; the next version is the author's to make. |
| `applied/<topic>` (`AppliedConfig`): source, `desired_timestamp`, the effective document as a string, `last_rejected` | The standard Report, keyed by the document's key, with the act's outcome and the version in force (§2.10, §3) | A tool reads any target's report without its application's types. The document in force is the target's own state to expose. |
| The never-list: a lint on member names, with numbers let through | The target refuses whole what it needs to reach the bus, and secrets (§2.7) | The target knows its type; the server refuses, as config.v1's does. |
| Refresh every `refresh_secs` (300) | A seed at start, at its author's appearance and after a loss; a period the deployment's (§2.5) | The owner's presence decides (S12); a period is a deployment's cost, priced per face. |

**What deliberately did not change.**
- **The document is its author's, keyed by target,** the target
  reconciling it: RFC 12 §3's convergence, not a durable command.
- **A delete reverts to the baseline** (ZenSight's `source: file`).
- **Invalid is refused, the previous kept,** never applied in part when
  refused, and never a crash loop.
- **The kill switch** is the target's file configuration, here an
  unbound optional role.
- **Reach is never desired state.**
- **`ttl_s = 0`:** a document never ages out; it is replaced or deleted
  (D16).

**What is not ported.**
- **The AdvancedSubscriber** with history and recovery as an
  accelerator: S4's GET at each seed is what converges, and a desired
  resource declares no `history`.
- **`effective_json`.** What runs is the target's own state to expose,
  typed by its own contract (ZenSight's `zs.thresholds.v1` `thresholds`).
- **A rejected sample's arrival time** (`last_rejected.at`): the report's
  stamp names the version, and its own put says when.

**The record.** Architecture §3.12's row holds: documents as state of the
authoring service, keyed by target, targets binding with `self`,
converging and reporting in their own state; cancellation by a terminal
document (E20, §2.8). Its `observed_revision` is the report's `observed`,
the stamp beside the type's revision (§2.4). D22 holds, with the list form
of G5. D16 holds as §2.2's SHOULD, and a horizon above 0 is refused.
