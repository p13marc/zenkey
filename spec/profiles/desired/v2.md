# `desired.v2`: desired documents, on a wire a far target can afford

| | |
|---|---|
| **Text version** | 0.3 ([`CHANGELOG.md`](CHANGELOG.md)) |
| **Status** | experimental |
| **Written against** | core 0.112 ([`../../core.md`](../../core.md)) |
| **Uses** | [`freshness.v2`](../freshness/v2.md), text 0.11: a document's horizon, and the heartbeat a target watches (§2.2, §2.5). It restates [`desired.v1`](v1.md)'s rules by reference, text 0.14, and replaces its version, its reading and its report. |
| **Evidence** | [`conformance/v2/`](conformance/v2/), [`scenarios-v2.md`](scenarios-v2.md), and `desired.v1`'s for the rules it keeps |

`desired.v1` lets a service say what another service should be doing, and
lets that service converge on it when it can. Its wire suits a wired
network. A target's periodic re-read brings the whole document back each
time. Its report is JSON, 294 bytes when it has converged. Its versions
are Zenoh timestamps, so their order rests on the author's clock.

`desired.v2` keeps every rule of `desired.v1` and changes three things:
- **The version is the in-band stamp.** A document's version is the run
  and the seq its put already carries (core §4.3). The desired resource
  carries no Zenoh timestamp, and its author answers a GET by snapshot.
- **A target asks less.** Its re-read names the version it holds, and an
  author whose document is unchanged answers with 6 bytes (core §4.2).
  Where the author's heartbeat reaches it, a target reads only when that
  heartbeat's digest moves.
- **The report is a packed record,** 12 bytes when it has converged and
  from 3 to 27 in all. A refusal names its place and its line by index,
  into tables the target's contract holds.

```toml
# The author's contract: one document per worker
[interface]
name  = "tasking"
major = 2
uses  = ["desired.v2", "freshness.v2"]

[resources."tasks/{system}/{service}"]
kind        = "state"
type        = "json:Task"
params      = { system = "string", service = "string" }
cardinality = 16
annotations = { "desired.target_param" = ["system", "service"], "freshness.ttl_s" = 600 }
```

```toml
# The target's contract: its report, and its role
[interface]
name  = "worker"
major = 2
uses  = ["desired.v2"]

[schemas]
packed = ["desired.v2.json"]

[resources."desired/task"]
kind = "state"
type = "packed:Report"

[resources."desired/task".annotations]
"desired.report"   = "task"
"desired.pointers" = ["", "/mode", "/rate_hz", "/endpoint"]
"desired.details"  = ["above what the drive supports", "names how the worker reaches the bus"]

[requires.task]
interface = "tasking.v2"
resources = ["tasks/{system}/{service}"]
optional  = true
```

```text
zk2/<author system>/<author>/<iface>/state/<template, its target parameters filled>   the document, as in desired.v1
zk2/<target system>/<target>/<iface'>/state/<a report resource>                       the target's report: a packed Report
```

The profile defines no contract and no kind, as `desired.v1` defines
none. The documents are the author's, and the reports the target's.

## 0. Conventions

The keywords, the roles and the evidence tags are core §0's. Here,
`[F: <file>]` names a fixture in [`conformance/`](conformance/), and
`[Sc: §n]` a section of [`scenarios-v2.md`](scenarios-v2.md). `v1 §n`
names a section of [`desired.v1`](v1.md), and a fixture of v1's says so,
as in `[F: v1 bindings.json]`.

**By reference.** Every rule of `desired.v1` holds for an author, a
target and a tool of a desired resource of this major, as written,
except where §2 replaces it. Where a rule of v1 names a stamp, its id or
its time, it reads the version, its run and its seq (§2.4). Where it
names a `reply_del`, it reads a tombstone (§2.5). Where it names a run
of the target, it reads the target's process (below).

Terms are v1 §0's, and these:
- **Desired resource:** as in v1, a state resource whose resolved
  annotations hold `desired.target_param`. It is of this major when its
  contract lists `desired.v2` in `uses`.
- **Run, seq:** core §4.3's. A run is an author's ordering epoch, and a
  seq counts within it. Two runs of different widths are two runs.
- **Version:** one mutation of a document's key, named by its in-band
  stamp: its run, with its width, and its seq (§2.4).
- **Process:** one process of the target. v1 calls it a run. The core
  has since given that word to the owner's epoch, so this text says
  process for the target's, and keeps run for the core's. What a target
  acted on, the runs it remembers (§2.6) and its last act are kept in one
  process, and only there.
- **Held stamp, conditional read:** core §7.5's and core §4.2's.
- **Section:** the part of a heartbeat that covers one collection: its
  digest and its live count (core §7.5).
- **Report resource:** a resource of a target's contract whose resolved
  annotations hold `desired.report`, of any kind (§2.10). Its declaration
  is invalid unless it is `state` or `@state`.
- **Report:** a record of the standard packed type `Report` (§3).

## 1. Extension points

| Point (core §10) | `desired.v2` |
|---|---|
| 1. A standard contract or a standard schema | A standard schema: the packed file [`desired.v2.json`](desired.v2.json) (§3), whose `Report` types a target's report, by the artifact's id. No contract: every author's interface is its own. |
| 2. An annotation vocabulary | `target_param`, as v1's, and `report`, `pointers` and `details` (§4). W105 reads this table for a contract that lists `desired.v2` (core §10). |
| 3. A registered verbatim kind | None. |
| 4. The descriptor's `profiles` | Through `uses` alone. An author's contract writes `desired.target_param`, and a target's writes `desired.report`, so each lists `desired.v2` (core §10 point 2), and so does its instance's descriptor. |

**Beside `desired.v1`.** A contract uses one major of a profile (core
§10). An author moves its interface from `desired.v1` to `desired.v2` by
a revision, and a target reads which major its author's revision uses
(§2.18).

## 2. Rules

### 2.1 Who implements it

v1 §2.1 holds.
- **An author** implements this major for each desired resource of a
  contract of its own that lists `desired.v2`.
- **A target** implements it for each role bound to such an author
  (§2.18).
- **`config.v1`'s and `config.v2`'s owners** are targets as v1 §2.16
  says (§2.16).

### 2.2 The declaration

v1 §2.2 holds, and `desired.target_param` means what it means there.
`[F: v2/declarations.json]` Its item "Its horizon" is replaced:
- **A horizon is a budget.** A desired resource declares
  `freshness.ttl_s = 0`, or none, where no target watches its author's
  heartbeat. It declares one above 0 where targets do (§2.5). v1
  advises 0 for every desired resource, and that advice goes.
- **Only under `freshness.v2`.** A desired resource that declares
  `freshness.ttl_s` above 0 MUST be of a contract that lists
  `freshness.v2` in `uses`. `[F: v2/declarations.json]`
  - A horizon under `freshness.v1` is confirmed by re-puts, each read
    for its Zenoh timestamp. That would put the resource back in core
    §4.3's table.
  - The declaration is invalid, `horizon_v1`. It is checked last, after
    v1 §2.2's seven reasons, and skipped where the resource is
    `not_state`.
- **What a linter reports.** A linter reports each reason of an
  invalid declaration as an error, where v1 §2.2 says warn. `link.v2`'s
  `packed_required` is one too. The core has no code for it. So the
  contract still loads, with its fingerprint (core §9.2). A target
  refuses to bind a role to such a resource, as in v1. The same holds of
  a report resource (§2.10).
- **What a horizon above 0 costs.** The author sends a heartbeat at most
  every half horizon (`freshness.v2` §2.4). It puts no document again,
  and no target's report moves.
  - The heartbeat holds one bit for each live document. An author of a
    large population keeps a horizon of 0, and its targets a period.
- **A document past its horizon stays in force.** Its author no longer
  vouches for it. A target never reverts on staleness, as in v1.
- **Across a constrained face,** the author's crossing heartbeat is the
  evidence of its liveness ([`link.v2`](../link/v2.md) §2.12).

### 2.3 The binding

v1 §2.3 holds. `[F: v1 bindings.json]`

### 2.4 The document and its version

This section replaces v1 §2.4.
- **A document is its author's state** (core S1–S3), put whole on its
  key. A target reads only its slice.
- **Its type is the adopter's.** A document is of any type: JSON,
  protobuf or packed. This profile adds no rule.
- **Its version is its in-band stamp.** Every put of a state key carries
  a run and a seq in its envelope, and every delete in its attachment
  (core S1, §7.5). That stamp is the version, and nothing else orders
  documents (§2.6).
- **No Zenoh timestamp.** A desired resource of this major is outside
  core §4.3's table. An author MUST NOT set a Zenoh timestamp on a put
  or a delete of it, and MUST answer a GET of it by snapshot (core S1,
  S2, §8.2). `[Sc: §1]` A contract that uses `redundancy.v1` is the one
  exception (below).
  - So a target's seed is a member read of one concrete key (core §4.2).
    Its answer is one page: one live entry, one tombstone, or no entry.
  - An author's clock orders nothing. One whose clock is wrong still
    orders its versions.
- **Two versions are the same** when their runs are the same, in width
  and value, and their seqs are equal.
- **A version is written** as its run, then `/`, then its seq. The run
  is written as a descriptor writes one (core §3.3): 4 lowercase
  hexadecimal digits for a 16-bit run, 8 for a 32-bit run. The seq is in
  decimal, without leading zeros. `0007/12` is seq 12 of the 16-bit run
  7, and `00000007/12` a version of another run.
- **A type MAY carry its own revision,** as in v1: a top-level member
  named `revision` of a JSON Schema type, a field named `revision` of a
  protobuf message, or a field named `revision` of a packed type. It
  orders nothing, and it tells two documents apart (§2.7).
  - **It is at most 4,294,967,295.** A report carries it in 32 bits
    (§2.10). A target MUST refuse whole a document whose revision is
    above 4,294,967,295, with the code `invalid`. `[F: v2/order.json]`
    `[Sc: §4]`
  - The report of that refusal carries no revision: it has no code.
- **A delete has no document,** so its version has no revision.
- **Under `redundancy.v1`.** Every state of a contract that uses
  `redundancy.v1` is a per-key resource (core §4.2). A desired resource
  of such a contract keeps a reply per key, with a Zenoh timestamp
  beside its in-band stamp.
  - Its version is still its in-band stamp.
  - A reply stands for a live entry, and a `reply_del` for a tombstone.
    No snapshot with no entry is answered (§2.8).
  - A conditional read of it is answered whole (core §4.2).

### 2.5 Reading

v1 §2.5 holds: subscribe, then seed; when a target seeds; its author's
instance token; its author absent; R6. `[Sc: §1, §5]` These items change.

**What a read draws.** A read of the slice is a member read of one
concrete key (core §4.2).
- **A live entry** is a put, with its version. **A tombstone** is a
  delete within the author's window, with its version.
- **A snapshot with no entry** is the author's word that it holds no
  document for the target. §2.8 says when a target acts on it.
- **No reply at all** is still no verdict (core O5).

**A conditional re-read.** A target that holds a version asks whether it
is still current, and is answered without the document.
- **The rule.** A target SHOULD make each read of its slice a
  conditional read (core §4.2) while it holds a version: its periodic
  re-read, the watch's read (below), and a seed made again. `[Sc: §13]`
- **The stamp it sends** is that of the latest version it admitted
  (§2.6): the one it holds waiting, else the running act's, else the
  last it acted on or adopted. A target that holds no version sends
  none. Core §4.2 forbids any other stamp.
  - **A snapshot with no entry** it admitted is no version (§2.6). The
    target sends none while that revert runs. It sends none after it
    either, ended or failed.
- **Answered unchanged,** by the held stamp it sent, the target judges
  nothing. Its author holds that version still. It is the author's own
  word of the version, so it confirms a last-known one (§2.9).
- **Answered whole,** by a snapshot, the target judges the entry as §2.6
  says. An author built before the conditional read always answers so.
- **A held stamp it did not send** is no answer (core §4.2, `held`).
- **It carries no time.** An unchanged answer says nothing of the
  document's age, and confirms no horizon.

**What a read waits.**
- **Across a face.** A target across a constrained face that states a
  reply timeout ([`link.v2`](../link/v2.md) §2.20) MUST wait at least
  that long for its seed and for each re-read. `[Sc: §13]` Core §8.1
  says SHOULD of every caller. A target's read that gives up early is
  answered all the same, and the answer crosses for nothing.
- **One read at a time.** A target MUST NOT read its slice while a read
  of it is outstanding. `[Sc: §13]` A seed that falls due meanwhile is
  made when that read ends.
- **A read that ends at its timeout** is no verdict (core O5). The
  target makes it again at its next trigger, a period or a heartbeat,
  never sooner.
  - v1 §2.5's seed made again soon still stands for a GET that ended
    with no reply before its timeout.
- **A period below the timeout** is refused at the target's start, as
  an invalid binding is (v1 §2.1). Such a target would always hold a
  read outstanding.

**The watch.** A far target can let its author's heartbeat say when to
read, in place of a period.
- **The condition.** The desired resource declares a horizon above 0
  (§2.2), so it is a collection of its author's heartbeat (core §7.5).
  And that heartbeat reaches the target: the heartbeat covering the
  author's interface, or the owner heartbeat that holds its group
  (`freshness.v2` §2.4).
  - A target subscribes to both forms' keys, as a `freshness.v2`
    subscriber does (`freshness.v2` §2.5). Its Consume grant covers them
    (core §11.1).
- **What it reads.** The target reads one section: its author's desired
  collection's digest and live count.
  - It holds one member, so it cannot compute that digest. It can see it
    move.
  - It reads each heartbeat by `freshness.v2` §2.5's steps, with the
    author's revision. A heartbeat of another revision (`revision`), a
    refused one (`refused`) and an older one (`older`) are not read.
  - A group of an owner heartbeat is read as a heartbeat is, its
    sequence the owner heartbeat key's. A group whose sections
    `freshness.v2` §2.5 does not read is a heartbeat not read. An owner
    heartbeat with no group for the author's interface has no section.
- **What it expects.** The target keeps the section it expects: a
  digest and a live count, or none. It starts with none.
- **The rule.** A target that watches MUST decide, for each heartbeat
  and each answer, exactly as the fixture does. `[F: v2/watch.json]`
  `[Sc: §14]` It takes the first of these that answers:
  1. **Not read.** After a heartbeat of another revision or a refused
     one, the target expects none. It makes no read for it, and the
     heartbeat moves no sequence.
  2. **Older.** In the last read one's run, its seq is not after that
     one's, by core §4.3's serial order. Nothing changes, and it moves
     no sequence.
  3. **Out of sequence.** Any other heartbeat is read, and is the last
     read one from then on. One of another run than the last read one's,
     or whose seq is not that one's plus 1 modulo 2^24, follows a change
     the target did not see. The target expects none, and goes on to
     step 4.
  4. **No section.** The collection's map bit is 0. The target expects
     none, and makes no read for it (`no_section`).
  5. **Unmoved.** The section is the one it expects. Nothing is read
     (`unmoved`). This is the usual case.
  6. **Moved.** The section differs, or the target expects none. It
     makes one conditional read of its slice (`read`). Where a read is
     outstanding it makes none (`outstanding`).
- **It MUST read** when its section moves, after a heartbeat lost and
  after a heartbeat of another run, as steps 3 and 6 say.
  `[F: v2/watch.json]` `[Sc: §14]`
- **The answer.**
  - **Unchanged:** the target expects the section of the heartbeat that
    made it read, where it still holds the version it sent. Where it
    holds another by then, it expects none.
  - **Whole:** it judges the entry (§2.6), and expects none. The next
    heartbeat makes it read once more, and that read settles what it
    expects.
  - **No answer,** a timeout or a held stamp it did not send: what it
    expects does not change. The next heartbeat is its next trigger.
- **Its own change costs nothing.** A target that admits a version of
  its slice heard live MAY move the digest it expects itself. The digest
  is an XOR of one value per live member (core §7.5), and the target
  knows its own member's key and its old and new stamps.
  - A put over a put XORs the old value out and the new one in.
  - A delete XORs the old value out, and the live count falls by 1.
  - A put over a delete XORs the new value in, and the count rises by 1.
  - It moves it only where it expects a section and holds a version.
  - A target that does not move it reads once at the next heartbeat.
- **Never a confirmation.** A target MUST NOT read an unmoved section as
  its author's confirmation of the version it holds. `[F: v2/watch.json]`
  `[Sc: §14]` It reads the section for one thing: whether it moved.
  - An unmoved section confirms no last-known version (§2.9).
  - A document past its horizon stays in force (§2.2).
- **At most one read per heartbeat.**
- **With no heartbeat,** the deployment's period stands (v1 §2.5), each
  re-read conditional. That is a resource with no horizon, a heartbeat
  that does not reach the target, and one the target cannot read: of
  another revision, or in a group whose catalog it does not hold.
  - A target that was to watch and reads no heartbeat says so, where it
    says what its seed found.
- **Any member's change wakes every watcher.** The digest covers the
  collection. So one target's new document makes each watching target
  read once. An author that changes often, for many far targets, is
  cheaper on a period.

**A periodic re-read** stays a deployment's setting, as in v1.

### 2.6 The order of versions

This section replaces v1 §2.6.

A target holds the version it last acted on or adopted (§2.7). It
remembers, per run, the highest seq it acted on or adopted a version of
in this process (below). It judges each version it receives against the
one it holds and the runs it remembers. While an act runs, it judges it
against the running act's version, and then against the one it holds
waiting (§2.7). A target MUST judge each version exactly as the fixture
does: `[F: v2/order.json]` `[Sc: §2]`
1. **No envelope:** a sample whose payload carries no in-band stamp. A
   target MUST NOT act on one, and ignores it (`unstamped`): its author
   broke core S1. Nothing it holds changes. `[F: v2/order.json]`
2. **Nothing held:** the first version a target receives in a process is
   admitted, whatever its stamp, and acted on.
3. **The held version's run:** a version of that run is ordered by seq.
   Seqs compare as integers (core §4.3, "Plain order").
   - higher: admitted;
   - equal: **the same version** (`same_version`), never acted on again.
     One equal delivery is not: its author's own sample or answer of a
     version the target holds from an archive, or holds waiting from
     one, **confirms** it (`confirmed`, §2.9);
   - lower: **older** (`older`), and a target MUST NOT act on it.
     `[F: v2/order.json]` `[Sc: §2]`
4. **Another run** is the author's restart, its failover, or a new run
   it took before its seq would wrap (core §4.3). It is admitted. **But
   never an older version of a run the target remembers.** A version of
   a remembered run is ordered by seq against the highest the target
   acted on or adopted under that run, whichever run is held, and from
   whichever path it came. Lower is **older**, and a target MUST NOT act
   on it. Equal is **the same version**. Higher is admitted.
   `[F: v2/order.json]` At a snapshot's asof it reverted on, equal is
   older too (§2.8).
5. **Admitted, and the same document:** an admitted version whose
   document is equal to that of the last version the target acted on or
   adopted (§2.7) is **adopted** (`adopted`), without an act. Any other
   admitted version is acted on (`act`, or `revert` for a delete).

- **What it remembers.** A target keeps, per run, the highest seq it
  acted on or adopted a version of in this process. It keeps it for at
  least the 16 runs it most lately acted on or adopted a version of.
  - A run it forgot beyond them is read as a new one (step 4). So a
    stale value of it can be acted on. That is the residual of an author
    that took more than 16 runs within one process of its target.
  - A new process forgets every run, as it forgets every act (§2.7).
- **While an act runs,** a version is judged against the running act's
  version by steps 3 and 4, then against the one held waiting: by seq
  within its run, and admitted under another run. Equal to the one
  held waiting, it is the same version. A version admitted so waits
  (`held`), in place of the one that waited.
- **A snapshot with no entry** names no version. §2.8 judges it.
- **Across an author's restart.** The new instance writes under a new
  run, and puts again each document it keeps (§2.11). Each is another
  run's version of the same document, so it is adopted (step 5). A
  target's report moves to the new version, and nothing is applied.
- **The residual, kept from v1.** A value of an old run can still be in
  transit when the target has acted on the new run's first value. Where
  its seq is higher than any the target acted on under the old run, it
  is admitted (step 4). The target then holds the old run's document
  until its author's next put.
  - That is core §4.3's residual risk, accepted here as v1 accepts it.
  - It follows every new run: a restart, a failover, a new instance
    minted in the author's own session, and a run taken before the seq
    wraps.
  - A conditional read makes it visible: the author answers whole, since
    the target holds another version. It does not heal it. The answer is
    of a remembered run, and is the same version or an older one.
- **Fencing a stale author** is `redundancy.v1`'s, as in v1.

### 2.7 Acting

v1 §2.7 holds, each "run" of the target read as its process.
`[F: v2/order.json]` `[Sc: §2, §4, §5, §6]`
- **A revision above 4,294,967,295** is refused whole, `invalid` (§2.4).
- **Where a refusal points** is v1's. The report carries the place as an
  index (§2.10).
- **An author's new instance** is another run, whether it restarted or
  minted in its own session. Its put of the same document is adopted.

### 2.8 Absence, deletes and cancellation

v1 §2.8 holds, but for its tombstone window. `[Sc: §3]`
- **A delete reverts,** heard live or read as a tombstone, as v1's
  delete and `reply_del` do. `[F: v2/order.json]` `[Sc: §3]`
- **A snapshot with no entry reverts under the held run.** A target that
  holds a document's version of the snapshot's run, with a seq at or
  below the snapshot's asof, reverts to its baseline (`revert`).
  `[F: v2/order.json]` `[Sc: §3]`
  - **Why that run.** It is one instance of the author. It put the
    document, and it has since deleted it beyond its window.
  - **Its report** is `reverted`, with no observed version: the
    delete's stamp left with the window (§2.10).
  - **One that fails** is `failed`, `source` `baseline`. It keeps the
    observed version it had, with its revision: the document's it was
    reverting. `[F: v2/order.json]` With none, its report would break
    `observed_outcome` (§2.10).
  - **What it records.** The target remembers the asof as the seq it
    acted on under that run. So a version of that run at or below the
    asof is older (§2.6).
  - **A seq above the asof.** A snapshot of the held run whose asof is
    below the held version's seq was built before that version. It is
    older (`older`).
- **Never under another run.** A target MUST NOT revert on a snapshot
  with no entry under another run than its held version's.
  `[F: v2/order.json]` `[Sc: §3, §15]` It is no verdict (`no_verdict`).
  - A paced author answers so for a document it has not put again
    (§2.11). So does one restarted with no record.
  - A target that holds no document's version has nothing to revert: no
    verdict either.
- **While an act runs,** a snapshot with no entry is judged against the
  running act's version, then against the one held waiting, each as
  above. Admitted by both, it waits as a delete does.
  - A version that arrives while it waits is judged against its asof:
    of its run, at or below the asof, it is older.
- **After it,** the target holds no document. A delete it admits next is
  a delete after a delete, adopted (§2.7), and gives the report its
  version.
- **Only on positive evidence,** as in v1. No reply, a timeout, a
  refused read and another run's snapshot with no entry are each no
  verdict.
- **The window rule relaxes.** v1 §2.8's rule on a deployment's
  tombstone window goes, for a target's sake. A delete made during an
  outage longer than the window reaches the target at its next read,
  as a snapshot with no entry.
  - **Unless the author also restarted.** Its new run's snapshot with no
    entry is no verdict. A target cut off across a delete past the
    window and a restart keeps the deleted document in force. `[Sc: §15]`
  - **An archive's window** is still core S3's.
  - **A template whose first chunk is a parameter** has no snapshot key
    (core §4.2), and keeps its floor across a face
    ([`link.v2`](../link/v2.md) §2.11).
- **Ending an act is a document,** as in v1.

### 2.9 Last-known

v1 §2.9 holds. `[F: v2/order.json]`
- **An archive's record** keeps the document's envelope (core §4.4), so
  its version is the author's.
- **Confirmed by the author:** its sample, its snapshot's entry, or its
  unchanged answer to a conditional read carries the same version
  (§2.5).

### 2.10 The report

This section replaces v1 §2.10.
- **The standard Report.** A target MUST report each role it holds on a
  desired resource of this major in a `Report` (§3): the member of a
  report resource of its own contract, which it puts as its own state
  (core S1–S3). `[F: v2/reports.json]`
- **Put before the tokens, and after each change.** A target MUST put
  its first report of each role before its tokens (core §8.2), `source`
  `baseline`. It MUST put it again whenever an act ends, a version is
  adopted (§2.7), the author confirms a last-known version (§2.9), or a
  call changes what is in force. `[Sc: §1, §5]`
- **It names no key.** v1's report named its slice's key, 59 bytes or
  more of text. Here the report resource names its role.

**The report resource.** `desired.report` names the role a report
resource reports. A reader MUST read a report resource's declaration
exactly as the fixture does. `[F: v2/declarations.json]`
- **Its value** is a string, in one of two forms. A name holds at least
  one character, and no brace. A value in neither form names nothing:
  - **a role's name:** a requirement of the same contract. The resource
    has no parameter, and its one member is that role's report;
  - **a parameter in braces,** as `{topic}`: the resource's one
    parameter. Each member is the report of the role its key's value of
    that parameter names, slugged as any parameter value is (core §1.4).
- **One report resource per role.** Two report resources of one contract
  that can report one role make both declarations invalid.
- **A declaration is invalid** for each of these, in this order. After
  `value`, no later check reads the value. After `not_a_param` or
  `rest_param`, `param_not_role` is skipped:
  - `not_state`: the resource is not `state` or `@state`;
  - `value`: not a string in one of the two forms;
  - `not_a_role`: a name that is no requirement of the contract;
  - `not_a_param`: braces around a name that is no parameter of the
    template;
  - `rest_param`: braces around a rest parameter;
  - `param_not_role`: a template parameter the value does not name;
  - `not_report`: the resource's type is not the profile's `Report`
    (§3);
  - `pointers`: `desired.pointers` is no table of places (below);
  - `details`: `desired.details` is no table of lines (below);
  - `two_reports`: another report resource of the contract names the
    same role, or one of the two names a parameter.
- **A resource without the key** is no report resource. On it,
  `desired.pointers` and `desired.details` mean nothing.
- **Of any kind.** A resource of another kind that holds the key is a
  report resource. Its declaration is `not_state`. It still names its
  role, to `two_reports` and to a tool's finding (below).
  `[F: v2/declarations.json, v2/slices.json]`
- **`two_reports` follows every reason but `value`.** It reads only the
  names. `[F: v2/declarations.json]`

**Its fields** (§3). `[F: v2/reports.json, v2/order.json]`
- `source`: what is in force: `baseline`, `desired` or `call`, as in v1.
- `outcome`: the last act's, which an adoption keeps. `not_acted` says
  no act yet in this process.
  - `converged`: applied whole. `source` is `desired`, and `in_force`
    `observed`.
  - `refused`: nothing applied. `source` and the version in force are as
    they were.
  - `failed`: applied in part. `source` is `desired` for a put and
    `baseline` for a revert, and `in_force` `none`.
  - `reverted`: a delete or a snapshot with no entry acted on. `source`
    is `baseline`, and `in_force` `none`.
- **A call** makes `source` `call` and `in_force` `none`. The rest
  stays.
- `last_known`: true when the observed version was read from an archive
  (§2.9).
- **The observed version** is the last the target acted on or adopted
  in this process. It is `observed_seq` and one of `observed_run16` and
  `observed_run32`, by its run's width. `revision` is its document's
  own, where its type carries one.
  - A revert on a snapshot with no entry that ends `reverted` has no
    observed version. One that fails keeps the one it had (§2.8). A
    snapshot names no version.
- `in_force`: the version wholly in force.
  - `observed`: it is the observed version. That is so after an act
    that converged, and after an adoption that followed one.
  - `other`: it is another version, which `in_force_seq`, one of
    `in_force_run16` and `in_force_run32`, and `in_force_revision` name.
    That is so after a refusal over a document in force.
  - `none`: no version is wholly in force: the baseline, a call, or a
    failed act.
- `code`, with `refused` or `failed`: the profile's five codes, as in
  v1. A code of the type's own is written as the escape, and a tool
  says "the type's own".
- `pointer`: where in the document, as an index into the report
  resource's `desired.pointers`.
- `detail`: a line for a person, as an index into its `desired.details`.

**The two tables** are the report resource's annotations.
- **`desired.pointers`** is an array of 1 to 255 strings. Its first is
  `""`, the document itself. Each is a JSON Pointer (RFC 6901): empty,
  or starting with `/`, with every `~` followed by `0` or `1`. None is
  there twice. A resource without the key has the table `[""]`.
- **`desired.details`** is an array of at most 255 strings, each of at
  least one character. A resource without the key has an empty table.
- **An index** is an entry's place in its table, from 0.
- **A place the table holds** is written as its index.
- **A place it does not hold** is written as its nearest listed
  ancestor: the longest listed pointer, other than `""`, that the place
  continues with a `/`. With none, it is written `out_of_range`.
  - So index 0 says the document itself is refused, never "somewhere".
- **A refusal that points nowhere** carries no `pointer`.
- **A line the table does not hold** is written `out_of_range`. The
  words stay in the target's log. A refusal with no line carries no
  `detail`.
- **A reader reads an index** with the revision of the target's
  contract that its descriptor names, or across a face its catalog
  names (core §8.6). An index past the table it holds is a later
  revision's: it shows the number. A tool with neither shows numbers.
- **A deployment appends.** A change to either table is
  `annotations_changed`, a review (core §9.8). A revision that appends
  keeps every index.

A target MUST write a refusal's place and line as this says.
`[F: v2/reports.json]`

**A target's report MUST be consistent.** A reader checks these, in this
order, and a report that breaks one is malformed: `[F: v2/reports.json]`
- `escape`: `source` or `outcome` is the escape, a value a later text
  names. A reader reports it alone, and checks nothing more.
- `run_fields`: the fields of one version do not hold together. A
  version is **stated** by its seq and exactly one of its two runs. The
  finding is any of a version's four fields present with no version
  stated. It is checked of the observed fields, and of the `in_force`
  ones.
- `observed_outcome`: an observed version stated with `not_acted`; or
  `converged`, `refused` or `failed` with none stated.
- `refusal`: `code`, `pointer` or `detail` with an outcome other than
  `refused` or `failed`; or one of those two without `code`.
- `source`: `desired` with no observed version stated; `converged` with
  `baseline`; `reverted` with `desired`.
- `in_force`: any of these:
  - `observed` or `other` with a `source` other than `desired`, or with
    `failed`;
  - `converged` with `desired`, and an `in_force` that is not
    `observed`;
  - `observed` with no observed version stated;
  - `other` with no `in_force` version stated, or with one that is the
    observed version;
  - an `in_force` field present with `none` or `observed`.
- `revision_on_revert`: `reverted` with `revision`.
- `last_known`: `last_known` true with no observed version stated.

**How a reader reads one.** A reader MUST read a report exactly as the
fixture does. `[F: v2/reports.json]`
- **Its bytes** are a packed record's, read as core §7.6 reads one, its
  tag CH's. A record that reading refuses is **unreadable**, for the
  refusal core §7.6 names: `tag`, `length`, `code`, `extension` or
  `pad`.
- **A later text's fields,** behind the marker, are ignored (core §7.6).
- **Then the checks above.** A report with a finding is **malformed**.
  A tool answers nothing from an unreadable or a malformed report
  (§2.17).
- **Every report a target writes reads back to its bytes.** The checks
  leave one record for one report.
  - Two records a reader meets read with no finding, and do not write
    back. One holds a later text's bits behind its marker. In the other,
    `code` is 5 or 6. It reads as the escape, written 7 (core §7.6).

**A tool finds a target's report** by type identity and by the
annotation, never by a resource's name. A tool MUST find it exactly as
the fixture does. `[F: v2/slices.json]`
- **The report resources of a role** are the resources of the contract
  that declares the role whose `desired.report` names it: by its name,
  or by a parameter in braces.
- **None names it:** no report was read.
- **Two or more name it:** the report is **unreadable** (`two_reports`).
  The target's contract says two things of one role.
- **One names it,** and its declaration is invalid: no report was read,
  the reasons beside.
- **One names it,** declared: the report is the reply on its member's
  key, read by S4's GET. That key is the resource's, its parameter
  filled with the role's name. With no reply, none was read. A record
  core §7.6 refuses is **unreadable**.
- **Two instances' reports on one key** are one reply after a tool's
  merge (observer §4.1), as in v1.

**Its horizon** is the target's to declare, as in v1, under the
`freshness` major its contract uses.

### 2.11 The author

v1 §2.11 holds, with these changes. `[Sc: §4, §6]`
- **"Its stamps" goes.** No rule orders an author's stamps by its clock,
  and core §4.3's catch-up plays no part. A run is never reused, and a
  seq never wraps (core S7).
- **A new instance takes a new run** (core §4.3), by a restart or a
  re-mint. v1's "Its zid" goes with it. An author MUST put again each
  document it keeps under its new run before it answers a GET with it,
  and MUST delete again each key its record holds a delete of within its
  window, as v1 §2.11 says of a new instance. `[Sc: §4, §6]`
- **No target acts again.** Each document put again is another run's
  version of the same document, adopted (§2.6). Each delete made again
  is a delete after a delete, adopted too.
- **Before it has put a document again,** an author answers a read of
  its key with a snapshot of no entry, under its new run. That is no
  verdict at its target (§2.8). A tool reads it `author_silent` (§2.17).
- **What the record holds.** An author's record SHOULD hold each
  document as it was put, by its key, and each delete it made within its
  tombstone window with when it made it. `[Sc: §6]` It holds no stamp.
- **With no record,** the deletes it made before are lost. A target cut
  off across one keeps the deleted document in force (§2.8).
- **Only on a change.** Under `freshness.v2` an author puts no document
  again to confirm it (`freshness.v2` §2.4).

### 2.12 The kill switch

v1 §2.12 holds. `[F: v1 bindings.json]` `[Sc: §8]` An unbound role's
report is the baseline's record: `source` `baseline`, `not_acted`. It
has no key to leave out, so it is the report any role starts with. A
tool answers the kill switch from the descriptor, as in v1.

### 2.13 Population

v1 §2.13 holds. A desired resource of a large population declares no
horizon above 0 (§2.2).

### 2.14 Constrained faces

v1 §2.14 holds, with these changes.
- **A far target waits the face's reply timeout** (§2.5).
- **It watches where its author's heartbeat crosses** (§2.5), and
  re-reads on a period where it does not. Either way its re-read is
  conditional.
- **The window has no floor** for a desired resource of this major with
  a snapshot key ([`link.v2`](../link/v2.md) §2.11, §2.8).
- **Liveness.** A desired resource with a horizon shows its author's
  liveness by its heartbeat, where that crosses (§2.2).
- **Packed, where exposed.** A contract that lists `link.v2` types each
  resource it exposes as packed (`link.v2` §2.17). That binds an exposed
  document type and an exposed report. A document read across a face by
  grant, never pushed, is not exposed.

### 2.15 The tokenless set, and access control

v1 §2.15 holds. `[Sc: §1]` A target's Consume grant on its author's

### 2.16 `config.v1` and `config.v2` as targets

v1 §2.16 holds, of a `config.v1` owner and of a `config.v2` owner
([`config.v2`](../config/v2.md) §2.18). `[Sc: §12]`
- **Its report is its own,** in its own record, with its own codes.
- **Its revision** is at most 4,294,967,295, as `config.v2` §2.18 and

### 2.17 What a tool concludes of one target

v1 §2.17 holds, with these changes. A tool MUST conclude exactly as the
fixture does. `[F: v2/conclusions.json]` `[Sc: §9]`
- **Step 3, its report,** is found as §2.10 says. No slice is needed to
  find it.
- **Step 4, its report's age,** is read by the `freshness` major of the
  target's contract (§2.10). Under `freshness.v2` it is the report's
  confirmation (`freshness.v2` §2.5, §2.6). No Zenoh timestamp ages it
  (core §4.3).
- **Step 5** reads the report's fields. `not_acted` is v1's "no
  `observed`".
- **Step 6, the author's version,** is its snapshot entry's: a live
  entry's, or a tombstone's.
  - **A snapshot with no entry, under the run of the report's observed
    version,** is the author's word that it holds no document. By the
    report's `outcome`: **yes**, `reverted`; any other, **not yet**,
    `behind`.
  - **A snapshot with no entry otherwise,** under another run or with
    no observed version: **unobservable**, `author_silent`. The author
    restarted, is pacing, or deleted the document. A tool cannot tell.
  - **No reply** is `author_silent`, as in v1.
  - **After a revert on a snapshot with no entry,** the report states no
    version (§2.10). So a tool answers `author_silent` beside such a
    snapshot, until the author's next document. Both sides hold no
    document. No run says they agree. `[F: v2/conclusions.json]`
- **Step 7, the comparison,** is by run and seq:
  - the same version: by `outcome`, as in v1;
  - the same run, a lower seq: **not yet**, `behind`;
  - the same run, a higher seq: **unobservable**, `ahead`;
  - another run: **not yet**, `other_epoch`. The author wrote under a
    run the target has not acted on.
- **How long behind** is decided by v1's first way alone: the same
  answer in every reading over the window. A version has no time, so
  v1's second way goes.
- **The slice from the target alone** goes. A report names no key, so
  it cannot choose among candidates.
  - A tool with no revision of the author's interface in hand has no
    slice. It answers §5's last three questions from the report.
  - It answers the first by the author's presence, as v1's step 6
    does. `[F: v2/conclusions.json]`
    - absent: **not asked**, `author_absent`;
    - possibly incomplete: **unobservable**,
      `author_presence_incomplete`;
    - otherwise: **unobservable**, `author_not_read`.

### 2.18 Beside `desired.v1`

`desired.v1` and `desired.v2` run side by side. Each author's revision
says which it uses.
- **An author moves by a revision** of its contract: `uses` goes from
  `desired.v1` to `desired.v2`. That is a review (core §9.8). From that
  revision on, its desired resource is answered by snapshot.
- **A target reads its author's revision** as core §4.2 reads which
  resources are per key. It is the one the author's descriptor names for
  the version's run. Where no descriptor reaches the target, it is the
  deployment's word. A target that holds another revision reads its
  author's, never its own alone.
  - It orders a `desired.v1` author's versions by v1 §2.6, and a
    `desired.v2` author's by §2.6 here.
- **Targets first.** A target built before this major, bound to an
  author of it, reads each version by v1 §2.6. What it reads depends on
  the routers between them and on the target's own session (core §4.2,
  "Observing S1"). `[Sc: §16]`
  - **Where none timestamps,** each put arrives with no Zenoh timestamp.
    The target reads it as unstamped, and acts on none. That is safe,
    and inert.
  - **Where one timestamps,** as a router does by default, each put
    arrives with the router's id. A target whose own session timestamps
    stamps each put it receives with its own. Either way the target acts
    on it. Each delete and
    each reply arrives with none, so the target never reverts. It runs a
    document its author deleted.
  - **So a deployment MUST NOT bind** such a target to such an author
    where a router between the two, or the target's own session,
    timestamps. `[Sc: §16]` It moves its targets first.
- **The report's type changes kind,** which is breaking (core §9.8). A
  target's contract takes a new major, or adds a report resource of
  this major in a minor.
  - A role bound to a `desired.v1` author is reported in a
    `desired.v1.Report`, and one bound to a `desired.v2` author in a
    `Report`. Neither carries the other's version.
  - A target that serves both declares a report resource of each. It
    puts the one of its author's major.
  - **One major's report alone** cannot report a role bound to an author
    of the other. That binding is invalid. A target given such an
    author's revision at its start MUST refuse to start, as v1 §2.1
    refuses `two_documents`. `[Sc: §16]` It names the role.
  - **Learnt after its start,** from its author's descriptor, such a
    revision stops the role. While the descriptor names it, a target
    MUST NOT act on a version of that author's. `[Sc: §16]` It says so
    where it says what its seed found, and its report stays as it was.
    - **A new run is read first.** A target MUST NOT judge a version
      under a run whose descriptor it has not read, nor a snapshot with
      no entry under it, before it reads its author's descriptors for
      that run. `[Sc: §14, §16]` It reads them once (core §3.3). It
      then judges what that run carries by the revision they name.
    - **A read that names none** leaves the deployment's word: no
      descriptor reached the target, as across a face, or the read
      failed.
    - **None states the run yet.** Where descriptors reach the target,
      a read that finds none stating the run holds that run's versions
      still. A read that draws no descriptor at all finds none stating
      it. The target reads again when an instance token of the author's
      appears after it first saw the run: the token follows its
      descriptor (core §8.2, steps 3 and 4). Only a read after such a
      token that names none leaves the deployment's word. `[Sc: §16]`
      An author MAY put a version before its descriptor (core §8.2
      orders a value before step 4, not after step 3), so the first
      read can find nothing.
      - **Where descriptors reach the target** is the deployment's, never
        what a read drew: wherever the author's instance tokens reach
        it, which is never across a face (core §8.1). A target whose
        author has not started yet holds too.
      - **The read at the token** that draws none MAY be made again, a
        few times and soon, as v1 §2.5's seed is: a token can reach the
        target before the route to the author's queryable does.
      - **A run first seen while its instance's token stood** is read at
        once. Unstated, it waits for the next appearance.
    - **Why.** An author that restarts on a revision of the other major
      puts its first version around its new descriptor (core §8.2),
      before a target has read it. Judged by the previous run's word,
      that version would be acted on.
    - **The cost** is one read's wait at each new run. Each version of
      that run that arrives meanwhile waits too, a read's answer among
      them. §2.6 orders them by seq, whatever their order of arrival.
- **A tool reads both,** per role: the report by its type identity, and
  the author's version by its revision's major.
  - **With no revision of the author's in hand,** a tool reads the role
    by the report it finds. A role a `desired.report` names is this
    major's. It is `desired.v1`'s where its packed report drew no reply
    and a `desired.v1.Report` names its slice by `key`. Any other role
    is `desired.v1`'s.

## 3. The standard schema

No contract. The profile's standard schema is the packed file
[`desired.v2.json`](desired.v2.json) (core §10 point 1, §9.4). Its type
is the profile's in any artifact whose id is one of these, and in no
other, whatever its types are named (core §7.1):

| Artifact id | Revision | What it holds |
|---|---|---|
| `sha256:1ac893a1cb14a102cc1b01ea526a317b19390a8ed6c40707f08754f4429532dd` | The first | `Report` |

`[F: v2/schema.json]` A target's contract lists the file, by its path or
a copy's, byte for byte or JCS-equal, in `[schemas] packed`. It types
each report resource `packed:Report`, or by core §7.1's qualified
spelling where another listed file defines a `Report`.

```text
source              enum baseline, desired, call; an escape                      2 bits
outcome             enum not_acted, converged, refused, failed, reverted; an escape   3
last_known          bool                                                         1
in_force            enum none, observed, other                                   2
observed_run16      int 0 to 65,535, optional                                    1 + 16
observed_run32      int 0 to 4,294,967,295, optional                             1 + 32
observed_seq        int 0 to 16,777,215, optional                                1 + 24
revision            int 0 to 4,294,967,295, optional                             1 + 32
in_force_run16      int 0 to 65,535, optional                                    1 + 16
in_force_run32      int 0 to 4,294,967,295, optional                             1 + 32
in_force_seq        int 0 to 16,777,215, optional                                1 + 24
in_force_revision   int 0 to 4,294,967,295, optional                             1 + 32
code                enum undecodable, reach, sensitive, invalid, apply; an escape; optional   1 + 3
pointer             int 0 to 254, reserved out_of_range, optional                1 + 8
detail              int 0 to 254, reserved out_of_range, optional                1 + 8
"..."               the extension marker                                         1
```

- **Its tag** is 12 (core §7.6). So a report's put has CH `0x0c` under a
  16-bit run of its target, and `0x1c` under a 32-bit run.
  `[F: v2/reports.json]`
- **Its sizes.** A record is 20 bits at the least. A consistent one is
  215 at the most.

| A report | Bits | Record | Put's payload |
|---|---:|---:|---:|
| the baseline, nothing observed; the kill switch's | 20 | 3 B | 9 B |
| converged, a 16-bit run, a revision | 92 | 12 B | 18 B |
| converged, a 32-bit run, a revision | 108 | 14 B | 20 B |
| refused over a document in force, with a code, a place and a line | 183 | 23 B | 29 B |
| the same, both versions on 32-bit runs | 215 | 27 B | 33 B |

  The payloads are under a 16-bit run of the target, 6 bytes of
  envelope. `[F: v2/reports.json]`
- **It grows behind its marker.** A later text appends optional fields,
  which a reader of this one ignores (core §7.6).
- **It uses core §7.6's kinds as they stand.** A word no table names is
  `out_of_range`, and stays in the target's log.

## 5. What a tool may conclude

v1 §5 holds: its four questions, its three kinds of "unestablished", and
its premises. The fixture
[`v2/conclusions.json`](conformance/v2/conclusions.json) states the
tokens, as v1's does.

| Question | What changes |
|---|---|
| Has the target converged on its author's current document? (§2.17) | The versions compared are runs and seqs. `other_epoch` is another run. A snapshot with no entry answers only under the report's observed run. |
| Is the target's last act refused or failed? | The refusal's place and line are indices, read with the target's contract. A code of the type's own is shown as "the type's own". |
| Is what the target acted on last-known? | Nothing. |
| Is a desired document in force? | `in_force` `observed` or `other` is v1's `in_force`; `none` with `source` `desired` is `partial`. |

**What a tool shows.** A version is shown as `<run>/<seq>` (§2.4), never
as a time. A held stamp in a reply is shown as "unchanged".

**Why a target behind** cannot be told from the reports alone, as in v1.
With a watch, what the target expects and its last read say more.

| `desired.v1` | `desired.v2` | Why |
|---|---|---|
| The version is the author's Zenoh timestamp: a time and an id (§2.4) | The in-band stamp: a run and a seq (§2.4) | Every put already carries it. Order no longer reads a clock. |
| A per-key resource: a reply per key, a `reply_del` within the window | Answered by snapshot: an entry, a tombstone, or no entry (§2.4, §2.5) | The resource leaves core §4.3's table. |
| Ordered by time within an id, 16 ids remembered (§2.6) | By seq within a run, 16 runs remembered (§2.6) | "id" read as "run", "time" as "seq". |
| An author never stamps at or below its last stamp, by rule (§2.11) | Gone: a run is never reused (core S7) | The rule existed because order rested on a clock. |
| A re-mint in the author's session keeps its zid, ordered by time | Another run, adopted (§2.6) | A new instance takes a new run. |
| A re-read answered with the whole document | A conditional read, answered unchanged in 6 bytes (§2.5) | The periodic re-read asked a yes-or-no question. |
| A period, the deployment's | The watch where the author's heartbeat reaches, else the period (§2.5) | Not asking saves more than asking less. |
| A caller's timeout, the caller's, with core §8.1's advice | A far target waits at least the face's reply timeout, by rule (§2.5) | A read that gives up early still costs its reply. |
| A delete past the window never reaches a target cut off (§2.8) | It reaches it as a snapshot with no entry, under the held run (§2.8) | A complete snapshot omits what was deleted. |
| The window covers the longest outage, by rule (§2.8) | No such rule for a target's sake (§2.8) | The snapshot says it. |
| A `desired.v1.Report`, JSON, with its slice's key (§2.10) | A packed `Report`, its role named by `desired.report` (§2.10) | 294 bytes became 18. |
| `refusal.pointer` and `refusal.detail`, text | Indices into two tables of the target's contract (§2.10) | A table's word costs a byte. |
| A revision up to 2^64 − 1 | Up to 4,294,967,295 (§2.4) | The report carries 32 bits. |
| A target behind for longer than, by the stamp's time (§2.17) | By the window alone (§2.17) | A version has no time. |
| `freshness.ttl_s = 0`, advised (§2.2) | A horizon is the watch's budget (§2.2) | The heartbeat carries no document. |

**Three guarantees change.**
1. **A document's revision is at most 4,294,967,295.** v1 allowed
   2^64 − 1. A document above the bound is refused whole (§2.4).
2. **A target reverts on more than a delete.** v1 reverted on a delete
   or a `reply_del` alone. Here a snapshot with no entry reverts too,
   under the held version's run and no other (§2.8). So a delete past
   the window now reaches a target, unless its author also restarted.
   That one case is left as v1 left every delete past the window.
3. **v1's residual is kept, and follows every new run.** A value of an
   old run in transit can be acted on after the new run's first (§2.6).
   v1 ordered a re-mint in the author's own session by time, under one
   zid. Here it is another run, so the residual covers it too.

**What a tool loses.** "Behind for longer than" by a version's age
(§2.17), and the slice from the target alone. After a revert on a
snapshot with no entry, it reads no convergence until the next document
(§2.17).

**What did not change:** each version acted on once, never an older one
within a run, adoption without an act, a refusal whole, last-known
flagged, a restart acting again, the kill switch, one author, and the
report before the tokens.

## Appendix B. The bytes, computed

Every figure here is computed from the layouts, through the wire
baseline's model
([`wire-baseline`](../../../docs/zk2/measurements/wire-baseline/README.md)).
None was measured on a wire. They are for zenoh-modem's simulated radio,
under its lean stack, with the face's 3-byte frame and 16-bit runs.

| A re-read of a 59-byte key | Request | Reply and final | The two SDUs |
|---|---:|---:|---:|
| `desired.v1`, W2's 44-byte document | 12 B | 166 + 6 B | 222 B |
| conditional, unchanged | 21 B | 94 + 6 B | 159 B |
| conditional, changed: the document's snapshot | 21 B | 154 + 6 B | 219 B |

- **Of the unchanged reply's 94 bytes,** 61 are its key and 20 its
  replier's id (core Appendix B). The document is W2's, not the
  scenarios', whose `v1` is 40 bytes.
- **A day of re-reads every 300 s** is 63.9 KB under `desired.v1`, and
  45.8 KB conditional.
- **A day of the watch** is the author's heartbeat. For one templated
  collection of cardinality 1,000 with one member live, it is a 17-byte
  payload in a 40-byte SDU. At a 600-s horizon that is 12.1 KB a day. At
  3,600 s it is 2.0 KB, and at 60 s 121 KB, more than polling.
- **A report's put** is a 43-byte SDU when it has converged, where
  `desired.v1`'s was 340 bytes in two.

## Appendix C. The adopters' mappings

No adopter's mapping uses this major yet.
- **ZenSight** (`examples/zk2/zensight/zs.desired.v1.toml`) stays on
