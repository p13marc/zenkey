# `link.v1`: what crosses a constrained face

| | |
|---|---|
| **Text version** | 0.2 ([`CHANGELOG.md`](CHANGELOG.md)) |
| **Status** | draft |
| **Written against** | core 0.30 ([`../../core.md`](../../core.md)) |
| **Uses** | no other profile. Its plan reads [`freshness.v1`](../freshness/v1.md)'s horizon, text 0.3, where a contract declares one (§2.12). |
| **Evidence** | [`conformance/`](conformance/), [`scenarios.md`](scenarios.md) |

A constrained face is a router's link to a part of the network that
cannot carry the bus: a radio at 2,400 bit/s, a satellite channel billed
by the message (core §8.5). `link.v1` says what may cross one, and how a
generator turns that into the router's configuration. It has two halves:
- **the contract's word**, one annotation, `link.exposure`: whether a
  resource is worth carrying across a constrained face at all (§2.2, §4);
- **the deployment's word**, the **face policy**: a file per router that
  marks its faces constrained, and gives each one how the far side
  attaches, which transports it is, what crosses it, at what rate, its
  maximum outage, its batch and its link's rate (§2.1).

From both, a generator derives a **plan** per face: named denies, one
downsampling rule per concrete key, the attachment, the tombstone window
each owner needs, and the liveness evidence that crosses (§2.3). Lints
read the policy, and checks read what a router runs (§2.15).

```toml
# The near router of zenoh-modem's RF node (Appendix B)
system   = "h-3fa9c2d41b7e"                         # hostid.v1
services = ["rf0"]                                  # the services this router carries

[face.rf]
far          = "ground"                             # the far side's principal (core §11.1)
attach       = "client"                             # or "south-region", with `region`
select       = { link_protocols = ["unixsock-stream"] }   # never `interfaces`
class        = "constrained"
expose       = "link"                               # what link.exposure = "link" marks crosses
interval_s   = 60                                   # one put per exposed stream key per minute
max_outage_s = 3600                                 # the floor of each listed owner's tombstone window
batch_bytes  = 220                                  # the radio's MTU bounds the batch
link_bps     = 2400
```

```toml
[resources."sdu/dropped_total"]                     # in modem.v3, which uses link.v1
kind        = "stream"
type        = "json:Counter"
annotations = { "link.exposure" = "link" }
```

## 0. Conventions

The keywords, the roles and the evidence tags are core §0's. Here,
`[F: <file>]` names a fixture in [`conformance/`](conformance/),
`[Sc: §n]` a section of [`scenarios.md`](scenarios.md), and `core` marks
the core's own evidence. References to `docs/zk2/architecture.md` (D9c,
D14, D15, E3, E9, E10, U23), to `docs/zk2/spike-report.md` (S3) and to
`examples/zk2/zenoh-modem/` (the sketch, `link.md`, and its README's
gaps) are informative: every rule is stated here.

Terms:
- **Face**, **far side**: core §8.5's. The **near router** is the router
  whose face it is, and whose file the face policy is. A **far principal**
  is the principal the far side attaches as: a gateway session's, or the
  far router's (core §8.5, §11.1).
- **Face policy**: the deployment file of §2.1. **Plan**: what a
  generator derives from it (§2.3). **Generator**: a tool that writes a
  router's configuration from a plan, as core §11's does from grants.
- **Listed service**: a service the policy's `services` names, on its
  `system`. **Listed interface**: an interface a listed service
  implements.
- **Exposed**: a resource whose `link.exposure` reads `link` (§2.2).
- **Push**: an owner's put or delete of a stream, state or event member,
  and the subscriber declarations that draw it. **Request**: a GET, a
  call, and their replies.
- **Crossing**: a resource whose pushes the plan lets cross a face (§2.7).
- **Messages and flows** are zenoh 1.10.1's access-control names (core
  §11.2). **The nine messages**, in this order: `put`, `delete`,
  `declare_subscriber`, `query`, `declare_queryable`, `reply`,
  `liveliness_token`, `declare_liveliness_subscriber`,
  `liveliness_query`. **The push messages**: `put`, `delete`,
  `declare_subscriber`. **Both flows**: `egress`, `ingress`.
- **Key expressions** in a plan are base-relative (core §1.6), except the
  admin space's `@/**`. A generator writes them under the deployment's
  namespace, as core §11.1 says of grants.
- **A template's pattern** is its key expression below the kind chunk: a
  literal segment as itself, `{p}` as `*`, and `{p...}` as `*/**` (one
  or more chunks, as a rest parameter takes). `sdu/endpoint/{endpoint}`
  is `sdu/endpoint/*`.
- **A resource's name** in a plan is `<iface>/<token>/<template>`, as in
  `modem.v3/stream/sdu/dropped_total`.

## 2. Rules

### 2.1 The face policy

A **face policy** is a TOML 1.0 file, one per near router, written by the
deployment. A generator and a linter MUST read it exactly as the fixtures
do: the same file refused with the same findings, or accepted with the
same warnings and the same plan. `[F: lints.json, plan.json]`

**The top level.**

| Key | Value | Required | Meaning |
|---|---|---|---|
| `system` | a string, a plain chunk (core §1.2) | yes | The system whose services the near router carries. A minted system (`hostid.v1`) is written as minted. |
| `services` | an array of strings, each a plain chunk, none repeated; it may be empty | yes | The **listed services**, on `system`: those whose exposed streams the plan downsamples (§2.8), whose tombstone windows it floors (§2.11), and whose interfaces the exposure denies are written for (§2.7). |
| `face` | a table of faces, each keyed by its name, a plain chunk; at least one | yes | The router's constrained faces. A face the policy does not name is not constrained, and `link.v1` says nothing of it. |

**A face**, `[face.<name>]`:

| Key | Value | Required | Meaning |
|---|---|---|---|
| `far` | a non-empty string | yes | The far principal, named as the deployment's principals are: a user name or a certificate CN, never a zid (core §11.1, §11.3). The plan's denies go into its policy (§2.4). |
| `attach` | `"client"` or `"south-region"` | yes | How the far side attaches (§2.5). `"router"` is refused. |
| `region` | a string of 1 to 32 bytes | with `attach = "south-region"`, and only then | The far router's `region_name`, which the near router's `gateway.south` lists (§2.5). |
| `select` | a table with exactly the key `link_protocols` | yes | Which of the near router's transports are this face. |
| `select.link_protocols` | a non-empty array of zenoh 1.10.1's link protocol names, none repeated: `tcp`, `udp`, `tls`, `quic`, `serial`, `unixpipe`, `unixsock-stream`, `vsock`, `ws` | yes | A transport whose link uses one of them is on the face. |
| `class` | `"constrained"` | yes | The only class at this version. |
| `expose` | `"link"` or `"none"` | yes | `"link"`: exposed resources cross (§2.7). `"none"`: no push crosses, whatever a contract says: a link with no affordable rate, such as a satellite channel billed by the message. |
| `interval_s` | an integer from 1 to 2^32−1 | with `expose = "link"`, and only then | The downsampling interval: at most one put per exposed stream key per interval crosses toward the far side (§2.8). |
| `max_outage_s` | an integer from 1 to 2^32−1 | yes | The longest outage the deployment expects on the face, in seconds (core §8.5): the floor of each listed owner's tombstone window (§2.11). |
| `batch_bytes` | an integer from 1 to 65,535 | yes | The batch the face's link runs with: the least of the configured `batch_size`, the link's MTU and the other end's (core §8.5 and its Appendix B). |
| `link_bps` | an integer from 1 to 2^32−1 | yes | The link's rate, in bits of zenoh's bytes per second: what a batch takes to cross is `batch_bytes` × 8 / `link_bps` seconds (§2.10). |
| `lease_ms` | an integer from 1 to 2^32−1 | no; 10,000 when absent | The transport lease the face's link runs with, zenoh's `transport.link.tx.lease`. |

**What a linter reports.** Each finding has a `code`, a `severity`
(`error` or `warning`), the `face` it is about (or none, for the top
level), and `at`: the key it is about, within the face for a face's key
(`select.link_protocols`), or at the top level (`services`). An error
refuses the policy: no plan is derived from it. `[F: lints.json]`

| Code | Severity | When |
|---|---|---|
| `toml` | error | The file is not TOML 1.0: a parse error, syntax only TOML 1.1 has, or an integer beyond 64 bits, as core §9.1 refuses a contract (E000). `at` is empty. |
| `unknown_field` | error | A key this table does not define, at the top level, in a face, or in `select`. |
| `missing_field` | error | A required key is absent, `face` included. |
| `bad_value` | error | A value of the wrong type or outside its range, a TOML datetime, a face name that is not a plain chunk or a face that is not a table (`at` empty), a `face` table with no face, a `region` with `attach = "client"`, or an `interval_s` with `expose = "none"`. |
| `router_attach` | error | `attach = "router"` (§2.5). |
| `select_interfaces` | error | `select.interfaces`: a face is selected by link protocol, never by interface (§2.14). |
| `unknown_protocol` | error | A link protocol zenoh 1.10.1 does not name. |
| `shared_protocol` | error | Two faces of the policy select a common link protocol (§2.14). Each such face has the finding. |
| `batch_over_lease` | warning | A batch takes more than a third of the lease to cross (§2.10). `at` is `batch_bytes`. |

- **Each key is checked alone.** A key whose value is wrong is reported
  once, and checks that need it are skipped: `region` is checked against
  `attach` only when `attach` is `client` or `south-region`, and
  `interval_s` against `expose` only when `expose` is `link` or `none`.
- **Findings are a set**, sorted by face (none first), then `at`, then
  `code`, each by its bytes.

### 2.2 `link.exposure`: the contract's word

`link.exposure` says whether a resource is worth carrying across a
constrained face. Its value is `"host"` or `"link"`, and `"host"` when
absent. A generator MUST read a resource's exposure exactly as the
fixture does. `[F: exposure.json]`

- **`"link"`**: the resource may cross a face whose policy exposes
  (`expose = "link"`): a stream at the face's rate, downsampled (§2.8), a
  state or an event whole (§2.7, §2.9).
- **`"host"`**: it never crosses a constrained face. The default is
  `host`, so a resource a later minor adds stays home unless its author
  says otherwise.
- **Any other value is not an exposure:** another string (`"LINK"`, v1's
  `"fleet"`), a boolean, a number, an array, a table. A generator MUST
  read it as `"host"`, and fail closed. `[F: exposure.json]` A contract
  linter SHOULD warn of one. The core has no code for it, as no core lint
  reads an annotation's value (`freshness.v1` §2.1 says the same of its
  own).
- **Where it is written**: on a resource, or in `[defaults]` or
  `[defaults.<kind>]` (core §9.3). The exposure is the resolved
  resource's annotation.
- **On an operation** it has no meaning, and a reader ignores it: a call
  crosses by grant, never by exposure (§2.9). `[F: exposure.json]`
  `[defaults]` spreads annotations to every kind, so a contract may resolve
  one there without meaning it.
- **On a requirement** (`[requires.<role>]`) it has no meaning at this
  version.
- **Exposure is the contract's, for every deployment.** It cannot be
  widened for one face, or for one principal, at this version (§2.14).

### 2.3 The plan

A generator derives a plan for each face of a policy, from the policy,
the interfaces each listed service implements (the deployment's, as core
§11.1's input names them), and the contracts of those interfaces. It
MUST derive it exactly as the fixture does. `[F: plan.json]`

| Member | What it is |
|---|---|
| `name`, `far` | The face's name and its far principal. |
| `attach` | `{shape: "client"}`, or `{shape: "south-region", region, gateway}` with the near router's `gateway` block (§2.5). |
| `deny` | The denies, each `{id, flows, messages, key_exprs}`, in this order: `zk`, `adv` and `admin` (§2.6), then the exposure denies (§2.7). |
| `downsampling` | `{id, link_protocols, flows, messages, rules}`, the rules each `{key_expr, freq}` (§2.8); or none. |
| `windows` | Each listed service that owns a state resource, `{service, min_s}`: its tombstone window's floor (§2.11). |
| `liveness` | Each listed service, `{service, evidence}`: the crossing resources that can show it live across the face (§2.12). |
| `findings` | The plan's warnings (below). |

- **Order.** Key expressions within a rule, downsampling rules, windows,
  liveness entries and evidence are sorted by their bytes. Faces are
  sorted by name. Messages are listed in §0's order.
- **Refusals.** A policy with an error has no plan. Neither has a
  deployment that names no interfaces for a listed service
  (`service_unknown`, `at` the service), or names an interface whose
  contract is not given (`contract_unknown`, `at` the interface). Both
  are errors, with no face.
- **The plan's warnings.** It is still derived with them:

  | Code | `at` | When |
  |---|---|---|
  | `templated_exposure` | the resource's name | An exposed stream whose template has a parameter, on a face that exposes: no rule names its members' keys, so it is denied (§2.8). |
  | `carve_out_overlap` | the resource's name | An exposed resource that a deny must include, because zenoh denies by inclusion: it does not cross (§2.7). |
  | `interval_over_horizon` | the resource's name | A crossing stream whose `freshness.ttl_s` is above 0 and below twice the face's `interval_s` (§2.12). |

### 2.4 Where the plan's denies go

- **Into every policy that can match a session on the face.** In zenoh
  1.10.1, a session matches every subject whose properties all match it,
  and across those subjects any allow wins (core §11.2, "every principal"
  compiled into each policy). A deny in one subject's policy is undone by
  another's allow. A generator MUST therefore put every deny of a face's
  plan into the policy of each subject that can match a session on the
  face: the far principal's, at least. `[Sc: §1, §2]`
  - Deny is evaluated first within a policy, so the far principal's own
    grants (core §11.1) hold where no deny of the plan includes them, and
    not elsewhere.
  - The near side's principals connect elsewhere, so their policies carry
    none of it.
- **No subject of the face's own.** A subject selected by link protocol
  alone matches every session on the face, the far principal's included.
  Under `allow`, its policy allows whatever its denies do not include, and
  that undoes the far principal's own denies (core §11.2's complement), as
  a catch-all subject undoes per-user denies (F-87). The plan therefore
  defines none. A session on the face is a principal's: under `deny`, a
  session that matches no subject is granted nothing, and under `allow`, a
  deployment refuses unauthenticated sessions at the link (core §11.3).
- **`select` places the downsampling** (§2.8), which zenoh 1.10.1 selects
  by interface or link protocol only, never by principal. A generator MAY
  also narrow the far principal's subject to the face's link protocols.

### 2.5 Attachment

- **Two shapes**, as core §8.5 recommends, each with the `@zk` deny
  (§2.6): `[F: plan.json]`
  - **`client`**: one far-side session, or a gateway session, as a client
    of the near router. It receives only the declarations its interests
    ask for. The plan's `attach` is `{shape: "client"}`, and the router
    needs no `gateway` block. `[Sc: §1]`
  - **`south-region`**: a far router in a south region of the near
    router. The far router names its region (`region_name = region`), and
    the near router's `gateway.south` lists it, after a subregion that
    keeps the near router's own peers and clients south:
    `{south: [{filters: [{modes: ["peer", "client"]}]}, {filters:
    [{region_names: [region]}]}]}`. `[Sc: §2]`
- **Router to router is refused.** A generator MUST refuse a policy with
  `attach = "router"`. `[F: lints.json]` A deny on a router-to-router link
  hides the denied declarations from the far side, but their key strings
  still cross: 11,330 B and 201 denied keys for 200 tokens, against 506 B
  and none in a south region (spike S3, core §8.5, §11.3).
- **A south region needs declarations sent toward it.** The far router
  learns of a queryable only from a declaration, so core §8.5 requires the
  far principal to be granted `declare_queryable` on egress over every
  queryable its side may query, **as the owner declares it** (core 0.30).
  zenoh checks a declaration by inclusion (core §11.3), against the
  queryable's own key expression, so a grant over the far side's GET and
  call selectors alone does not send it. The grant covers: `[Sc: §2]`
  - **a state GET:** the owner's state queryables over its interface's
    `state/**` and `@state/**` (core S2), with the providers as bound, as
    `zk2/lab/*/radio.v1/state/**` covers `zk2/lab/radio-a/radio.v1/state/**`
    where `state/oper` and `state/peers/*` would not;
  - **a call:** the operation's queryable over its template's pattern
    (core §5), `@op/set/*` for a call of `set/duty`;
  - **an archive's last-known GET:** its queryable over its `@state` forms
    (core §4.4).

  That is a grant, the far principal's (§2.9), and no deny of the plan
  includes `declare_queryable` outside `@zk`, `@adv` and the admin space.
  A declaration crossing toward the far side carries a key expression and
  no value: what the far side may read is still what its Consume and Call
  grants let the replies carry.

### 2.6 The `@zk` deny, and the other planes

Every face's plan opens with three denies of the nine messages, both
flows:

| `id` | `key_exprs` | Why |
|---|---|---|
| `zk` | `zk2/**/@zk/**` | Presence, descriptors and contract bundles (core §8.5). |
| `adv` | `zk2/**/@adv/**` | zenoh-ext's advanced publication: its publishers' liveliness tokens, heartbeats and history queryables (core §2.5). |
| `admin` | `@/**` | The routers' admin space, never namespaced (core §11.1). |

- **`zk` is never omitted.** A generator MUST put it in every face's
  plan, and a deployment MUST NOT remove it from a router's block.
  `[F: plan.json, lints.json]` `[Sc: §1, §2]`
  - No `@zk` traffic is required across a face: bindings resolve
    statically (core R7), and bundles come from holders on each side, or
    are compiled in (core §8.5).
  - It is not defense in depth. Presence would cost zenoh-modem 277 B per
    device per reconnect, 7.4 s of air at 300 bit/s, more than its four
    link keys together (the sketch's §5), and a router link re-declares
    every token on each coverage gap (spike S3: 11.8 KB per gap, against
    536 B to a client).
  - `zk2/**/@zk/**` includes the contract keys, `zk2/@zk/contract/…`:
    `**` matches zero chunks.
- **`adv`**: across a face, a consumer reads an exposed resource live,
  never with history. Advanced publication's tokens are presence of
  publishers, and its replay is bounded by no face's rate.
- **`admin`**: a tool that reads the near router's admin space (core §4.2,
  "What the check reads") runs on the near side. Across the face, a check
  that needs the admin space is unobservable, never clean.

### 2.7 What crosses: the pushes

A face's plan denies the push messages, both flows, on every resource
that does not cross. A resource is **crossing** on a face when all of
these hold: `[F: plan.json, exposure.json]`
- it is a stream, a state or an event (an operation has no pushes, §2.9);
- its exposure is `link` (§2.2);
- the face exposes (`expose = "link"`);
- it is not a stream whose template has a parameter (§2.8).

An owner's pushes of a crossing resource cross the face, and no push of
another resource of a listed interface does, in either direction (below,
for an interface no listed service implements). `[Sc: §1, §4]`

**The exposure denies**, computed per kind token *K*, in the order
`stream`, `@stream`, `state`, `@state`, `events`: `[F: plan.json]`
1. **The face exposes nothing** (`expose = "none"`), or no listed
   interface has a crossing resource of token *K*: one deny, id *K*, key
   expression `zk2/*/*/*/K/**`. It covers every interface, listed or not.
2. **Otherwise**, one deny per listed interface *I*, id `K:I`, sorted by
   the interface id, and none when its key expressions are empty:
   - *I* has no crossing resource of token *K*: `zk2/*/*/I/K/**`, whole,
     so a resource a later minor adds stays home;
   - otherwise, the **carve-out** of *I*'s templates of token *K*, below.

**The carve-out.** Deny works by inclusion (core §11.3), so a resource
that crosses is an absence from the denies. Write `R` for
`zk2/*/*/I/K`, and a prefix *P* of template segments as `R/` followed
by *P*'s pattern. Start with the empty prefix and *I*'s templates of
token *K*. At a prefix *P*, over the templates that begin with *P*:
1. If none crosses: deny `R/P/**` (`R/**` for the empty prefix), and
   stop.
2. If every one crosses: deny nothing, and stop.
3. Otherwise:
   1. If a template equal to *P* does not cross, deny `R/P`.
   2. If no template longer than *P* crosses, deny `R/P/*/**`, and stop.
   3. If the templates longer than *P* continue with more than one kind
      of segment (literals with a parameter, or `{p}` with `{p...}`),
      deny each of them that does not cross by its own pattern, and stop.
   4. Otherwise group them by their next segment (a literal by its text,
      a parameter by its kind), and apply these steps to each group, with
      *P* extended by that segment.

A `**` that a pattern ends with is written once before a `/**` that
follows it (`R/x/*/**`, never `R/x/*/**/**`).

- **Why step 3.3.** Below a literal and a parameter side by side, a
  subtree deny of one would include keys that resolve to the other (core
  §2.2). Each template's own pattern is then denied alone. Zenoh still
  cannot deny `x/*` without `x/special`: an exposed `x/special` beside a
  host `x/{id}` is **overlapped**, and the plan says so
  (`carve_out_overlap`). A crossing template is overlapped when a template
  denied by its own pattern in step 3.3 overlaps it (some key matches
  both) and it takes precedence over that template (core §2.2): the keys
  they share are its own. An overlapped resource does not cross: it is not
  downsampled, and is no liveness evidence. `[F: plan.json]`
- **What a later minor adds.** A subtree with nothing crossing is denied
  whole, so what a minor adds under it stays home. One added beside a
  crossing resource, under a prefix where something crosses, is in no
  deny until the plan is derived again, and crosses under `allow` (the
  sketch's gap 12). Under `deny`, it crosses only if the far principal is
  granted it.
- **Interfaces no listed service implements** are in step 1's whole
  denies, and in no step 2 deny. Under `allow`, their resources of a kind
  the face exposes something of cross as the posture lets them, as every
  key no contract declares does (core §11.2, "the complement's key set").
- **`@stream`** is denied unless it is exposed and downsampled, as core
  §8.5 recommends: an exposed `@stream` resource is downsampled like any
  stream (§2.8). A named key's frames are queued, not dropped, and starve
  the face for minutes (spike S3). `[Sc: §1]`
- **The face's own messages.** Requests are not pushes: no exposure deny
  names `query`, `reply` or `declare_queryable` (§2.9).

zenoh-modem's RF face derives 21 names and 4 subtrees for `modem.v3`'s
streams, the whole of `config.v1`'s and `health.v1`'s, and every state,
`@stream`, `@state` and event wholesale (Appendix B).

### 2.8 Downsampling

- **One rule per concrete key.** A face that exposes, with `interval_s`
  *n*, has one downsampling rule for each crossing stream (`stream` or
  `@stream`) of each listed service: key expression
  `zk2/<system>/<service>/<iface>/<token>/<template>`, and `freq` 1/*n*,
  the quotient as an IEEE 754 double. A generator MUST NOT emit a rule
  whose key expression has a wildcard, nor two rules that intersect.
  `[F: plan.json, lints.json]` `[Sc: §1, §3]`
  - zenoh 1.10.1 gives each rule one timer, and resolves a key to the
    first rule it intersects (`interceptor/downsampling.rs`). A rule with a
    `*` makes every key it covers share one sample per interval, and two
    rules that intersect pick one arbitrarily (D14; the sketch's gap 11).
  - The block is `{id: <face>, link_protocols: select.link_protocols,
    flows: ["egress"], messages: ["put"], rules}`, and none when there is
    no rule. Egress, so that the near router caps what it sends; `put`,
    so that a delete still crosses.
- **Only streams are downsampled.** A stream's samples each stand alone
  (core §2.1), so dropping some is what a sampled reading tolerates. A
  state or an event crosses whole (§2.7, §2.9).
- **A stream with a parameter cannot cross.** Its members' keys are not
  known when the plan is derived, and a rule over its template would
  share one timer among them. It is denied, and the plan warns
  (`templated_exposure`). `[F: plan.json, exposure.json]`
- **List every service whose exposed streams reach the face.** A
  deployment MUST list in `services` every service whose exposed streams
  the far side can receive through the face. An exposed stream of a
  service the policy does not list is in no rule, and, where the face lets
  streams cross, in no deny: it crosses at its owner's rate. `[Sc: §3]` No
  rule can name a service the policy does not know, and a wildcard rule
  would share its timer.
- **The rate is the face's.** `interval_s` is a deployment fact, and the
  contract states none (core 0.29 removed the interim
  `link.downsample_ms`). Two faces of one network carry one resource at
  their own rates.

### 2.9 Events and requests

- **An exposed event crosses whole**, every occurrence, never
  downsampled. A generator MUST NOT downsample an event. `[F: plan.json]`
  `[Sc: §4]`
  - Each occurrence has a key of its own (core §2.6), so no rule names it
    before it happens, and a rule over the template would drop
    occurrences behind one timer, which no reader could tell from
    silence.
  - What it costs the face is its `rate` (core §2.6, §2.7), which its
    owner keeps.
- **An event that is not exposed never crosses**, nor does any event of a
  face that exposes none. `[Sc: §4]` zenoh-modem's events are such: its
  RF face denies `zk2/*/*/*/events/**` (Appendix B).
- **Requests cross by grant.** A GET of a state (core S4), a replay of
  events (core §2.6) and a call (core §5) cross a face when the far
  principal is granted them (core §11.1), never by exposure, and are never
  downsampled. `[Sc: §1, §2]`
  - A request crosses once, when it is asked; a push crosses on its
    owner's initiative, for as long as the subscription lasts. Exposure
    governs what crosses unasked.
  - A dropped query or reply is a call left without its reply (core O5),
    so a request is never downsampled.
  - A south region needs its queryables declared toward it (§2.5).
  - So a far operator GETs `config.v1`'s status and calls its `set`, by
    grant, across a face that pushes none of it (`config.v1` §2.19).
- **An operation's `link.exposure`** is ignored (§2.2).

### 2.10 The batch against the lease

- **A batch SHOULD take at most a third of the lease to cross the face**
  (core §8.5): `batch_bytes` × 8 / `link_bps` ≤ `lease_ms` / 3,000, in
  seconds. A linter warns when `batch_bytes` × 24,000 > `lease_ms` ×
  `link_bps` (`batch_over_lease`), computed exactly, in integers.
  `[F: lints.json]` `[Sc: core constrained.md §4]`
  - At 2,400 bit/s with the 10 s lease, a batch of up to 1,000 B
    qualifies, exactly a third. The spike's 1,024 B batches took 3.41 s,
    a little over, and the link held. zenoh's 65,535 B default would take
    218 s, and the link reconnected in a loop (spike S3).
  - The batch is the link's, the least of the configured size, the MTU
    and the other end's (core Appendix B). zenoh-modem's radio links have
    a 220 B MTU, 0.73 s at 2,400 bit/s.
- **Why the batch, and not the lease.** A shorter batch keeps the 10 s
  failure detection; a longer lease would slow it (spike S3). The policy
  states both, and the linter weighs one against the other.
- **What the router runs is not on the bus** (core §11.3): the policy
  states the batch, and a tool cannot observe that the link runs with it.

### 2.11 The maximum outage and tombstone windows

- **Every listed owner of state keeps deletes for the outage.** A
  deployment MUST configure each listed service that owns a state
  resource (`state` or `@state`, exposed or not) with a tombstone window
  of at least the face's `max_outage_s`, and of at least the largest, on
  a router with several faces. `[F: plan.json, lints.json]` `[Sc: §5]`
  - Core S3 requires it for state an archive records across the face.
    This profile requires it of every state behind the face: a state
    crosses as a push when exposed, and as a GET when granted (§2.9), and
    a late joiner across the face seeds by a GET after each outage (core
    §4.2). A delete made during an outage longer than the window is
    answered by no `reply_del`, and the deleted key stays standing on the
    far side.
  - The window is the owner's configuration, 60 s unless set (core S3).
    It costs about 100 B per tombstone kept (architecture E3).
- **The plan states the floor**, `{service, min_s}` for each listed owner
  of state, and a linter given the windows the deployment configures
  reports each one below it (`window_under_outage`, an error, `at` the
  service; a window not given is 60 s). `[F: plan.json, lints.json]`

### 2.12 Liveness across the face

- **From what crosses** (core R7, `freshness.v1` §2.9). Presence does not
  cross (§2.6), so a consumer across the face judges a provider live
  while a member of a crossing resource of it, with a horizon above 0, is
  fresh by a subscriber's receive clock.
- **The plan names the evidence**: per listed service, the crossing,
  not overlapped resources of its interfaces whose `freshness.ttl_s` is
  above 0 (`freshness.v1` §2.1, §2.2: a stream or a state). A horizon of
  0 is never stale, so it shows nothing of liveness. `[F: plan.json]`
- **No evidence, no verdict.** Where the plan lists no evidence for a
  service, a tool across the face MUST report its liveness unobservable,
  never down (core R7). `[F: plan.json]` `[Sc: §6]` A face that exposes
  none is such a face for every service: liveness across zenoh-modem's
  SBD face is unobservable by design.
- **The interval against the horizon.** The far side receives at most
  one sample per `interval_s`, and the owner publishes one at least every
  ttl/2 (`freshness.v1` §2.4), so a gap between two samples across the
  face is at most `interval_s` + ttl/2. A stream is sure to cross fresh
  only when `interval_s` ≤ ttl/2. The plan warns of a crossing stream with
  2 × `interval_s` > ttl (`interval_over_horizon`), which the far side can
  judge stale between two samples. `[F: plan.json]`

### 2.13 Counters

- **A counter that crosses SHOULD carry its epoch** in-band, in its value
  or its attachment (core §1.5, architecture D9c). The instance id, which
  is a counter's continuity epoch, lives in `@zk` (core §1.5, §8.1), and
  does not cross (§2.6).
- **Without a visible epoch, a decrease is a reset.** A reader across the
  face SHOULD read a decrease of such a counter as a reset, never as a
  negative count or a fault. It cannot tell a reset from an owner's fault
  (the sketch's gap 1).
- **A counter** is a resource whose `telemetry.kind` is `counter` (core
  Appendix D's interim `telemetry` row), until `telemetry.v1` defines its
  counter type. zenoh-modem's `sdu/dropped_total` is one, and its `Counter`
  is a bare number, with no epoch (Appendix B).

### 2.14 What a deployment must not expect

- **Two lanes of one link protocol are one face.** zenoh selects a
  transport by its link protocol, so it cannot tell two lanes of one
  protocol apart (D14; the sketch's gap 10). A policy MUST NOT give two
  faces a common link protocol. `[F: lints.json]` Two radios on
  `unixsock-stream` need a router each, or links of distinct protocols.
  `zids` subjects would tell them apart, but they are unauthenticated
  (core §11.3), and zenoh's downsampling cannot select by zid.
- **Never by interface.** A transport whose link reports no interface,
  such as `unixsock-stream`, matches no subject or downsampling item that
  selects by interface (zenoh 1.10.1), so a face selected by interface
  would guard nothing. `select.interfaces` is refused. `[F: lints.json]`
- **No exposure per principal at this version.** A face policy cannot
  let one principal receive a resource's pushes and not another: exposure
  is the contract's (§2.2). zenoh-modem's operator wants `config.v1`'s
  view pushed to it alone, and a standard profile's contract cannot be
  annotated by the deployment that uses it (the sketch's gap 20). What
  0.1 gives instead is requests by grant (§2.9). Exposure per principal
  is deferred to a later version of this text.
- **No guard against what the plan does not name.** Under `allow`, a
  resource no listed contract declares, or one a later minor adds beside
  a crossing one, is in no deny (§2.7). A deployment that wants the face
  closed to what it does not know runs `deny` (core §11.2).
- **The running block is not on the bus** (core §11.3). A tool checks a
  block that someone says the router runs (§2.15), never the router.

### 2.15 Checking a router's block

A tool checks a block read from a router's configuration against the
face it guards. It MUST report what the fixture reports: `[F: lints.json]`
- **`zk_not_denied`** (error, `at` `@zk`): for one of the 18 pairs of the
  nine messages and both flows, no deny of the block, for that message on
  that flow, has a key expression that includes the namespace's
  `zk2/**/@zk/**` (`<namespace>/zk2/**/@zk/**`, or `zk2/**/@zk/**` with
  none). A key expression that is not one includes nothing.
- **`wildcard_downsampling`** (error, `at` the key expression): a
  downsampling rule whose key expression is not concrete. A key expression
  that is not one is not concrete, and intersects nothing.
- **`intersecting_downsampling`** (error, `at` the later rule's key
  expression, in the block's order): two rules whose key expressions
  intersect, equal ones included.

Whether a block holds the whole plan, every deny and every rule, is a
comparison of the block with the plan, which a generator makes as it
checks its grants (core §11; the reference: `zenctl acl gen --check`, which
`zenctl check face` runs beside these checks).

## 3. Contract

None. The face policy is a deployment file: it is never on the bus, and
nothing of `link.v1` is. A face changes what a router lets through, and
puts nothing of its own.

On a face that exposes, a stream crosses at the face's rate, downsampled per key (§2.8), and a state or an event crosses whole (§2.7, §2.9). `"host"`: it never crosses one. |

## 5. What a tool may conclude

"Not asked" (nobody put the question) and "unobservable" (it was put, and
the observation could not be had) are different facts, and neither is a
"no" (core O5). "Not this profile's" marks a question whose premise does
not hold. A face policy and the contracts answer most of these alone; a
router's block is a file someone read, since the running block is not on
the bus (core §11.3).

| Question | Yes | No | Unestablished | Finding on |
|---|---|---|---|---|
| Is this face policy sound? | No error finding (§2.1). | An error finding: the policy is refused, and no plan is derived. | **Not this profile's:** a router with no face policy has no constrained face. | No. |
| Does this resource's push cross this face? | Crossing (§2.7): `downsampled` for a stream, `whole` for a state or an event (`exposure.json`). | Denied: host, an invalid exposure, a face that exposes none, a stream with a parameter, or overlapped (§2.7, §2.8). | **Not this profile's:** an operation, whose calls cross by grant (§2.9). | Neither: informative. |
| Does this face's block deny `@zk`? | Every one of the 18 pairs is denied (§2.15). | One is not: `zk_not_denied`, an error. | **Not asked:** no block was read. **Unobservable:** whether the router runs the block read (core §11.3). | No. |
| Is each downsampling rule of the block one concrete key? | Every rule is concrete, and no two intersect (§2.15). | `wildcard_downsampling`, `intersecting_downsampling`. | **Not asked:** no block was read. | No. |
| Does this face carry an exposed stream at its rate? | The plan has its key's rule (§2.8). | A listed service's, which the plan denies (`templated_exposure`, `carve_out_overlap`); or a service the policy does not list: no rule names its key, and it crosses at its owner's rate (§2.8). | **Not this profile's:** a stream that is not exposed, or a face that exposes none. **Unobservable:** whether the router runs the plan (core §11.3). | No. |
| Is this owner's tombstone window at least the face's outage? | The window configured, or 60 s, is at least `max_outage_s` (§2.11). | It is below: `window_under_outage`, an error. | **Not asked:** no windows were given. **Not this profile's:** a service that owns no state, or is not listed. **Unobservable:** whether the owner runs with the window given: it is the owner's configuration, not on the bus. | No. |
| Is the batch within a third of the lease? | `batch_bytes` × 24,000 ≤ `lease_ms` × `link_bps` (§2.10). | `batch_over_lease`, a warning. | **Unobservable:** whether the link runs with that batch and lease (§2.10). | No. |
| Is this provider live across the face? | `freshness.v1` §5's row, over the plan's evidence (§2.12). | Never from freshness (`freshness.v1` §5). | **Unobservable:** the plan lists no evidence for it, or none of it is fresh (§2.12, core R7). | Neither: informative. |
| Did this counter reset across the face? | It decreased, and it carries no epoch, or its epoch changed (§2.13). | It did not decrease, and its epoch is the same. | **Unobservable:** a decrease under the same epoch is a reset or the owner's fault, which the value cannot tell. | Neither: informative. |

## Appendix A. Against v1

v1 stated constrained links in RFC 09 §4 ("Constrained links", v1.43 and
v1.49), with the registry's per-subject `exposure` (RFC 08 §2) and
`zenctl acl gen --face constrained --link-protocol <P> | --link-interface
<I> --link-interval <SECS|none>`, on the `v1` branch.

**What changed.**

| v1 | `link.v1` | Why |
|---|---|---|
| `exposure = host \| link \| fleet`, default `fleet` (v1.43) | `link.exposure = host \| link`, default `host` (§2.2) | A resource a later minor adds stays home. v1's unmarked registry crossed whole. |
| The face selected by `--link-protocol` or `--link-interface` | `select.link_protocols` only; interfaces refused (§2.14) | A `unixsock-stream` lane reports no interface, so a face selected by one guarded nothing. |
| `--link-interval <SECS\|none>` on the command line | `expose` and `interval_s` in a face policy, with the attachment, the outage, the batch, the link's rate and the lease (§2.1) | A face is a deployment fact, kept in a file the deployment versions, and checked by a linter. |
| `default_permission: "allow"` forced; a subject by link, and one more per operator repeating every face deny (v1.49) | The posture is the deployment's (core §11.2). The denies go into every policy that can match a session on the face, the far principal's at least; no subject of the face's own (§2.4) | Any allow wins across subjects. Under `allow`, a link subject undoes the far principal's own denies (F-87). |
| A procedure's `exposure`; `**/@rpc/**` denied when any procedure is `host` | An operation crosses by grant, never by exposure; the plan denies no `@op` (§2.9) | Exposure governs what crosses unasked. A call is asked, once, and a grant says who may ask. |
| One deny per `host` subject by pattern, or a whole class under a producer | Per kind token: wholesale when nothing of it crosses, else per interface, whole or carved into subtrees and names (§2.7) | Interfaces are what contracts annotate, and a subtree with nothing crossing stays home whatever a minor adds to it. |
| `**/@media/**`, `**/@blob/**` always denied | Not denied by name | zk2 has neither kind at this version: core §1.2 refuses verbatim kinds a profile registers. A later version that registers one says what crosses. |
| `@/**` and `**/@adv/**` always denied | `admin` and `adv` (§2.6) | Kept. |
| `downsampling`, egress, `put`, one rule per `link` subject at 1/interval | The same, one rule per concrete key of a listed service (§2.8) | v1's rules spanned `*` devices, a latent bug on a two-device node (the sketch's §3). |
| No `@zk` | `zk`, never omitted (§2.6) | zk2's presence, descriptors and bundles live there. |

**New:** the attachment and its refusal of router to router (§2.5), the
batch against the lease (§2.10), the windows' floor (§2.11), the liveness
evidence and the interval against the horizon (§2.12), counters (§2.13),
and the block checks (§2.15).

**What is not ported.**
- **`fleet`**, the third value. A resource either crosses a constrained
  face or not; a face that is not constrained has no policy.
- **The note naming what crosses unclassified.** Nothing crosses
  unclassified: the default is `host`.
- **`--explain` over a face plan** is a tool's, over the generator's
  block (core §11).

## Appendix B. The adopters

**zenoh-modem** (`examples/zk2/zenoh-modem/`), the reference adopter.
Its sketch, `link.md`, is superseded by this text, and kept as the record
it was.

The RF node's policy is the one at the head of this text. Its plan
(`plan.json`, the first case):
- `zk`, `adv`, `admin`;
- `stream:config.v1` and `stream:health.v1` whole, and `stream:modem.v3`
  carved: the subtrees `if`, `layer`, `link` and `radio`, and 21 names
  under `air`, `sched` and `sdu`, leaving the four link streams;
- `@stream`, `state`, `@state` and `events` wholesale: nothing of those
  crosses;
- four downsampling rules at 1/60 Hz, one per link stream of `rf0`;
- `rf0`'s window floor at 3,600 s;
- **no liveness evidence**: the four link streams declare no
  `freshness.ttl_s`, so across RF, liveness is unobservable. A horizon of
  at least 120 s on each, twice the interval (§2.12), would make them
  evidence, as the sketch's §5 expected.

The SBD terminal's policy exposes none (`expose = "none"`, no
`interval_s`), and its plan denies every push wholesale, with no
downsampling.

**What changed from the sketch**, and why:
- **Events are keyed under `events/`.** The sketch's
  `face-deny-modem-streams` named draft-0 keys,
  `zk2/*/*/modem.v3/stream/{oper_change, device_fault, identity_change,
  action_event}/**`. Under draft 1 these are events,
  `…/modem.v3/events/<template>/<ulid>` (core §2.6), which that rule no
  longer covers: under the sketch's `allow`, they would have crossed the
  RF face. The plan denies `zk2/*/*/*/events/**` (§2.9).
- **Companions by interface.** The sketch denied `config.v1`'s and
  `health.v1`'s streams by service, so that an application's own could
  cross. Exposure is the contract's (§2.2), and theirs is `host`, for
  every service.
- **No `@op` deny, and no link subject.** The sketch denied every
  operation to a subject selected by link protocol, and let an operator's
  own policy carve its calls out. Here calls cross by grant (§2.9), and
  the denies go into the far principal's policy (§2.4).
- **Names as subtrees.** A host stream beside a link one is denied as
  `…/sdu/tx_sdus_total/**`, which includes the key itself (§2.7).
- **Attachment, outage, batch, link rate.** The sketch's face file gave
  none; core §8.5 needs the attachment and the outage, and §2.10 the
  batch and the rate.

**What remains open for zenoh-modem.**
- **The counter's epoch** (gap 1): `sdu/dropped_total` crosses as a bare
  number (§2.13).
- **Two radios on one node** (gap 10): one router per radio, or links of
  distinct protocols (§2.14).
- **The operator's pushes** (gap 20): deferred (§2.14). Its calls and
  GETs cross by grant (§2.9).

**The walkthrough** (`examples/zk2/acl/walkthrough.enrollment.toml`)
attaches its ground side across a face, by its face policy
(`walkthrough.face.toml`), in the reference generator's fixtures. None of
its contracts uses `link.v1`, so every push across that face is denied,
wholesale per kind token: the ground's bindings cross as GETs, by grant,
until its contracts expose what it reads.

**The scenarios' radio** (`examples/zk2/link/`, 0.2) is the reference's
example of every kind exposed in part: the `radio.v1` contract of
[`scenarios.md`](scenarios.md), its enrollment, and the lab router's face
policy.
