# `redundancy.v1`: one instance serves, the others stand by

| | |
|---|---|
| **Text version** | 0.3 ([`CHANGELOG.md`](CHANGELOG.md)) |
| **Status** | draft |
| **Written against** | core 0.40 ([`../../core.md`](../../core.md)) |
| **Uses** | no other profile |
| **Evidence** | [`conformance/`](conformance/), [`scenarios.md`](scenarios.md) |

`redundancy.v1` lets several instances of one service run at once, so that
one serves an interface and the others stand by to take over, and lets a
tool tell a standby from a twin. Core O1's at most once holds only while
one instance serves (core §5.1, spike S6), and the core leaves that
exclusivity here (core §6). An interface whose contract lists the profile
in `uses` is **governed**; its election is `claim`, this profile's
protocol, unless the contract says `external`, an outside lock's:

```toml
[interface]
name  = "zs.catalog"
major = 1
uses  = ["redundancy.v1", "freshness.v1"]

[defaults]
annotations = { "redundancy.election" = "claim" }   # the default; "external" for an actuator's own lock
```

The profile adds no key. A candidate's claim is its instance token, and
the incumbent is the instance holding the interface's token, the core's
own presence (core §8.1); a standby says so in its descriptor, with the
core's mark (core §3.3, 0.39):

```text
zk2/fleet/catalog/@zk/instance/<instance>                        every candidate's claim, its descriptor listing the interface
zk2/fleet/catalog/@zk/alive/zs.catalog.v1/<instance>/<fp16>      the incumbent: the one instance serving the interface
```

```json
{"iface": "zs.catalog.v1", "contract": "sha256:…", "minor": 0, "token": true, "standby": true}
```

A live incumbent keeps the interface whatever its instance id. With none,
the lowest instance id of a complete read wins. A standby follows the
incumbent's token live, and campaigns again when a complete read confirms
it gone. Two incumbents that see each other, after a partition heals,
leave the lower id serving. That is eventual single writer, never a lock:
an actuator keeps its lock outside the bus, and the profile only says how
its standby shows.

---

## 0. Conventions

The keywords, the roles and the evidence tags are core §0's. Here,
`[F: <file>]` names a fixture in [`conformance/`](conformance/),
`[Sc: §n]` a section of [`scenarios.md`](scenarios.md), and `core` marks
the core's own evidence. References to `docs/zk2/architecture.md` (§3.8,
§3.12, r3.2, r3.3), to the spike report (S6), to v1's RFC 03 §1.5 and RFC
06 §5.3, and to the adopters' code are informative: every rule is stated
here.

Terms:
- **Governed interface:** an interface whose contract, at the revision an
  instance implements, lists `redundancy.v1` in `uses` (§2.2). Its
  **election** is `claim` or `external` (§4).
- **Address:** a service's `<system>/<service>` (core §1.1). The profile
  works per address and governed interface: each pair has its own claim
  set and its own incumbent.
- **Candidate:** an instance of the address whose descriptor lists the
  governed interface (core §3.3), marked standby or not. Its **claim** is
  its instance token. The **claim set** is the candidates a read finds
  live (§2.3).
- **Incumbent** (or **holder**): an instance of the address holding the
  governed interface's token, `…/@zk/alive/<iface>/<instance>/<fp16>`
  (core §8.1), at any revision (§2.3).
- **Standby:** a candidate whose descriptor marks the interface
  `"standby": true` (core §3.3, §6, 0.39). It exposes nothing of the
  interface and holds none of its tokens (§2.4). A candidate listing the
  interface unmarked is **serving**, or claims to.
- **Twin:** an instance its address cannot account for: one of two or
  more incumbents in two reads a grace apart (a **split**), or a candidate
  whose listing and tokens disagree in two reads (§2.15).
- **Vacancy:** no incumbent, established by a complete read, while a
  candidate is present (§2.8).
- **Lower:** of two instance ids, the one earlier in their order (§2.3).
- **Read:** one liveliness read of the address's `@zk/**` (core §8.1),
  which returns its instance and interface tokens at once, with the
  descriptors it needs (core §3.3's GET). **Complete** is core §8.1's: it
  ran to the routers' final reply with no error reply, on a session that
  has never held a liveliness subscriber (0.37, 0.38), and that session's
  links held both before the read and when it ended (0.37, 0.38). So none
  of these is complete: a read that ended at its timeout or drew an error
  reply; a read **cut off while it ran**, its links gone when it ended,
  which core §8.1 calls possibly incomplete (0.38); a read **not made**,
  its session reaching no node before it (0.37). A read refused by access
  control is complete and empty (core §8.1, 0.8), which §2.5's own claim
  tells apart, the read made on a session that does not hold the claim
  (§2.5 step 1, 0.2). A read that is not complete can miss a token, never
  invent one (core §6): the tokens it returned were seen. A complete read
  covers what its routers' clients and its linked peers hold, and no more
  (core §8.1, 0.40).
- **Watch session** and **round trip** are core §8.1's (0.37).
- **Grace:** core §6's grace period, a setting of the instance's or the
  tool's, longer than the deployment's longest re-mint overlap (core §8.1).
- **Lock:** under `external`, the deployment's exclusivity outside the
  bus: a `flock`, a tty held with `TIOCEXCL`, the kernel's own ownership
  of a qdisc (§2.11).

## 1. Extension points

| Point (core §10) | `redundancy.v1` |
|---|---|
| 1. A standard contract or a standard schema | None (§3). |
| 2. An annotation vocabulary | Yes: `election` (§4). This table replaces the interim row of core Appendix D (core 0.39), with the same key. |
| 3. A registered verbatim kind | None. |
| 4. The descriptor's `profiles` | Only through `uses`: a governed interface's contract lists `redundancy.v1`, so an instance implementing it lists the profile in its descriptor's `profiles` (core §3.3). It is not derivation-only. |

The **standby mark** (`"standby": true` on an interface entry) is not one
of the four points: it is the core's own member (core §3.3, §10, 0.39),
which says what a standby is, holds and exposes. This profile says when an
instance of a governed interface stands by, and when it serves.

## 2. Rules

### 2.1 Who implements it

- **An instance of a governed interface**, a candidate: it claims, elects
  or follows its lock, stands by or serves, follows the address, campaigns
  on a vacancy and heals a split (§2.3 to §2.11).
- **A consumer of a governed interface:** it SHOULD follow the incumbent's
  samples, and its seed's cost during a split is stated (§2.10).
- **A caller** keeps core O1: nothing here changes how it calls, and a
  call finds no standby (§2.4, §2.10).
- **A tool** answers §5's questions of an address and of one instance
  (§2.15).
- **A deployment** runs the instances, keeps them in one presence domain
  (§2.13), and never puts a governed interface in a tokenless set (§2.14).
  Its contract chooses the election (§2.2).

### 2.2 The declaration

A reader MUST read an interface's declaration exactly as the fixture
does. `[F: declarations.json]`
- **Governed** is a contract's `uses` listing `redundancy.v1`. It governs
  the whole interface at that revision: every resource of it, its
  operations included. A contract whose `uses` lists no `redundancy.v1`
  is not this profile's, whatever else it holds; one listing another major
  of `redundancy` is that major's.
- **The election** is the annotation `redundancy.election`, `"claim"` or
  `"external"` (§4). A contract writes it once, on `[defaults]` (core
  §9.1), where it reaches every resource (core §9.3), and the canonical
  form carries it on each (core §9.5), which is where a reader of a
  bundle finds it (core §7.2).
  - Each resource's election is its resolved value, or `claim` where it
    carries none.
  - The interface's election is the one every resource resolves to. An
    interface with no resource is `claim`.
  - On a requirement (`[requires.<role>]`) the key means nothing at this
    version, and a reader ignores it. Another `redundancy.<key>` is W105's
    (§4), and makes nothing invalid.
- **A declaration is invalid** for each of these, checked in this order,
  each alone: `[F: declarations.json]`
  - `not_used`: a resource carries `redundancy.election`, and `uses` names
    no major of `redundancy`. A contract that loads cannot hold it (core
    E020); a reader of resolved annotations that come from elsewhere can;
  - `value`: a resource's `redundancy.election` is not the string `claim`
    or `external`;
  - `disagrees`: two resources resolve to two elections, each valid, one
    carrying none read as `claim`. A resource found `value` takes no part;
  - `tokenless`: the interface is governed, and the deployment's tokenless
    set names it (§2.14).
- **What a reader does with an invalid declaration.** A runtime MUST
  refuse to start an instance whose interface's declaration is invalid,
  as core §8.2 step 2 refuses: no instance token appears.
  `[Sc: §11]` A tool reports it as a contract's finding, or the
  deployment's for `tokenless`. No core lint reads an annotation's value;
  a contract linter SHOULD warn of `value` and `disagrees`.
- **Across revisions.** Each instance is governed by the revision its
  descriptor names. A minor that adds or drops `redundancy.v1` in `uses`
  is a review (core §9.8, `uses_changed`), and so is one that changes the
  election, an annotation. The candidates of one address SHOULD run
  revisions that agree on both: an instance of a revision that is not
  governed serves whatever the others do, and two elections never agree
  on an incumbent. A tool reads the address's governance from every
  candidate's revision, and answers unobservable where they disagree
  (§2.15).

### 2.3 The claim set and the incumbent

- **A candidate's claim is its instance token** (core §8.1), with its
  descriptor listing the governed interface, marked standby or not
  (core §3.3). No other key is a claim: a pure consumer on the address,
  or an instance listing other interfaces only, is no candidate (core
  §8.1: every instance holds an instance token).
- **The claim set** is the candidates a read finds live: their instance
  tokens in the read, their descriptors listing the interface.
- **The incumbent** is the instance holding the governed interface's
  token at the address, at any revision of the interface (any `fp16`).
  Nothing else makes an incumbent: a token is the incumbent's whatever its
  holder's descriptor says, and a holder whose descriptor marks the
  interface standby is an incumbent whose descriptor disagrees with its
  tokens (core §6, 0.39; §2.15).
- **Instance ids compare** as their 16 lowercase hexadecimal digits (core
  §3.3, D002), character by character, which is their order as unsigned
  64-bit integers. **Lower** and **lowest** mean this order everywhere
  here. `[F: elections.json, heals.json]`
- **Several governed interfaces** at one address are elected apart, each
  with its own claim set and incumbent. An instance may serve one and
  stand by on another, its descriptor marking each entry apart.

### 2.4 The standby

- **What it holds.** A standby holds its instance token, and serves its
  descriptor listing the interface with `"standby": true` and `"token":
  true` (core §3.3, 0.39). It MUST hold none of the interface's tokens,
  interface or member (core §8.1), and expose none of its resources,
  required ones included: no publisher, no state queryable, no operation
  queryable and no `unavailable` queryable for it (core §5.1, §8.2).
  `[Sc: §1, §8]` `[F: descriptors.json]`
- **What it still declares:** its descriptor's queryable and the
  interface's contract queryable (core §8.2 step 3, §8.4). A bundle is
  not a resource of the interface, and any participant may hold one.
- **Its entry's `unavailable` and `cardinality`** state what it will
  expose once it serves (core §3.3, 0.39), so that a tool sees, before a
  takeover, a capability the standby lacks. It validates them at its
  start (core §8.2), so that its takeover cannot fail step 2.
- **A call finds no standby.** With no operation queryable, a concrete
  call (`BestMatching`, core O1) reaches the incumbent's `complete`
  queryable or none, and a fan-out (`All`, O2) the incumbent's only. A
  call made while no instance serves is silence (core O5). `[Sc: §8]`
- **It writes nothing of the interface.** A standby MUST NOT put or
  delete any of the interface's keys: they are the incumbent's (core §6),
  and a delete would read as the incumbent's to every consumer.
  `[Sc: §7]` What it keeps ready for a takeover is the application's,
  outside the interface's keys. A runtime SHOULD refuse its application's
  write of them while it stands by, saying so, rather than drop it, so
  that the application is never left guessing its role (0.2). `[Sc: §7]`
- **Every interface at the address.** A standby stands by on each
  governed interface it lists. An interface it implements at the same
  address that is not governed it exposes as any owner does, so two
  instances expose it at once, which core §6 forbids of an exclusive
  resource. An address with a governed interface SHOULD implement only
  governed interfaces. A process's own reporting, `health.v1` and
  `alarms.v1` among it, which no contract of theirs governs, goes on an
  address of its own, as ZenSight's correlator runs its own host service
  beside the catalog (Appendix B).

### 2.5 The election under `claim`

An instance of a governed interface whose election is `claim` MUST elect
in these steps, in this order, and MUST decide each read exactly as the
fixture does. `[F: elections.json, lifecycle.json]` `[Sc: §1–§5]`
1. **Claim before reading.** It puts its descriptor, the interface marked
   standby, and declares its instance token (core §8.2 steps 3 and 4, with
   no interface token: §2.4), and declares its watch (§2.7), before it
   reads anything. A campaign that read first could see an empty set, then
   race another instance doing the same (ZenSight #1104). `[Sc: §3]`
   - **Its read goes on a session of its own** (0.2, F-204): one that
     holds neither a liveliness subscriber (core §8.1, 0.37, 0.38) nor
     the claim. A session answers a liveliness read with its own tokens
     itself, even through a router that refuses the read (core §8.1,
     0.40), so a read on the claim's session finds the claim whatever the
     bus holds, and step 3's own-claim check would never see a refusal.
     The instance makes one round trip on the claim's session after
     declaring it, and before the read, since zenoh orders no two
     sessions' messages (core §8.1, 0.37). A candidate so runs three
     sessions: the claim's, the watch (§2.7) and the reader. The reader
     MAY be shared with the application's other reads that meet core
     §8.1. `[Sc: §5]`
   - **Where its sessions are** (0.2, F-206). A candidate's sessions, and
     those of a tool that reads the address, MUST be clients of a router,
     or peers linked to every other candidate's: a complete read covers
     only what its routers' clients and its linked peers hold (core §8.1,
     0.40), so a peer that cannot link to another candidate's reads a
     vacancy beside a live incumbent, and takes over. `[Sc: §5]`
2. **A live incumbent wins.** The read shows another instance holding the
   interface's token: the instance stands by (§2.4), whatever the holder's
   id and revision, and whether or not the read is complete, since a read
   cannot invent a token. A live incumbent never yields to a lower id: the
   lowest id is a tie-break for simultaneous starts, not an entitlement.
   `[Sc: §4]`
3. **No incumbent: the claim set, read whole.** The instance stands by,
   and campaigns again after its retry interval (below), unless all of
   these hold: `[Sc: §5]`
   - the read is complete (core §8.1). A read cut off while it ran is
     possibly incomplete, and a read not made is read as one (core §8.1,
     0.38: a profile's premise): the instance stands by, and campaigns
     again once its session holds a link and its retry interval has run;
   - it shows the instance's own claim. A read that misses the instance
     token the instance knows it holds missed what it could not see, its
     claim not yet at its router, or the read refused (core §8.1's
     refused read is complete and empty);
   - the descriptor of every instance in it with a lower id than its own
     was read, to tell a candidate from a pure consumer. A higher id
     cannot beat it, so its descriptor need not be read.

   An unreadable claim set is never "the only candidate" (ZenSight #1105).
4. **The lowest instance id wins.** No candidate of the read has a lower
   id: the instance takes over (§2.6). One does: it stands by, and
   campaigns again after its retry interval, as that candidate should
   take over meanwhile.

- **The retry interval** is the instance's setting, SHOULD be a few
  seconds (ZenSight polls every 2 s), and runs only while the instance
  stands by with no incumbent seen, or while a heal's read ends nothing
  (§2.9). A standby that saw an incumbent waits on its watch instead
  (§2.7, §2.8).
- **What it hears while a read runs** (0.2, F-199). A read takes a round
  trip, and its watch hears meanwhile. An appearance of another holder's
  token, or a withdrawal, heard while a read is asked (campaigning, or
  healing, §2.9) or while an act runs (taking over, stepping down), is
  kept, and decided as if heard at that read's decision or that act's
  end, in the state it leaves: an appearance kept through a takeover
  reads for a heal once it serves (§2.9); a withdrawal kept past a
  stand-by on an incumbent reads again (§2.8's 0.1 s); one kept through
  a step-down campaigns once it stands by (§2.8), under `external` only
  with the lock (§2.11, F-207). A candidate MUST decide them exactly as
  the fixture does. `[F: lifecycle.json]`
- **A race the claim narrows, and the heal ends.** Two instances whose
  reads each missed the other's claim, behind two routers or within one
  read's round trip, both take over. They then see each other, and §2.9
  leaves the lower serving. `[Sc: §3, §7]`

### 2.6 Taking over

- **In core §8.2's order.** An instance taking over MUST do core §8.2's
  steps 1 to 4 for the interface, in their order (core 0.39, "serving
  later"): `[Sc: §1, §2]`
  1. declare the interface's resources: its publishers, its state and
     operation queryables, and the `unavailable` queryables of its
     optional operations it does not expose (core §5.1);
  2. step 2's validation, already passed at its start (§2.4);
  3. put each state value it holds (core §8.2's SHOULD), then put its
     descriptor again, the interface's entry without the mark;
  4. declare the interface's token last, then a member token per member
     as each appears (core §8.1).

  Alive ⇒ callable then holds as at a start: a caller that sees the token
  finds the queryables. ZenSight's guard declares `alive` only once it
  serves, for this reason (Appendix B).
- **Its state.** A new incumbent is another session than the last, so its
  stamps carry another id, and a consumer accepts its first value as a new
  epoch (core §4.3, S7). What it puts is the application's: its own
  record, an archive on its own side (core §4.3's catch-up), or a value it
  computes. The profile moves no state between instances at 1.0 (§2.16).
  An instance taking over again SHOULD hold nothing of the interface's
  state from an earlier incumbency that it does not put again: another
  incumbent may have written since, and a GET it answered would give a
  value older than the address's last word (0.2). `[Sc: §7]`

### 2.7 Following the address

- **A subscriber, where it can.** A candidate MUST follow the address's
  tokens, its instance and interface tokens alike, from before its first
  read (§2.5 step 1), for as long as it runs: as a standby, to hear its
  incumbent go; as an incumbent, to hear a second one come (§2.9). It
  SHOULD follow them with a liveliness subscriber on
  `zk2/<system>/<service>/@zk/**` (0.2; a MUST at 0.1). `[Sc: §1, §6]`
- **On a watch session** (core §8.1, 0.37): the subscriber is on a session
  of the candidate's own that makes no read it concludes absence from,
  with one round trip there after declaring it and before its first read.
  It is callback-driven or drained as its samples arrive (core §8.1).
- **A periodic re-read** MAY back the subscriber up, at a period the
  deployment chooses. It never replaces it.
- **A poll, where no watch session can be held** (0.2). A candidate
  without one reads the address every period instead, on its reader
  (§2.5 step 1), and MUST compare each read's holders with the last's
  exactly as the fixture does, where a read not complete removes no
  holder from the last's: a holder it shows that is new is an appearance,
  and only a complete read can show one gone, a withdrawal (core §8.1: a
  read not complete can miss a token, never invent one; 0.3, F-215).
  `[F: polls.json]` It misses what comes and goes within one period:
  its incumbent's router restarting, a split shorter than the period. It
  costs one presence read of the address per period, where the watch
  costs none, and a takeover waits up to one period more. ZenSight's
  guard polled every 2 s (Appendix B); the reference polls every 500 ms.

### 2.8 A vacancy

- **What it is.** The interface's tokens at the address withdrawn, the
  last holder's included, then none in a complete read (core §8.1, 0.37).
  `[F: lifecycle.json, conclusions.json]`
- **A withdrawal heard live is a reason to read again, never a vacancy by
  itself.** A candidate MUST NOT take over on a withdrawal alone: its
  router's restart, or its own link's drop, withdraws every token at once
  while the incumbent still serves (core §8.1). It reads again soon after
  a withdrawal that leaves no holder heard, one read for a burst (the
  reference: 0.1 s after the first), and campaigns from that read: §2.5's
  step 2, then 3 and 4, its claim already held. A read it cannot make, its
  session cut off, leaves the withdrawal unconfirmed until it can, and one
  cut off while it ran confirms nothing absent (core §8.1, 0.38).
  `[Sc: §6]`
- **A re-mint is no vacancy.** An incumbent's make-before-break re-mint
  holds its new token before its old one goes (core §8.1).
- **Every standby campaigns again** on a vacancy, and the lowest id wins,
  as at a simultaneous start (§2.5). `[Sc: §1, §2]`
- **When a departure is seen** (0.2, F-201). A clean stop undeclares the
  incumbent's tokens at once. A crash whose host's kernel closes its
  links is seen at once too, as their transports close. A lost host, or
  a partition, is seen at zenoh's lease, 10 s by default, when the
  incumbent's router withdraws its tokens (core Appendix B). A takeover
  then costs the withdrawal, the read after it, the descriptors of the
  lower ids, and core §8.2's steps. `[Sc: §1, §10]`

### 2.9 Healing a split

- **What a split is.** Two or more incumbents of the address in each of
  two reads a grace apart, not necessarily the same instances (core §6).
  A re-mint's overlap shows in one read at most. A partition makes one: an
  incumbent on each side, each side's standby taking over at its vacancy.
- **The higher ids step down.** Under `claim`, an incumbent that sees a
  split in which the second read shows a holder with a lower id than its
  own MUST step down, exactly as the fixture decides. The lowest holder
  of the second read stays. A healed partition so ends with one
  incumbent, and no vote. `[F: heals.json, lifecycle.json]` `[Sc: §7]`
  - **How it sees one.** Its watch hears another holder's token appear
    (§2.7). It reads at once, and again a grace later. A read cannot
    invent a holder, so a read not complete that shows two counts, one cut
    off while it ran counts the holders it returned, and a read not made
    shows none (core §8.1, 0.37, 0.38).
  - **A heal read that ends nothing** (0.2, F-199). A heal's read not
    complete that shows fewer than two holders, its own counted, leaves
    the split undecided: the incumbent stays healing, and makes that read
    again after its retry interval. Only a complete read showing one
    holder ends a heal. A watch session that reconnects before its reader
    after a partition hears the other holder at once, and the reader's
    first read may not be made. `[F: lifecycle.json]`
  - **Its own re-mint is no appearance** (0.2, F-209). A candidate's
    make-before-break re-mint (core §8.1) declares its token under a new
    id, which its own watch hears. From the re-mint on, the new id is its
    own and every former id is its own too, never another holder or
    another candidate. A runtime tells its election of the new id before
    it declares the new id's tokens, in every state, a standby's
    included. `[F: lifecycle.json]`
  - **A lower holder about to go.** A crashed lower holder keeps its token
    until its lease, so a higher one may step down to a holder that then
    vanishes. The vacancy that follows is campaigned for (§2.8).
  - **An incumbent cut off** from the rest for longer than its standbys
    wait is a partition of one: a standby takes over, and at its return
    the lower of the two serves, which may be either.
- **The order of a step-down.** An instance stepping down MUST undo core
  §8.2's steps in their reverse order (core 0.39, "stopping"): `[Sc: §7]`
  1. undeclare the interface's tokens, its interface token and its member
     tokens;
  2. undeclare the interface's resources: its publishers and queryables;
  3. put its descriptor again, the interface marked standby;
  4. follow the address as a standby (§2.7).

  Alive ⇒ callable holds at each step. It puts and deletes none of the
  interface's keys (§2.4): before step 1 it stops writing them, and lets
  the writes already made end, so that none is put once its token is
  withdrawn (0.2). At step 2 the reference forgets what it put of them,
  as §2.6 asks of a later takeover.
- **It is no fence.** Stepping down stops the higher instance's writes;
  writes already in flight may still land after the lower's, and a
  consumer following the incumbent discards them (§2.10). No epoch rides
  a payload (§2.16).
- **Under `external`** no instance steps down by this rule (§2.11), and
  a split never heals: two holders of two locks serve until a person
  decides (0.2). `[Sc: §10]`

### 2.10 Consumers, callers, and the stamps they read

- **An instance's stamps.** A candidate of a governed interface MUST
  state its session's zid as `meta.zid` (core §3.3), and MUST enable its
  session's HLC (core §4.3), whatever kinds it serves, so that each of its
  state, stream and event samples carries a stamp whose id is its own
  (core §4.1). `[Sc: §9]`
- **Follow the incumbent.** A consumer of a governed interface SHOULD
  accept its state, stream and event samples only from the incumbent: a
  sample whose stamp's id is the incumbent's `meta.zid`, compared by value
  (core §3.3, S1). It learns the incumbent as a candidate does: a watch on
  the provider's `@zk/**` (§2.7), a complete read, and the holder's
  descriptor. `[Sc: §9]`
  - **During a split** it follows the lowest holder it sees, the one the
    heal keeps (§2.9), and changes when a lower holder appears or its
    incumbent's token goes.
  - **With no incumbent seen,** a vacancy or before its first read, it
    accepts nothing new, and what it holds is the last incumbent's last
    word.
  - **A sample it cannot attribute,** unstamped, or under an id that is
    no incumbent's `meta.zid`, it discards.
- **Why.** Core S7's consumer accepts the first value under a new id and
  restarts its ordering there, so two writers flip it at each put, each
  the first value of its id since the other's: ZenSight's sensors flapped
  between two configurations so (#1104). Following one id ends it. This is
  the profile's only fencing: by presence, never an epoch in the payload.
- **What a split still costs, stated.**
  - **Calls.** A caller keeps core O1: during a split a concrete call runs
    once on each side (spike S6), and a caller with `None` consolidation
    receives both replies on one key (core §5.1). The profile does not
    hide it. A caller MAY read the address's presence first, and refuse
    to call during a split.
  - **A seed.** S4's GET is answered by every incumbent, and `Latest`
    keeps the later stamp per key, whichever wrote it (core §4.1). A
    consumer following the lower discards a reply of the higher's, and
    holds no value for that key until the incumbent it follows puts it
    again: silence, never a verdict (core S6, O5).
  - **A consumer that does not follow** reads both incumbents' samples by
    core S7 alone, until the heal.

### 2.11 `election = "external"`

- **An outside lock elects.** An instance whose interface's election is
  `external` MUST serve it only while it holds the deployment's lock,
  MUST NOT take over by §2.5's lowest id (its step 4), and MUST NOT step
  down by §2.9's rule. `[F: elections.json, lifecycle.json]` `[Sc: §10]`
  It steps down, in §2.9's order, when it loses the lock.
- **Without the lock,** it either refuses to start, as core §8.2 step 2
  refuses (no instance token appears), or stands by as §2.4 says, its
  claim marked, until it holds the lock. zenoh-modem and tcgui refuse
  (Appendix B).
- **With the lock,** it takes over (§2.6) once a read shows no other
  holder of the interface's token, complete and holding its own claim, as
  §2.5 steps 2 and 3 read it, without step 4: the lock decided. Until
  then it waits on its watch for a vacancy (§2.8), and retries an
  unreadable read after its retry interval. The lock says the previous
  holder no longer drives; its token outlives a crash by up to a lease,
  and a takeover before it goes would show as a split until then. A
  withdrawal heard while it steps down for a lost lock campaigns only
  once it holds the lock again (0.2, F-207). `[F: lifecycle.json]`
- **Two locks.** Two instances that each hold a lock of their own (a
  misconfiguration, or two hosts) serve together only when their reads
  miss each other: the later reads the earlier's token and stands by on
  it (§2.5 step 2), lock or no lock. Once both serve, behind a partition,
  neither steps down when it heals (0.2, F-200). `[Sc: §10]`
- **The anti-twin probe.** It MAY read presence before its tokens, and
  refuse to start when another instance holds the interface's token. The
  probe is an early refusal, never the interlock: a partition hides a twin
  from it, and the lock does not (RFC 03 §1.5, Appendix A).
- **What a tool concludes** is §5's, as under `claim`. Two incumbents are
  a split the profile does not heal: the lock failed, or two hosts run one
  address, and a person decides. A standby is recognised by its mark.

### 2.12 Population

- **One incumbent** per address and governed interface: the profile's
  aim. Between a partition and its heal there are more, by design
  (eventual single writer, §2.16).
- **Standbys:** any number. Each costs one token, its instance token
  (core §8.3), a descriptor and a watch, and at each vacancy one read and
  the descriptors of the ids below its own. A deployment SHOULD run few,
  one or two: ZenSight runs one of each singleton.
- **Members.** A standby holds no member token, and the incumbent's
  population is its own (core §2.7).

### 2.13 Constrained faces

- **Presence does not cross** a constrained face (`link.v1` §2.6, core
  §8.5): no claim, no interface token and no descriptor crosses it.
  Candidates of one address on two sides of a face never see each other,
  so each side elects its own, and no heal ends it. A deployment SHOULD
  keep every candidate of a governed address on one side of every
  constrained face, in one presence domain (core §8.3).
- **What `link.v1` exposes of a standby:** nothing. A standby exposes no
  resource (§2.4), so no face carries a push of one, and a far reader's
  GET by grant (`link.v1` §2.9) reaches the incumbent's queryables only.
- **A tool across a face** answers §5 unobservable, `across_face`: the
  deployment's word names the address, never which instance serves it.
  `[F: conclusions.json]`

### 2.14 The tokenless set

- **Never a governed interface.** A governed interface MUST NOT be in an
  instance's tokenless set (core §8.1, U22): its incumbent is the holder
  of its token (§2.3), and a tokenless interface has none. A runtime MUST
  refuse to start an owner whose tokenless set names a governed interface
  it implements, as core §8.2 step 2 refuses `archive.v1` (core 0.39).
  `[F: declarations.json]` `[Sc: §11]`
- **What a reader sees.** A descriptor entry marked `"standby": true` and
  `"token": false` is core D012 (core §3.3, 0.39). An entry marked
  `"token": false` whose contract governs the interface is this profile's
  `governed_tokenless`, which only a reader holding the contract can see.
  A reader MUST read an entry's mark as the fixture does.
  `[F: descriptors.json]` `[F: core descriptors/d012-standby-tokenless]`
- **A mark no profile governs.** An entry marked standby whose contract
  does not use this profile says what core §6 says, the instance exposes
  nothing of it, and none of §5's questions is this profile's:
  `not_governed`. `[F: descriptors.json]`

### 2.15 What a tool concludes

A tool judges an address and governed interface from two reads a grace
apart (core §6), each its tokens, its completeness and the descriptors of
the instances in it, and MUST conclude exactly as the fixture does. "Not
asked", "unobservable" and "not this profile's" are never folded into
"no" (core O5). `[F: conclusions.json]` `[Sc: §12]`
- **Completeness** is core §8.1's (§0), and a tool's sessions are where
  §2.5 step 1 puts a candidate's (0.2, F-206). A read not made is read as
  one not complete (core §8.1, 0.38: a profile's premise): its answer is the
  one a read not complete gives, `presence_incomplete` where the steps
  below give it, and the tool reports the read's own reason beside it (not
  made: cut off, or beside a liveliness subscriber; possibly incomplete:
  its timeout, an error reply, or cut off while it ran).
- **The premises,** for every question, in this order:
  1. across a constrained face: **unobservable**, `across_face` (§2.13);
  2. the address's presence, from the second read: no instance in it,
     **not asked**, `absent`, when it is complete, and **unobservable**,
     `presence_incomplete`, when it is not. For one instance's question,
     that instance not in the second read, the same;
  3. the governance, read from the contract each candidate's descriptor
     names (§2.2): not governed, **not this profile's**, `not_governed`;
     a contract not read, or one whose declaration is invalid (§2.2:
     it gives no election, and a tool reports its reasons beside the
     answer; 0.3), **unobservable**, `no_contract`; candidates'
     revisions that disagree on governance or on the election,
     **unobservable**, `revisions_disagree`. A tool that holds the
     contract offline reads governance from it whatever the bus serves:
     where no candidate serves the bundle, a vacancy's standbys gone and
     no other holder, retrieval answers nothing (core §8.4; 0.3).
     `[Sc: §12]`
- **Is the address served by exactly one incumbent?** The holders of the
  first read are H1, of the second H2:
  1. two or more in both: **no**, `split`, whatever each read's
     completeness, since a read cannot invent a holder;
  2. two or more in the second alone: **unobservable**, `in_transition`,
     a re-mint's overlap or a split not yet established;
  3. one in the second: **yes**, `one`, when that read is complete, and
     **unobservable**, `presence_incomplete`, when it is not;
  4. none in the second: that read not complete, **unobservable**,
     `presence_incomplete`; no candidate in it, **unobservable**,
     `no_descriptor` when a descriptor in it was not read, and else **not
     asked**, `no_candidate`; a holder in the first, **unobservable**,
     `in_transition`, a takeover due (§2.8); the first not complete,
     **unobservable**, `presence_incomplete`; otherwise **no**, `vacant`:
     a vacancy in both reads.
- **Is there a vacancy?**
  1. a holder in the second read: **no**, `held`;
  2. that read not complete: **unobservable**, `presence_incomplete`;
  3. no candidate in it: **unobservable**, `no_descriptor` when a
     descriptor in it was not read, else **not asked**, `no_candidate`;
  4. none in the first read too, and it complete: **yes**, `lasting`;
     otherwise **yes**, `vacant`, a takeover due.
- **Does any instance stand by, and how many?** The standbys are the
  instances of the second read whose descriptor lists the interface
  marked standby, and that hold none of its tokens:
  1. one or more: **yes**, `standing_by`, with the count, exact when the
     read is complete and every descriptor in it was read, and otherwise
     a lower bound;
  2. none, the read not complete: **unobservable**, `presence_incomplete`;
  3. none, a descriptor not read: **unobservable**, `no_descriptor`;
  4. otherwise **no**, `none`, the count 0, exact.
- **Is this instance a standby, or a twin?** Of an instance X in the
  second read, X1 and X2 being what each read shows of it: its token, and
  its descriptor, unread, not listing the interface, or listing it marked
  or unmarked. "X1 the same" means X in the first read too, with the same
  token and the same descriptor reading as X2:
  1. X holds the token in both reads, and both show two or more holders:
     **yes**, `split_lowest` when X is the lowest holder of the second
     read, else **yes**, `split`;
  2. X2's descriptor not read: **unobservable**, `no_descriptor`;
  3. X2 not listing the interface: holding no token, **not asked**,
     `not_a_candidate`; holding one, and X1 the same, **yes**,
     `unlisted`; otherwise **unobservable**, `in_transition`;
  4. X2 holding the token: another holder in the second read,
     **unobservable**, `in_transition`; X2 marked standby, and X1 holding
     the token marked standby too, **yes**, `marked_holding`, and
     otherwise **unobservable**, `in_transition`; X2 unmarked, **no**,
     `incumbent`, when the second read is complete, and else
     **unobservable**, `presence_incomplete`, since it may have missed
     another holder;
  5. X2 holding no token, marked standby: **no**, `standby`, when the
     second read is complete, else **unobservable**,
     `presence_incomplete`;
  6. X2 holding no token, unmarked: X1 the same, both reads complete,
     **yes**, `unmarked`; X1 the same, a read not complete,
     **unobservable**, `presence_incomplete`; otherwise **unobservable**,
     `in_transition`.
- **`hostid.v1` §2.12's standby** (its text 0.6, its reads of the
  address's `@zk/**` since 0.7) is the instance this
  question answers **no**, `standby`, of every interface it lists, each
  of them governed: a second process of the address that the deployment
  runs on purpose, which `hostid.v1` does not count, and which a tool
  names beside its answer (0.3). `[Sc: §12]`
- **Holders counted by token.** A holder whose descriptor says standby is
  counted a holder by the first two questions and the third does not
  count it, as core §6 counts it (0.39).
- **One split, one finding** (0.3). A tool that also judges core §6's
  split-brain judges a governed interface's by the first question: two or
  more holders in both reads are `split` whatever their marks and
  whatever they expose, which core §6's exposure rule would read apart.
  So it reports a split once, as this profile's, and core §6's rule
  decides only interfaces this profile does not govern. `[Sc: §12]`
- **A standby's exposure, probed** (0.3). A tool MAY check that a
  standby exposes nothing (§2.4) by a GET, target `All` and
  consolidation `None`, over a wildcard of each of the interface's
  operations whose fan-out is forbidden: every operation queryable at the
  address answers it before any handler runs (core O2), so a reply that
  zenoh attributes to the session of an instance marked standby, with no
  token, in a read before the probe and one after it, is a queryable it
  holds, and the instance a twin. Silence proves less: a state queryable
  holding nothing answers nothing, and an operation whose fan-out is
  allowed is never probed this way, since the call would run it.
  `[Sc: §12]`

### 2.16 Not at 1.0

- **Quorum or consensus.** One complete read and the lowest id decide.
- **Fencing epochs or claim ids in a payload,** v1's promised claim id and
  `elected_at` among them (Appendix A). A sample's stamp already names its
  writer's session (§2.10).
- **Leases** other than zenoh's liveliness.
- **Exclusivity across routers** stronger than eventual single writer:
  two incumbents between a partition and its heal are by design, and so
  are the calls run on each side (§2.10).
- **Moving state** between incumbents (§2.6), a **preferred** incumbent or
  a priority, a **switchover** operation (an incumbent's clean stop is
  one), a standby's own reporting at the address (§2.4), and an election
  across a constrained face (§2.13).

## 3. Contract

None. The profile defines no standard contract and no standard schema:
its claim, its incumbent and its mark are the core's presence and the
core's descriptor member (core §8.1, §3.3), and it puts nothing of its
own on the bus. A schema would type a payload, and the profile carries
none: no epoch, no claim id (§2.16).

## 5. What a tool may conclude

"Not asked" (nobody put the question), "unobservable" (it was put, and the
reading could not answer it) and "not this profile's" (the interface is
not governed) are different facts, and none is a "no" (core O5). The
fixture [`conclusions.json`](conformance/conclusions.json) states the
tokens: `yes`, `no`, `unobservable`, `not_asked`, `not_this_profiles`,
each with a reason (§2.15).

The premises, for every row (§2.15): not across a constrained face
(**unobservable**, `across_face`); the address present in the second read
(**not asked**, `absent`, or **unobservable**, `presence_incomplete`); the
interface governed, by contracts read and agreeing (**not this
profile's**, `not_governed`; **unobservable**, `no_contract`,
`revisions_disagree`).

| Question | Yes | No | Unestablished | Finding on |
|---|---|---|---|---|
| Is the address served by exactly one incumbent? | The second read complete, one holder of the interface's token in it, and not two or more in both reads (`one`). | Two or more holders in both reads (`split`), or none in both, complete, with a candidate present (`vacant`). | **Unobservable:** a read not complete where it decides (`presence_incomplete`); the shape seen in one read only (`in_transition`); no candidate seen, a descriptor unread (`no_descriptor`). **Not asked:** no candidate (`no_candidate`). | No. |
| Is there a vacancy? | The second read complete, no holder, a candidate present: in both reads (`lasting`), or in the second only (`vacant`). | A holder in the second read (`held`). | **Unobservable:** that read not complete; no candidate seen, a descriptor unread. **Not asked:** no candidate. | Yes, `lasting`: the election did not end, or no instance holds the lock. `vacant` is a takeover due. |
| Does any instance stand by, and how many? | One or more marked standby and holding no token in the second read, with the count, exact or a lower bound (`standing_by`). | None, the read complete and every descriptor read (`none`). | **Unobservable:** the read not complete, or a descriptor unread. | Neither: informative. A deployment that expects a standby MAY read no as its finding. |
| Is this instance a standby, or a twin? | A twin: one of a split (`split`, or `split_lowest`, the one the heal keeps); holding the token while marked standby (`marked_holding`), or not listing it (`unlisted`); listing it unmarked with no token (`unmarked`): each in both reads. | A standby: marked, no token, the read complete (`standby`). The sole incumbent, unmarked, the read complete (`incumbent`). | **Unobservable:** its descriptor unread; a read not complete where it decides; a shape in one read only (`in_transition`). **Not asked:** not listing the interface and holding no token (`not_a_candidate`). | Yes. |

**Which cause** a split has (a partition, a lock that failed, two hosts
running one address) is unobservable from presence alone, and so is
whether a lasting vacancy's candidates are stuck or merely slow.

## Appendix A. Against v1

v1's exclusivity was RFC 06 §5.3's ownership protocol, for the `@catalog`
and `@desired` service origins: a claim token `…/state/claim/<zid>` per
candidate, `…/state/alive` declared by the owner, the lexically lowest
claim elected, standbys idle in the queue (D-Bus `IN_QUEUE`). RFC 03 §1.5
asked an actuating producer to lock outside the bus, and to probe for a
twin. ZenSight implemented the protocol in `zensight-common`'s
`service_guard.rs`, fixed in ZenSight #1104 and #1105.

**What changed.**

| v1 | `redundancy.v1` | Why |
|---|---|---|
| A claim token per candidate, hand-built (`keyexpr.rs`) | The instance token, its descriptor listing the interface (§2.3) | Every instance holds one already (core §8.1): no new key. |
| One `alive` key for the owner | The interface token, which names its holder (§2.3) | Two incumbents are two keys a tool counts (core §6). |
| The lowest claim elected at every election (RFC 06 §5.3 step 2) | A live incumbent wins whatever its id; the lowest id breaks a tie with none (§2.5) | ZenSight #1104: a later, lower zid displaced a running owner, and every sensor flapped between two configurations. |
| Losers exit, or keep their claim idle | A standby, marked, holding its instance token, following the address (§2.4, §2.7) | Killing the winner left no service until a supervisor restarted a loser whose zid sorted right (#1104). |
| A claim-set read that timed out: "assuming sole candidate" | Stand by, and campaign again (§2.5 step 3) | A slow bus elected everybody (#1105). |
| A standby polls `alive` every 2 s (`STANDBY_POLL`) | A liveliness subscriber on a watch session; a complete read after a withdrawal (§2.7, §2.8) | Core 0.37: a withdrawal heard live is no absence, a read beside a subscriber can miss tokens, and a poll that timed out read as a vacancy. |
| `elected_at` and the writer's claim id in every document, promised and never implemented | Nothing in a payload; consumers follow the incumbent's stamp id (§2.10, §2.16) | Every sample already carries its writer's zid in its stamp (core §4.1). |
| After a partition, both write until the pure-function recompute converges | The higher id steps down after two reads a grace apart (§2.9) | Deterministic, without a vote; and an actuator's effects do not converge (tcgui's assessment, G3). |
| An anti-twin probe before `alive` (RFC 03 §1.5, a SHOULD) | Under `external`, the lock is the interlock and the probe an early refusal (§2.11) | "Presence is not a lock" (RFC 03 §1.5). |

**What deliberately did not change.**
- **Eventual single writer, said so.** RFC 06 §5.3 accepted it, and so
  does this text (§2.16).
- **Claim, defer to the incumbent, elect, stand by:** the D-Bus shape,
  with ZenSight's fixes.
- **Claim before reading,** and the winner's `alive` only once it serves
  (§2.5 step 1, §2.6).
- **An actuator's lock outside the bus** (§2.11).

**What is not ported.**
- **The claim key, the claim id and `elected_at`** (§2.16).
- **v1's `@rpc/names` queryable,** declared only by the owner: zk2's
  standby declares no operation queryable at all (§2.4).

**The record.** Architecture §3.8 holds: the core has no role concept
beyond the mark, a standby exposes nothing and declares no interface
token, split-brain is a tool's finding, and the core's runtime does not
fence; this profile's step-down is no fence either (§2.9). §3.12's row
lists election, fencing epochs and role naming: the election is §2.5 to
§2.11, the roles named are standby and serving, and fencing epochs are not
at 1.0 (§2.16). r3.2's "a standby holds its instance token only;
ZenSight's `service_guard` is the reference" and r3.3's "instance tokens
as the claim set, and the interface token as the incumbent" are §2.3 and
§2.4 as written. Spike S6's standby, "2 instances seen, no finding, 20/20
executions on the active", is §8's scenario.
