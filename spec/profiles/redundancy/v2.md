# `redundancy.v2`: one instance serves, and its followers know it by its run

| | |
|---|---|
| **Text version** | 0.1 ([`CHANGELOG.md`](CHANGELOG.md)) |
| **Status** | experimental |
| **Written against** | core 0.119 ([`../../core.md`](../../core.md)) |
| **Uses** | no other profile. It restates [`redundancy.v1`](v1.md)'s rules by reference, text 0.11, and replaces its stamps, its consumers' fence and how its state is answered. |
| **Evidence** | [`conformance/v2/`](conformance/v2/), [`scenarios-v2.md`](scenarios-v2.md), and `redundancy.v1`'s for the rules it keeps |

`redundancy.v1` lets several instances of one service run at once. One
serves a governed interface, and the others stand by to take over. Its
consumers tell the incumbent's samples by their Zenoh timestamps' id.
So every candidate's session stamps every write it makes. That costs 26
bytes on each put, a reply per member to every GET of its state, and a
clock guard that holds every write while the clock runs ahead.

`redundancy.v2` keeps v1's election whole, and changes three things:
- **No session stamp.** A candidate's session runs without
  timestamping, as any owner's does (core §8.2). Its puts carry the
  in-band stamp alone.
- **The fence is by run.** A consumer that follows the incumbent accepts
  a sample only under one of the incumbent's runs. The incumbent's
  descriptors state them (core §3.3), and every form but a request
  carries one (core §7.5). So a seed's snapshot and a heartbeat are
  fenced too.
- **The state is answered by snapshot.** A governed state is no longer
  a per-key resource (core §4.2). A follower whose incumbent changes
  reads it again, one snapshot a collection.

```toml
[interface]
name  = "ledger"
major = 1
minor = 1
uses  = ["redundancy.v2"]

[defaults]
annotations = { "redundancy.election" = "claim" }   # the default, as in redundancy.v1
```

The keys are `redundancy.v1`'s. A candidate's descriptor states its run
from its claim on:

```text
zk2/lab/ledger/@zk/instance/<instance>                        a candidate's claim; its descriptor lists the interface and states its run
zk2/lab/ledger/@zk/alive/ledger.v1/<instance>/<fp16>          the incumbent: the one instance serving the interface
zk2/lab/ledger/ledger.v1/state/balance                        a put: CH · the writer's run · seq · record, no Zenoh timestamp
```

The profile adds no key and no byte. The run is in every envelope
already.

## 0. Conventions

The keywords, the roles and the evidence tags are core §0's. Here,
`[F: <file>]` names a fixture in [`conformance/`](conformance/), and
`[Sc: §n]` a section of [`scenarios-v2.md`](scenarios-v2.md). `v1 §n`
names a section of [`redundancy.v1`](v1.md), and a fixture of v1's says
so, as in `[F: v1 elections.json]`.

**By reference.** Every rule of `redundancy.v1` holds for a candidate, a
consumer, a caller, a tool and a deployment of an interface this major
governs, as written, except where §2 replaces it.
- Where a rule of v1 names `redundancy.v1` in a contract's `uses`, it
  reads `redundancy.v2`.
- Where it names a stamp's id or `meta.zid`, it reads a run (§2.10).
- v1's fixtures hold for this major, but two: `v2/declarations.json`
  and `v2/descriptors.json` replace v1's files of those names.

Terms are v1 §0's, and these:
- **Governed interface:** an interface whose contract, at the revision
  an instance implements, lists `redundancy.v2` in `uses` (§2.2). It is
  governed by **either major** where it lists `redundancy.v1` or
  `redundancy.v2`.
- **Run:** core §4.3's, of 16 or 32 bits. Two runs of different widths
  are two runs. This text writes a run as a descriptor does: 4 or 8
  lowercase hexadecimal digits (core §3.3).
- **An instance's runs:** the runs its descriptors stated, as a reader
  read them. It reads them by a GET of the descriptor, and by each put
  of it that it hears (core §3.3).
- **Follower:** a consumer of a governed interface that follows its
  incumbent (§2.10).
- **A sample's run:** the run its form carries (§2.10).
- **Unattributed:** a sample whose run no descriptor the follower holds
  states (§2.10).

## 1. Extension points

| Point (core §10) | `redundancy.v2` |
|---|---|
| 1. A standard contract or a standard schema | None (§3). |
| 2. An annotation vocabulary | `redundancy.v1`'s: `election` (§4). W105 reads core Appendix D's `redundancy` row for a contract that lists either major. |
| 3. A registered verbatim kind | None. |
| 4. The descriptor's `profiles` | Only through `uses`, as v1's: an instance implementing a governed interface lists `redundancy.v2` in its descriptor's `profiles` (core §3.3). |

The **standby mark** is the core's own member, as v1 §1 says.

**Beside `redundancy.v1`.** A contract uses one major of a profile (core
§10). An interface moves from `redundancy.v1` to `redundancy.v2` by a
revision, and candidates of both majors elect together (§2.17).

**Why a new id.** v1's consumer fences by a stamp's id, and this one by
a run. A consumer built for v1 alone, under an incumbent of this major,
finds no stamp of its incumbent's id. It discards every sample, as v1
§2.10 says of one it cannot attribute. That is safe, and inert. A tool
built for v1 alone reads a revision of this major as another major's,
never as v1's (§2.17).

## 2. Rules

### 2.1 Who implements it

v1 §2.1 holds, with these changes:
- **A consumer** SHOULD follow the incumbent by its runs (§2.10).
- **A caller** MAY tell which instance answered a call by its reply's
  run (§2.10).
- **A tool** reads both majors (§2.15, §2.17).

### 2.2 The declaration

v1 §2.2 holds, with `redundancy.v2` where it reads `redundancy.v1`. A
reader MUST read an interface's declaration exactly as the fixture
does. `[F: v2/declarations.json]`
- **Governed** is a contract's `uses` listing `redundancy.v2`. A
  contract whose `uses` lists `redundancy.v1` and no `redundancy.v2` is
  v1's, and not this text's.
- **The reasons.** v1's four hold, in v1's order, each checked alone.
  This text adds one before them and one after them:
  - `majors`: `uses` lists `redundancy.v2` and another major of
    `redundancy`. Core E002 refuses such a contract (core §10), so a
    contract that loads cannot hold it. A reader of resolved annotations
    that come from elsewhere can. The interface is read as governed for
    the checks after it;
  - `explicit_stream`: the interface is governed, and declares a
    `stream` resource with `explicit = true`. Its samples carry no
    envelope (core §4.3), so no run, and no follower can fence them
    (§2.10).
- **A runtime refuses** an invalid declaration of this major as v1 §2.2
  refuses one: no instance token appears. `[Sc: §11]` A contract linter
  SHOULD warn of `explicit_stream`, as v1 §2.2 says of `value` and
  `disagrees`. `[F: v2/declarations.json]`
- **A reader of `redundancy.v1` alone** reads a contract listing both
  majors as v1's (v1's `declarations.json`). A reader of both majors
  reads it `majors`, and the instance does not start.
- **Across revisions.** v1 §2.2's holds. A minor whose `uses` moves from
  `redundancy.v1` to `redundancy.v2` is a review (core §9.8,
  `uses_changed`).
  - **Two majors, one election.** Candidates whose revisions use the two
    majors, with one election, agree on governance.
  - **A tool** reads the address's governance from every candidate's
    revision, of either major, exactly as the fixture does.
    `[F: v2/declarations.json]` A revision unread or invalid gives no
    election, a revision not governed beside a governed one disagrees,
    and so do two elections.

### 2.3 The claim set and the incumbent

v1 §2.3 holds, word for word. The election reads presence alone: a
claim is an instance token, the incumbent is the holder of the
interface's token, and a tie is broken by instance ids. None of it reads
a stamp.

### 2.4 The standby

v1 §2.4 holds, word for word. A standby holds no token of the interface,
exposes none of it and writes none of its keys. It sends no heartbeat
for it either ([`freshness.v2`](../freshness/v2.md) §2.4).

### 2.5 The election under `claim`

v1 §2.5 holds, word for word: claim before reading, a live incumbent
wins, the claim set read whole, and the lowest id. A vacancy is
confirmed by a complete read, never by a stamp.

### 2.6 Taking over

v1 §2.6 holds: its order, its alive ⇒ callable, and an instance that
takes over again holding nothing it does not put again. Its state
changes:
- **Under its own run.** A new incumbent writes under the run its
  descriptor stated from its claim on (core §3.3). Its puts carry that
  run in band, and no Zenoh timestamp of its own (§2.10).
- **Answered by snapshot.** This profile makes no state per key. A
  state of an interface this major governs is answered by snapshot, as
  core §4.2 answers any collection, unless another row of core §4.2's
  list of per-key resources names it. `[Sc: §13]`
- **Each held value is still put,** before the descriptor and the token
  (core §8.2's SHOULD). A consumer that does not follow hears the new
  incumbent only through those puts.
- **The descriptor is still put again,** unmarked. A holder whose
  descriptor marks the interface standby is a twin, `marked_holding`
  (v1 §2.15), so the mark must move.
- **A follower's view** moves to the new incumbent's by its seed (§2.10).

### 2.7 Following the address

v1 §2.7 holds, word for word.

### 2.8 A vacancy

v1 §2.8 holds, word for word.

### 2.9 Healing a split

v1 §2.9 holds. Its "It is no fence" reads by run: a write in flight
from an instance stepping down is under its run, which is no longer the
incumbent's, and a follower discards it (§2.10).

### 2.10 Consumers, callers, and the runs they read

This section replaces v1 §2.10.

**An instance's run.**
- **Drawn at random.** A candidate draws a 32-bit run, as core §4.3 says
  of a candidate of either major. Its descriptor states it from its
  claim on (core §3.3).
- **No session stamp.** Core §8.2's posture holds for a candidate as for
  any owner. Its session runs without timestamping, and it sets no Zenoh
  timestamp on a put or a delete of the interface's keys. Core §8.2's
  exception is `redundancy.v1`'s alone. `[Sc: §9]`
- **`meta.zid`.** Core §3.3's SHOULD holds. v1's MUST does not: this
  major's fence reads no zid.
- **A run no other states.** A candidate SHOULD draw a new run before it
  serves, when it reads its own run in the descriptor of another
  instance of its address. `[F: v2/fences.json]` `[Sc: §14]`
  - It reads the lower ids' descriptors at each campaign anyway (v1 §2.5
    step 3).
  - Two runs are one where their widths and their values are.
  - A new run is core §4.3's: the candidate puts its descriptor again
    before it writes under it.

**The fence.**
- **Follow the incumbent.** A consumer of a governed interface SHOULD
  accept the interface's samples, and the heartbeats that cover it, only
  under the incumbent's runs. `[Sc: §9]` A consumer that does is a
  follower.
  - **The incumbent** is learnt as v1 §2.10 learns it: a watch on the
    provider's `@zk/**`, a complete read, and the holder's descriptor.
    During a split, it is the lowest holder the follower sees.
  - **Each instance's runs** are learnt from its descriptors. A
    follower MUST read a descriptor's run and mark exactly as the
    fixture does. `[F: v2/descriptors.json]` It keeps each run it read
    for as long as it follows the address.
  - **The entry it reads** is the first of the descriptor's
    `interfaces` that is not an object, or whose `iface` is the governed
    interface's. One that is not an object is malformed. No later entry
    is read for the mark. The run is read whatever the entries hold.
- **A sample's run** is the one its form carries (core §7.5):

  | Form | Its run |
  |---|---|
  | mutation, frame, heartbeat, owner heartbeat (a put's payload) | its envelope's |
  | delete | its attachment's |
  | snapshot, held stamp (a GET's reply) | its header's, for every entry the snapshot lists |
  | event | its key's occurrence chunk's (core §1.2) |
  | value, error (a call's reply) | the replying instance's as-of mark (core §5.1) |

  - **A snapshot's entries** are its owner's mutations, an entry's own
    run among them (core §7.5). The header's run names the instance that
    answered, as core §4.2 maps a snapshot to its owner's revision.
  - **A sample with no envelope** has no run. It broke core S1, or it is
    an `@stream` sample, which §2.2 refuses in a governed interface.
- **The rule.** A follower MUST accept and discard each sample exactly
  as the fixture does. `[F: v2/fences.json]` `[Sc: §9]` For each, the
  first of these that holds decides:
  1. it sees no incumbent: discarded, `no_incumbent`. What it holds is
     the last incumbent's last word (v1 §2.10);
  2. the incumbent's revision uses `redundancy.v1`: v1 §2.10 decides,
     by the sample's stamp. Its run is not read (below);
  3. the sample has no run: discarded, `no_run`;
  4. its run is one of the incumbent's: accepted;
  5. its run is one of another instance's that the follower holds:
     discarded, `not_incumbent`;
  6. no descriptor the follower holds states its run: **unattributed**
     (below).
- **A `redundancy.v1` incumbent,** step 2, is followed by `meta.zid`
  (§2.17). For a sample, the first of these that holds decides:
  1. it carries no Zenoh timestamp: discarded, `no_stamp`;
  2. the follower holds no `meta.zid` of the incumbent's: discarded,
     `unattributed`. v1 holds no sample for a read;
  3. its stamp's id is the incumbent's `meta.zid`, compared by value
     (observer §4.4): accepted;
  4. otherwise: discarded, `not_incumbent`.

  A sample with no envelope is read so too. This step reads no run.
- **An incumbent whose major is not known,** its descriptor not held
  yet, is read by run, from step 3 on. No run of its is held. So its
  sample is unattributed, or `not_incumbent` where another instance's
  descriptor states the run.
- **What the rule reads.** Runs compare by width and value. Nothing
  orders two runs (core §4.3), so the fence is by presence, never by an
  epoch in the payload.
  - **A run two instances state** is the incumbent's, by step 4. Two
    live candidates share one run 1 time in 2^32. The draw above narrows
    it to candidates that never read each other.

**An unattributed sample.** A descriptor's put and a sample ride two
keys, so a follower can receive an instance's first sample under a new
run before the descriptor that states it.
- **Held for one read.** A follower MUST NOT discard an unattributed
  sample before a read of the address's descriptors, asked after the
  sample arrived, has ended. `[F: v2/fences.json]` `[Sc: §14]`
  - It decides the sample by the rule as soon as a descriptor it reads
    or hears states the run.
  - It decides it again when that read ends. Still unattributed then, it
    discards it, `unattributed`.
  - It asks one such read at a time. A sample that arrives while one
    runs waits for the next, which the follower asks as that one ends.
  - **A token decides nothing.** An interface token that appears or is
    withdrawn decides no held sample. The rule reads the holders as they
    stand when a descriptor or a read's end decides it.
- **A state member.** Meanwhile the follower holds one unattributed value
  of the member: the one core §4.3's consumer rule would keep. That is
  the higher seq within one run, and the later arrival across two. At an
  equal seq within one run it keeps the value it holds.
- **Every other sample is held alone:** a stream sample, an event and a
  heartbeat, two on one key included.
- **A stream sample** it MAY drop instead. Each stands alone.
- **How often.** At a takeover, only for a follower that holds none of
  the new holder's runs. A standby states its run from its claim on
  (Appendix B). A follower started after that claim heard none of it,
  and a standby holds no interface token. So it learns the run from the
  new holder's descriptor, read at its token. A sample between the two
  is held. Otherwise, only at an incumbent's new run within its
  instance: once per 16,777,216 state mutations and events, before
  its seq would wrap, and whenever its owner takes one (core §4.3).

**A change of incumbent.**
- **Seed again.** A follower whose incumbent changes SHOULD read the
  interface's state again by core S4, and merge only the new
  incumbent's answers. `[Sc: §13, §15]` They are its snapshots, or its
  replies per key under a `redundancy.v1` incumbent (v1 §2.10).
  - **Why.** The takeover's puts come before the new incumbent's token
    (§2.6). So a follower can have discarded them, `no_incumbent` or
    `not_incumbent`, and the seed gives it what they carried.
  - **The omission rule applies** (core §4.2). A member that the new
    incumbent's complete snapshot lists neither live nor as a tombstone
    leaves the follower's view. `[Sc: §13]` No omission rule applies to
    replies per key. Under a `redundancy.v1` incumbent the follower
    keeps what the last incumbent held, as v1 §2.10's does.
  - **Another holder's snapshot** is discarded, `not_incumbent`, as any
    of its samples is.
  - **What it reads.** The collections it is bound to, not every one.
- **The address's word is its incumbent's.** v1's follower kept the last
  incumbent's values until the new one put each again. This one holds
  the new incumbent's.

**What the fence covers.**
- **A seed during a split.** S4's GET is answered by every incumbent.
  Under consolidation `None` each one's snapshot arrives, under its own
  run (core S4). The follower merges its incumbent's, and discards the
  other's. `[Sc: §9]` Where its incumbent's did not arrive, it holds no
  value for those members until its incumbent puts them again: silence,
  never a verdict (core S6, O5).
- **A heartbeat.** The heartbeat that covers the interface, and the
  interface's group in an owner heartbeat, ride `freshness.v2`'s keys of
  the address ([`freshness.v2`](../freshness/v2.md) §2.4, §3). During a
  split each incumbent's carries its own run. A follower reads its
  incumbent's alone, by the rule. Another run's is no heartbeat of its
  incumbent's: neither a lost delivery nor a divergence (`freshness.v2`
  §2.5).
- **A router.** A router rewrites no envelope. v1's fence read a Zenoh
  timestamp, which a router re-stamps or drops beyond its delta (core
  §4.1), so a v1 follower could discard its incumbent's own sample.
- **A clock ahead.** No write of a candidate of this major carries a
  Zenoh timestamp, so the clock guard holds none of them (core §4.3,
  "What goes on").

**Callers.** v1 §2.10's "Calls" holds. During a split a concrete call
runs once on each side, and the profile does not hide it.
- **Which instance answered.** A caller MAY read its reply's run against
  the descriptors' runs, as the rule reads a sample's.

**A consumer that does not follow** reads both incumbents' samples by
core §4.3's consumer rule alone, until the heal (v1 §2.10).

**Why.** v1 §2.10's reason holds. Core §4.3's consumer accepts the
first value under a new run, so two writers flip it at each put.
Following one instance's runs ends it.

### 2.13 Constrained faces

v1 §2.13 holds, with these:
- **A far consumer cannot follow.** Presence does not cross a

### 2.15 What a tool concludes

v1 §2.15 holds: its reads, its premises, its four questions and the
probe. v1's `conclusions.json` holds for this major, given the
governance a tool read.
- **Governance from either major.** A tool reads it from every
  candidate's revision, as §2.2 says. A `redundancy.v1` candidate and a
  `redundancy.v2` one, with one election, are one election. `[F:
  v2/declarations.json]`
- **Each candidate's run.** A tool SHOULD show each candidate's run
  beside its instance, as the candidate's descriptor states it.
  `[Sc: §12]`
- **The probe.** v1 attributes a reply to an instance's session by its
  zid. A reply's error carries the replying instance's as-of mark (core
  §5.1), so a tool MAY attribute it by its run instead, where an
  instance states no `meta.zid`.

### 2.16 Not at 1.0

v1 §2.16 holds. Its "Fencing epochs" item reads: no epoch and no claim
id in a payload. A sample's run already names the instance that wrote
it, by its descriptors (§2.10). A run is no fencing token: nothing
orders two runs (core §4.3).

### 2.17 Beside `redundancy.v1`

`redundancy.v1` and `redundancy.v2` run side by side. Each candidate's
revision says which it uses.
- **An interface moves by a minor revision:** `uses` goes from
  `redundancy.v1` to `redundancy.v2`. That is a review (core §9.8).
- **Candidates of both majors elect together.** The election is v1 §2.3
  to §2.9, which both majors share. Each instance stamps, and answers a
  GET, as its own revision says. Core §4.2 reads which resources are per
  key from the owner's revision. `[Sc: §15]`
- **A follower reads its incumbent's revision,** the one its descriptor
  names. It follows a `redundancy.v1` incumbent by `meta.zid`, as v1
  §2.10 says, and a `redundancy.v2` one by run. It changes as its
  incumbent does. `[F: v2/fences.json]` `[Sc: §15]`
- **Followers first.** A follower built before this major finds no
  stamp of its incumbent's id under a `redundancy.v2` incumbent. It
  discards every sample: safe, and inert. So a deployment SHOULD move
  its followers to a reader of both majors first, then its standbys,
  then its incumbent. `[Sc: §15]`
- **A tool built before this major** reads a revision of it as another
  major's: `not_governed`, or `revisions_disagree` beside a v1
  candidate. Its answer is unobservable or not this profile's, never a
  wrong verdict. Its split-brain check falls back to core §6's
  ([`observer.md`](../../observer.md) §6.1).

## Appendix A. Against `redundancy.v1`

| `redundancy.v1` | `redundancy.v2` | Why |
|---|---|---|
| A candidate's session stamps every write: core §8.2's exception (§2.10) | It runs without timestamping, as any owner's (§2.10) | The run in every envelope names the writer already. |
| `meta.zid` a MUST (§2.10) | Core §3.3's SHOULD (§2.10) | The fence reads no zid. |
| A follower accepts a stamp whose id is the incumbent's `meta.zid` | A sample under one of the incumbent's runs, as its descriptors state them (§2.10) | A run rides every form but a request, and no router rewrites one. |
| A sample it cannot attribute is discarded | Held until one read of the descriptors ends (§2.10) | A run, unlike a zid, changes within an instance. |
| Every state per key: a reply a member, each with its stamp | Answered by snapshot (§2.6) | The state leaves core §4.2's list. |
| A seed during a split: the other incumbent's replies discarded by id | The other's snapshot discarded by run (§2.10) | |
| At a takeover, the last incumbent's values held until each is put again | The new incumbent's snapshot, with its omissions (§2.10) | The takeover's puts precede its token, so v1's follower discarded them. |
| An explicit stream fenced by its stamp | Refused in a governed contract, `explicit_stream` (§2.2) | An `@stream` sample carries no run. |
| The clock guard holds every write | It holds none (§2.10) | No write carries a Zenoh timestamp. |

**Five guarantees change.**
1. **An unattributed sample is held, not discarded.** For one read's
   round trip a follower holds a value it has not attributed.
   - A follower that cannot read descriptors, its GET refused or cut
     off, accepts nothing under a new run until it can.
2. **A follower's view at a takeover is the new incumbent's.** A member
   the new incumbent's complete snapshot leaves out leaves the view.
   v1's follower kept the last incumbent's value until each was put
   again.
3. **An explicit stream is refused, not fenced.** A governed interface
   of this major declares no `@stream` resource.
4. **Two candidates can share a run,** 1 time in 2^32 a pair. Two
   sessions' zids, of 128 bits, effectively never do. A follower then
   accepts both, until the heal. The draw again narrows it to candidates
   that never read each other's descriptors.
5. **A contract listing both majors is invalid,** `majors`, to a reader
   of both. A reader of v1 alone read it as v1's.

**What did not change:** an eventual single writer, never a lock; the
election, the heal and twin detection, all by presence; a standby that
exposes and writes nothing; a call that finds no standby; alive ⇒
callable at a takeover; and a far reader that cannot fence.

## Appendix B. The bytes, computed

The payloads were measured on `redundancy.v1` today, through one router
on loopback. Every other figure is computed from them, through the
constrained-overhead review's model
([`constrained-overhead-review.md`](../../../docs/zk2/constrained-overhead-review.md),
Appendix A), for a put on a key its reader declared. None crossed a wire
under this major.

| | `redundancy.v1` | `redundancy.v2` |
|---|---:|---:|
| `ledger.v1`'s `balance`, a 5-byte record: payload (measured) | 13 B | 13 B |
| the same put | 43 B | 17 B |
| a takeover's puts, 100 members of 200 B, an 18-character id | 25.9 KB | 23.3 KB |
| a follower's seed of those 100 members | 28.3 KB in 100 replies | 22.5 KB, one snapshot in pages |
| the descriptor, marked standby (measured) | 340 B | 340 B |
| the descriptor, put again at a takeover (measured) | 325 B | 325 B |

- **The put** is 26 bytes shorter: the Zenoh timestamp.
- **A standby states its run** from its claim on. Each measured standby's
  marked descriptor and its unmarked one, put at its takeover, state the
  same 32-bit run. Its first put as incumbent is under that run, at
  seq 0.
- **A seed's saving** is the replies, not the bytes. At 10,000 members
  of 200 B the snapshot is 2.25 MB, where the per-key answer is 2.83 MB
  in 10,000 replies.
