# `hostid.v1`: a system minted from the machine id

| | |
|---|---|
| **Text version** | 0.1 ([`CHANGELOG.md`](CHANGELOG.md)) |
| **Status** | draft |
| **Written against** | core 0.19 ([`../../core.md`](../../core.md)) |
| **Uses** | no other profile |
| **Evidence** | [`conformance/`](conformance/), [`scenarios.md`](scenarios.md) |

`hostid.v1` lets every service on a host derive the same system name from
the host's machine id, with no coordination. The system is position 2 of
every key a service writes (core §1.1), so one host is one system across
every zk2 application on it (core §1.5, "system = host").

```text
zk2/h-bbd1aa1db10b/sysinfo/sysinfo.v1/stream/cpu/usage
    └─ minted from /etc/machine-id by hostid.v1
```

It defines no contract, no annotation and no kind. It is
**derivation-only** (core §10, 0.19): the system it mints goes where every
system goes, and an instance whose system is minted says so in its
descriptor's `profiles`.

---

## 0. Conventions

The keywords, the roles and the evidence tags are core §0's. Here,
`[F: <file>]` names a fixture in [`conformance/`](conformance/),
`[Sc: §n]` a section of [`scenarios.md`](scenarios.md), and `core` marks
the core's own evidence.

Terms:
- **Service:** an owner, or a consumer with an address of its own. Both
  have a system, and both hold an instance token (core §8.1), so the rules
  bind both.
- **Machine id:** the content of `/etc/machine-id` or
  `/var/lib/dbus/machine-id`, 32 hex digits (machine-id(5)).
- **Input:** a file this profile reads an id from (§2.4).
- **The shared file:** `/var/lib/zk2/hostid` (§2.5).
- **Minted system:** a system this profile derives, from an input or
  ephemeral (§2.6). A **literal** system is one the deployment names itself.
- **Run:** one start of a service's process, until it exits.

## 1. Extension points

| Point (core §10) | `hostid.v1` |
|---|---|
| 1. A standard contract | None. It defines no interface, resource or key. |
| 2. An annotation vocabulary | None. A contract has no reason to list it in `uses`, and SHOULD NOT (§2.8). |
| 3. A registered verbatim kind | None. |
| 4. The descriptor's `profiles` | Yes: an instance whose system is minted lists `hostid.v1` (§2.8). |

It uses point 4 alone, so it is derivation-only (core §10, 0.19).

## 2. Rules

### 2.1 The derivation

An implementation MUST derive a system from an input and a salt exactly as
follows. `[F: vectors.json]`
1. **Normalise.** Remove from both ends of the input the ASCII whitespace
   bytes 0x09 (TAB), 0x0A (LF), 0x0C (FF), 0x0D (CR) and 0x20 (SPACE), and
   no other character. Then lowercase the letters `A`–`Z`.
2. **Check.** The result MUST be exactly 32 hexadecimal digits,
   `[0-9a-f]`, and not all zeros. Anything else is refused: it yields no
   system.
3. **Hash.** Take the sha256 of the normalised text followed by the salt,
   both as UTF-8, with no separator.
4. **Truncate.** The system is `h-` followed by the first 12 lowercase hex
   digits of the digest: its first 6 bytes.

```text
norm   = lower(trim(input))        32 hex digits, not all zeros, or refused
system = "h-" ++ hex(sha256(utf8(norm) ++ utf8(salt)))[0..12]
```

- **Example.** `b642b4217b34b1e8d3bd915fc65c4452` with `zk2-hostid-v1`:
  the sha256 of `b642b4217b34b1e8d3bd915fc65c4452zk2-hostid-v1` begins
  `bbd1aa1db10b`, so the system is `h-bbd1aa1db10b`.
- **The trimmed set is exact.** Python's `str.strip()` and `bytes.strip()`
  also remove 0x0B. `str.strip()`, like Rust's `str::trim`, also removes
  Unicode spaces such as U+00A0. An implementation names the five bytes,
  and refuses an id with any other character around it.
- **All zeros** is refused because machine-id(5) says a machine id "may
  not be all zeros", and every host carrying one would mint the same
  system.
- **The result** is 14 characters. It is a plain chunk (core §1.2), and its
  own slug, since it does not start with `x-` (core §1.4 rule 1).

### 2.2 The salt

The salt is the constant `zk2-hostid-v1`, 13 ASCII bytes. A service MUST
derive its system with it, and an implementation offers no setting that
changes it. `[F: vectors.json]` `[Sc: §1]`
- **One salt for every application** (architecture D26). A machine is one
  system across tcgui, ZenSight, zenoh-modem and every other zk2
  application on it, where v1 gave it one origin per application.
- **The parameter.** §2.1 takes the salt as a parameter only so that the
  vectors can hold v1's own vector, and so that the migration table
  (Appendix B) can be computed.
- **Another salt** would mint other names. It would be a new major, never
  an amendment of this text ([`../README.md`](../README.md), "The
  process").

### 2.3 Asking for a minted system

A system is the deployment's choice (core §1.5). It is minted only when the
deployment asks for it, in the service's configuration. As for bindings
(core R1), the configuration's format is a recommendation, not a rule. The
recommended spelling, which the reference runtime reads:

```toml
address = "@hostid.v1/sysinfo"   # the system is minted by hostid.v1
hostid  = { ephemeral = true }   # optional, false by default (§2.6)
```

- **`@hostid.v1` at the system position** of `address` asks for a minted
  system. It starts with `@`, so it is not a plain chunk (core §1.2), and
  no literal system is spelled the same way.
- **A literal system** is written as before: `address = "vehicle-01/nav"`.
  A literal name in the minted shape, such as `h-3fa9c2d41b7e/nav`, is
  literal. Nothing is minted, and the service does not list `hostid.v1`
  (§2.8).
- **`hostid.ephemeral`** opts into an ephemeral system (§2.6). Set without
  `@hostid.v1`, it is a configuration error.
- **One process, one system.** The minted system is the process's (§2.7),
  so this setting is too. A process whose services disagree on
  `hostid.ephemeral` does not start.

### 2.4 The inputs, in order

A service that asked for a minted system MUST take the first of these
inputs that yields an id, in this order: `[Sc: §1]`
1. `/etc/machine-id`;
2. `/var/lib/dbus/machine-id`;
3. the shared file, `/var/lib/zk2/hostid`, created when it does not exist
   (§2.5).

An input yields no id, and the next one is tried, when it is absent, or
when §2.1 refuses its content: empty, `uninitialized` (systemd's
first-boot marker), not 32 hex digits once normalised, or all zeros.
`[F: vectors.json]`
- **An input that exists but cannot be read** (a permission refused, an
  I/O error) is not skipped: the service fails closed (§2.6), naming it.
  `[Sc: §3]` Skipping it would mint another system than the services on
  the host that can read it.
- **The input is the file's bytes.** Bytes that are not UTF-8 are not 32
  hex digits.
- **A path is read as the operating system resolves it,** symbolic links
  included: `/var/lib/dbus/machine-id` is often a link to
  `/etc/machine-id`.
- **The paths are Linux's.** A host without either machine-id file uses
  the shared file.
- **The order is part of the wire.** An input added before the shared
  file, or a change of order, would change the system of a host that has
  that input. It would be a new major.

### 2.5 The shared file

The shared file gives a host without a usable machine id a stable system,
the same for every service on it.
- **Content.** 32 lowercase hex digits, the hex of 16 bytes from the
  operating system's cryptographically secure random source
  (`getrandom(2)`), then a newline (0x0A). It goes through §2.1 like a
  machine id, with the salt.
- **Creation.** When opening the file fails because it does not exist, a
  service MUST create it so that every racer ends with the same content.
  `[Sc: §2]`
  1. Create `/var/lib/zk2` if it is missing, mode 0755. An `EEXIST` there
     is success.
  2. Create a temporary file in that directory, under a name no racer
     shares (such as `.hostid.<16 random hex digits>`), exclusively
     (`O_CREAT | O_EXCL`), mode 0644.
  3. Write the content, then `fsync(2)` the temporary file.
  4. `link(2)` the temporary file to `/var/lib/zk2/hostid`:
     - on success, the service's content is the file's. It then `fsync`s
       the directory;
     - on `EEXIST`, another racer won. The service reads the final file,
       which `link(2)` published only once complete, and uses its content.
  5. Unlink the temporary file, in both cases.
- **Never replace, never write in place.** A service MUST NOT create the
  final name with `rename(2)`, which replaces a file a racer may already
  have read, nor by writing it in place, where a racer can read it empty.
  A file system where `link(2)` fails (`EPERM`, `ENOTSUP`) is one where the
  file cannot be created, and §2.6 applies. `[Sc: §2]`
- **An existing file without an id** (empty, or anything §2.1 refuses) is
  not replaced. It yields no id, and §2.6 applies, naming it. Two racers
  that each replaced it would hold two systems, and whatever wrote it
  wrong needs an operator to look. `[Sc: §3]`
- **One path per host.** The path is `/var/lib/zk2/hostid` for every
  application, user and deployment on the host, never one per application
  or per user. Every service on the host agrees through it without
  coordination: one system per host (D26). The file is readable by every
  user, like `/etc/machine-id`.

### 2.6 Failure, and ephemeral systems

- **Fail closed.** When no input yields an id, the shared file included,
  or an input cannot be read (§2.4), a service that asked for a minted
  system MUST NOT start. `[Sc: §3]`
  - It stops before core §8.2 step 1, so nothing of it appears on the bus.
  - Its error names every path it tried, each with why it gave no id:
    absent, unreadable, refused by §2.1, or not created, with the
    system's error.
  - v1 fell back to an unpersisted random id without a warning
    (Appendix A). The system then changed at every start, unannounced,
    which splits the host's history and breaks every binding to it.
    Refusing makes someone fix the host.
- **Ephemeral, by opt-in.** A deployment MAY opt into an ephemeral system
  (`hostid.ephemeral`, §2.3). It is the last rung, after the shared file:
  where the service would refuse, it mints a fresh system instead.
  `[Sc: §4]`
  - It draws 32 hex digits as §2.5 does, derives the system from them by
    §2.1, and writes them nowhere.
  - It says so. At every start, the service logs that its system is
    ephemeral, with every path it tried and why each gave no id.
  - An ephemeral system lives for one run (§2.7). A restart mints another
    one, and two processes on one host mint two. System = host does not
    hold for it, and that is what the opt-in accepts.
  - It is minted by this profile, so the service lists `hostid.v1`
    (§2.8).
  - An input that yields an id still wins: ephemeral is a fallback, not a
    mode.

### 2.7 Minted once per run

A process MUST mint its system once, before core §8.2 step 1 of the first
service it starts, and keep it until it exits. `[Sc: §5]`
- **A re-mint keeps it.** `new_epoch` (core §8.1) starts a new instance of
  the same address: the instance id changes, and the system does not.
- **Every service the process hosts** with a minted system has the same
  one, an ephemeral one included. `[Sc: §4]`
- **A changed machine id** gives a new system at the process's next
  start, never during a run. The old system's keys fall silent, and
  nothing on the bus links the two systems (Appendix A: v1's alias
  machinery is not ported).

### 2.8 Declaration

- A service whose system is minted, from an input or ephemeral, MUST list
  `hostid.v1` in its descriptor's `profiles` (core §3.3, 0.19). `[Sc: §1]`
  `[F: core descriptors/ok-derivation-profile]`
- A service whose system is literal MUST NOT list it, even when the name is
  in the minted shape. `[Sc: §1]`
- A contract SHOULD NOT list `hostid.v1` in its `uses`. The system is the
  deployment's choice, never the contract's (core §1.5), and this profile
  has no vocabulary. Core §3.3 puts every used profile in `profiles`, so a
  contract that lists it makes the listing ambiguous, and a tool cannot
  read minting from it (§5).

### 2.9 Containers

- **A container that is part of its host** (it runs the host's services,
  under the host's name) sees the host's `/etc/machine-id` through a
  read-only bind mount, and so mints the host's system. Where the host uses
  the shared file, the container sees the host's `/var/lib/zk2` the same
  way.
- **A container that is a host of its own** (its own init, a machine id
  generated at its first boot) mints its own system.
- **A container with neither** mints from a shared file in its own file
  system, a system that lasts as long as that file does.
- **No shipped id.** A deployment MUST NOT ship a machine id, or a shared
  file, in an image. Every machine or container started from it would mint
  the same system: cloned ids are the realistic way two hosts collide
  (§2.12). An image's `/etc/machine-id` is absent or empty, as
  machine-id(5) recommends. `[Sc: §6]`

### 2.10 Privacy

- **Never on the bus.** A service MUST NOT put a machine id, or the shared
  file's content, on the bus: in no key, payload, attachment, reply or
  descriptor, `meta` included. machine-id(5) asks the same of the machine
  id. `[Sc: §1]`
- **The system does not reveal them.** It is 48 bits of a sha256 over 128
  random bits.
- **It is linkable on purpose.** Every zk2 application on a host, in every
  deployment the host joins, mints the same system (D26). machine-id(5)
  recommends a key per application instead. One name across applications
  is the point of system = host.
- **A deployment that wants a host unlinkable** names its system literally
  (§2.3).

### 2.11 Recognising the shape

- **The shape.** A string is in the minted shape when it is exactly `h-`
  followed by 12 lowercase hex digits: `^h-[0-9a-f]{12}$`, matched against
  the whole string. An implementation's check MUST agree with every case
  of the fixture. `[F: shapes.json]` In Python, that is `re.fullmatch`,
  since `re.match` with `$` also accepts a trailing newline.
- **A hint, never proof.** A deployment may name a system `h-3fa9c2d41b7e`
  literally, and v1 minted the same shape under other salts. Only the
  descriptor's `profiles` establishes a minted system (§2.8). A tool MUST
  NOT report a system as minted from its shape alone (§5). `[Sc: §6]`

### 2.12 Collisions and cloned ids

- **The odds.** A minted system keeps 48 bits. Among n hosts with distinct
  machine ids, two share a system with a probability of about
  n² / 2⁴⁹:

  | Hosts | Probability that two share a system |
  |---|---|
  | 1,000 | 1.8 × 10⁻⁹ |
  | 100,000 | 1.8 × 10⁻⁵ |
  | 1,000,000 | 1.8 × 10⁻³ (0.18 %) |

  These are v1's figures (RFC 06 §1), and the 48 bits are unchanged. A
  cloned machine id (§2.9) collides with certainty, so it is the case that
  matters.
- **What a collision shows.** Where the two hosts run services of the same
  name, two sessions hold instances of one address. Where their service
  names differ, no key collides, but a per-host selection
  (`zk2/<system>/**`) shows the two hosts as one.
- **Detected, not prevented.** Two or more instances of one address whose
  descriptors list `hostid.v1`, seen in both of two presence reads a grace
  apart (core §8.1), with different `meta.zid` (compared by value, core
  §3.3), are a **finding whose cause is undecided**. A tool diagnoses it,
  as it diagnoses core §6's split-brain.
  - Its causes are a collision, a cloned machine id, and a second process
    started as the same service on one host, a standby (core §6) included.
    Nothing on the bus tells them apart, so a tool that reports the
    finding MUST NOT name one of them as the cause. `[Sc: §6]` It MAY show
    each instance's `meta.host` (§2.13) beside the finding, as evidence
    for the operator.
  - A re-mint is not this finding: its overlap shows in one read at most
    (core §8.1).
  - An instance whose descriptor could not be read, or states no
    `meta.zid`, leaves the address undecided: unobservable, never clean.
  - Where two instances are active on one exclusive interface, core §6's
    split-brain finding fires too. On a minted system, its causes include
    a collision and a cloned machine id.

### 2.13 `meta.host`

A service SHOULD state its host name as `meta.host` (core §3.3), for
display. The system names the host opaquely, and `meta.host` names it for
a person. It is never part of an identity: host names change and repeat,
and a tool keys nothing by one.

## 3. Contract

None. `hostid.v1` defines no interface, resource, operation or key. It
puts nothing of its own on the bus beyond the listing in the descriptor's
`profiles` (§2.8).

## 4. Vocabulary

None: it has no annotation key (core §10 point 2), so core Appendix D has
no interim table for it, and none is needed.

The words it uses are not annotations, and none is fingerprinted:

| Word | Where | Meaning |
|---|---|---|
| `@hostid.v1` | the system position of a service's configured `address` | mint the system (§2.3) |
| `hostid.ephemeral` | a service's configuration | allow the last rung (§2.6) |
| `hostid.v1` | the descriptor's `profiles` | this instance's system is minted (§2.8) |
| `meta.host` | the descriptor | the host name, for display (§2.13); the core's own member |

## 5. What a tool may conclude

"Not asked" and "unobservable" are different facts, and neither is a "no"
(core O5, Appendix A).

| Question | Yes | No | Unestablished | Finding on |
|---|---|---|---|---|
| Is this instance's system minted by `hostid.v1`? | Its descriptor lists `hostid.v1`, and no contract it implements lists it in `uses` (§2.8). | Its descriptor does not list it. | **Not asked:** no descriptor was read. **Unobservable:** the descriptor could not be read; or a contract the instance implements lists `hostid.v1` in `uses`. **From the shape alone:** unobservable, never yes (§2.11). | Neither: informative. |
| Is this string in the minted shape? | `h-` and 12 lowercase hex digits, the whole string (§2.11). | Anything else. | Never: it is a function of the string. | Neither. It is a hint, and never answers the question above. |
| Do these two instances run on one host? | Both systems are minted (the first question, yes for each), and equal. This holds up to §2.12: a collision or a cloned id makes two hosts one system. | Never from the systems alone. | **Unobservable:** either system is not known to be minted, since a literal system says nothing about hosts; or the two minted systems differ, since one host has two systems across a change of machine id (§2.7), and ephemeral ones (§2.6). | Neither: informative. |
| Do two sessions claim one address of a minted system? (§2.12) | Two or more instances of the address in both of two reads a grace apart, with different `meta.zid`: the finding, its cause undecided. | One of the two reads, ended by the routers' final reply (core §8.1), shows at most one instance of the address. | **Not asked:** the address's system is not minted (the first question). **Unobservable:** a read that ended at its timeout shows at most one instance, which it may have missed, and the other read does not settle it; or a descriptor could not be read, or states no `meta.zid`. | Yes. |

**Which cause** a finding of the last question has is unobservable,
always: nothing on the bus tells a collision, a cloned machine id and a
second process apart (§2.12).

## Appendix A. Against v1

v1 minted host origins by RFC 06 §1 and §1.1, implemented in zenkey 0.11's
`origin.rs` and `profile.rs` (`v1` branch).

**What changed.**

| v1 | `hostid.v1` | Why |
|---|---|---|
| One salt per application, an `AppProfile` constant (RFC 06 §1) | One salt, `zk2-hostid-v1` (§2.2) | D26: one system per host, across applications |
| Any non-empty text, trimmed and lowercased, was hashed, never checked (`HostId::from_machine_id`, `HostId::mint`) | 32 hex digits, not all zeros; anything else is skipped (§2.1, §2.4) | v1 hashed `uninitialized`, a UUID or garbage into a valid-looking origin, the same on every host carrying it |
| Rust's `str::trim`: Unicode whitespace | Five ASCII bytes (§2.1) | One exact set, which two languages can agree on |
| `/etc/machine-id` only (`AppProfile::host_id`). tcgui's own ladder also read `/var/lib/dbus/machine-id`. | Both, in that order, then the shared file (§2.4) | |
| A fallback file **per application and per user**: `$XDG_STATE_HOME/<app>/host-id`, else `/var/lib/<app>/host-id` (`AppProfile::host_id_fallback_path`), holding an `h-` origin. tcgui's held 32 hex digits, under `$XDG_STATE_HOME/tcgui/host-id` or `~/.local/state/tcgui/host-id`. | **One file per host**, `/var/lib/zk2/hostid`, holding 32 hex digits that go through §2.1 (§2.5) | The per-application, per-user path contradicts D26: two applications, or two users, on one host minted two origins. |
| **Create-exclusive, then write** (`HostId::mint_persisted`). A racer that read the file between the winner's create and its write found it empty, and kept its own fresh id: two origins on one host. RFC 06 §1.1 asked for both write-temp-and-rename and create-exclusive. | A temporary file, `fsync`, then `link(2)`; `EEXIST` reads the winner's complete file (§2.5) | The race |
| Randomness: the sha256 of the pid, the time and `$HOSTNAME` (`HostId::random`) | 16 bytes from a CSPRNG (§2.5) | |
| A last resort: a fresh random id, persisted best-effort, without a warning; tcgui's ladder then fell back to the host name | Fail closed, naming every path; an ephemeral system only by opt-in, and said (§2.6) | The maintainer, 2026-10-09 |
| An origin: a key position only `h-` could fill | The system position, which any plain chunk fills; minted only when asked (§2.3), and declared (§2.8) | Core §1.5: the system is the deployment's choice |

**What deliberately did not change.**
- **The hash construction:** the sha256 of the normalised id followed by
  the salt, as UTF-8, with no separator.
- **48 bits:** 12 hex digits.
- **The `h-` prefix.**
- **The test-vector discipline.** RFC 06's own vector is kept, with its
  own salt, in [`conformance/vectors.json`](conformance/vectors.json).

So for every valid machine id, v1 and this profile agree, given the same
salt. The migration table (Appendix B) rests on that.

**What is not ported.**
- **RFC 06 §1.1's hardware-id rung:** a hash of the primary MAC or a
  serial. A MAC moves with a network card and repeats across virtual
  machines, and the shared file gives the same stability without one.
- **Typed origins** (`LocalOrigin`, `RemoteOrigin`, `ServiceOrigin`,
  `Fleet`; RFC 08 §1.1). A zk2 system is a plain chunk of an address, and
  core §1.5's "no implicit identity" covers what they guarded.
- **The catalog and alias machinery** (RFC 06 §4 and §5: `evidence/self`
  claims, `@catalog`, `alias/<old>`, the operator's `link` after a
  reinstall). A changed machine id is a new system, and nothing on the bus
  links the two. D26 notes that ZenSight's catalog can publish the
  migration as aliases: that is ZenSight's to do, not this profile's.
- **The catalog's collision check,** by disjoint `evidence/self` claims
  under one origin. §2.12's finding replaces it, with what presence and
  descriptors show.

**The record.** D26 supersedes the wording of
`docs/zk2/architecture.md` §3.5 (around its line 499), "v1's `h-<12hex>`
derivation, byte-precise": the construction is v1's, byte for byte, but
the salt is not, so every minted value changes. The row of §3.12 ("v1's
`h-<12hex>` derivation, with test vectors") holds as written.

## Appendix B. The migration table

A host maps its v1 origins to its zk2 system when it is ported. Both are
derived from the same machine id, so only a reader of that id, the host
itself, can compute the pair. A v1 origin alone does not give the zk2
system, because the hash is one-way.

For a machine id M:
- its v1 origin under an application is §2.1 with that application's v1
  salt;
- its zk2 system is §2.1 with `zk2-hostid-v1`.

With M = `b642b4217b34b1e8d3bd915fc65c4452`:

| Application | v1 salt, as its source spells it | Source | v1 origin of M | zk2 system of M |
|---|---|---|---|---|
| tcgui | `tcgui-host-id-v1` | `tcgui-shared/src/identity.rs:30` (tcgui) | `h-eed9ac91da20` | `h-bbd1aa1db10b` |
| ZenSight | `zensight-host-id-v1` | `zensight-common/src/lib.rs:159` (zensight) | `h-94431c427f53` | `h-bbd1aa1db10b` |
| zenoh-modem | `zenoh-modem-host-id-v1` | `modem-contract/src/lib.rs:52` (zenoh-modem) | `h-1a0f888ca063` | `h-bbd1aa1db10b` |
| zenwatch | `zenwatch-host-id-v1` | `zenwatch/src/publish.rs:48` (this repository) | `h-050c47dd65e7` | `h-bbd1aa1db10b` |
| RFC 06's vector | `example-salt-v1` | RFC 06 §1 (`rfcs/06-identity.md`, `v1` branch) | `h-20609002f7b6` | `h-bbd1aa1db10b` |

Every value is a case of [`conformance/vectors.json`](conformance/vectors.json).
The four v1 origins of one machine become one system.

- **A host whose v1 origin did not come from a machine id** has no mapping
  by derivation. Its zk2 system comes from §2.4, and only whoever ports the
  host can record the pair.
