# Zenkey v2: revised architecture proposal (r2)

*Proposal r2, 2026-10-07. It supersedes §8 of the r1 analysis, which was
shipped as Part 2 of `r1-analysis.md`. It incorporates the review
of r1 and is self-contained. It is not code. It exists for the maintainer's
decisions and for the spike. Zenoh facts were read in the zenoh 1.10.1
source; Appendix B lists them with file references.*

**Objective.** The smallest durable, language-independent API-contract and
reflection layer that makes Zenoh suitable as the foundation of an
application architecture.

**Standing rule.** When we can either add a Zenkey abstraction or use an
existing Zenoh primitive with a small semantic rule, we use the primitive.

---

## 0. What changed since r1

The review accepted §8's architecture and asked for five changes. All five
are adopted. Three come back with more precision than requested, because the
zenoh source sharpened them.

| Review item | Disposition | What r2 does |
|---|---|---|
| **F1** Grammar major in the key | **Adopted** | `zk2/` as the first chunk, an ordinary chunk (§2.1). Beyond the reviewer's orthogonality argument there is a coexistence argument: without a fixed first chunk, a system named `0` collides with rmw_zenoh's ROS domain 0, and v1's keys start with `v1/`. |
| **F2** Exclusive by default, not single-active | **Adopted, simplified** | A serving model per resource: `exclusive` (the default) or `replicated` (operations only). The core keeps **no role concept**: ownership is visible through each instance's declared exposure, and active/standby belongs to the redundancy profile (§2.4). |
| **F3** State timestamps normative (blocker) | **Adopted, strengthened** | The source shows why this is a blocker, not hygiene. The network never stamps deletes or query replies, and `Latest` consolidation ranks an unstamped reply *below* a stale stamped storage reply. r2 adds producer-set timestamps on every mutation, tombstone replies via `reply_del`, and an explicit target and consolidation. Clock regression on restart is a named open hazard (§2.5, U1–U3). |
| **F4** Contract fetch tolerates many replies | **Adopted** | Correctness comes from verifying the sha256, never from routing uniqueness. First valid reply wins. On no valid reply, retry with target `All` (§2.9). |
| **F5** Behavioural profiles need specs | **Adopted; r1's claim withdrawn** | A profile is a versioned spec contributing through four core extension points (§2.11). Config, jobs, redundancy, freshness, media and bulk all carry normative behaviour. |
| A1 Page budget as pressure, fixtures where machine-testable | Adopted | The rule becomes: every machine-testable normative rule has a fixture or a scenario test. |
| A6 Asymmetric schema recommendation; careful protobuf hashing | Adopted, approach changed | No invented "normalized" protobuf representation. Bundles are **built once and embedded**, fingerprints cover bytes, and a **retention rule** absorbs toolchain drift (§2.7). |
| B4 Directional metadata compatibility | Adopted | A directional table (§2.10). |
| Presence: API before instance | Adopted provisionally | Benchmarked against the alternative in spike S2 (U5). |
| Decision 6: no "1.0" until the core is stable | Adopted | Plus two practical consequences: production zenctl builds and the open 0.15.0 milestone (§4). |
| New in r2, from the source | Proposed | Operation queryables become `complete`, so a concrete call executes **at most once**, even under split-brain (§2.6, U4). |

**Where r2 still disagrees with the review.** Only in phrasing. "Storage
MUST preserve the original timestamp" binds Zenoh's storage manager, which
Zenkey cannot oblige. r2 states it as a **deployment** conformance
requirement and makes the spike verify it.

## 1. Principles

1. **Small core, extension points, independent profiles.** The core
   defines identity, three resource kinds, contracts, discovery and
   compatibility, and nothing else.
2. **Rules on Zenoh primitives, not new machinery.** There is no daemon,
   no central registry and no heartbeat topic:

   | Need | Zenoh primitive | Zenkey's rule |
   |---|---|---|
   | Presence | Liveliness token | One per (instance × API); the key carries the identity |
   | Stream | Declared publisher | Kind chunk; delivery class |
   | State | Publisher + queryable + timestamps + `reply_del` | Producer stamps every mutation; GET uses `All` + `Latest` |
   | Operation | Queryable, `complete`, concrete key | Concrete calls run at most once; fan-out only if allowed; server-side refusal |
   | Contract retrieval | `complete` queryable + `BestMatching` | Content-addressed key; verify the hash |
   | Descriptor | Put + queryable | Built from declared handles before presence |
   | Isolation | Session namespace | Optional deployment prefix |
3. **Correctness from content, not from routing.** Hashes verify bundles;
   timestamps order state; explicit query targets replace defaults.
4. **Contract and runtime are separate documents.** The contract (static,
   by hash) says what may exist. The descriptor (per instance) says what
   does exist here.
5. **Truthful by construction.** Exposure is computed from declared
   handles, never from observed traffic or a separately published file.
6. **Every machine-testable normative rule ships with a fixture or a
   scenario test.** The core targets 20–30 pages as a design pressure.

## 2. The architecture

### 2.1 Grammar

```
[<namespace>/]                                                   optional deployment prefix (session namespace)
zk2/<system>/<service>/<api>.v<major>/stream/<resource…>         stream
zk2/<system>/<service>/<api>.v<major>/state/<resource…>          state
zk2/<system>/<service>/<api>.v<major>/@op/<operation…>           operation (verbatim plane)
zk2/<system>/<service>/@zk/alive/<api>.v<major>/<instance>/<fp16>     presence (liveliness tokens only)
zk2/<system>/<service>/@zk/instance/<instance>                         instance descriptor
zk2/@zk/contract/<api>.v<major>/<sha256>                               contract bundles (location-free)
```

| Pos | Chunk | Rule |
|---|---|---|
| 1 | `zk2` | Zenkey grammar major. A plain chunk: never verbatim, because v1's verbatim `@v1` broke zenoh-ext's advanced-publisher detection. `zk<int>` is reserved. |
| 2 | `<system>` | One plain chunk (§2.2). Under `zk2/@zk/…`, position 2 is the control token instead. |
| 3 | `<service>` | One plain chunk. |
| 4 | `<api>.v<major>` \| `@zk` | API identity, or the per-service control token. |
| 5 | Kind | `stream` \| `state` \| `@op`, or a verbatim kind registered by a profile (`@media`, `@blob`). |
| 6+ | Resource path | Literal chunks and `{param}` chunks from the contract template. Parameter values are slugged injectively (v1's `x-` rule, with its decoder and fixtures). |

**Why `zk2`:**

- the grammar major is orthogonal to API majors;
- it gives clean coexistence with v1 (`v1/…`), rmw_zenoh
  (`<domain>/…`) and raw applications on one bus;
- one prefix names all Zenkey traffic for ACL, link budgets and storage;
- "is this a Zenkey key?" becomes a prefix test.

The cost is one interned chunk per declaration, not per sample.

**Properties by key algebra:**

- **Exact kind selectors.** Positions 1–5 have fixed arity, so
  `zk2/*/*/*/state/**` is exact.
- **The system firehose is data-only.** `zk2/vehicle-01/**` reaches
  every stream and state key of the system, and never `@op`, `@zk`,
  `@media` or `@blob` (verbatim).
- **Majors and grammars are mutually invisible.** `zk2/**` never matches
  `zk3/…`, and `nav.v2` never matches `nav.v3`.

### 2.2 Identity

| Concept | Example | Chosen by | Where it lives |
|---|---|---|---|
| Deployment | `prod`, `sim-42` | Operator | Optional session namespace |
| **System**: the logical deployment and ownership unit used as the outer application policy boundary | `vehicle-01`, `ground`, `fleet` | Deployment config | Key, position 2 |
| **Service**: logical, stable | `navigation`, `imu0` | Deployment config | Key, position 3 |
| **API**: name + major | `nav.v2`, `health.v1` | Contract author | Key, position 4 |
| **Instance**: one run of a service | `8f3a5c2e9b1d4f70` (random 64-bit, minted at service start) | Runtime | Presence token, descriptor |
| Host, process, build, zid | | Runtime | Descriptor metadata only |

- **The system models no hierarchy.** It does not model the
  organizational hierarchy: fleet/site/vehicle/subsystem lives in
  deployment metadata or naming conventions. The grammar stays
  fixed-arity.
- **Validation of the system chunk.** Spike S8 validates it against five
  deployment shapes. If it forces fake system names, revisit.
- **No implicit identity.** Clients always pass an explicit service
  address. Server handles are bound to the service that declared them.
  Fleet selection is a named constructor, never a default.

### 2.3 Resource kinds

| Kind | Meaning | Zenoh mapping |
|---|---|---|
| **stream** | Values pushed by the service; each sample stands alone | A declared publisher. `delivery = sampled \| reliable`. No late-joiner guarantee in the core. |
| **state** | The latest value is the truth; it may be deleted | A declared publisher + a non-`complete` queryable over the API's `state/**`. Semantics in §2.5. |
| **operation** | Request and reply | A `complete` queryable on the concrete `@op` key. Rules in §2.6. |

- **Templates.** All three kinds take resource templates with typed
  parameters (`tracks/{track}`, `devices/{device}/sample`). A wildcard GET
  on a state template is the collection listing.
- **Presence is not a kind.** It belongs to the instance (§2.9).
- **Events, media and bulk are not kinds.** Events are a reliable stream,
  or a state-per-alarm through a profile. Media and bulk are profile
  kinds.

### 2.4 Ownership and serving

Every resource has a **serving model**, declared in the contract:

| `serving` | Applies to | Meaning |
|---|---|---|
| `exclusive` *(default)* | All kinds | At most one instance at a time exposes the resource. |
| `replicated` | Operations only, in v2 | Any number of instances expose it. The contract MUST also say `idempotent = true` (lint), unless a profile supplies stronger semantics (fencing or deduplication). |

- **The core does not elect.** It has no `role` concept. A standby
  instance is simply one that exposes no exclusive resources. It still
  holds its presence tokens, and may expose replicated operations.
- **Ownership is visible.** Each instance's descriptor lists its exposure.
  **Two instances exposing the same exclusive resource is a split-brain
  finding**, diagnosed from descriptors. Samples cannot carry this
  diagnosis: Zenoh's `SourceInfo` is unstable, unvalidated, and set only
  by advanced publishers.
- **The redundancy profile** (§2.11) adds election, fencing epochs and
  role naming. Whatever it does, a side-effecting actuator still needs an
  exclusivity lock outside the bus (v1, RFC 03 §1.5).
- **Replicated streams and state are deferred** (§6).

### 2.5 State semantics

**Zenoh facts this section is built on** (1.10.1 source, Appendix B):

- **Stamping:**
  - Routers stamp **puts only**, and only where timestamping is enabled
    (routers yes; peers and clients no, by default).
  - **Deletes and query replies are never stamped by the network.**
- **Consolidation:**
  - `Latest` keeps, per reply key, the reply with the greatest timestamp.
    **An unstamped reply ranks below any stamped one.**
  - Replies under `Latest` are delivered only when the query completes.
- **Tombstones:** `Query::reply_del` is stable, so a GET can be answered
  with a tombstone.
- **Clocks:**
  - `Session::new_timestamp()` uses the session HLC if one is enabled,
    and otherwise wall clock + zid.
  - The HLC catches up only from routed puts received while timestamping
    is enabled.
  - A router with timestamping on **re-stamps puts dated in the future**
    (`drop_future_timestamp = false`, the default).

**Rules** (normative in the spec, with scenario tests):

| # | Rule |
|---|---|
| S1 | Every state mutation, **put and delete**, MUST carry a timestamp set by the producer (`new_timestamp()`), never left to router stamping. |
| S2 | A producer's GET reply MUST carry the timestamp of the mutation it represents, the same value it published. |
| S3 | A producer MUST answer a GET that covers a key it deleted within the **tombstone window** with `reply_del` carrying the deletion timestamp. This is what makes the delete beat a storage's older put under `Latest`. |
| S4 | A state GET MUST set target `All` and consolidation `Latest` explicitly. It never relies on defaults. |
| S5 | **Deployment conformance:** storages covering state MUST preserve sample timestamps and retain tombstones for at least the tombstone window (v1's "GC lifespan ≥ TTL" rule). |
| S6 | A consumer distinguishes **current** state (its owner instance is present) from **last-known** state (owner absent), and SHOULD present the difference. This uses presence, not payload. |
| S7 | A session that serves state SHOULD enable HLC timestamping. Whether this becomes a MUST is open (U2). |

**Hazards the spike must settle** (U1–U3):

- **Clock regression on restart.** A restarted producer whose wall clock
  is behind its previous incarnation's last timestamp writes values that
  lose to the storage's older value until its clock catches up.
- **Re-stamping at the router.** A producer whose clock runs ahead of the
  router beyond the HLC tolerance gets its puts re-stamped. Its GET
  replies then carry a different timestamp than storages hold, which
  violates S2 through no fault of its own.

If S1–S5 cannot be made robust on stable APIs, the fallback is **U1
option C**: only owners answer state GETs, and "last known" becomes an
explicit archive API. The fallback does **not** weaken the semantics.

### 2.6 Operation calling rules

| # | Rule |
|---|---|
| O1 | Operation queryables are declared on their **concrete key** and **`complete`**. A concrete call with the default `BestMatching` target therefore executes on **at most one** instance: the owner (exclusive), the nearest replica (replicated), or one of two split-brain owners (failure contained, still diagnosed). |
| O2 | A wildcard (fan-out) call is legal only to `fanout = "allowed"` operations. It uses target `All` and consolidation `None`. A server MUST refuse any non-concrete query to any other operation with `fanout_forbidden`, whatever the ACL says. |
| O3 | The reply goes on the operation's own concrete key. Success is a value reply; failure is `reply_err` with the core error envelope (codes `invalid_request`, `not_found`, `unavailable`, `forbidden`, `fanout_forbidden`, `busy`, `internal`, `app`). |
| O4 | Only idempotent operations may be retried. |
| O5 | An empty reply set is not a verdict. Since zenoh 1.3, ACL-refused queries return empty. Callers attribute silence through presence. |

**Why O1 reverses v1's "never `complete`" rule safely.** v1 forbade
`complete` on `@rpc` queryables because a broad `complete` queryable, such
as a storage on `**`, would capture wildcard fan-in queries. Neither risk
exists here:

- an exact-key queryable can never include a wildcard query, so fan-in
  falls through to `All`;
- no storage's `**` crosses `@op`.

Spike S6 verifies both (U4).

### 2.7 Contracts, bundles, fingerprints

- **Authoring.** One TOML file per API (Appendix A). It is validated by a
  language-independent JSON Schema plus lint rules that have fixtures.
- **Canonical form.** A JSON document serialized with **JCS (RFC 8785)**:
  - every machine-relevant field is included (resources, templates,
    types, serving, delivery, idempotency, fanout, timeouts, optional
    flags, annotations, the profiles used);
  - **documentation is excluded**;
  - each type is referenced as `{name, kind, sha256}` of its schema
    artifact.
- **Bundle.** The canonical contract plus its schema artifacts:
  - for protobuf, a `FileDescriptorSet` with imports, source info
    stripped, deterministically serialized;
  - for jsonschema, the committed documents.
- **Bundles are built once and embedded everywhere.** The contract's own
  CI builds the bundle and commits or publishes it. Every implementation,
  in any language, embeds those bytes. **No implementation regenerates a
  bundle from source; it only verifies the sha256.** This removes
  cross-language protobuf canonicalization from the conformance burden
  entirely.
- **The fingerprint** is the sha256 of the canonical contract bytes. Same
  fingerprint means exactly the same machine-relevant contract. A
  different fingerprint means something changed, so run the classifier.
- **The retention rule.** Fingerprints may over-detect, never
  under-detect. A rebuild that produces different bytes but that the
  classifier judges *identical* (a toolchain upgrade, say) MUST keep the
  previous bundle, and mints no new fingerprint. The artifacts therefore
  include every wire- and compatibility-relevant element, and spurious
  differences are absorbed at build time.
- **`minor`** is an informative label. CI enforces it to be monotonic,
  and the protocol never compares it.
- **Composition is a list of implemented APIs.** There is no inheritance.
  Shared types are shared schema packages.

### 2.8 Schemas

| Kind (MCAP spelling) | Role |
|---|---|
| `protobuf` | **The default** for portable inter-service APIs, because it has the strongest cross-language compatibility semantics. Its compatibility is delegated to buf-style WIRE_JSON rules (tools transcode to JSON). |
| `jsonschema` | **First-class** for JSON/CBOR payloads, document-shaped and configuration data, and Rust-first teams. A schemars-generated schema is fine, but it is committed and checked, and the artifact is the protocol. The core defines a conservative compatibility subset; anything undecidable is classified "review". |

- **Stream and state samples carry the predefined Zenoh `Encoding` id
  only**, never a schema suffix. The suffix is sent with every non-default
  put and capped at 255 bytes, and the contract already binds the type.
- **One type and one encoding per resource.** Other kinds (CDR/ROS IDL)
  are extensions.

### 2.9 Presence, descriptors, contract retrieval

**Presence** uses one liveliness token per (instance × API), with all
information in the key (tokens carry no payload):

```
zk2/<system>/<service>/@zk/alive/<api>.v<major>/<instance>/<fp16>
```

| Question | Liveliness selector |
|---|---|
| All implementations of `nav.v2`, with their contract revisions | `zk2/*/*/@zk/alive/nav.v2/**` |
| Everything alive on vehicle-01 | `zk2/vehicle-01/*/@zk/alive/**` |
| Instances of one service | `zk2/vehicle-01/navigation/@zk/alive/*/*/*` |

- **How tokens propagate.** Routers hold every token. Clients and peers
  receive only the tokens their interests match.
- **The fingerprint prefix in the key** (`fp16`) is a drift hint. The
  descriptor holds the full sha256.
- **The layout is provisional (U5).** The API-first order is benchmarked
  against instance-first, and against one token per instance.

**The descriptor** lives at `zk2/<system>/<service>/@zk/instance/<instance>`.
It is put on every change and answered on GET:

```json
{
  "zk": 2, "system": "vehicle-01", "service": "navigation",
  "instance": "8f3a5c2e9b1d4f70", "generation": 3,
  "started_at": "2026-10-07T09:12:44Z", "zid": "a1b2…",
  "apis": [
    { "api": "nav.v2", "contract": "sha256:3fa9…", "minor": 1,
      "exposed": ["origin", "position", "set_origin", "status"],
      "unavailable": { "reset": "reset line not wired on this platform" } },
    { "api": "health.v1", "contract": "sha256:77e0…", "exposed": "*" }
  ],
  "profiles": ["redundancy.v1"],
  "meta": { "host": "nav-computer-2", "build": "nav-svc 4.2.0 (9c1e2f0)" }
}
```

**Contract retrieval** uses the key `zk2/@zk/contract/<api>.v<major>/<sha256>`.
Every holder declares a `complete` queryable on it. The client:

1. GETs the key with `BestMatching`, which routes to the nearest holder;
2. verifies the sha256 of each reply, and **accepts the first valid one**
   (duplicates are harmless);
3. on zero valid replies (timeout, or a corrupt nearest holder), retries
   once with target `All`;
4. if still nothing, reports the contract as **unavailable**: a reported
   state, not an error.

Tools may also load bundles from a directory.

**Start-up order:**

1. Declare the resources.
2. Validate required exposure.
3. Declare the descriptor and contract queryables.
4. Declare the presence tokens.

So alive ⇒ callable.

**Tooling obligation.** Liveliness queries use an explicit large handler.
zenoh#2678 (open) deadlocks past about 256 matching tokens on the default
handler.

### 2.10 Compatibility

**Inside one API major**, every revision MUST be **FULL_TRANSITIVE**
compatible: in both directions, against every earlier revision of the
major. A change that cannot meet this needs a new major. History is kept as
committed canonical snapshots per major, append-only and CI-checked.

**Payload types** are delegated to the schema kind's rules and evaluated
in both writer/reader directions:

- stream, state and response: the service writes, clients read;
- request: the client writes, the service reads.

**Metadata is directional:**

| Change | Class |
|---|---|
| Add a resource | compatible |
| Remove a resource; change its kind, parameters or template | breaking |
| `idempotent` false → true | compatible |
| `idempotent` true → false | **breaking** (clients may retry) |
| `delivery` sampled → reliable | compatible |
| `delivery` reliable → sampled | **review** (consumers lose every-sample delivery) |
| `fanout` forbidden → allowed | review (security) |
| `fanout` allowed → forbidden | **breaking** (fleet callers) |
| `serving` exclusive → replicated | review (requires idempotent) |
| `serving` replicated → exclusive | review |
| `timeout_ms` increased | compatible |
| `timeout_ms` decreased | review |
| `optional` → required | breaking for implementers |
| Required → `optional` | review for clients (they must now handle `unavailable`) |
| Enum value added, in any direction | review |
| A semantic annotation changed | review (the profile declares which keys are semantic) |
| Documentation only | none (not in the fingerprint) |

Spike S7 turns this table into a fixture matrix.

### 2.11 Profiles

A **profile** is an independently versioned spec (`profiles/<name>/v<N>`):
a few pages of normative behaviour plus scenario tests. The core never
depends on one. A profile contributes through any of **four core extension
points**:

| Extension point (core) | A profile contributes | Examples |
|---|---|---|
| An ordinary contract | A standard API | `health.v1`, `config.v1`, `alarms.v1` |
| Contract `annotations` in the profile's namespace, plus `uses = ["<profile>.v<N>"]` in the contract (fingerprinted) | A vocabulary bound to resources of *any* API | `freshness.v1` (TTL, refresh), `telemetry.v1` (unit, counter/gauge, histogram), `qos.v1`, `jobs.v1` (marks an API's own start/status/cancel resources) |
| The position-5 kind registry | A verbatim kind and its wire semantics | `media.v1` (`@media`), `bulk.v1` (`@blob`) |
| The descriptor `profiles` list | Behaviour across instances | `redundancy.v1` |

**Which profiles carry normative behaviour.** These do:

- `config.v1` (commit-confirm state machine: set → apply → confirm
  window → confirm or roll back; hot versus reach groups);
- `jobs.v1` (lifecycle, terminal states, retention);
- `redundancy.v1`;
- `freshness.v1`;
- `media.v1`;
- `bulk.v1`.

Whether `health.v1` and `alarms.v1` need behavioural text, or are pure
contracts, is decided per profile.

### 2.12 Security

The key layout gives every grant a prefix to name:

| Principal | Grants |
|---|---|
| Application | Subscribe on `…/stream/**`, `…/state/**` of the APIs it uses. Query `…/state/**`. Query the specific `…/@op/<op>` keys it needs. Liveliness-subscribe `zk2/*/*/@zk/alive/<api>/**`. |
| Operator | All of the above, plus query `zk2/*/*/@zk/instance/*` and `zk2/@zk/contract/**` (or per API). |
| Administrator | Privileged `@op` keys, one by one. |
| A service's own principal (cert CN bound to its system) | Publish and serve on `zk2/vehicle-01/**`, `zk2/vehicle-01/*/*/@op/**`, `zk2/vehicle-01/*/@zk/**`. Serve `zk2/@zk/contract/<api>/*` for the APIs it implements. |

Facts the spec states plainly:

- deny works by inclusion, so deny with the widest pattern (`**/@op/**`);
- **multicast transports bypass ACL**;
- `zids` subjects are unauthenticated, so bind a system to a certificate
  CN;
- ACL is enforced per hop;
- the running ACL is not observable.

Authorization policy stays outside the core. ACL generation (contracts
plus a role file) is a tool.

### 2.13 Rust shape

Unchanged from r1 except for serving and state.

- **Generated per-API code:** a `Server` with a `Handlers` struct (the
  compiler enforces completeness for required operations), a `Client`
  with typed `subscribe`/`get`/`call`, and a `Fleet` constructor spelled
  by name.
- **State writers** stamp with `new_timestamp()`, remember tombstones for
  the window, and answer GETs (S1–S3) without application code.
- **Replicated operations** are declared through the same handler, with
  `serving = "replicated"` in the contract.
- **Every handle exposes `key_expr()`,** and builders accept a closure
  over the zenoh builder.
- **zenkey never owns the session.**

## 3. Unresolved design decisions

These are what the next round should argue about. Each has a current lean,
the spike test that decides it, and the fallback if the lean fails.

| # | Question | Options | Lean | Decided by | If the lean fails |
|---|---|---|---|---|---|
| **U1** | How do producer and storage answers to a state GET combine? | **A.** Merge by timestamp (S1–S5). **C.** Owners only answer; "last known" is an explicit archive API (`archive.v1`), and deployments run no storage on `state/**`. | A | S5 | C. It costs zero-config storage, and buys trivially correct GETs with explicit provenance. |
| **U2** | Clock discipline | S7 stays a SHOULD, or becomes a MUST (HLC on every serving session). Restart regression: (a) GET own keys at start and hold writes until the local clock passes the last stored timestamp; (b) an incarnation epoch inside the value; (c) accept the window and document it. | MUST HLC + (a) | S5 (restart, skew, re-stamping cases) | (b). It needs a profile-level field, so it is avoided unless forced. |
| **U3** | Tombstone window | Fixed core default (for example 15 min), or per resource (a `freshness.v1` annotation) | Core default, overridable by annotation | S5 memory and latency measurements | n/a |
| **U4** | `complete` operation queryables | O1 as written, or v1's "never complete" | O1 | S6: split-brain at-most-once, fan-in still reaches all, hung nearest replica | Back to non-complete. At-most-once is then lost under split-brain, and replicated calls hit every replica (fine only for idempotent calls). |
| **U5** | Presence token layout and granularity | API-first; instance-first; one token per instance (APIs in the descriptor) | API-first, per (instance × API) | S2 at 100 / 1k / 10k / 50k tokens | Per-instance tokens + descriptor fan-in |
| **U6** | Mandatory one-chunk `system` | Keep; allow multi-chunk; make it optional | Keep | S8: vehicle, ground, fleet-global, simulator and device-driver deployments | Revisit only if fake system names appear |
| **U7** | Bundle stability across toolchains and languages | Build once + embed + retention rule (§2.7); or a spec-defined normalized description per kind | Build once + embed | S7 (rebuild with a different protoc/buf; a Python implementation verifying an embedded bundle) | A normalized description, fixture-heavy |
| **U8** | Core error envelope encoding | (a) A core `Error` defined in both protobuf and jsonschema, with `detail` encoded in the API's encoding; (b) always JSON with `detail` base64 | (a) | Spec draft and S1 | (b) |
| **U9** | Profile binding | `uses` in the contract (fingerprinted) + `profiles` in the descriptor; or descriptor only | Both | Spec draft | Descriptor only (loses static checking) |
| **U10** | Large collections | Wildcard state GET over large templates (10k tracks): unbounded, buffered until query completion under `Latest` | No pagination in the core; a budget annotation; large collections become streams or operations | S5 (wildcard GET at 1k and 10k keys: latency, memory) | A small paging rule on GET parameters |

## 6. Deliberately not in the v2 core

Listed so the next rounds can refuse them quickly:

- replicated streams and state;
- load balancing beyond "nearest replica";
- pagination;
- per-sample instance attribution;
- durable commands;
- several encodings per resource;
- schema kinds beyond the two;
- authorization policy;
- central caches or indexers (optional tools later);
- a ROS 2 bridge (a tool or profile later);
- recording formats (tooling);
- observer-honesty rules and exit codes (a tooling guide);
- everything ZenSight-specific (catalog, evidence, incidents, impact).

## Appendix B: Zenoh facts relied on

All of these were read in the zenoh 1.10.1 source. Paths are relative to
the crate unless noted.

| Fact | Source |
|---|---|
| Liveliness tokens carry no payload (`DeclareToken{id, wire_expr}`) | `commons/zenoh-protocol/src/network/declare.rs` |
| Routers hold every token; clients and peers receive tokens on matching interest | `src/net/routing/hat/{router,client,peer,broker}/token.rs` |
| Verbatim = a chunk starting with `@`; `*`/`**` never match it | `commons/zenoh-keyexpr/src/key_expr/borrowed.rs` |
| `BestMatching` = the nearest `complete` queryable whose key includes the query's key, else `All` | `src/net/routing/dispatcher/queries.rs` |
| `Latest` consolidation per reply key by timestamp (`>=`; `None` ranks lowest); replies delivered at completion | `src/api/session.rs` (reply handling, ~l.3540–3605) |
| Routers stamp puts only, and only where timestamping is enabled; future-dated puts are re-stamped unless `drop_future_timestamp` | `src/net/routing/dispatcher/pubsub.rs` (`treat_timestamp!`); `DEFAULT_CONFIG.json5` (`timestamping.enabled: {router: true, peer: false, client: false}`) |
| `Query::reply_del` (stable); `Session::new_timestamp()` = HLC if enabled, else wall clock + zid | `src/api/queryable.rs:437`; `src/api/session.rs:1038` |
| Encoding schema suffix ≤ 255 bytes, sent per non-default put | `commons/zenoh-codec/src/core/encoding.rs` |
| ACL matches by inclusion; multicast transports bypass ACL; `zids` subjects are unauthenticated | `src/net/routing/interceptor/{authorization,access_control}.rs`; `DEFAULT_CONFIG.json5` |
| `SourceInfo` unstable and unvalidated, set only by advanced publishers; matching status is a boolean | `src/api/{sample,matching}.rs` |
| `liveliness_query` deadlock past ~256 tokens on the default handler (open) | eclipse-zenoh/zenoh#2678 |
